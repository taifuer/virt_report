KVM Forum 2012 精选解读

2012 年精选覆盖 QEMU/KVM 后续发展的几块基础：MemoryRegion 统一地址空间描述，APICv 减少中断相关退出，多队列网络扩大并行数据路径，KVM/ARM 接入新的硬件虚拟化模型。围绕 BQL 的讨论进一步说明性能路径拆分所需的锁顺序与对象寿命规则，原型限制和负面测试一并保留。

5 篇精选

目录

  1. 一、本届观察
  2. 二、QEMU 内存 API：把总线拓扑变成地址视图

  4. 四、Virtio-net 多队列：从网卡队列到宿主线程
  5. 五、KVM/ARM：Hyp 模式、二级页表与设备协作
  6. 六、绕过 BQL：低延迟设备路径需要怎样的锁规则

一、本届观察

本届五项精选既有新硬件能力，也有软件基础模型的重整。APICv 和 Arm 虚拟化扩展改变 CPU 与中断路径，MemoryRegion 则把设备拓扑整理成各组件能共同观察的地址视图。多队列和 BQL 改造说明，硬件并行能力最终还要由线程、锁和生命周期设计承接。

二、QEMU 内存 API：把总线拓扑变成地址视图

原始演讲：Revamping the QEMU Memory API · 原始讲稿（PDF）

Avi Kivity · Red Hat

1. 问题与工程价值

客户机物理地址经过桥和设备窗口，最终可能落在 RAM、ROM 或 MMIO。不同发起者还可能看见不同布局。旧式按页登记和原地覆盖难以维护区域重叠：移动一个 BAR，可能同时改变另一个区域的可见部分。新的内存 API 希望让模型贴近硬件组合关系，减少各设备自行修补全局映射的代码。

2. 实现挑战

区域可以嵌套、别名或互相遮挡，配置变化时必须重新确定可见范围。CPU、DMA、KVM 内存槽和 vhost 等后端又需要一致观察。逐页保存大量元数据会增加内存开销，并发读取时原地修改结构还可能暴露中间状态。接口必须同时处理表达能力、更新正确性和查询效率。

3. 解决方案

设备只声明自己的 MemoryRegion，桥和容器负责组合区域，内存核心按优先级生成平坦可见布局。RAM、I/O、容器和别名等区域各自表达不同语义，字节序、访问宽度和对齐规则由统一接口承接。事务把相关配置变化合并，避免消费者看到不完整更新。

MemoryListener 通知需要平坦布局的组件处理区域增删，还承载脏页跟踪、coalesced MMIO 和 ioeventfd 等状态变化。内部查询结构使用可变深度树，让大段相同区域共享较少元数据；更新构建新结构，也为后续 RCU 读取提供条件。

4. 验证结果

讲稿给出地址覆盖示例、接口和 info mtree 输出，可以直接检查设备声明与最终视图是否一致。它还比较旧、新查询结构的元素大小与层级组织，但没有完整应用基准，不能把结构压缩比例当作 QEMU 总内存下降比例。主要贡献是统一模型及可调试性。

5. 局限与后续工作

统一描述地址关系并不自动解决所有设备内部并发，监听者也必须正确执行更新。后续验证需要覆盖 BAR 移动、别名覆盖、不同发起者和热拔除，确认 KVM 与设备后端不保留失效映射。RCU 是材料中的准备方向，不能仅凭“更新时创建新结构”就判定整个访问路径已经无锁安全。

三、APICv：让硬件处理更多虚拟中断状态

原始演讲：Enabling Optimized Interrupt/APIC Virtualization in KVM · 原始讲稿（PDF）

Jun Nakajima · Intel

1. 问题与工程价值

虚拟机频繁读写 APIC、结束中断或等待可注入窗口，会产生大量退出和软件状态维护。网络与存储请求越密集，中断路径的固定成本越突出。APICv 把部分寄存器操作、优先级判断和虚拟中断投递交给硬件，让 KVM 主要负责配置与仍需软件参与的边界。

2. 实现挑战

APIC 包含待处理、服务中和优先级状态，软件与硬件必须共享一致视图。某些 EOI 仍需通知外部设备模型，不能一律免退出。来自其他 CPU 的中断还要处理目标 vCPU 运行状态，以及并发设置待处理中断时的同步，避免丢失或重复通知。

3. 解决方案

APIC 寄存器虚拟化利用虚拟 APIC 页处理部分访问，对仍需软件处理的写操作可提供已完成写入的退出信息，减少指令解码。虚拟中断投递使用 RVI、SVI 等状态在合适时机交付中断，EOI-exit bitmap 决定哪些结束操作仍需要退出。

Posted Interrupt 使用描述符保存待处理向量，并通过通知让正在运行的目标 vCPU 接收更新。讲稿的客户机 IPI 示例中，发送侧访问 ICR 仍可能退出，由软件设置目标描述符并发送通知；目标侧免退出并不表示整个 IPI 路径完全没有软件参与。

4. 验证结果

作者报告 APIC 寄存器与虚拟投递补丁已经提交评审，Posted Interrupt 的目标侧无退出路径有工作原型。初步 Netperf 结果最多消除约 50% 的 VM-exit，并让部分其余退出的模拟更简单。这是退出数量与处理路径的结果，不能直接换算成吞吐提升 50%，材料也没有完整平台与负载配置。

5. 局限与后续工作

硬件功能、客户机 APIC 模式、路由和 vCPU 调度状态都会影响快速路径是否成立。后续应测量端到端延迟、CPU 时间和阻塞 vCPU 的唤醒，并验证 EOI、重路由及迁移时状态同步。讲稿展示的是 2012 年启用方案，实际支持范围需要对应具体软件和硬件版本。

四、Virtio-net 多队列：从网卡队列到宿主线程

原始演讲：Multiqueue Networking for KVM · 原始讲稿（PDF）

Jason Wang · Red Hat

1. 问题与工程价值

物理网卡已经具有多个队列，客户机单组 Virtio 收发队列和单个 vhost 线程却可能把流量集中在少量 CPU。跨 CPU 转交又引入 IPI 和缓存竞争。多队列方案希望让多个流并行处理，并维持每条流的顺序，使客户机和宿主共同利用多核能力。

2. 实现挑战

只增加客户机队列数量并不够，QEMU、TAP 和后端线程都需要相应通路。队列选择需要兼顾流归属、收发方向和动态启停，切换策略还不能造成不必要的乱序。更多线程会改变 NUMA 访问和 TCP 批处理行为，因此并行度提高可能伴随新的 CPU 成本和吞吐退化。

3. 解决方案

方案把 Virtio 队列对映射到多个网络后端，每个 TAP 队列通过对应文件描述符和 socket 接入，QEMU 配置多个 vhost 处理通路。流到队列的关联帮助收发维持局部性，没有记录时使用散列。控制队列和设备配置用于协商、调整活动队列数量。

讲稿中的模式切换及接口仍有 RFC 成分，部分命令名属于原型。工程上的核心是让前端队列、后端执行单元和物理网卡能力形成完整链路，而非把同一串行瓶颈前的队列简单复制。

4. 验证结果

双 E5620、82599 网卡、4 vCPU 客户机的实验，把 vCPU 与 vhost 线程放在不同 NUMA 节点。100 个 TCP_RR 会话时，四队列图示约为每秒 26 万次事务，单队列约 11 万次。但两会话、512 字节发送场景的吞吐从 9263 降至 4662，CPU 使用量还增加；作者将其与 TCP 批量减小联系起来。

5. 局限与后续工作

多队列收益依赖流数量、报文大小、批量及线程放置，单流并不会自然扩展到所有队列。后续工作包括流转向、NUMA、零复制和更多网卡测试。部署评估应同时测量事务延迟、流式吞吐和宿主 CPU，保留单队列作为对照，避免把队列数当作性能保证。

五、KVM/ARM：Hyp 模式、二级页表与设备协作

原始演讲：ARM Virtualization for the Masses · 原始讲稿（PDF）

Christoffer Dall · Virtual Open Systems / Columbia University

1. 问题与工程价值

Arm 设备和服务器需要复用 Linux 的调度与内存管理来承载虚拟机。Armv7 虚拟化扩展提供 Hyp 模式和 Stage-2，但它与 x86 的硬件状态容器和进入退出方式不同。KVM/ARM 的任务是在这些硬件约束下建立 Linux 宿主与客户机之间的运行路径，并接入既有 QEMU 管理接口。

2. 实现挑战

当时 Hyp 模式不足以直接承载完整宿主 Linux，关键切换代码与普通内核分处不同模式。引导时还必须正确取得 Hyp 控制权。客户机寄存器、异常和二级缺页需要在两部分之间交接；MMIO 解码提示也不能覆盖所有指令形式，平台设备与中断模型仍要配套。

3. 解决方案

宿主 Linux 保留普通内核执行环境，低层 Hyp 代码负责关键寄存器和世界切换。KVM 按需建立 Stage-2 映射：客户机访问尚未映射的 IPA 时进入缺页处理，查找宿主页面并安装映射，随后恢复执行。MMU notifier 等机制连接宿主换页和映射失效。

RAM 之外的访问交给设备模拟，QEMU 负责平台和多数设备；VGIC 与架构定时器等高频功能由 KVM 配合硬件处理。虚拟中断装入 List Registers，客户机部分计数器读取无需陷入。讲稿同时说明硬件中断返回宿主处理的路径。

4. 验证结果

材料报告 Cortex-A15/A7 等支持虚拟化扩展的平台，以及第 14 版上游补丁的评审进展，并安排运行演示。PDF 没有系统性能数据，部分大页支持仍待依赖条件满足。它证明的是实现路径与集成进度，无法据此声称所有 Arm 设备都支持 KVM，或与 x86 性能等同。

5. 局限与后续工作

固件启动模式、平台设备和指令解码都会影响可用性。并发缺页、页面回收、VGIC 状态和定时器恢复需要继续验证。阅读时应限定为早期 Armv7 KVM 架构，不能把后来 Arm64 VHE 或更先进中断能力提前套入这一设计。

六、绕过 BQL：低延迟设备路径需要怎样的锁规则

原始演讲：For Performance and Latency, Not for Fun — How to Overcome the Big QEMU Lock · 原始讲稿（PDF）

Jan Kiszka · Siemens

1. 问题与工程价值

QEMU 全局锁简化了设备模型，但高频 I/O 和实时任务可能被不相关设备、图形或管理工作阻塞。讲稿希望建立可独立运行的低延迟路径，同时让大量非性能关键设备继续使用原有锁规则。这样可以逐步改善关键场景，控制全局改造的风险。

2. 实现挑战

细粒度锁会引入锁顺序问题。设备 A 的操作可能调用后端 B，B 的回调又访问 A；两个执行上下文反向获取锁就可能死锁。内存区域从地址空间移除时，已经拿到回调的线程仍可能继续访问，必须保证设备对象存活。定时器和事件框架的内部锁也会影响实时优先级。

3. 解决方案

作者提出由粗到细的加锁规则，避免持有细锁时调用需要 BQL 的服务。内存分发在保护地址视图期间取得区域引用，再按区域声明选择细粒度处理或传统 BQL 路径。移除与回收分开，最后一个引用释放后才销毁对象；回调不得重新激活已进入销毁流程的设备。

前后端可以采用独立锁加受控回调，也可以把后端作为由调用者管理上下文的库。讲稿用 RTC 周期中断贯通 PIO、定时器和中断路径，展示真正绕开 BQL 需要多个子系统同时提供相容接口。

4. 验证结果

原型能够让客户机把 RTC 作为可靠时钟源，但作者明确列出未处理的热插拔、HPET 联动、丢失 tick 补偿和部分时钟模式。PDF 没有可复核的延迟分布，因此应将其视作路径可行性验证，不能写成完整低延迟设备框架已经完成。

5. 局限与后续工作

阻止嵌套 MMIO 可以降低死锁风险，也可能限制合法设备行为，需要进一步论证。调度优先级、对象回收和事件源停用同样影响结果。后续验证应在设备拔除、回调并发和管理操作压力下测量长尾延迟，确保优化路径的可维护性与原有功能都得到保留。
