KVM Forum 2016 精选解读

2016 年精选同时覆盖接口演进与隔离边界。userfaultfd 和统一 CPU 热插拔模型让管理软件获得新的控制能力；mdev、SEV 与 vIOMMU 分别处理共享设备、客户机内存和 DMA 的权限。原子操作讲解补上这些并发实现所依赖的内存模型，实验部分也保留性能退化和接口尚未定稿的情况。

一、本届观察

这一年的多项工作把原来隐藏在内核或厂商实现中的职责，整理成可以协作的接口：缺页交给用户态处理，CPU 拓扑可由管理层查询，共享 GPU 接入 VFIO，Virtio 后端开始遵守客户机 DMA 权限。SEV 又改变了宿主访问客户机内存的前提。接口越灵活，对状态、并发和失败路径的约束也越重要。

二、userfaultfd：把缺页处理交给用户态

原始演讲：Userland Page Faults and Beyond: Why, How and What's Next · 原始讲稿（PDF）

Andrea Arcangeli · Red Hat

1. 问题与工程价值

内核能够处理普通匿名页分配，却不知道一页数据位于哪个远端进程、应使用什么网络协议取回。应用需要在缺页时介入内存管理。虚拟机迁移和进程延迟恢复都是典型场景：执行已经开始，部分内存尚未到达，本地访问必须等到正确内容就绪。userfaultfd 为这类需求提供专门通知与补页接口。

2. 实现挑战

直接使用信号处理缺页会涉及信号屏蔽、执行上下文和地址空间修改。对于 QEMU 的 vCPU 线程，缺页可能发生在 KVM 执行期间，不适合要求该线程返回用户态自行处理。补页还必须具有原子可见性：其他线程不能观察到只复制了一半的页面。并发访问同一页、后台传输与按需请求之间也需要协调。

3. 解决方案

应用创建 userfaultfd、协商能力并注册地址范围。缺失页面被访问时，内核阻塞访问线程，把地址等信息送到文件描述符；另一个用户态线程读取事件并取得数据，通过 UFFDIO_COPY 或 UFFDIO_ZEROPAGE 安装页面并唤醒等待者。vCPU 可以始终停留在内核等待，处理线程独立完成网络通信。

讲稿强调快速路径不需要反复拆分 VMA。2016 年已合入的基础支持主要面向匿名内存缺页；写保护、其他内存类型和跨进程管理等扩展处于不同开发阶段，不能把讲稿列出的全部方向视为当时已经发布。

4. 验证结果

120 GiB 客户机、10 Gbit 网络的数据库实验中，持续写入使预拷贝长期不能完成，业务吞吐也受到干扰；切换到按需取页的后拷贝后，示例在约两分钟内传完剩余内存，但期间出现明显吞吐下降。图表说明迁移可完成性与访问延迟之间的交换，无法证明所有负载都能在相同时间完成。讲稿另外列出 Linux 4.3、QEMU 2.5 等基础支持版本。

5. 局限与后续工作

远端失联会直接影响缺页等待线程，应用需要考虑超时、故障恢复和资源耗尽。页面粒度也影响大页恢复与访问性能。写保护扩展还要处理交换和并发写入的一致性。这篇材料的价值在于建立通用内存事件接口的模型；具体使用时，应按目标内核协商实际能力，并分别验证正常补页和失败时的行为。

三、mdev：共享 GPU 的 VFIO 接口

原始演讲：vGPU on KVM — A VFIO Based Framework · 原始讲稿（PDF）

Neo Jia、Kirti Wankhede · NVIDIA

1. 问题与工程价值

整卡分配让客户机直接使用 GPU，却限制了设备共享密度，也让宿主难以进行厂商特有的资源管理。共享 GPU 需要宿主厂商驱动调度物理资源，同时向每个客户机提供设备视图。mdev 的目标是给这些厂商实现提供共同的 VFIO 接口，使 QEMU 可以复用设备区域、DMA 和中断管理方式。

2. 实现挑战

不同 GPU 的共享机制不相同，框架无法代替厂商驱动完成命令隔离和显存管理。客户机看到的寄存器中，一部分必须由软件审查或模拟，另一部分可以直接访问硬件资源。DMA 映射也需要跟随客户机内存生命周期，防止设备继续访问已解除映射的页；多个实例的中断则必须归属正确客户机。

3. 解决方案

厂商驱动注册物理设备及支持的虚拟设备类型，mdev 核心管理实例，VFIO 接口把实例呈现给 QEMU。对于模拟区域，客户机 MMIO 访问被捕获，经 KVM、QEMU 和 VFIO 读写接口交给厂商回调。对于可直映区域，映射建立后 CPU 可以直接访问对应设备区域，稳定路径不要求每次重新经过软件模拟。

内存方面，QEMU 提供客户机地址与用户态内存范围关系，厂商驱动按需要固定并转换页面，再建立设备 DMA 映射。中断通过 eventfd 与 KVM irqfd 等接口连接。框架统一的是这些协作接口，具体隔离强度仍取决于设备能力和厂商实现。

4. 验证结果

讲稿报告在 Linux 4.7 上测试了多个 mdev、多个直通设备以及二者混用，并提供 NVIDIA vGPU 演示。当时补丁处于 v7 评审阶段。材料没有提供足够的性能、隔离压力测试或公平性数据，因此可以确认接口与集成路径被验证，不能把“接近原生”当作已经量化的普遍结论。

5. 局限与后续工作

POWER 的 IOMMU 接入、QEMU/libvirt 管理和更完整的生命周期支持仍属于后续工作。直映区域必须确实只暴露该实例获准使用的资源，实例销毁也要停止 DMA 并回收映射。讲稿中的 sysfs 细节属于当时接口提案，适合理解架构，不应直接作为当前系统的操作命令。

四、SEV 的早期架构：客户机内存与密钥隔离

原始演讲：AMD's Virtualization Memory Encryption Technology · 原始讲稿（PDF）

Thomas Lendacky · AMD

1. 问题与工程价值

传统虚拟化依赖宿主配置页表和设备权限，宿主本身通常能够读取客户机内存。云租户因此必须把机密数据托付给宿主管理栈。SEV 尝试用每台虚拟机独立的内存加密密钥缩小这一信任关系，使普通宿主软件无法直接取得客户机私有内存的明文。这是理解后续机密虚拟机软件改造的重要起点。

2. 实现挑战

加密影响整个生命周期：启动镜像需要进入受保护状态，vCPU 必须使用正确密钥身份，迁移要保护传输内容，调试权限要由客户机策略控制。设备和宿主后端仍需要读写 I/O 缓冲区，因此全部页面都私有并不可行。密钥隔离本身也不能推导出对所有篡改、重放或侧信道的防护。

3. 解决方案

讲稿区分使用系统级密钥的 SME 与按虚拟机区分密钥的 SEV。安全处理器负责密钥和启动等管理操作，内存控制器完成加解密；ASID 参与确定虚拟机使用的密钥。客户机通过页面属性区分私有和共享内存，Virtio 队列、宿主需要访问的缓冲区及 DMA 页面必须按协议共享。

KVM、QEMU 与管理工具需要配合处理平台认证、启动测量、ASID 分配和策略。共享与私有缓冲区之间可能通过 SWIOTLB 等路径复制。加密能力因而同时改变 CPU 状态管理和 I/O 路径，不能仅理解成内存控制器上的一个开关。

4. 验证结果

这份材料是早期架构与集成说明，没有给出可复核的应用性能表，也没有完整攻击验证。作者列出的软件状态包括内核 RFC、固件与驱动开发，以及待完成的 KVM/QEMU 支持。“较小性能影响”等目标缺少本文可量化的依据，应保留为设计预期。讲稿最扎实的部分是接口职责和共享内存要求。

5. 局限与后续工作

不能用后来的寄存器保护或页面完整性能力解释这份早期 SEV 材料。实际安全结论需要对应具体代际、固件和威胁模型。共享 I/O 缓冲区、测量链、调试策略与迁移目标认证都值得分别审查；性能验证也应区分私有内存访问、共享缓冲区复制和生命周期操作的成本。

五、QEMU 原子操作：从共享变量到内存顺序

原始演讲：Atomic.h Weapons: The C11 Memory Model and QEMU · 原始讲稿（PDF）

Paolo Bonzini · Red Hat

1. 问题与工程价值

QEMU 的多线程扩展需要减少粗粒度锁，但共享变量仍必须正确交换状态。队列生产者发布一个指针时，消费者不仅要读到完整指针，还要看到指向对象的初始化内容。单个整数统计与对象发布的同步需求不同。讲稿用 C11 内存模型解释这些区别，帮助开发者判断原子操作适合替代哪部分锁。

2. 实现挑战

编译器优化和处理器重排都会影响观测顺序，代码在一台 x86 机器上运行正常并不能证明可移植。普通读写与并发写入形成数据竞争时，语言层面可能已经出现未定义行为。volatile、编译器屏障和硬件屏障的作用也不同，随意组合容易留下缺口，尤其是在兼容旧编译器的代码中。

3. 解决方案

讲稿从 happens-before 关系说明发布与获取：当 acquire 读取对应的 release 发布值时，初始化数据可以通过同步关系对消费者可见。独立统计量可以使用较弱的原子操作，因为它不承担发布其他对象状态的责任；同样的 relaxed 访问放到对象发布路径，却不能自动保证内部字段已可见。

QEMU 把旧编译器兼容处理集中在 atomic.h，避免业务代码散落架构汇编与编译器特例。API 选择在表达能力和可审查性之间取舍，较强的默认语义便于维护，需要更弱顺序时应有明确理由。讲稿还提醒 seqlock 保护的数据访问也要考虑语言层面的竞争规则。

4. 验证结果

材料提供小型并发示例、不同架构的指令映射和内存顺序反例，没有给出端到端性能提升。它的验证方式主要是说明哪些执行结果被模型允许、哪些同步关系能够排除错误。原子性、acquire/release 与顺序一致性仍应分别理解，不能把任意“使用了原子操作”的程序都判定为顺序一致。

5. 局限与后续工作

原子变量不会自动解决对象寿命、内存回收或多字段不变量，相关问题仍需要锁、RCU 或其他协议。讲稿提出继续整理旧屏障代码、采用更明确的访问封装。用于代码审查时，应写清共享数据、发布点、读取点和回收条件，并结合目标编译器与弱内存架构测试，而非只统计减少了多少锁。

六、CPU 热插拔：拓扑、设备模型与迁移身份

原始演讲：CPU Hotplug Support in QEMU · 原始讲稿（PDF）

Bharata B Rao · IBM；David Gibson、Igor Mammedov · Red Hat

1. 问题与工程价值

运行中的虚拟机增加或减少 CPU，可以按负载调整计算资源。早期 cpu-add 接口主要面向 x86，缺少统一查询与拔除模型，管理软件需要猜测 CPU 拓扑。POWER 按核热插拔、x86 按线程热插拔等差异，又使“新增一个 vCPU”无法覆盖所有平台。讲稿讨论如何把这些差异放入统一设备管理框架。

2. 实现挑战

客户机固件协议决定可操作的粒度，QEMU 对象粒度也必须匹配。热插拔顺序还会影响迁移：若 CPU 标识按创建顺序分配，源端与目标端即使最终拓扑相同，也可能无法匹配迁移状态。CPU 创建失败时，如果已经完成内核资源分配，回滚会变得复杂；拔除也不等于所有 KVM 对象都能立即销毁。

3. 解决方案

QEMU 使用 QOM 对象表示可热插拔单元，并允许通过标准 device_add/device_del 管理。query-hotpluggable-cpus 返回类型、拓扑属性和可用槽位，让管理软件按机器模型提供的信息操作。机器的 pre_plug 回调在设备实现前检查约束并补充属性，减少晚期失败。

迁移身份改为由稳定拓扑信息决定，避免依赖历史插拔顺序。对于当时 KVM 无法单独销毁并重新创建的 vCPU 实例，QEMU 可以保留处于停放状态的内核对象，后续同一 CPU 再插入时复用。客户机可见移除与宿主资源寿命因此需要分别管理。

4. 验证结果

讲稿展示 x86 与 pseries 的对象模型，以及 POWER 单线程、SMT4、SMT8 下的查询和插拔示例。这些例子验证接口能够表达不同热插拔粒度；材料没有给出大规模频繁插拔的稳定性统计。迁移身份问题提供了明确的故障原因，也说明功能测试必须包含不同创建顺序下的迁移。

5. 局限与后续工作

NUMA 归属查询、更多机器类型、启动 CPU 拔除和部分 POWER 热插拔状态迁移仍待完善。平台允许创建对象也不意味着客户机一定愿意下线 CPU，负载与客户机策略会影响操作完成。管理层应观察异步完成与失败，并验证并发迁移、插拔和清理流程，而非只以 QMP 命令返回作为成功标准。

七、vhost 与 vIOMMU：DMA 权限和转换缓存

原始演讲：Vhost with Guest vIOMMU · 原始讲稿（PDF）

Jason Wang、Wei Xu、Peter Xu · Red Hat

1. 问题与工程价值

客户机使用 IOMMU 限制设备可访问的内存，Virtio 后端也需要遵守相同地址与权限规则。传统 vhost 路径通常按客户机物理地址访问缓冲区，绕过客户机建立的 DMA 映射。对运行用户态驱动的客户机，这会削弱其内部设备隔离。讲稿研究如何让 Virtio、QEMU vIOMMU 与内核 vhost 共同执行这套约束。

2. 实现挑战

vIOMMU 的地址翻译在 QEMU 中，而高频数据处理位于内核 vhost。每次访问都往返用户态查询会产生很大开销；缓存翻译又必须及时处理解除映射和权限变化。中断重映射同样影响 irqfd 快速路径，需要在保留内核注入能力的同时，让路由与客户机配置保持一致。

3. 解决方案

客户机驱动使用 DMA API 提交设备地址，后端通过设备 IOTLB 缓存把 IOVA 转换到获准访问的宿主地址。缓存缺失时向 QEMU 请求翻译，更新和失效消息同步映射变化；区间树用于维护缓存范围。这种分工保留用户态 vIOMMU 的平台语义，也让常见命中路径留在内核。

中断方面，讲稿利用 KVM 的 GSI 路由，在设置阶段完成重映射相关翻译，运行时继续使用 irqfd 通知。2016 年方案对 irqchip 模式存在限制，不能将其理解成所有中断配置都已透明支持。

4. 验证结果

当时动态 DMA 映射实验中，TCP_STREAM 从 24500 Mbps 降到 600 Mbps，TCP_RR 从 25000 降到 11600 次事务每秒；采用静态映射的 DPDK 类负载，吞吐下降约 5%。平台细节披露有限，这些数据不能用于预测现代实现，但清楚表明映射更新频率对性能有决定性影响。只引用静态映射结果会掩盖主要问题。

5. 局限与后续工作

讲稿当时的组件状态并不一致：部分驱动和中断支持已合入，QEMU DMA 路径仍在评审，vhost-user 的缓存支持也在开发。后续重点包括动态映射成本、失效通知和错误处理。工程评价需要覆盖频繁 map/unmap、权限撤销与并发请求，检查安全语义在优化后是否仍然完整。
