会议/KVM Forum

KVM Forum 2011 精选解读

2011 年精选把设备与存储能力推进到可管理、可隔离的接口层。VFIO 重新划分设备分配职责，virtio-scsi 扩展存储模型；qcow2 与块层限速分别处理一致性和资源控制。实时虚拟机实验则直接暴露用户态设备路径的长尾，说明吞吐之外还需要观察响应时间和调度影响。

一、本届观察

这一年的五项工作强调系统能力背后的管理接口。设备分配需要由真正的驱动承担隔离与事件处理，存储需要明确命令语义和资源限制，映像格式需要在一致性与异步执行之间配合。实时实验则提醒开发者，功能正确和平均吞吐良好仍可能掩盖不可接受的长时间阻塞。

二、VFIO：把设备分配从 KVM 中拆出来

原始演讲：VFIO: PCI Device Assignment Breaks Free of KVM · 原始讲稿（PDF）

Alex Williamson · Red Hat

1. 问题与工程价值

早期 KVM 设备分配组合了 PCI stub、sysfs 资源访问、QEMU 模拟和 KVM 中断接口，职责与权限分散，也主要面向 x86。用户态驱动同样需要安全访问设备，却不应依赖创建虚拟机。VFIO 提案把设备管理放回独立驱动，向不同使用者提供一致的区域、中断和 DMA 接口。

2. 实现挑战

CPU 访问 BAR 与设备 DMA 使用不同的地址转换路径，必须分别限制权限。配置空间有些字段可直接访问，有些需要虚拟化。传统 INTx 还涉及屏蔽、EOI 和芯片组路由变化，无法像简单通知一样处理。不同架构的 IOMMU 隔离粒度也不一定等于单个 PCI 功能。

3. 解决方案

VFIO 通过设备文件提供配置空间、区域读写和 mmap，QEMU 根据区域性质选择直映或捕获模拟。IOMMU 管理接口建立设备可访问的内存范围，eventfd 传递设备中断，并可与 KVM irqfd 快速路径连接。设备安全管理因此可以独立于 KVM，同时被虚拟机监控器和用户态驱动复用。

讲稿中的 UIOMMU、文件路径和命令行属于早期接口提案。INTx 需要额外 EOI 与路由通知，MSI/MSI-X 的路径相对直接；这一区别解释了为什么设备分配还需要配置和中断控制面，而不能只映射 BAR。

4. 验证结果

材料提供实验代码位置、设备访问方式和中断连接图，没有完整性能或安全基准。作者把上游合入、非 x86 和非 PCI 支持列为后续工作，并明确当时方案仍假设整段客户机内存映射及设备级隔离。可确认的是职责拆分与原型路径，不能把后来成熟 VFIO 的全部能力追溯到此时。

5. 局限与后续工作

POWER 等平台的隔离组、IOVA 窗口与 DMA 模型促使接口进一步调整。分配单位必须匹配真实硬件隔离边界，单个文件描述符并不能证明设备可独立安全使用。后续验证需要覆盖设备移除、错误通知、DMA 撤销和路由变化，同时限定客户机能够访问的物理资源。

三、qcow2：元数据一致性与异步 I/O 的改造

原始演讲：The Reinvention of qcow2 · 原始讲稿（PDF）

Kevin Wolf · Red Hat

1. 问题与工程价值

qcow2 的稀疏分配与快照依赖地址映射和引用计数。一次新簇写入需要更新多处元数据，崩溃时的顺序错误可能损坏映像。简单在每一步同步落盘可以维持顺序，却降低分配吞吐，并让共享执行路径长时间等待。讲稿研究如何在保留格式功能的同时改善这些成本。

2. 实现挑战

L1/L2 映射、引用计数和数据写入必须按一致性要求提交。缓存模式不同，哪些写入需要同步也不同，不能通过省略必要 flush 获取虚假性能。新的映像格式虽然可以简化部分元数据，却会增加工具、兼容和维护负担，已有功能也未必同时保留。

3. 解决方案

Qcow2Cache 引入写回元数据缓存，将多次更新合并并按依赖关系提交，减少每次分配都执行昂贵同步。数据读写也逐步去除不必要的中转缓冲区。协程改造则让等待 I/O 的逻辑能够主动挂起，在保持接近同步代码结构的同时，释放执行线程去处理其他工作。

这两种改造解决不同问题：缓存主要降低重复元数据操作，协程主要避免等待期间阻塞其他任务。讲稿还讨论可选脏标记、零簇和子簇等格式演进，但它们在当时属于后续版本提案。

4. 验证结果

作者报告 QEMU 0.15 的写回元数据缓存让某些分配基准提高一个数量级以上，但 writethrough 并未获得相同改善。协程部分明确说明吞吐大体相近，主要收益是元数据访问不再按原方式阻塞 vCPU。不能把两项优化合并成统一性能倍数，测试块大小和缓存模式同样影响结果。

5. 局限与后续工作

异步执行引入更多同时在途状态，仍需检查锁粒度、错误回滚和崩溃恢复。格式扩展需要工具链及旧版本兼容，不能仅凭原型设计判断可部署性。后续测试应同时包含新分配、已分配覆盖写、快照与断电恢复，确认性能优化没有破坏映像一致性。

四、virtio-scsi：把存储功能放回 SCSI 协议

原始演讲：Virtio SCSI: An Alternative Virtualized Storage Stack for KVM · 原始讲稿（PDF）

Stefan Hajnoczi · IBM；Paolo Bonzini · Red Hat

1. 问题与工程价值

早期 virtio-blk 简单高效，但每块磁盘占用设备实例，复杂存储功能又需要不断扩展专用协议。多路径、持久预留和大量 LUN 更适合由成熟 SCSI 语义承载。virtio-scsi 希望保留 Virtio 共享队列的效率，让一个虚拟控制器连接多个目标与逻辑单元，降低设备规模与功能扩展的限制。

2. 实现挑战

运输 SCSI 命令只是第一步，后端 target 还需要正确处理 sense、无效 LUN、复位和异步事件。多队列不能默认提供所有请求的全局顺序。热插拔、设备重置和迁移期间的在途命令，也要求驱动、传输和 target 对同一状态有一致理解。

3. 解决方案

协议设置请求队列、控制队列和事件队列：请求承载 SCSI 命令，控制路径负责任务管理，事件路径通知复位、介质和设备变化。发生事件丢失时，客户机还需要通过既有 SCSI 机制重新确定状态。设备功能由 target 实现，Virtio 提供高效传输边界。

后端可以采用 QEMU 用户态 target，也可以借助 vhost 接入内核 LIO。QEMU 侧需要提取设备共有的 SCSI 行为、增加散列表访问并完善多 LUN 管理。内核后端复用已有 target，但拥有不同的权限和管理条件，两条路线并不能只按数据路径长度判断优劣。

4. 验证结果

讲稿列出草案、QEMU 实验分支与 tcm_vhost 代码，说明设计已进入实现讨论。PDF 没有提供可比较的 IOPS 或时延数据，许多迁移和 target 改进仍在规划。能够确认的是接口能表达更丰富的存储语义，不能据此认定性能已全面超过 virtio-blk。

5. 局限与后续工作

持久预留、多路径和透传是否可用，取决于后端与存储系统共同支持，前端协议不能凭空提供这些能力。迁移时重置和重提交也需要检查应用语义。后续验证应覆盖错误命令、丢失事件、热拔除和多发起者访问，避免只测试正常读写。

五、实时虚拟机：定位用户态设备模拟的长尾

原始演讲：Using KVM as a Real-Time Hypervisor · 原始讲稿（PDF）

Jan Kiszka · Siemens

1. 问题与工程价值

嵌入式系统希望同时运行实时操作系统和通用系统，兼顾设备共享与管理能力。KVM 可以复用成熟平台支持，但完整设备模拟会增加响应时间的不确定性。讲稿分别测量定时任务唤醒和外部网络事件，定位哪些路径可以达到较低延迟，哪些仍被用户态执行阻塞。

2. 实现挑战

vCPU 实时优先级不能消除 QEMU 全局锁中的慢操作。磁盘提交、图形更新、网络回调和脏页同步都可能让关键设备访问等待。客户机中一个实时 vCPU 与另一个通用 vCPU 共享设备模型时，这类干扰尤其容易跨越原本的 CPU 分区。

3. 解决方案

作者把 CPUState 归属明确到对应 vCPU，减少共享状态访问，并讨论独立 I/O 分发、中断快速路径及设备执行上下文。设备可以使用细粒度锁，也可以由专用服务线程串行处理复杂操作；两种方式都需要处理前后端回调及状态顺序。

实验配置通过 PREEMPT_RT、优先级和 CPU 放置控制宿主环境，并尽量让实时路径避开用户态模拟。路线图中的并发设备重构用于逐步减少这一限制，不能理解为只设置一个实时优先级即可完成。

4. 验证结果

Core i7、PREEMPT_RT 2.6.33.9-rt31 的约三小时 cyclictest 中，宿主最大观测延迟 29 µs，客户机 112 µs，作者明确提醒测试时长不足以可靠确定最大值。另一组直通网卡外部测量运行约 16 小时，最大往返延迟 330 µs；换成模拟网卡后出现 100 ms 甚至更高延迟，显示路径差异的重要性。

5. 局限与后续工作

这些数值依赖特殊补丁、设备和负载，不能作为一般 KVM 实时保证。条件变量内部锁、IRQ 线程管理和设备回调还存在优先级问题。后续验证应延长测试并加入故障、管理操作和压力负载，同时使用外部测量确认真正的设备响应，而非只观察客户机定时器。

六、QEMU I/O 限速：统一后端控制与执行成本

原始演讲：Keep a Limit on It — IO Throttling in QEMU · 原始讲稿（PDF）

Ryan Harper · IBM

1. 问题与工程价值

多台虚拟机共享存储，需要限制某台客户机消耗的 IOPS 或带宽。宿主块设备控制器可以限制部分本地 I/O，却难以统一覆盖 NFS 等非本地块路径。QEMU 在块层实施限速，可以按客户机设备观察请求，为多种后端提供相近的管理入口。

2. 实现挑战

客户机看到的请求数量与宿主实际 I/O 不一定相同，缓存、合并和映像元数据都会改变计费单位。限速还需要处理短期突发与定时器唤醒，避免排队逻辑本身消耗过多 CPU。平均值接近上限也不意味着所有时间窗口都没有超限。

3. 解决方案

块层在提交前检查额度，超过限制的异步请求进入队列，并计算后续可提交时间；满足条件时再交给真实后端。这把控制位置放在映像与存储后端之前，让同一客户机磁盘的请求能够统一计量。

讲稿比较 QEMU 限速与 cgroup blkio，覆盖 LVM、ext4、NFS、raw/qcow2 和不同缓存模式，同时使用单虚拟机及五台虚拟机负载。这样的矩阵帮助区分后端可控性、客户机观测值和执行成本，避免只在一种本地磁盘上得出结论。

4. 验证结果

实验使用双 X5670、128 GB 内存与 RHEL 6.1。图中 QEMU 能限制 NFS 后端请求，部分场景的实际速率略低于上限；CPU 成本图则显示该原型在用户态和内核态消耗明显增加，单位 CPU 完成的工作下降。作者明确写出数据尚不完整，并把减少 CPU 消耗列为后续工作。

5. 局限与后续工作

统一控制接口不代表免费，也不代表计量与物理磁盘工作量完全相同。后续需要优化突发抑制、唤醒频率和多队列公平性，并检查缓存模式改变后的限额语义。工程上应同时观察客户机延迟、实际 I/O 与宿主 CPU，明确限速目标是客户机请求还是底层资源占用。
