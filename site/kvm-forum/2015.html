会议/KVM Forum

KVM Forum 2015 精选解读

本届精选连接性能、兼容性与安全三类工程问题。实时 KVM 控制响应长尾，40GbE 原型尝试保留直通性能与迁移能力；Virtio 1.0 和多线程 TCG 整理接口与并发语义，SMM 与 Arm VGIC 则展示固件保护和中断模型如何落到 QEMU/KVM 实现。六项工作分别保留当年的实验条件及未完成部分。

一、本届观察

2015 年精选中的方案都在处理虚拟化对既有系统语义的影响：实时任务跨越两层调度，网卡迁移需要保存硬件状态，软件模拟并行化需要重建内存顺序，安全启动需要保护固件运行时状态。Virtio 与 Arm 中断模型的演进则表明，长期可维护的接口和数据结构与单次性能优化同样重要。

二、实时 KVM：控制调度延迟的长尾

原始演讲：Real-time KVM from the Ground Up · 原始讲稿（PDF）

Rik van Riel · Red Hat

1. 问题与工程价值

电信和控制类应用需要在约定时间内响应，少量很慢的请求就可能造成业务故障。虚拟化增加了宿主调度、客户机调度和设备模拟等边界，平均延迟难以反映这些边界偶发的停顿。讲稿从硬件到软件梳理延迟来源，为实时虚拟机配置提供可解释的依据。

2. 实现挑战

SMI 可以让 CPU 进入操作系统无法调度的固件代码；内核不可抢占区、IRQ 和后台任务也会延迟应用。宿主只看见 vCPU 线程，无法直接知道客户机内哪个任务最重要。把 vCPU 设为高实时优先级后，客户机空闲轮询又可能让宿主低优先级任务长期得不到执行，形成新的饥饿问题。

3. 解决方案

方案以资源分区为基础：宿主把实时 vCPU 放到专用 CPU，日常维护任务留在其他 CPU；客户机内部同样区分实时任务与设备管理等系统任务。这样可以减少慢速设备模拟把实时任务所在 vCPU 阻塞的机会。内核抢占、优先级继承、IRQ 线程化和定时器调整进一步缩短软件不可响应的区间。

讲稿还要求检查固件延迟、时钟稳定性、缺页、换页和缓存干扰。CPU 绑核只是其中一项措施；电源状态、共享缓存和客户机操作都可能重新引入长尾。2015 年 PREEMPT_RT 的合入状态也应按当时背景理解。

4. 验证结果

作者给出的客户机 cyclictest 示例为最小 5 µs、平均 6 µs、最大 14 µs。这组延迟是在资源专用、调度经过配置的客户机上测得；其中 14 µs 是该次运行观测到的最大值。

5. 局限与后续工作

讲稿列出调频、CPU 热插拔、模块装卸、任务迁移和慢设备访问等风险操作。资源超分也与这套专用 CPU 方案的保证前提冲突。工程验证应增加长期运行、宿主干扰、缓存竞争和实际业务截止时间统计，同时确认高优先级 vCPU 没有饿死完成 I/O 或维护系统所需的宿主线程。

三、可迁移 40GbE：直通设备状态怎样接管

原始演讲：Migratable 40GBit/s Ethernet · 原始讲稿（PDF）

Alexander Graf · SUSE

1. 问题与工程价值

VFIO 直通可以减少网络数据路径的软件开销，但通用驱动并不了解每种网卡内部状态。迁移时，仅复制客户机 RAM 无法恢复网卡的队列位置、控制配置和仍在进行的 DMA。讲稿选择特定 40GbE VF，尝试由了解设备协议的后端补足这些信息，探索高吞吐与热迁移能否共存。

2. 实现挑战

控制队列会改变 MAC、队列地址和工作属性，数据队列又持续与硬件并发交互。目标端设备复位后的队列位置可能不同于源端，DMA 写入还会修改客户机内存。接管必须同时考虑队列中的在途请求、已收到但尚未处理的报文，以及迁移期间哪些内存页被设备改写。

3. 解决方案

原型 vfio-i40evf 介入管理队列，跟踪客户机对设备的控制操作，以便在目标设备重建配置。运行态数据路径尽量保留直接访问；迁移阶段增加接收队列跟踪和中转，掌握缓冲区使用情况与相关内存修改。讲稿用动画解释源、目标队列位置重建及 DMA 状态交接。

这是针对设备协议的专用方案。通用 VFIO 框架提供分配与隔离基础，设备相关后端补充状态语义；其他 PCI 设备要采用同一路径，也需要提供相应的状态保存和恢复能力。讲稿还比较硬件感知 vhost 和队列转换等其他设计方向。

4. 验证结果

图表中，大报文场景的迁移跟踪路径可以接近普通 VFIO 的吞吐；1024 字节报文的测试则出现了明显下降。延迟图里，跟踪模式约为 0.3 ms，高于对应普通 VFIO 示例。作者报告热迁移可工作、正常运行性能接近直通，但同时注明不支持内存超分。测试平台细节有限，这些结果属于特定原型。

5. 局限与后续工作

方案依赖对网卡协议的了解，硬件与固件版本变化可能扩大兼容成本。完整评价还需要丢包、停机时间、错误恢复与多队列压力测试。它的工程价值是揭示迁移所需的控制面可观测性和 DMA 跟踪，而非给出可泛化的“直通设备都能迁移”结论。

四、Virtio 1.0：把隐含约定变成明确协议

原始演讲：Virtio 1 — Why Do It? And Are We There Yet? · 原始讲稿（PDF）

Michael S. Tsirkin · Red Hat

1. 问题与工程价值

早期 Virtio 实现中存在未充分写明的默认行为，包括驱动何时可以通知设备、配置值怎样读取，以及不同架构如何解释数据。随着驱动、后端和硬件实现增多，这些约定会成为兼容性问题。Virtio 1.0 的重要变化是把初始化、字节序和能力发现转化为明确协议，使独立实现有可核对的契约。

2. 实现挑战

协议升级必须兼容已经部署的客户机，无法要求所有驱动与后端同时更新。PCI 接口还要适应 MMIO 和可扩展的区域布局，避免固定位置限制后续功能。配置可能在读取过程中发生变化，驱动选择的特性组合也可能不被设备接受；这些情况需要协议层给出可判断的状态。

3. 解决方案

FEATURES_OK 为特性协商增加双方确认，驱动提交特性后必须检查设备是否接受；DRIVER_OK 明确设备开始工作的边界。配置代际计数帮助驱动发现多次读取期间的更新，固定字节序减少跨架构歧义。Modern PCI 接口通过 capability 描述区域，通知地址布局也为降低解码成本留下空间。

过渡设备和驱动组合提供 Legacy 与 Modern 的兼容路径。错误状态与复位协议使后端异常有机会通过设备重新初始化恢复，但具体恢复能力还依赖驱动和设备实现。讲稿中的下一版设备类型与功能规划，应与当时已经定稿的 1.0 内容分开。

4. 验证结果

材料通过状态机、布局及访问开销图表说明设计效果，并展示驱动与后端生态的实现进展。图表的测试条件并不完整，无法给出可复用的整体性能提升比例。更直接可检验的收益是错误协商能够被识别、配置变化能够被检测、接口可以通过能力发现扩展，适合写成兼容性与异常路径测试。

5. 局限与后续工作

前后端协商决定实际启用的特性。实际部署仍需检查前后端协商结果及过渡模式，尤其是固件、引导驱动与内核运行时驱动的组合。后续优化也不能破坏旧默认值。评估 Virtio 升级时，应同时关注协议正确性、启动兼容和特定队列路径的性能，避免仅凭版本号判断能力。

五、多线程 TCG：并行执行与客户机内存语义

原始演讲：Towards Multi-threaded TCG · 原始讲稿（PDF）

Alex Bennée · Linaro；Frederic Konrad · GreenSocs

1. 问题与工程价值

多核客户机在单个 TCG 执行线程上轮流运行，无法充分利用多核宿主，也难以暴露真实并发中的软件错误。多线程 TCG 希望让不同模拟 CPU 同时执行翻译代码，服务跨架构开发、系统验证与多核负载。问题既包含速度，也包含客户机看到的并发行为是否可信。

2. 实现挑战

TCG 的代码生成和运行时结构存在全局状态，翻译块补丁、跳转缓存和跨 CPU 操作需要同步。客户机的原子指令、LL/SC 和内存屏障语义也不能依靠单线程执行顺序自然满足。设备模型及辅助函数有些只访问当前 CPU，有些修改共享系统状态，必须区分处理。

3. 解决方案

讲稿中的原型将可拆分状态移到每 CPU 或线程对象，使用锁保护翻译生成与相关缓存修改，让翻译代码的常见执行路径能够并行。修改多个 vCPU 状态的操作可以通过延迟工作机制，在相关 CPU 到达安全点后执行，避免复杂的交叉加锁。

LL/SC 原型利用新的 TCG 操作与 SoftMMU 慢路径记录排他访问状态；设备 MMIO 继续通过内存 API，按设备能力选择无锁处理或 BQL。这些操作名来自演讲时的原型。

4. 验证结果

演示采用 ARM32 客户机和 x86 宿主，重点验证这组前后端能否协同执行。能够确认的是全局状态整理、并行执行路径和原子语义方案已经有补丁与测试工作；当时仍需补齐内存屏障，并验证各前后端组合的内存访问顺序。

5. 局限与后续工作

弱内存宿主可能暴露 x86 测试中难以出现的问题，跨页访问、自修改代码和翻译失效也需要并发压力验证。后续工作包括内存屏障操作、架构覆盖、文档和专门测试。验证多核模拟要同时看执行结果是否正确，以及增加线程后性能如何变化。

六、SMM 与 Secure Boot：保护虚拟机固件状态

原始演讲：Securing Secure Boot with System Management Mode · 原始讲稿（PDF）

Paolo Bonzini · Red Hat

1. 问题与工程价值

Secure Boot 的签名检查依赖可信密钥和固件状态。如果操作系统能够直接修改保存密钥的变量或 S3 恢复脚本，启动链仍可能被破坏。SMM 提供受保护的固件执行环境，虚拟机需要由 QEMU、KVM 和 OVMF 共同模拟其状态切换、内存隔离与闪存访问规则。

2. 实现挑战

SMM 内存必须对普通模式隐藏，又要对进入 SMM 的 CPU 可见；多 vCPU 同时处于不同模式时，不能简单修改一份全局映射。闪存访问同样需要知道发起访问的 CPU 当前模式。迁移还要保存相关状态，而固件处理程序自身若错误访问不可信内存，硬件隔离也无法修复逻辑漏洞。

3. 解决方案

QEMU 补齐 Q35 的 SMRAM/TSEG 和锁定行为，利用内存事务属性判断访问是否来自 SMM，对普通模式下不允许的闪存写入进行限制。KVM 维护普通与 SMM 两套内存视图，由 vCPU 当前模式选择，避免每次变化为所有 vCPU 分别更新完整映射。

KVM 还负责 SMI 进入、RSM 返回和寄存器状态处理，QEMU 将模式信息传给用户态设备访问路径。讲稿展示虚拟硬件可以采用更简单的受控闪存写入方式，减少对真实芯片组复杂协议的复制，同时保持固件需要的保护语义。

4. 验证结果

作者列出 QEMU 2.4 与 Linux 4.2 的相关支持状态，OVMF 补丁当时仍在评审，示例还受 32 位、单处理器等条件限制。演示覆盖寄存器和地址空间访问，整条固件信任链的验证还需要安全审计。

5. 局限与后续工作

SMM 处理程序、共享通信缓冲区、恢复脚本和嵌套状态都需要继续审查。客户机固件隔离也不负责防御恶意宿主修改虚拟硬件。后续评价应明确威胁边界，并测试多 CPU、迁移及异常进入返回，检查受保护变量在不同运行阶段是否始终遵守同一权限规则。

七、Arm 中断虚拟化：从 GICv2 到 GICv3

原始演讲：ARM Interrupt Virtualization · 原始讲稿（PDF）

Andre Przywara · Arm

1. 问题与工程价值

中断虚拟化需要让客户机接收、确认和结束设备事件，同时尽量减少每次操作引起的软件切换。GICv2 已提供虚拟 CPU 接口与 List Registers，GICv3 又引入更大 CPU 规模、Redistributor 和 MSI/LPI。原有按少量连续中断组织的 VGIC 软件模型，因此需要适应新的数量与路由方式。

2. 实现挑战

GICv2 的部分 MMIO 寄存器按 CPU 分组，同一地址的意义取决于访问 vCPU。GICv3 的状态分布和系统寄存器接口又不同，软件需要同时支持两种模型。大量稀疏 LPI 不适合沿用固定大位图，ITS 表位于客户机内存还会增加访问成本；迁移时软件状态与硬件 List Registers 必须一致。

3. 解决方案

GICv2 路径由软件模拟 Distributor，把待处理中断装入 List Registers；客户机通过虚拟 CPU 接口执行部分确认与 EOI，无需每次退出，运行后再同步相关状态。对可以关联的物理和虚拟中断，硬件还能协助结束物理中断，减少额外监视。

面向 GICv3，讲稿提出按实际使用的中断组织状态，分离不同 IRQ 类型与模拟模型。ITS 用设备 ID、门铃地址和消息内容共同识别中断；KVM 路由接口需要表达这些信息。

4. 验证结果

讲稿区分已完成的初始化与多模型重构，以及正在处理的物理/虚拟中断关联和后续结构调整。材料没有吞吐或延迟基准，能够确认的是硬件快速路径的职责和软件扩展性问题。GICv4 直接注入虚拟 LPI 是当年列出的后续方向。

5. 局限与后续工作

状态缓存、失效与迁移会影响中断是否丢失、重复或发给错误 vCPU。稀疏分配结构也需要兼顾常见路径成本。后续验证应覆盖电平与边沿触发、不同中断类别、vCPU 调度和迁移同步，既检查快速注入，也检查不满足硬件直达条件时的软件回退。
