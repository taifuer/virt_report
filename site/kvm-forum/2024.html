一、本届观察

2024 年的精选覆盖性能与维护两类实际需求。多核客户机提交更多 I/O 后，QEMU 的线程分配和存储后端成为瓶颈；开启内存超分后，迁移扫描可能破坏正常业务的工作集；给虚机分配多个直通设备后，设备状态传输又拉长了停机窗口。这些问题都需要沿完整路径分析。

本页还选择了 Akamai 的原机内核更新实践，以及 SNP 迁移和中断保护的接口设计。前者揭示运维成本与硬件初始化的关系，后两者展示机密计算如何改变宿主的职责。七场分享的证据层次不同：已合入功能、原型数据、生产平台经验与待完成设计，在各节中分别标明。

二、virtio-blk 多队列：把请求分配到多个 IOThread

原始演讲：IOThread Virtqueue Mapping: Improving virtio-blk SMP scalability in QEMU · 原始讲稿（PDF）

Stefan Hajnoczi

1. 问题与工程价值

virtio-blk 多队列可以让不同 vCPU 独立提交请求，并把完成中断送回相应 CPU。但宿主若仍用一个 IOThread 处理所有 virtqueue，请求解析、块层操作、完成回填与中断通知仍挤在同一条执行线上。高速 NVMe 的性能容易被这段 CPU 工作限制。

2. 实现挑战

增加线程需要块层支持并发请求，不能只把设备入口分给几个线程。镜像格式、共享状态和完成回调必须具有正确的线程归属；同时，多占用 IOThread 会减少客户机业务可以使用的 CPU。配置还要覆盖多磁盘共享线程和虚机迁移后的 CPU 放置。

3. 解决方案

QEMU 9.0 增加 virtqueue 到 IOThread 的映射，依托块层多线程请求处理，让同一设备的不同队列并行运行。Libvirt 10.0 提供相应 XML 配置，可轮转分配，也可在 QEMU 中显式指定队列集合。多个低负载磁盘可以共享 IOThread，减少空闲线程的资源占用。

讲稿推荐 cache=none、io=native 的配置路径，并明确区分设备处理线程与 io=threads 的后端工作池。绑核时应考虑客户机内存和存储控制器所在 NUMA 节点，避免通知和数据在节点之间反复移动。

4. 验证结果

测试使用 Intel Optane SSD DC P4800X，以原始块设备作为后端，fio 运行八个任务的 4 KiB 随机读。在队列深度 64 时，一个 IOThread 约 24 万 IOPS，四个约 50 万 IOPS。作者也展示数据库负载随并发增加而收益收窄的情况：当宿主 CPU 或磁盘带宽已耗尽，新增线程无法创造额外资源。

5. 局限与后续工作

较大块 I/O 更容易由单线程占满存储带宽，64 KiB 以上负载未必需要更多 IOThread。本地 NVMe 实验中的四到八线程只能作为测量起点。后续方向包括 virtio-scsi、其他 virtio 设备及处理路径本身的 CPU 效率。部署评价应同时记录业务吞吐、尾延迟与宿主 CPU 成本。

三、进程外存储：性能、隔离与管理接口的取舍

原始演讲：Practical and efficient out-of-process storage backends · 原始讲稿（PDF）

Kevin Wolf

1. 问题与工程价值

把存储后端从 QEMU 拆到 QEMU Storage Daemon，可以独立运行块任务、共享镜像链，并缩小设备进程的职责范围。KubeVirt 等平台还希望把这些能力作为普通文件或块设备交给虚机和容器。不同传输方式在性能与运维接口之间存在明显取舍。

2. 实现挑战

共享客户机内存能够减少拷贝，却需要给外部进程相应的访问权限，并协调回收、迁移和资源生命周期。保留普通文件、块设备接口便于管理，但数据通常要经过更多层。具备最短数据路径的协议，未必符合容器平台的权限模型或现有镜像管理方式。

3. 解决方案

讲稿比较了几条路径。NBD 通过 socket 转发，适用范围广；FUSE 以普通文件暴露后端，用户权限要求较低；vhost-user-blk 直接处理共享内存中的 virtqueue，数据路径可绕过 QEMU；vDPA 可通过 vhost-vdpa 接入虚机，也可通过 virtio-vdpa 暴露宿主块设备，但需要相应内核支持和权限。

ublk 提供另一种宿主块设备接口。作者讨论让用户态守护进程只处理元数据、复用内核缓冲区的零拷贝方向，以及在内核缓存映射或用 eBPF 处理简单请求的原型。这些优化尝试减少 QSD 侧往返，同时保留通用块设备的管理方式。

4. 验证结果

测量覆盖 null 后端、NVMe 分区与 XFS/LVM/LUKS 上的文件，比较 4 KiB 和 64 KiB 随机读。小请求更容易暴露传输与调度开销；大请求在部分后端上受存储带宽限制，各方案差距收窄。vhost 路径在部分测试中优于单线程进程内基线，但 ublk 示例使用 ubdsrv 和不同线程布局，不能据此排列一个通用性能榜。

5. 局限与后续工作

作者发现队列长度不同、导出端缺少多线程和 NBD 异常开销都会影响比较。演讲时 ublk 还不是 QEMU 已实现的导出类型，零拷贝和内核处理也有待完善。选择方案时，应把请求大小、线程数、权限、内存共享和迁移要求一起列入条件；仅凭“零拷贝”标签不足以判断整体收益。

四、userfaultfd 内存超分：让换页策略与迁移协调

原始演讲：UserfaultFD-based Memory Overcommitment · 原始讲稿（PDF）

Tejus GK, Manish Mishra, Rohit Kumar

1. 问题与工程价值

宿主换出部分客户机页面，可以在有限 DRAM 上容纳更多实例。但热迁移会读取客户机内存，把冷页重新调入，挤压业务工作集。传输变慢又给客户机更多写脏时间，导致更长的迁移过程。控制换出位置与页面状态，可以让换页和迁移使用一致的信息。

2. 实现挑战

用户态管理器需要接管缺页、页面状态和换出决策，还要在源端与目的端之间保持状态一致。客户机修改页面、迁移传输和后台回收可能同时发生。任何组件私自移除页面，都可能破坏管理器对内容和位置的记录。

3. 解决方案

方案为 QEMU 禁用原生换页，由外部 Mem-controller 分配共享内存、维护页面状态图，通过 userfaultfd 处理访问缺页，并通过 UNIX socket 与 QEMU 通信。原型采用静态内存限制、随机选页和分组换出，允许后续按虚机实现不同策略或存储分层。

迁移时，控制器向 QEMU 提供状态图，源端跳过仍在换出目标中的页面，在最终阶段传递其位置。目的端把这些信息交给控制器，缺页时从相应存储读取，并在后台同步。已由迁移流更新的页面必须使用新内容，源、目的换出状态也要持续协调；避免重复读入冷页的收益来自这套配合。

4. 验证结果

12 GB、12-vCPU 虚机运行单线程、10 GB 工作集的合成负载，SATA SSD 换出、比例 0.5 时，迁移时间从 214.1 s 降到 45.5 s，传输量从 9.6 GB 降到 7.8 GB。5 GB、4-vCPU Redis 示例中，平均操作数从 1534/s 增到 1848.8/s。

收益并不普遍：RAM-disk 后端的合成吞吐从 780 MB/s 降到 720 MB/s；2 GB、4-vCPU 的内核编译时间从 1263.2 s 增到 1376.5 s。更快的后端或不同访问模式，会放大用户态缺页处理本身的成本。

5. 局限与后续工作

主要瓶颈包括上下文切换、UFFD_COPY 拷贝，以及移除页面时的地址空间排他锁。作者提出扩大换页粒度、并行处理和改进通知方式，并要求把 balloon 操作也纳入控制器。工程上还需要验证控制器故障、存储不可达和迁移取消时的数据完整性；额外的策略控制同时意味着额外的可靠性职责。

五、设备状态并行迁移：减少多 VF 的停机时间

原始演讲：QEMU live migration device state transfer parallelization via multifd channels · 原始讲稿（PDF）

Maciej S. Szmigiero

1. 问题与工程价值

SmartNIC 和 GPU 的设备状态可能达到数百 MiB，其中一部分只能在虚机停机后提取。传统主迁移通道依次保存和加载设备，多个 VF 会互相等待。即使内存预拷贝已收敛，设备状态仍可能决定最终停机长度。

2. 实现挑战

设备状态和普通 RAM 不同：需要经驱动读取并按设备要求恢复，多个通道到达的数据还要重新排序。并发过高会增加缓冲区和线程成本；内核驱动、设备固件若仍串行工作，增加 QEMU 线程也难以获益。恢复过程中部分核心地址空间操作还要求持有大锁。

3. 解决方案

方案复用 multifd 通道，分离设备状态读取与排队、网络传输和目的端加载。每个设备的状态按序送回驱动，并限制接收缓冲区大小。加载线程可由线程池管理，使线程数不必永久等于设备数。mlx5 的分块读取和双缓冲配套让设备取数与 QEMU 消费能够重叠。

早期原型曾为设备单独设置通道，后来测试发现减少共享通道总数也能取得相近效果。演讲时只并行化了部分 VFIO 状态转换，仍有主迁移线程串行处理的步骤。

4. 验证结果

测试使用两台 Xeon 主机、ConnectX-7 和 100GbE，虚机为 24 vCPU、15 GiB 内存，配置一到四个 VF，每 VF 约 100 MiB 状态。重复迁移七十余次后，取最低停机值观察相对空闲情况下的表现。

配置 原路径 并行设备状态传输
1 个 VF 283 ms 274 ms
2 个 VF 614 ms 434 ms
4 个 VF 1783 ms 1068 ms

四 VF 的停机时间约减少 40%。六通道的中位数为 1130 ms，增到二十通道后为 1310 ms，说明通道数量需要测量，不能简单叠加。

5. 局限与后续工作

当时补丁处于第二版，目标是后续 QEMU 版本。测试最多覆盖四 VF，最低值也不能代表线上尾延迟。后续包括更多状态转换并行化、非阻塞驱动接口、运行阶段设备预拷贝和更准确的停机估算。评测应保留分位数，并观察业务负载、设备数量和状态量变化后的稳定性。

六、Akamai 内核热更新：原机保留内存并恢复虚机

原始演讲：Live Updates @ Akamai · 原始讲稿（PDF）

Michael Galaxy

1. 问题与工程价值

Akamai 介绍的平台面临容量、CPU 特性、安全和客户约束，未必能为每次宿主维护找到迁移目标。更新等待会拖慢安全修复，预留过多空闲容量又增加成本。原机更新通过保存客户机 RAM，避免把全部内存搬到另一台服务器。

2. 实现挑战

跨内核保留内存只解决了状态的一部分。设备驱动、网络、文件系统、cgroup 和 vhost 文件描述符都需要重建，客户机还要重新连接到原来的内存。驱动固件初始化可能耗时不稳定，启动编排中的每个额外服务也会扩大停机窗口。

3. 解决方案

实践使用 PMEM 区域、DAX 文件系统和共享的文件内存后端保存客户机 RAM，QEMU CPR 保存其余设备状态。维护流程保存命令行与资源层级，退出 QEMU、同步并卸载文件系统，然后 kexec 进入新内核。在 initramfs 中重建所需设备和环境，恢复 cgroup、vhost/virtio 文件描述符，并以原配置重新启动 QEMU、接回内存。

这一路径仍会重新初始化宿主设备，与持续保留设备运行状态的方案不同。为减少启动服务的开销，实践中的部分恢复步骤绕过了常规管理流程，因此维护工具也必须承担一致性检查与失败处理。

4. 验证结果

讲稿把停机分为 kexec、驱动初始化、平台中间件和客户机恢复几个阶段：kexec 可小于一秒，简单硬件有机会把整体更新控制在五秒以内；复杂硬件、尚未充分优化的中间件约为十秒，设备固件还可能进一步延长时间。这些是平台经验范围，并非所有硬件都能满足的停机承诺。

5. 局限与后续工作

预留 PMEM 区域带来固定的宿主内存开销，方案当时不能自由进行 NUMA 页面迁移和 swap。客户机时间在更新期间暂停，也可能影响上层服务。后续需要改进多内存后端、NUMA 配套和循环升级测试。真正的验收标准应包括长连接、时钟与业务恢复，而不只是 QEMU 成功重新启动。

七、SNP 迁移：在受保护上下文中打包内存

原始演讲：SNP Live Migration with guest-memfd and mirror VM · 原始讲稿（PDF）

Tom Lendacky, Pankaj Gupta

1. 问题与工程价值

SEV-SNP 保护客户机私有内存的机密性和完整性，宿主无法像普通虚机迁移那样直接读取明文。迁移又需要把正在变化的内存和 CPU 状态安全交给目的端。因此，打包与验证工作需要进入可信上下文，同时保留宿主管理迁移进度的能力。

2. 实现挑战

可信迁移工作不能与客户机操作系统共享所有执行假设。它需要自己的 vCPU、运行级别和资源计费方式，还要与原 VM 访问同一份客户机内存。演讲时 guest_memfd 紧密绑定单个 KVM 对象，这给独立迁移 VM 共享地址空间带来障碍。

3. 解决方案

Mirror VM 路径创建临时 KVM 虚机，让迁移辅助 vCPU 在 VMPL0 的 SVSM 中运行，宿主跟踪脏页，可信组件完成内存打包。迁移线程以辅助 vCPU 的形式执行，可按需求增加并行度；独立对象也便于云平台计费和控制生命周期。

另一条 Shadow vCPU 路径把辅助 vCPU 放在原 KVM 对象中，减少跨对象共享内存的要求，但需要不与原 CPU 冲突的 APIC ID，以及动态创建 VMPL0 执行状态的支持。两条路径都还需要目的端身份验证、密钥交换、VMSA 传输和迁移结束时的完整性确认。

4. 验证结果

讲稿展示设计拆分与实现状态：迁移线程运行成 Shadow vCPU 的部分已有代码，而 APIC ID 范围、Mirror VM 地址空间共享和相关 KVM 接口仍待完成。它没有提供完整 SNP 热迁移的吞吐或停机基准。选入本页的价值在于它明确了受保护内存给迁移执行模型带来的接口约束。

5. 局限与后续工作

Mirror VM 的独立资源管理与 guest_memfd 共享支持相互依赖，Shadow vCPU 则增加原 VM 内部的拓扑与生命周期管理。还需要定义源、目的可信组件的认证边界和中止流程。工程评价应覆盖错误密钥、传输中断和部分状态恢复，确保失败时不会留下可继续运行的冲突实例。

八、SNP 中断保护：让可信组件决定注入

原始演讲：Securing Interrupt Delivery for SEV-SNP Guests · 原始讲稿（PDF）

Melody (Huibo) Wang

1. 问题与工程价值

即使客户机内存已经加密，不可信宿主仍可能通过异常和中断注入改变客户机执行。讲稿列举了利用特定异常向量和软件中断的风险，提出把接受、过滤和转交事件的权力移到客户机可信边界内。这个问题说明，机密性与完整性需要覆盖控制流入口。

2. 实现挑战

直接限制注入有助于缩小接口，却会影响 Linux 复杂的异常嵌套处理。引入 SVSM 后，还要区分不同 VMPL 的中断来源、APIC 状态和完成确认，同时保证可信组件本身不会被恶意注入破坏。固件与操作系统可能采用不同的中断模式，启动交接也需要明确状态。

3. 解决方案

Restricted Injection 限制宿主的常规事件注入，通过 #HV 等受控接口通知可信侧。Alternate Injection 在此基础上，让 VMPL0 的 SVSM 接收通知、模拟 APIC，并把认可的中断写入较低 VMPL 的 VMSA，再切换到相应客户机上下文。

KVM 需要为每个 vCPU 的各 VMPL 维护独立事件来源；SVSM 通过 APIC 协议提供寄存器访问与配置；Linux 客户机识别该模式后，把相关 APIC 操作交给 SVSM。GHCB 的通知向量、定时器和 EOI 接口也要扩展。各层共同维护事件状态，才能避免把宿主提供的请求直接视为可信事实。

4. 验证结果

演讲时，面向 VMPL0 客户机的 Restricted Injection KVM 支持已提交评审，#HV IPI 等部分仍在开发。Alternate Injection 的多 VMPL 配套、客户机支持和若干 SVSM 功能尚未完成。讲稿给出了协议流程与代码入口，但没有端到端的安全中断性能基准；性能代价只能从新增 VMPL 切换等路径分析，不能据此给出固定开销。

5. 局限与后续工作

后续重点包括嵌套异常、不同 VMPL 的状态隔离、固件到内核的模式交接，以及高频中断下的切换成本。Secure AVIC 被介绍为未来的硬件加速方向。可信过滤可以减少恶意注入造成的完整性风险，宿主仍可能延迟或停止调度；这类可用性问题需要另行考虑。
