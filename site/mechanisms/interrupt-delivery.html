中断递送与客户机响应

一、场景与边界

virtio 设备完成请求后，先把结果发布到共享队列，再按通知条件提醒客户机。以接收队列的一次完成为例，MSI-X 表项选择 APIC ID 1 和向量 0x51，KVM 将消息送入目标 vCPU 的中断状态，处理器在允许的时机进入客户机处理程序。驱动随后读取队列并取得结果。

这段路径有三种容易混淆的等待：MSI-X 屏蔽使通知留在设备的 PBA；客户机暂不能接受使向量留在 LAPIC 的 IRR；线程未获得 CPU 又会推迟执行。下面按通知路径、屏蔽与等待、硬件递送组织示例，观察每一种状态由谁保存、何时推进。irqfd 连接后端事件与 KVM，APICv 优化后续的硬件交付，两者可以配合使用。

示例采用 x86-64、Intel VMX、QEMU 10.2.0 和 Linux 6.18。前四种使用软件 LAPIC 注入路径；posted 场景固定硬件支持、APICv 已启用且目标 vCPU 正在运行。它们是具有明确条件的对照场景，不将任意设备、屏蔽和硬件加速选项自由组合。

源码版本：QEMU 10.2.0、Linux 6.18。

      MSI-X 屏蔽与 PBA

      设备表项被屏蔽时把通知记入 PBA，解除屏蔽后再补发 MSI-X 消息。

      • QEMU 软件 MSI-X 设备，表项 2 已分配，功能级 mask 关闭
      • 表项级 mask 初始为 1；不用 irqfd notifier 路径，聚焦 msix_notify 与 mask update
      • APICv 关闭，目标 Guest IF、shadow 与优先级均允许交付
      1. 表项处于屏蔽状态 · QEMU 设备模型

        请求数据已完成，设备准备发出通知，但表项 2 的 mask = 1。 屏蔽通知不撤销已经写入的完成记录。驱动若主动轮询队列，也可以发现 used。

        QEMU 10.2：msix_notify 的屏蔽检查与消息发送 · Linux 6.18：virtqueue used 消费与描述符回收

        屏蔽检查命中，设置 PBA[2] 后返回，暂不发送 MSI-X。 PBA 按表项保存待发送通知，不计数每一个请求；多次通知可合并在同一位。目标 LAPIC 的 IRR 此时仍为 0。

        QEMU 10.2：msix_notify 的屏蔽检查与消息发送

        QEMU 清 PBA[2]，再次调用 msix_notify，发出目标 1、向量 0x51 的消息。 消息随后进入正常 MSI 路由；PBA 清零与 LAPIC IRR 置位是不同对象上的操作。

        KVM 将消息路由到目标 vCPU，设置 IRR[0x51]。 设备侧 pending 已处理完毕；向量现在等待 CPU 侧的接受与交付。

        条件满足，软件注入路径把向量从 IRR 转为 ISR，并进入客户机。 若客户机 IF 为 0，流程会在 CPU 侧继续等待；该情形由独立场景展示。

        Linux 6.18：清 IRR、设置 ISR · Linux 6.18：VM Entry 外部中断注入字段
      7. 客户机 EOI · 客户机 IRQ 路径

        EOI 清除 ISR 中的本次服务位。 设备队列中的数据和完成项仍由驱动读取；PBA、IRR、ISR 分别承担设备待发、CPU 待处理和 CPU 服务中状态。

      APICv Posted Interrupt

      目标 vCPU 正在运行时，KVM 将向量写入 PIR，硬件同步到虚拟 IRR 并向客户机交付。

      • Intel 处理器支持并启用 APICv、virtual interrupt delivery 与 posted interrupts
      • KVM 内核 LAPIC，目标 apicv_active，非嵌套虚拟化，vCPU 正在另一宿主 CPU 的 non-root 模式运行
      • PID 初始 ON = 0、SN = 0，正确配置通知向量与目的 CPU；无并发重复通知
      • Guest IF = 1，无 interrupt shadow，向量优先级允许；固定为普通边沿向量 0x51
      • EOI-exit bitmap 不为向量 0x51 请求退出
      • 本例采用 KVM 软件 posting，不展示物理设备经 VT-d 直接 posting
      1. 目标 vCPU 正在运行 · KVM 投递入口

        目标具备 posted interrupt 条件，PID 与虚拟 APIC 均无本次向量。 本场景固定 vCPU 正在另一宿主 CPU 上运行。阻塞、抢占和迁移需要额外唤醒或状态同步，不套用这条最短路径。

        Linux 6.18：VMX posted 路径与 IRR 软件回退 · Linux 6.18：PIR、ON 与 posted notification
      2. 把向量记入 PIR · KVM · __vmx_deliver_posted_interrupt

        原子设置 PIR[0x51]，再把 ON 从 0 置为 1。 PIR 已有该位或此前通知仍 outstanding 时，可省去重复通知。本例固定二者初始为 0，继续发送。

        Linux 6.18：PIR、ON 与 posted notification
      3. 通知目标物理 CPU · KVM → 目标处理器

        KVM 向正在运行目标 vCPU 的 CPU 发送 posted notification。 宿主通知向量用于提示处理器检查 PID，与客户机的 0x51 向量不是同一编号。本例条件下无需为该通知退出 Guest。

        Linux 6.18：PIR、ON 与 posted notification · Intel SDM：APIC virtual interrupt delivery 与 posted-interrupt processing
      4. 硬件同步待处理中断 · 目标处理器

        posted-interrupt processing 把 PIR 位合入 vIRR，清除已取出的 PIR 与 ON，并更新 RVI。 此时 vIRR 表示客户机尚待接受的向量；它与 PID 中用于跨 CPU 发布的 PIR 分属两个阶段。图中拆开显示硬件处理的逻辑结果。

        Linux 6.18：VMX posted 路径与 IRR 软件回退 · Intel SDM：APIC virtual interrupt delivery 与 posted-interrupt processing
      5. 硬件交付虚拟中断 · 虚拟 APIC / 处理器

        满足 Guest IF、shadow 与优先级条件，硬件清 vIRR、设置 vISR，并进入客户机中断入口。 没有其他 pending 向量时，RVI 回到 0。Guest 的中断架构规则保持有效；关闭 IF 时仍会保留 pending 等待。

        Intel SDM：APIC virtual interrupt delivery 与 posted-interrupt processing
      6. 完成虚拟 APIC 应答 · 客户机 → 虚拟 APIC

        客户机 EOI 结束本次 in-service 状态，vISR[0x51] 清零。 本例固定 EOI-exit bitmap 对该向量未请求退出，硬件可处理这次应答。其他 EOI 配置、未运行 vCPU 或不满足 APICv 条件的情况仍需软件路径。

      EOI 只应答 APIC 服务状态。Linux 边沿中断路径可以先应答，再执行设备处理；virtio-net 还可把队列消费交给 NAPI。EOI 之后，完成记录可能仍未被驱动消费。演示因此把 EOI 与 last_used_idx 的变化分成两个步骤。

      MSI-X 表项 2、KVM 路由键 GSI 37、APIC ID 1、向量 0x51 各自标识不同对象。直接 MSI 路径每次提交地址和 data；irqfd 路径预先登记路由，再用 eventfd 触发该路由。配置变更时，路由与 notifier 绑定也要保持一致。

      四、中断路径的演进

      把 LAPIC 放进 KVM 后，待处理向量、优先级与许多控制器访问可在内核中完成，减少用户态往返。在这一基础上，irqfd 缩短后端事件进入 KVM 的交接：后端触发 eventfd，KVM 按预登记路由投递，无需用户态逐次监听后再发起中断 ioctl。

      APICv 继续优化控制器访问与 CPU 交付。posted interrupt 把待处理向量放进 PID 的 PIR，通知正在执行目标 vCPU 的处理器；硬件将 PIR 合入虚拟 IRR，再按客户机规则交付。示例中从“发布 PIR”到“进入 handler”的逻辑阶段分别显示，实际硬件处理不提供供软件任意插入的中间停顿。

      irqfd 与 APICv 作用于不同环节，可以同时使用。目标 vCPU 未运行、被阻塞或正在迁移时，还需要唤醒、重新进入或同步 PID 状态；硬件能力、Guest 屏蔽规则和调度等待仍然存在。本页展示 KVM 软件 posting，物理设备经 VT-d 直接 posted delivery 还涉及中断重映射表和设备绑定。

      实际优化可以从“设备完成 → 通知产生 → LAPIC / PID pending → vCPU 执行 → 驱动消费”逐段计时。批处理减少通知数量，irqfd 减少通知中转，APICv 减少部分交付退出，CPU 绑定与调度影响运行机会；收益和代价应在各自对应的阶段评价。
