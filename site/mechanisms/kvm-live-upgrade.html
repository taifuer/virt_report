一、云平台在线升级的需求

一台虚拟机长期运行时，支撑它的虚拟化软件仍需要修复漏洞、改进性能和增加功能。KVM 在宿主内核中管理 vCPU 执行，QEMU 在用户态组织虚拟机内存和设备。安装新版软件包后，已有的 QEMU 进程和 KVM 实例仍在执行旧代码；运行中的虚拟机需要一次明确的状态交接，才能用上新实现。

以一台运行数据库服务的虚拟机为例：它有 4 vCPU、8 GiB RAM 和一块直通网卡。宿主需要更新 KVM，客户机中已有的进程、内存内容和网络连接都应保留。如果每次修复都要求客户重启业务，更新就会受维护窗口限制；如果先把所有虚机迁走，云平台又要准备接收它们的服务器与网络容量。单台机器上的维护步骤，到了数万台宿主上就会成为升级进度的瓶颈。

Orthus 利用同机升级的条件，把 Guest RAM 和物理设备留在原处，由新 KVM 与新 QEMU 接管运行状态。虚拟机会短暂停顿，随后从原来的执行位置继续，客户机操作系统不重新引导。本文沿上述数据库虚机的一次升级，介绍这条路径的设计、实现和效果；示例配置用于讲解，不代表论文的测试配置。只更新 QEMU 的方式见 QEMU 热升级：CPR 的资源交接与状态恢复。

后文再对照字节跳动的 VMM Live Upgrade 和 HyperFresh：前者继续处理同机模块交接中的设备与通知，后者借助嵌套虚拟化替换承载业务虚机的 Hypervisor。本文关注实际 KVM 实现的在线替换，保留 Guest 运行状态，允许切换时短暂停顿；宿主基础内核或底层管理层保持运行。

论文依据：Orthus · ASPLOS 2019、HyperFresh · APSys 2017、HyperFresh · VEE 2019。

二、已有升级方式与同机接管的挑战

升级方案首先取决于准备替换哪一层，以及业务能接受多大的中断。下面把三种路径放到这台虚拟机上比较；CPR 用于说明用户态进程替换的范围，不属于 Orthus 论文当年的实验对照。

路径操作与收益主要代价或限制
停机更新并重启虚机关闭虚拟机，释放旧实现的引用，完成更新后重新启动业务中断包含关机、更新、引导及应用恢复
跨主机热迁移后更新在另一台宿主恢复虚机，腾空原宿主；也适合原宿主的硬件维护需要目标容量、迁移带宽和兼容配置；直通设备还要有受支持的迁移或替代路径
只替换 QEMU，例如 CPR-transfer共享 RAM，交接进程资源及运行状态这一步保留原来的宿主内核与 KVM 实现，无法独自完成 KVM 版本替换

内存复制的成本可以用一个简单估算理解：假设这台虚机的 8 GiB RAM 全部需要传送，有效带宽为 1 GiB/s，第一轮就需要约 8 秒，尚未计入重传脏页和其他开销。预拷贝期间客户机可以继续运行，因此这 8 秒属于迁移总耗时，不能直接算成停机时间。批量迁移还会让多台虚机竞争同一条网络链路。

同机升级省去了更换物理宿主的必要，但仍有三个难点。首先，旧 KVM 正被 VM 和 vCPU 引用，必须让新实现能先准备好。其次，客户机的内存、寄存器和设备状态需要形成可恢复的运行现场。最后，直通设备独立于 vCPU 工作，CPU 暂停时，设备仍可能 DMA 写入内存并产生中断。Orthus 的三个机制分别处理这些困难。论文 §2–3

三、Orthus 的整体设计与新旧 KVM 共存

Orthus 是完整的升级系统，Dual KVM 是其中负责新旧实现共存的一部分。只有模块共存，还不能让原虚机自动转入新版；内存、运行状态和设备都要沿着各自的路径交接。

需要解决的困难机制示例中的结果
旧 KVM 仍服务运行中的虚机，不能直接卸载Dual KVM：保留稳定接口，让新旧实现并存数据库虚机仍用旧版时，新版已经可以接受接管
RAM 很大，执行状态分散在 QEMU 与 KVM 中VM grafting：原地保留内存，保存并恢复其余状态8 GiB 物理页保留，4 个 vCPU 从保存的位置继续
网卡还有正在进行的 DMA 与完成通知Device handover：保留设备连接，交接控制与通知关联设备仍访问原来的内存，接收完成由接管后的客户机处理

具体到 KVM，Orthus 将原来 kvm.ko 的大部分实现移入经过改造的 kvm-intel.ko，留下与宿主内核衔接的薄层。新旧模块通过各自的函数接口注册到这个薄层，再分别提供 /dev/kvm0 和 /dev/kvm1。全局变量按实例隔离，函数符号的可见范围也作相应调整，避免两份实现相互覆盖。

对示例虚机，旧 QEMU 仍通过旧入口运行，新的 QEMU 将通过新入口建立 VM 和 vCPU。宿主按调度安排不同 vCPU 使用硬件虚拟化能力；同一台虚拟机的旧、新 vCPU 不会同时推进客户机执行。

其他虚拟机可以暂时继续使用旧实现。等旧实例上的最后一台完成接管，才卸载旧模块。这样就能逐台升级，并把失败处理限制在尚未完成切换的虚机上。代价是预先改造模块边界，并维护两套实例的隔离与资源协调；原版发行版重复加载模块不具备这套协议。论文 §3.1

四、一台虚拟机的完整升级

1. 保留内存，区分运行状态与实现对象

数据库缓存、应用堆栈和接收缓冲区都在这 8 GiB Guest RAM 中。交接后这些字节应继续留在原来的宿主物理页上；客户机看到的地址也要保持一致。新 QEMU 可以重新映射这些页，但不必另外复制 8 GiB 内容。

4 个 vCPU 的寄存器和模拟设备状态则需要保存、加载。新 KVM 创建自己的 VM / vCPU 对象，再恢复客户机可见的执行状态。旧对象中的内核指针、锁和实现布局不能原封不动地当成新对象使用。这也是内存保留与状态恢复必须分别处理的原因。

Orthus 使用 fork() 创建接管进程，再用 execv() 加载新 QEMU。普通 exec 会替换进程地址空间，fork 继承下来的匿名映射不能直接沿用。论文为 Guest 内存增加 MAP_KVM_RESERVED 保留与映射支持，这是它的内核扩展。基于文件的共享内存也可以通过保留后备文件再建立映射；关键在于后备页的生命周期能够跨过进程替换。

2. 从旧端暂停到新端恢复

新版 KVM 已加载后，单台虚机依次完成下面的交接。新端需要采用与原虚机兼容的 CPU、机型和设备配置；执行新的 QEMU 程序不等于让 Guest 再次经过固件引导。

  1. 准备保留页，fork 子进程。旧父进程暂时保留，它掌握原 VM 的状态和失败恢复所需的资源。
  2. 暂停旧端 vCPU，通过 savevm_state 保存 CPU 与设备状态。数据库线程在这个窗口中不继续执行，直通网卡的已有操作另行处理。
  3. 子进程 execv 新 QEMU，经 /dev/kvm1 使用新版 KVM，初始化 VM、vCPU 和相应设备模型。
  4. 新端通过 loadvm_state 加载保存的状态，建立保留 RAM 的映射。数据库内存中的内容继续存在，寄存器对应旧端停止时的执行位置。
  5. 完成设备与通知关联的交接后，新端取得执行权并恢复 vCPU；确认成功再让旧 QEMU 退出。此后数据库线程继续执行，其他尚未升级的虚机仍可留在旧 KVM 上。

论文把保存状态到恢复执行之间的间隔作为停顿窗口。省去 RAM 复制后，新端初始化、状态加载与恢复运行成为主要工作；它们仍需要时间。论文 §3.2、图 3

3. 接管前失败与单一执行权

新 QEMU 初始化或加载状态失败时，保留的旧父进程使回退成为可能：清理失败的新端，确认设备和通知的控制关系回到旧端，再恢复原虚机。保留旧进程的价值就在于，新端失败不必立刻演变成一次客户机重启。

成功恢复后，新端会继续修改同一份 RAM 和设备状态。此时旧端保存的寄存器现场已经过时，不能再直接恢复旧 vCPU。回退边界因此位于新端真正开始推进客户机状态之前；后续若要回到旧版本，需要一次新的受控交接。

五、直通网卡的 DMA 与中断交接

继续观察这台数据库虚机。暂停前，Guest 驱动已经给网卡提供了接收缓冲区 B；暂停期间，一帧报文 P 到达。网卡可以继续把 P 写进 B，客户机驱动则要等 vCPU 恢复后才能处理它。因此升级期间需要同时保住数据目标、设备控制关系和完成通知。

本例采用设备 DMA 地址与 Guest 物理地址一致的映射，IOMMU 把它转换到宿主物理页。新旧 QEMU 共用原来的 Guest RAM，物理页未移动，原有 IOMMU 映射就可以继续使用。保留数据页时还必须保留这些映射及其引用，避免设备仍在访问时把页面释放给别的用途。

Orthus 的 VFIO connector 在用户态集中管理 VFIO 描述符以及 eventfd、KVM irqfd 相关接口。旧 QEMU 把 connector 的控制权交给新 QEMU，底层 VFIO 连接保持打开，避免关闭再打开时重置设备或撤销 DMA 关系。设备内部正在进行的操作留在硬件上，PCI 配置和相关软件状态仍要按升级协议保存、恢复。

对报文 P，可以分开检查两件事：B 中的数据是否完整，以及驱动能否获知接收已经完成。eventfd 提供事件通知，不保存报文载荷；保住 B 并不能自动保证完成通知也连续。

论文通过保留的通知关联接续中断，但在大规模测试中仍发现遗漏中断，因而在设备交接后补充注入虚拟 IRQ，使客户机重新检查完成状态。这项补救体现了设备交接中较难的部分：DMA 可以持续，通知路径却跨越了新旧 VM 的切换。vCPU 恢复和 Guest 的中断接收条件允许后，驱动才实际处理完成；暂停较长时还要考虑设备队列容量与业务超时。论文 §3.3

六、实验效果与开销来源

1. 暂停时间与迁移总耗时

暂停时间衡量客户机停止推进的窗口；迁移总耗时还包含运行期间的准备和数据传送。Orthus 不迭代复制 RAM，论文中单台交接的总耗时与暂停窗口接近。跨机预拷贝则可能运行较长时间，最终才短暂停机。

2. 省下的复制时间与剩余的恢复开销

这些结果与设计相对应：原有内存直接交给新端，省去了复制大块 RAM 及反复追踪脏页的过程。对本文的 8 GiB 示例，内存内容也无需经过前面估算的那轮传输；它仍然要经历对象创建、状态恢复与映射关联。

论文图 6 把一次约 30 ms 的停顿进一步拆开：等待 Libvirt 的启动信号占 12 ms，恢复 16 个 vCPU 占 4 ms，其他时间用于 VGA、virtio-net、virtio-balloon 等设备。这说明，消除内存复制后，管理端协调和设备恢复同样值得优化。

GPU 实验也体现了这个边界：增加设备会增加 PCI 配置与 VFIO-pci 状态处理，空闲 GPU 的唤醒还可能拉长停顿。GPU 已提交的任务可以在 vCPU 暂停时继续工作，但新的客户机指令仍要等待恢复。CPU 停顿、设备工作和应用响应应分别观察。论文 §4.2–4.3、图 5–7

3. 从单台交接到整批升级

云平台更大的收益来自资源调度。跨机迁移通常要等待空闲宿主，并限制带宽和同时迁移的数量；同机交接保留原资源，多台宿主可以分别推进。分发新版 KVM/QEMU 仍有成本，但不再需要逐台通过网络复制 Guest RAM。

论文 §4.4 记录，使用传统迁移部署 halt polling 功能时，4.5 万台 VM 的升级历时 15 天，受到备用容量、夜间维护窗口和灰度安排限制。随后使用 Orthus 更新其余百万量级 VM，作者报告升级执行合计约 45 分钟，分三天灰度推进。两次记录的规模与运维条件不同，不能直接用日历时间相除得到算法加速比；它们反映的是批量更新对备用容量和迁移网络的依赖显著下降。部署记录

七、字节跳动：设备连续性与暂停窗口优化

省去 RAM 复制后，设备恢复和通知交接成为影响暂停时间的重要因素。字节跳动在 KVM Forum 2020、2022 的两次分享采用多 KVM 模块、共享 RAM 和新旧 QEMU 交接的结构，分别讨论直通设备中断与外部后端的处理。

1. 2020：让待处理中断跨过交接窗口

设报文 P 恰好在新旧端交接时完成 DMA。2020 年方案让两端共享 posted-interrupt descriptor（pi_desc），用其中的 PIR 位保留待处理向量。新端不重新初始化或复制 PIR，也不改写原有 Interrupt Remapping Table，让通知继续落到同一份记录上。这条路径依赖 VT-d Posted Interrupt；恢复后的 vCPU 才能继续处理客户机中断。

暂停窗口还可以缩短：新端提前创建 virtio eventfd，旧端在升级成功后清理，并通过共享内存并发保存与加载状态。分享报告的 vCPU 暂停范围为 11–38 ms，来自不同配置与负载，不能直接与 Orthus 的平均值比较。2020 年分享：中断交接与测量

2. 2022：保持 vhost-user 后端运行

若示例虚机使用 DPDK vhost-user 网络后端或 SPDK vhost-user 存储后端，替换 QEMU 时也要处理独立的后端进程。2022 年方案继承连接及共享文件描述符，让后端继续运行，跳过重复初始化；配置在暂停前预保存，发生变化再补传。KVM 升级仍通过多模块交接完成。2022 年分享：后端连接与配置

持续运行也带来约束：交接期间可能遗漏中断，分享采用恢复前补充 IRQ 的办法；后端保存的内存地址需要更新或保持有效；后端崩溃及部分异步消息会使本次升级失败。其 QEMU-only 模式直接继承 KVM 描述符，保留旧 KVM，需与替换 KVM 的模式分开。2022 年分享：一致性处理与模式边界

八、HyperFresh：通过嵌套虚拟化接管

1. 把可替换的 Hypervisor 放到 L1

Orthus 在同一个宿主内核内安排两份 KVM。HyperFresh 则预先增加 L0 hyperplexor 管理层：旧、新 Linux/KVM/QEMU 分别运行在 L1，数据库虚机运行在 L2。L0 在整个交接期间保留，负责让新 L1 接管原有客户机内存。这套结构需要事先部署，不能直接套到普通单层 KVM 宿主上。APSys 2017 论文

沿用前文的数据库虚机，交接可分为三步：先启动新 L1，并提前映射原 Guest 内存页；再暂停旧端的数据库虚机，转移 vCPU 和 I/O 状态；最后由新 L1 恢复虚机，旧端停止服务它。数据库缓存留在原页上，客户机操作系统不重新引导。这里替换的是 L1 Hypervisor，L0 的更新不在此次接管范围内。内存共映射与执行权转移

2. 从 2017 年原型到 2019 年实现

APSys 2017 报告约 100 ms 的切换时间；VEE 2019 的后续论文扩展了多虚机支持，并报告约 10 ms 的替换时间。后者还处理嵌套运行的额外开销，包括向 L1 直通设备、使用专用物理 CPU，以及减少不必要的轮询和退出。两篇是同一工作的演进，数字均来自各自实验。VEE 2019 论文

HyperFresh 把替换边界放在完整的 L1 环境上；代价则出现在日常运行中：L0 仍需维护，嵌套执行和设备路径需要优化。评价它时，应同时观察交接停顿与平时的运行成本，不能只比较最短暂停时间。嵌套层级的基础机制见 KVM 嵌套虚拟化。

九、方案对比与适用范围

几种实现都保留客户机运行状态，并让新实现接管执行。下表按替换边界和主要成本归纳；不同论文与分享的硬件、虚机配置及测量口径不同，暂停时间应回到各自实验中理解。

方案替换与保留主要收益与代价
Orthus / Dual KVM替换主要 KVM 实现和 QEMU，保留薄接口层、宿主内核与 Guest RAM同机接管减少内存搬运；需要改造模块边界，并维护状态和设备兼容性
字节跳动 VMM Live Upgrade同机多 KVM 模块交接，按设备路径保留通知记录或后端连接进一步压缩设备恢复工作；硬件能力、地址有效性和异步事件约束仍需处理
HyperFresh替换 L1 Hypervisor，保留 L0 hyperplexor 和 Guest 内存页可交接整个 L1 环境；增加嵌套层级，需要兼顾平时的运行开销

Orthus 保留薄 kvm.ko、宿主内核与设备基础设施。它的优势来自这些部分在交接时持续存在；修改保留层或维护物理硬件，需要另行选择升级路径。厂商实现中可替换的边界，也需要随内核演进持续维护。

新 QEMU 必须能读取旧 QEMU 保存的状态格式，CPU 与设备配置也要兼容。原有状态无法被新端正确解释时，保持同一份内存并不能解决问题。论文把不兼容的恢复失败纳入回退设计，再通过兼容代码支持相应版本；这项条件与迁移的状态兼容要求相通。Orthus 论文 §6

回到数据库虚机，一次成功升级应同时满足：进程与内存内容继续存在、vCPU 只在一端运行、设备访问正确缓冲区、完成通知能够接续。再结合外部请求的时延、超时和数据校验，才能评价升级对业务的影响。选型也应先确认可替换层与保留层，再检查状态兼容、设备支持和失败恢复。
