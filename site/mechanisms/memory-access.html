内存访问与异常处理

本演示由 OpenAI Codex (GPT-6-Astra) 辅助编写。

一、场景与边界

一条客户机访存指令可以直接由硬件完成，也可能停在客户机页表、EPT 或宿主后备页这几个不同位置。演示沿同一组 RAM 地址切换条件，观察由哪一层处理、修改哪份结构，以及原指令在何时完成。

RAM 示例沿用EPT 缺页处理中的地址：GVA 0x40203080 → GPA 0x00403080 → HPA 0x21000080，页大小为 4 KiB。内存槽从 GPA 0x00400000 开始、长度为 2 MiB，后备 HVA 基址为 0x7f0000000000。因此目标页是槽内第 3 页，对应后备页 HVA 0x7f0000003000。

硬件执行两级转换；HVA 则用于 KVM 向宿主内存管理查询后备页。映射建立后，正常访存不会逐次经过 QEMU 的 HVA 查询。MMIO 分别展示 QEMU 模拟寄存器、KVM 内核 LAPIC、ioeventfd 门铃写入与 VFIO BAR 的稳态直接映射。这四类设备访问所需的硬件退出和用户态交接各不相同。

先选择 RAM 或 MMIO，再观察具体条件下的处理过程。RAM 的场景分为正常访问、Guest 缺页与宿主处理：例如，转换缓存未命中后，硬件遍历中还可能遇到页表缺项；KVM 建立 EPT 时，也可能需要等待宿主后备页。一次访问可以经过多个环节，下面的示例分别固定其他前提，展示各处的状态变化。

源码采用 QEMU 10.2.0、Linux 6.18，处理器采用 Intel VMX / EPT。普通 RAM 场景均使用 HVA 后备内存，未加入嵌套虚拟化或私有内存。具体前提位于演示下方的“当前场景配置与源码版本”；步骤间隔不表示实际时延。

源码版本：QEMU 10.2.0、Linux 6.18。

当前场景配置与源码版本

    源码版本：QEMU 10.2.0、Linux 6.18。

    以下按场景列出处理顺序。启用 JavaScript 后可逐步观察结构与状态变化。

    RAM · 转换缓存命中

    有效地址转换已经缓存。处理器检查权限后访问宿主物理内存，KVM 与 QEMU 不参与本次读取。

    • Intel VMX + EPT，x86-64，4 KiB 页；不含嵌套虚拟化。
    • 读取 GVA 0x40203080 的 32 位值，目标内存值为 0x12345678。
    • 当前地址空间的组合转换缓存有效、权限允许；未发生并发失效。
    • 转换缓存命中与 CPU 数据缓存命中是两件事，本演示不模拟缓存层级与访问时延。
    1. 访问前 · Guest 用户态

      读取指令准备访问 GVA 0x40203080。既有页表和转换缓存均有效。 页表给出 GPA 0x00403080、HPA 0x21000080；初始图展示已存在的关系，尚未执行本次读取。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    2. 查询地址转换 · CPU 硬件

      处理器用当前地址空间与 GVA 查询转换缓存。 缓存标签包含地址空间相关信息，切换虚机或进程后不能直接套用其他上下文的映射。这里展示逻辑转换，不模拟处理器内部微操作次序。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    3. 取得已缓存的映射 · CPU 硬件

      有效转换直接给出目标 HPA，并通过本次读取的权限检查。 命中时无需重新遍历 Guest 页表与 EPT。GPA 表示两级转换中的逻辑中间地址，不要求硬件在每次命中时先输出 GPA 再做第二次软件查询。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    4. 读取后备内存 · CPU 硬件

      沿 HPA 0x21000080 读取 4 字节，得到 0x12345678。 数据可能由 CPU 缓存提供，也可能需要继续访问内存层级。转换命中本身并不保证数据已经在缓存中。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    5. 完成读取 · Guest 用户态

      结果写入 EAX，客户机继续执行下一条指令。 本次访问没有引发 EPT VM-Exit，也没有让 KVM_RUN 返回 QEMU。QEMU 先前的内存注册仍是这条硬件路径成立的前提。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    RAM · TLB 未命中

    转换缓存没有目标条目，但 Guest 页表和 EPT 都有效。硬件遍历页表后完成访问，不需要软件缺页处理。

    • Intel VMX + EPT，4 KiB 页；读取 GVA 0x40203080 的 32 位值。
    • Guest 各级页表和对应 EPT 均有效，目标数据页也有允许读取的 EPT 映射。
    • 本例只展开最终叶子关系，页表遍历缓存可以省略部分中间访问。
    1. 访问前 · Guest 用户态

      目标地址暂时没有转换缓存条目，页表映射已经准备好。 TLB 未命中描述缓存状态；是否发生异常，还取决于接下来遍历到的页表内容和权限。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    2. 转换缓存未命中 · CPU MMU

      处理器查询 GVA 0x40203080，启动硬件页表遍历。 在本例的 EPT 配置下，普通 TLB miss 本身不产生 VM-Exit，也不会调用 QEMU。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    3. 解析 Guest 页表 · CPU MMU

      硬件读取 Guest 页表，得到 GPA 页 0x00403000，加上偏移 0x080。 Guest 页表存放在 Guest 物理内存中，读取页表页本身也要经过 EPT。本图将重复的层级遍历收束为一条关系。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    4. 解析目标 EPT 叶子 · CPU MMU

      目标 GPA 有有效 EPT 映射，页内偏移保持为 0x080。 叶子给出 HPA 页 0x21000000，本次地址为 0x21000080。两级权限都允许访问，硬件无需请求软件修复。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    5. 完成数据读取 · CPU 硬件

      处理器读取目标内存，将 0x12345678 写入 EAX。 与缓存命中相比，这次增加了页表遍历成本；整个成功路径仍由硬件完成。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    Guest #PF · 按需分配

    客户机应用首次写入合法匿名映射，Guest PTE 尚不存在。客户机内核分配并映射页面，返回后重试写入。

    • Guest 运行 Linux 6.18；匿名私有 VMA 允许读写，目标 PTE 为 non-present。
    • Guest 用户态写入 0x12345678；未启用 userfaultfd，不发生内存不足。
    • 本例由 Guest 分配器选到 GPA 页 0x00403000；该页以及页表页已有可写 EPT 与驻留的宿主后备页。
    • Intel EPT 已启用，本例 Guest #PF 不被 VMX 拦截；不含特殊 MAXPHYADDR 或嵌套配置。
    1. 访问前 · Guest 用户态

      应用已有合法的匿名地址范围，目标页尚未分配。 创建 VMA 与建立每一个 PTE 可以发生在不同时间。这里从目标页的首次写入开始。

      Linux 6.18 · do_user_addr_fault 与 handle_mm_fault
    2. 产生 Guest #PF · CPU 硬件

      Guest PTE 的 P 位为 0，处理器转入客户机的缺页异常处理入口。 CR2 记录 GVA 0x40203080，错误码为 0x6：non-present、write、user。原应用写指令尚未完成。本例无需先退出到 KVM。

      Linux 6.18 · do_user_addr_fault 与 handle_mm_fault · Linux 6.18 · Guest #PF 拦截条件
    3. 检查地址范围 · Guest Linux 内核

      do_user_addr_fault() 找到对应 VMA，确认应用具有写权限，交给 handle_mm_fault()。 本例选择可修复的匿名缺页。若地址不属于合法 VMA 或权限不允许，Guest 可能给应用发送 SIGSEGV，不会继续本例的分配路径。

      Linux 6.18 · do_user_addr_fault 与 handle_mm_fault
    4. 分配并建立 Guest PTE · Guest Linux 内核

      客户机分配、清零 GPA 页 0x00403000，并建立应用虚拟页的可写映射。 这个 GPA 页对应的 EPT 和宿主页已就绪。Guest 内核管理自己的页分配与 PTE，无需调用 QEMU 设备模型。

      Linux 6.18 · do_user_addr_fault 与 handle_mm_fault · Linux 6.18 · KVM MMU 地址空间与两级转换
    5. 返回并重试原写入 · Guest 用户态

      异常返回恢复应用执行，处理器重新执行同一条写指令。 硬件现在能完成 Guest 页表与 EPT 转换，目标地址是 HPA 0x21000080。页故障处理期间 Guest 内核执行了其他指令，应用的这条写指令一直保持待完成。

      Linux 6.18 · do_user_addr_fault 与 handle_mm_fault · Linux 6.18 · KVM MMU 地址空间与两级转换
    EPT · 映射尚未建立

    Guest 页表有效，目标 RAM 页没有 EPT 叶子。KVM 由 memslot 找到已有宿主页，建立第二级映射后重试。

    • Intel VMX + EPT，Linux 6.18 TDP MMU，QEMU 10.2，4 KiB 页。
    • Guest 页表页的 EPT 映射已经存在，只有目标数据页 EPT 缺失。
    • RAM memslot 从 GPA 0x00400000 开始，长度 2 MiB，HVA 基址 0x7f0000000000。
    • 后备页已驻留，当前 PFN 为 0x21000；访问期间映射没有并发失效。
    1. 访问前 · Guest 用户态

      QEMU 已注册 RAM 范围，目标数据页的 EPT 叶子尚未建立。 注册 GPA 与 HVA 对应范围，并不要求 KVM 立即为整段 RAM 填完 EPT。

      QEMU 10.2 · kvm_set_user_memory_region · Linux 6.18 · kvm_tdp_mmu_page_fault
    2. EPT 转换引起退出 · CPU 硬件 → KVM

      Guest 页表给出 GPA 0x00403080，EPT 转换无法找到有效叶子，触发 EPT violation。 VMX 记录 GPA 和访问类型。这里发生硬件 VM-Exit，KVM_RUN 仍在宿主内核内执行；Guest 不接收 #PF。

      Linux 6.18 · handle_ept_violation
    3. 由 memslot 定位 HVA · KVM

      GFN 为 0x403，槽内页号为 3；KVM 据此算出后备页 HVA。 0x7f0000000000 + 3 × 0x1000 = 0x7f0000003000。HVA 只服务于软件查找宿主页，不加入 Guest 的硬件 GVA → GPA → HPA 转换链。

      Linux 6.18 · HVA、GUP 与后备 PFN · QEMU 10.2 · kvm_set_user_memory_region
    4. 取得当前后备页 · KVM → 宿主内存管理

      后备页已经驻留，宿主内存管理返回 PFN 0x21000。 KVM 获得页引用和可写状态，并检查相关映射失效条件。这并不意味着整台虚机的 RAM 被永久固定。

      Linux 6.18 · HVA、GUP 与后备 PFN
    5. 安装 EPT 叶子 · KVM TDP MMU

      KVM 建立 GPA 页 0x00403000 到 HPA 页 0x21000000 的映射，再进入客户机。 TDP MMU 在锁与失效检查保护下提交 SPTE。Guest PTE 保持原样，原读取指令没有被跳过。

      Linux 6.18 · kvm_tdp_mmu_page_fault
    6. 重试并完成读取 · CPU 硬件

      处理器重新执行读取，沿新 EPT 映射取得 0x12345678。 这次 RAM 缺项在 KVM 内修复完成，整个过程中没有调用 QEMU 的设备读回调。

      Linux 6.18 · kvm_tdp_mmu_page_fault · Linux 6.18 · KVM MMU 地址空间与两级转换
    宿主后备页 · 换入等待

    Guest PTE 有效，但 RAM 后备页已被宿主换出。KVM 取得 PFN 时进入宿主缺页慢路径，等待页面驻留后重新建立 EPT。

    • 普通 HVA 后备 RAM，4 KiB 页；匿名宿主页已换出，相关 EPT 已通过失效机制撤销。
    • Guest 页表页和内核所需页面均驻留，本例只跟踪目标 RAM 数据页。
    • Guest 未启用 KVM 异步缺页协议，本例使用允许等待 I/O 的同步取页路径。
    • 换入成功、无信号和硬件错误；换入后的示例 PFN 为 0x21000，原数据值为 0x12345678。
    1. 访问前 · Guest 用户态

      Guest 地址仍合法，宿主已经将目标后备页换出并撤销相关 EPT。 Guest 页表与宿主页的驻留状态由不同层管理。页面换出不要求 Guest 删除自己的 PTE。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    2. EPT 退出到 KVM · CPU 硬件 → KVM

      读取命中缺失的 EPT 映射，KVM 接手处理 GPA 0x00403080。 此时 Guest 没有收到 #PF。故障地址是第二级映射对应的 GPA，随后才会查找宿主 HVA。

      Linux 6.18 · handle_ept_violation · Linux 6.18 · kvm_tdp_mmu_page_fault
    3. 非等待取页无法完成 · KVM → 宿主内存管理

      KVM 用 HVA 取页，FOLL_NOWAIT 尝试发现页面需要 I/O。 返回 KVM_PFN_ERR_NEEDS_IO 后，KVM 检查能否走异步缺页。本例未启用相应 Guest 协议，继续同步慢路径。

      Linux 6.18 · 后备页需要 I/O 时的同步与异步路径 · Linux 6.18 · HVA、GUP 与后备 PFN
    4. 等待宿主换入 · 宿主内存管理

      KVM 去掉 FOLL_NOWAIT 后再次取页，宿主读取交换后备并等待页面可用。 同一 vCPU 线程仍处于 KVM_RUN 的宿主内核调用中，等待期间可以被调度出去；这种等待不等于返回 QEMU 用户态。其他 vCPU 的运行取决于其自身状态。

      Linux 6.18 · 后备页需要 I/O 时的同步与异步路径 · Linux 6.18 · HVA、GUP 与后备 PFN
    5. 后备页重新驻留 · 宿主内存管理 → KVM

      页面内容恢复，宿主返回当前 PFN 0x21000。 换入后的 PFN 可以不同于换出前的 PFN；本例显示本次返回值。KVM 仍需核对失效条件后才能发布 EPT。

      Linux 6.18 · 后备页需要 I/O 时的同步与异步路径 · Linux 6.18 · kvm_tdp_mmu_page_fault
    6. 恢复 EPT 并重试 · KVM → CPU 硬件

      KVM 建立新的 EPT 叶子，重新进入 Guest。原读取沿 HPA 0x21000080 完成。 成功后 EAX 得到 0x12345678。宿主缺页带来的主要额外成本是取页与等待，Guest 页表没有因此被改写。

      Linux 6.18 · kvm_tdp_mmu_page_fault · Linux 6.18 · KVM MMU 地址空间与两级转换
    MMIO · QEMU 设备读取

    地址落在 QEMU 模拟设备寄存器。KVM 返回 MMIO 退出，QEMU 填回读值，再次 KVM_RUN 后完成待决指令。

    • Guest 内核读取 32 位 MMIO 寄存器；GVA 0xffffc90070001000 映射到 GPA 0xf0001000。
    • 对应设备由 QEMU 模拟，内核设备不能处理该访问；该区域不作为普通 RAM memslot 映射。
    • 一次 4 B 读取，不跨页、不拆分；设备回调返回 0x12345678。
    • 未涉及直通设备 BAR、内核 LAPIC 或 ioeventfd 门铃写入。
    1. 访问前 · Guest 驱动

      Guest 已映射设备寄存器，准备执行 4 B 读取。 Guest 页表中的地址有效，GPA 落在模拟设备区域。这里没有可供普通 RAM 读取使用的宿主页。

      Linux 6.18 · MMIO 数据与重新进入 KVM_RUN · QEMU 10.2 · KVM_EXIT_MMIO 与 address_space_rw
    2. 退出并识别设备访问 · CPU 硬件 → KVM

      访存引起 EPT 退出，KVM 进入指令模拟路径。 KVM 无法用普通 RAM 映射或内核设备满足该读取，保留尚未完成的指令状态，准备请求用户态设备处理。

      Linux 6.18 · handle_ept_violation · kvm_mmu_page_fault() · emulator_read_write_onepage()
    3. 返回 QEMU · KVM → QEMU

      KVM_RUN 返回 KVM_EXIT_MMIO，并在共享结构中填写地址、长度与方向。 phys_addr=0xf0001000，len=4，is_write=0。KVM_RUN 在这里从宿主内核返回 QEMU 用户态。

      Linux 6.18：填写 KVM_EXIT_MMIO 请求 · QEMU 10.2 · KVM_EXIT_MMIO 与 address_space_rw · Linux 6.18 · MMIO 数据与重新进入 KVM_RUN
    4. 执行设备读回调 · QEMU 设备模型

      QEMU 调用 address_space_rw()，在 MemoryRegion 地址空间中定位设备。 设备模型按寄存器语义返回 0x12345678。真实设备可能有读清除等副作用，本示例使用固定值寄存器。

      QEMU 10.2：按读写方向选择地址空间访问 · QEMU 10.2：翻译地址并进入 MemoryRegion 读路径 · QEMU 10.2：检查访问并分派设备读回调
    5. 填回 MMIO 读值 · QEMU

      共享区 data[0..3] 填入小端字节 78 56 34 12。 Guest EAX 此时仍未更新，待决读指令也尚未完成。设备回调结束与客户机指令完成处在两个不同阶段。

      QEMU 10.2 · KVM_EXIT_MMIO 与 address_space_rw · Linux 6.18 · MMIO 数据与重新进入 KVM_RUN
    6. 重新进入并完成待决读 · QEMU → KVM → Guest

      QEMU 再次调用 KVM_RUN，KVM 消费返回字节，完成指令模拟后恢复 Guest。 EAX 现在成为 0x12345678，执行位置前进。演示合并了内核完成待决操作与后续 VM-entry；KVM 会先完成待决操作，再处理可能阻止 Guest 继续运行的信号等事件。

      kvm_arch_vcpu_ioctl_run() · Linux 6.18：复制返回读值并完成 MMIO · Linux 6.18：恢复原指令模拟
    脏页记录 · EPT 写保护

    Guest PTE 允许写入，KVM 为记录脏页撤掉 EPT 写权限。首次写入触发退出，KVM 记录脏页并恢复写权限后重试。

    • 普通 RAM，4 KiB EPT 叶子，Guest 用户态写入 0x12345678。
    • memslot 启用 KVM_MEM_LOG_DIRTY_PAGES，使用位图；未启用 Dirty Ring 或硬件 PML。
    • 本轮已对目标 EPT 叶子写保护并完成所需失效，Guest PTE、宿主页及 KVM 软件记录都允许最终恢复写权限。
    • 固定为成功的 fast_page_fault 修复路径，无并发 SPTE 改动、页跟踪或其他写保护原因。
    1. 访问前 · Guest 用户态

      客户机允许写入该页，EPT 暂时禁止写入，以捕获本轮第一次写访问。 槽从 GFN 0x400 起始，因此 GFN 0x403 对应脏位图中的槽内页号 3。

      Linux 6.18 · 写保护快速修复与脏页记录 · Linux 6.18 · mark_page_dirty_in_slot
    2. 写权限检查触发退出 · CPU 硬件 → KVM

      Guest PTE 的写权限通过，但 EPT W=0，写入在修改数据前触发 EPT violation。 这次写保护由 KVM 为脏页记录设置；不会因此向 Guest 抛出权限 #PF。目标内存仍是 0x00000000。

      Linux 6.18 · handle_ept_violation · Linux 6.18 · 写保护快速修复与脏页记录
    3. 恢复 EPT 写权限 · KVM fast_page_fault

      KVM 确认映射允许恢复写权限，原子更新 SPTE。 本例沿 fast_pf_fix_direct_spte() 的顺序展示：先成功更新 SPTE，随后记录脏页，再返回 Guest。这里只展示一个 vCPU 的成功路径，不将图中分步视为可供其他线程观察的同步屏障。

      Linux 6.18 · 写保护快速修复与脏页记录
    4. 记录脏页 · KVM

      mark_page_dirty_in_slot() 将槽内页号 3 标记为脏。 该记录按页表示需要重新同步的数据范围。它可以保守地早于实际写入完成；这里仍未执行 Guest 的原写指令。

      Linux 6.18 · 写保护快速修复与脏页记录 · Linux 6.18 · mark_page_dirty_in_slot
    5. 重试写入 · CPU 硬件 / Guest

      重新进入 Guest 后，同一条写指令通过两级权限检查，将 0x12345678 写入 RAM。 此次处理不返回 QEMU。本轮内该页后续写入通常无需再次因这项写保护退出；开始新一轮记录时还需按脏页 API 的规则重新建立跟踪条件。

      Linux 6.18 · 写保护快速修复与脏页记录 · Linux 6.18 · mark_page_dirty_in_slot
    KVM 内核 LAPIC 读取

    Guest 读取 xAPIC ID 寄存器，访问退出到 KVM 后由内核 LAPIC 返回结果，不交给 QEMU。

    • x86-64 / Intel VMX，Linux 6.18 与 QEMU 10.2.0；仅跟踪所选设备访问
    • 硬件 VM-exit 与 KVM_RUN 返回用户态是两个不同边界；没有其他异步退出
    • 内核 LAPIC、xAPIC MMIO 模式；关闭 APIC-access / APIC-register virtualization 等相关硬件加速
    • Guest LAPIC 基址 0xfee00000，ID 寄存器偏移 0x20；示例 APIC ID = 1，32 位读取值为 0x01000000
    1. 读取前 · Guest 内核

      驱动即将读取 LAPIC ID。 QEMU 只在准备阶段配置虚拟机；本次寄存器读由内核设备处理。

      apic_mmio_read()
    2. 设备访问退出到 KVM · 处理器 → KVM

      所选配置下，该 MMIO 访问使处理器退出 Guest。 这是硬件 VM-exit，不是 KVM_RUN 返回 QEMU。

      Linux 6.18 · handle_ept_violation · vcpu_mmio_read()
    3. 优先检查内核 LAPIC · KVM · vcpu_mmio_read

      KVM 先把地址交给内核 LAPIC，apic_mmio_read 命中此地址。 内核处理成功就不再为这部分访问创建 KVM_EXIT_MMIO。

      vcpu_mmio_read() · apic_mmio_read()
    4. 读取虚拟 APIC ID · KVM · apic_mmio_read

      内核 LAPIC 返回 0x01000000。 返回值先交给指令模拟器，Guest 原目标寄存器随后才更新。

      apic_mmio_read() · emulator_read_write_onepage()
    5. 完成读指令并继续 Guest · KVM → Guest

      模拟器写回目标寄存器并推进原指令，随后恢复客户机。 整个访问没有把 KVM_RUN 交回 QEMU 用户态；不需要一次额外用户态读回调。

      emulator_read_write_onepage() · vcpu_mmio_read()
    ioeventfd 队列门铃写入

    Guest 发布队列后写门铃，KVM 匹配 ioeventfd 并发出通知；vCPU 不经通用用户态 MMIO 返回。

    • x86-64 / Intel VMX，Linux 6.18 与 QEMU 10.2.0；仅跟踪所选设备访问
    • 硬件 VM-exit 与 KVM_RUN 返回用户态是两个不同边界；没有其他异步退出
    • 已注册地址、宽度与 datamatch 匹配的 ioeventfd，固定为 2 字节队列 0 门铃写
    • 队列描述符与 available 索引已按协议发布，本场景只跟踪通知写；后端采用 QEMU IOThread
    • 只优化匹配的写通知；寄存器读取、未匹配访问和具体后端数据处理不适用该捷径
    1. 门铃写入前 · Guest 驱动

      共享队列已经发布，驱动准备写队列号 0。 发布数据和门铃通知是两个动作；先发布，再判断是否需要 kick。

      ioeventfd_write()
    2. 捕获门铃写入 · 处理器 → KVM

      本次设备写入退出到 KVM 的 MMIO 总线。 本场景没有硬件直通门铃；省掉的是通用用户态 MMIO 往返，不是硬件 VM-exit。

      vcpu_mmio_write() · ioeventfd_write()
    3. 匹配注册的 ioeventfd · KVM · ioeventfd_write

      地址、宽度和 datamatch 均匹配，KVM 接管这次写。 不匹配时返回 EOPNOTSUPP，仍可继续尝试其他 MMIO 处理者；本例不走该分支。

      ioeventfd_write()
    4. 发出后端事件通知 · KVM · eventfd_signal

      KVM 对已绑定的 eventfd 发出信号，后端获得处理机会。 通知不表示后端已取链或完成 I/O；IOThread 与 vCPU 是异步上下文。

      ioeventfd_write()
    5. vCPU 继续执行 · KVM → Guest

      内核把门铃写标记为已处理并恢复客户机。 KVM_RUN 没有返回 QEMU vCPU 用户态；QEMU IOThread 仍可能稍后处理队列，两者不能混为一谈。

      vcpu_mmio_write() · emulator_read_write_onepage()
    VFIO BAR 已建立直接映射

    访问已映射且允许直访的 VFIO BAR 区间，CPU 经 Guest 页表与 EPT 访问设备，无需逐次陷入 QEMU。

    • x86-64 / Intel VMX，Linux 6.18 与 QEMU 10.2.0；仅跟踪所选设备访问
    • 硬件 VM-exit 与 KVM_RUN 返回用户态是两个不同边界；没有其他异步退出
    • 固定可 mmap 的 BAR 区间，宿主 VFIO 映射、KVM memslot 与有效 EPT 映射均已建立
    • 不包括 MSI-X 表、需模拟寄存器、首次建图故障、权限变更、设备复位和映射撤销
    • 本例观察 CPU 对设备 BAR 的读取，不是设备 DMA；IOMMU 的设备地址转换不串入这条 CPU 路径
    • 示意地址和读值仅用于观察；实际可映射范围、内存类型和访问语义以具体设备为准
    1. 稳态映射已经就绪 · Guest 驱动

      准备读取已允许直接映射的设备区间。 vfio_region_mmap 与 memslot 配置发生在准备阶段；每次访问不会重新执行这些设置函数。

      vfio_region_mmap() · QEMU 10.2 · kvm_set_user_memory_region
    2. 硬件解析 CPU 地址 · 处理器

      CPU 使用 Guest 页表和有效 EPT 找到设备 BAR 目标。 此处无软件页表遍历，也不经过设备 DMA 的 IOMMU 翻译；配置假设保证本次映射与权限有效。

      Linux 6.18 · KVM MMU 地址空间与两级转换 · vfio_region_mmap()
    3. 访问物理设备区间 · 物理处理器 / PCIe

      CPU 把读取送往映射对应的设备区域。 QEMU vCPU 线程仍处于 KVM_RUN；本次没有调用 vfio_region_read。

      vfio_region_mmap()
    4. 设备返回读值 · 物理设备 → CPU

      设备提供示意值 0x12345678。 这是设备读完成，不代表 GPU 或其他设备上此前提交的异步任务全部完成。

      vfio_region_mmap()
    5. 完成 Guest 读取 · Guest 驱动

      CPU 更新目标寄存器，执行下一条指令。 这条稳态直接映射路径不因本次访问退出；其他寄存器区间与异常条件可能仍需要 KVM/QEMU 处理。

      vfio_region_mmap() · Linux 6.18 · KVM MMU 地址空间与两级转换

    三、异常处理的分工

    判断一次访存的处理路径，可以先看阻塞位置，再看需要修改的结构。Guest 的页表缺项、KVM 的 EPT 缺项和宿主页未驻留，对应不同的处理者。

    场景处理者与结构变化原指令如何继续
    转换缓存命中CPU 使用有效的地址转换和权限硬件读取 RAM；无访存引起的 VM-Exit
    TLB 未命中、页表有效CPU 遍历 Guest 页表与 EPT得到有效转换后完成读取；无需软件缺页处理
    Guest #PFGuest Linux 检查 VMA，分配页面并填写 Guest PTE异常返回后重试；本例不退出到 KVM
    EPT 映射缺失KVM 查 memslot、取得 PFN、建立 EPT 叶子VM-entry 后重试；无需返回 QEMU
    宿主后备页未驻留宿主内存管理提供页面，KVM 再建立 EPT本例 vCPU 线程等待换入，再进入 Guest 重试
    QEMU 模拟设备 MMIOKVM 返回退出信息，QEMU 设备回调填入读值再次 KVM_RUN，完成待决模拟后恢复 Guest
    KVM 内核 LAPIC MMIO限定关闭相关硬件加速，退出后由内核设备返回读值内核完成原指令，不需要 KVM_RUN 返回 QEMU
    匹配 ioeventfd 的门铃写KVM 匹配地址、宽度及数据后触发 eventfdvCPU 继续执行；已通知的后端仍可能在用户态异步处理
    VFIO 可 mmap 的 BAR 区间已有有效映射与权限，CPU 直接访问设备区间稳态访问不因该指令退出，不经过逐次 QEMU 设备回调
    脏页记录写保护KVM 恢复 EPT 写权限并标记脏页VM-entry 后重试写入；Guest PTE 保持不变

    普通 TLB miss 只说明转换缓存没有可用条目。Guest 页表和 EPT 都有效时，硬件能够自行完成遍历。CPU 数据缓存则保存数据或指令，其命中情况与转换缓存要分别观察。

    Guest #PF 示例选用合法匿名映射的首次写入，由客户机内核处理；非法地址与权限错误可能终止应用。宿主缺页示例选用未启用 KVM 异步缺页协议的同步换入，由宿主内存管理提供后备页；在其他配置中，KVM 可以把等待转成异步处理。

    只有交给用户态的 MMIO 读才需要这次往返：kvm_run.mmio.data 已填好时，Guest 寄存器仍可能保留旧值，用户态需重新进入 KVM_RUN，由内核先完成待决操作。KVM 在此之前会尝试内核 LAPIC 与 MMIO 总线；命中的 ioeventfd 写通知也可在内核完成。相关执行循环见KVM vCPU 运行与退出。

    VFIO 直接访问只适用于允许映射的 BAR 区间，且本例从映射已建立的稳态开始。MSI-X 表、需模拟区域、首次映射缺失与权限变化不属于这条无退出路径。这里的 CPU 地址链是 Guest 页表与 EPT；设备自身发起 DMA 时使用的 IOMMU 地址链是另一个方向，不能串成一次 CPU 读取的必经环节。

    四、映射管理与取舍

    影子页表把 Guest 虚拟地址到宿主物理地址的关系合并到一套硬件可用的映射中，KVM 需要跟踪 Guest 页表的修改。EPT 将第二级转换交给硬件，使 Guest 更直接地管理自己的页表；新增的转换层级也带来页表遍历和缓存压力。TLB、页表遍历缓存与大页共同降低重复转换成本，代价涉及缓存失效、页粒度与内存布局。

    按需建立 EPT 可以避免启动时为未访问页面做全部工作，首次访问则需要承担建图开销。宿主继续管理后备页，使换出、迁移和内存回收能够生效；这些变化要求 KVM 撤销旧映射，防止 Guest 沿失效 HPA 继续访问。映射生命周期见EPT 缺页与宿主后备页，QEMU 的 RAM 注册过程见MemoryRegion 与地址空间。

    迁移期间还需要知道哪些页面被修改。演示选择软件写保护与位图这一条路径，优点是按页发现首次写入，代价是额外退出、记录与下一轮跟踪。硬件 PML 和 Dirty Ring 分别改变脏页发现或交付方式，不能直接套用本例的每一步行为。
