CPU 指令执行过程

本演示由 OpenAI Codex (GPT-6-Astra) 辅助编写。

一、场景与边界二、逐步演示三、执行路径的差异四、退出处理与优化五、源码与相关内容

一、场景与边界

使用 KVM 时，QEMU 的 vCPU 线程通过 KVM_RUN 进入宿主内核，再由 VM Entry 开始执行客户机指令。普通加法、客户机内核中的大量代码都可以由物理处理器直接完成。CPUID、模拟设备访问和空闲等待则需要不同的处理路径。

基础场景从同一个位置开始：vCPU 已经运行，QEMU 的 KVM_RUN 尚未返回，物理处理器正在执行 Guest 指令。演示固定显示当前指令、RIP、寄存器、Guest CPL 与 VMX 模式；只有跨越执行上下文时才转移时间线位置。

硬件路径采用 x86-64、Intel VMX 与 EPT，源码对应 QEMU 10.2.0 和 Linux 6.18。普通指令、系统调用、内核处理退出与用户态设备交接先共用执行时间线；HLT 和定时休眠放在“等待与唤醒”组，进一步观察 Guest 任务和宿主线程两层调度。各场景分别列出使用的拦截、设备和中断配置。

先看“普通 ADD”，再切换到“CPUID 内核处理”和“MMIO 返回 QEMU”：三者依次展示直接执行、内核处理和用户态设备交接。“Guest SYSCALL”区分客户机权限切换与虚拟化退出；“HLT 空闲等待”展示 vCPU 阻塞。两个定时休眠场景再用同一次 nanosleep 对比：客户机继续执行其他任务，或者进入空闲、等待定时器唤醒。

源码版本：QEMU 10.2.0、Linux 6.18。

    普通 ADD

    从已经运行的 Guest 指令 ADD EAX, 1 开始，观察 EAX、标志位与 RIP；本次不发生 VM-exit 或返回 QEMU。

    • x86-64，Intel VMX + EPT，Linux 6.18 / QEMU 10.2.0
    • 指令页映射有效；不加入调试单步、宿主抢占及无关异步事件
    • 83 c0 01 编码为 3 字节；示例初值 EAX = 41
    • 共同起点：QEMU vCPU 线程已经处于 KVM_RUN，处理器正在执行 Guest；初始化只列在源码配置路径中
    • Guest 指令直接在物理处理器的 non-root 上下文执行；Guest 表示客户机执行环境，CPU 是执行指令的硬件
    1. 当前指令准备执行 · Guest 用户态 · CPU non-root

      EAX = 41，RIP 指向 ADD EAX, 1。 KVM_RUN 已在调用中；QEMU 与 KVM 运行循环此刻不逐条解释普通 Guest 指令。

      Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境
    2. 识别当前 ADD 指令 · 物理处理器 · Guest 上下文

      处理器执行位于 RIP=0x400000 的寄存器加法。 此处展示指令语义，不模拟具体处理器的取指、解码或流水线周期。

      Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境
    3. 观察运算输入 · 物理处理器 · Guest 上下文

      本次加法的输入为 EAX=41 和立即数 1。 输入观察与下一步结果是一次架构指令的展示拆分，不意味着中间插入另一条 Guest 指令。

      Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境
    4. 提交寄存器运算结果 · 物理处理器 · Guest 上下文

      EAX 从 41 变为 42，相关算术标志位按结果更新，RIP 前进。 不需要把请求交给另一个 Guest 部件；这就是 CPU 直接执行 Guest 代码。

      Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境
    5. 继续下一条 Guest 指令 · Guest 用户态 · CPU non-root

      RIP=0x400003，客户机继续执行。 本次无硬件 VM-exit；KVM_RUN 保持调用中，也没有 QEMU 设备回调。

      Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境
    Guest SYSCALL

    客户机应用通过 syscall 进入自己的内核，再由正常快速返回路径回到应用。

    • x86-64 Linux 客户机，SYSCALL 已启用，LSTAR 等 MSR 已配置
    • 直接执行 x86-64 getpid 系统调用（RAX=39），不发生设备访问和缺页；无信号或调试干预，满足 SYSRETQ 快速返回条件
    • 省略信号、调试、抢占与安全缓解细节，聚焦 Guest 权限切换
    • 共同起点：QEMU vCPU 线程已经处于 KVM_RUN，处理器正在执行 Guest；初始化只列在源码配置路径中
    • Guest 指令直接在物理处理器的 non-root 上下文执行；Guest 表示客户机执行环境，CPU 是执行指令的硬件
    1. 系统调用前 · 客户机应用

      应用把系统调用号 39 放入 RAX，即将执行两字节的 syscall。 IA32_LSTAR 指向客户机内核入口，KVM 已维护好对应的客户机执行环境。

      Linux 6.18：x86-64 getpid 系统调用号 · Linux 6.18：Guest 系统调用汇编入口 · Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境
    2. 保存返回位置 · 物理处理器

      SYSCALL 把返回 RIP 保存到 RCX，把原 RFLAGS 保存到 R11。 SYSCALL 在一次架构转换中保存下一条 RIP，清除 RF 后保存 RFLAGS，并切换入口。这些变化由同一条指令完成，RSP 保持原值。本例调用前 RF=0。

      Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境 · Linux 6.18：Guest 系统调用汇编入口
    3. 进入客户机内核 · 物理处理器 → Guest 内核

      RIP 切到客户机 LSTAR 指定入口，CPL 变为 0。 entry_SYSCALL_64 执行 swapgs、保存用户 RSP、切到内核栈并构造 pt_regs，再 call do_syscall_64。SYSCALL 硬件不自动选择内核栈；处理器仍为 VMX non-root。

      Linux 6.18：Guest 系统调用汇编入口 · Linux 6.18：系统调用分派与 SYSRET 条件检查
    4. 准备返回值 · 客户机内核

      客户机内核查询当前进程信息，在返回路径把结果放入 RAX。 do_syscall_x64 经 x64_sys_call 的 switch 分派到 __x64_sys_getpid；SYSCALL_DEFINE0(getpid) 的函数体返回 task_tgid_vnr(current)。结果存入 pt_regs->ax，返回汇编再恢复到 RAX。本例结果 1234；没有向宿主发起 getpid。

      Linux 6.18：系统调用分派与 SYSRET 条件检查 · Linux 6.18：检查调用号并保存 regs->ax · Linux 6.18：按调用号执行 switch 分派 · Linux 6.18：SYSCALL_DEFINE0(getpid) 生成的系统调用实现 · Linux 6.18：零参数系统调用包装器生成规则
    5. 返回客户机应用 · 客户机内核 → 应用

      正常快速路径执行 SYSRETQ，恢复应用 RIP、标志与 CPL 3。 do_syscall_64 检查 RCX/RIP、R11/RFLAGS、用户段与地址等快速返回条件；通过后走 syscall_return_via_sysret，恢复用户栈并执行 SYSRETQ。不满足条件时走 IRET 返回，本例不包含该分支；无需 VM-exit 或 KVM_RUN 返回。

      Linux 6.18：系统调用分派与 SYSRET 条件检查 · Linux 6.18：恢复 Guest 用户态寄存器与 SYSRETQ · Intel SDM：ADD、SYSCALL、SYSRET 与 VMX 执行环境
    CPUID 内核处理

    CPUID 触发 VM Exit，KVM 按虚拟 CPU 配置给出结果，再直接进入客户机。

    • Intel VMX，关闭 CPUID faulting 与调试单步
    • 示例执行 CPUID leaf 0，虚拟 CPU 厂商配置为 GenuineIntel
    • 返回值由客户机可见 CPU 配置决定，不直接照抄宿主能力
    • 共同起点：QEMU vCPU 线程已经处于 KVM_RUN，处理器正在执行 Guest；初始化只列在源码配置路径中
    • Guest 指令直接在物理处理器的 non-root 上下文执行；Guest 表示客户机执行环境，CPU 是执行指令的硬件
    1. CPUID 执行前 · 客户机程序

      RIP 指向 CPUID，EAX 与 ECX 指定查询项。 QEMU 已在启动时配置客户机 CPUID；当前运行阶段由 KVM 使用这套配置。

      Linux 6.18：kvm_emulate_cpuid
    2. 硬件退出到 KVM · 物理处理器 → KVM

      CPUID 触发 VM Exit，VMCS 记录 CPUID 退出原因。 处理器从 non-root 返回 root，执行宿主内核 VMX 退出处理；KVM_RUN 此时仍未返回 QEMU。

      Linux 6.18：VMX 退出处理与处理函数分派 · Linux 6.18：VMX 退出分派
    3. 写回虚拟 CPU 信息 · KVM · kvm_emulate_cpuid

      KVM 读取查询项，按配置计算结果，写回四个通用寄存器。 leaf 0 的厂商串由 EBX、EDX、ECX 依次组成；示例采用 GenuineIntel，EAX 为配置的最大基础 leaf。

      Linux 6.18：kvm_emulate_cpuid
    4. 推进指令位置 · KVM

      KVM 跳过已模拟的两字节 CPUID，RIP 变为 0x400202。 退出处理返回“已完成、允许继续”，内核运行循环无需把此事件交给用户态。

      Linux 6.18：kvm_emulate_cpuid · Linux 6.18：VMX 退出分派 · Linux 6.18：vcpu_run 的执行与等待分支
    5. 重新进入客户机 · KVM → 客户机

      VM Entry 后，客户机从 CPUID 的下一条指令继续。 本例有一次硬件退出，KVM_RUN 用户态返回次数仍为零；VMCS 留存的退出原因描述刚才的事件。

      Linux 6.18：vcpu_run 的执行与等待分支 · Linux 6.18：kvm_emulate_cpuid
    MMIO 返回 QEMU

    读取 QEMU 模拟的 32 位设备寄存器，观察 MMIO 请求、读结果与下一次 KVM_RUN 的继续执行。

    • Intel EPT，客户机页表有效，GPA 0xf0001000 对应 QEMU 模拟 MMIO 区域
    • 读取无法由内核设备处理；单片段长度 4 字节，无 ioeventfd 读处理
    • 示例指令为 mov eax, [rbx]，RBX 已映射到目标地址；设备返回 0x12345678
    • 共同起点：QEMU vCPU 线程已经处于 KVM_RUN，处理器正在执行 Guest；初始化只列在源码配置路径中
    • Guest 指令直接在物理处理器的 non-root 上下文执行；Guest 表示客户机执行环境，CPU 是执行指令的硬件
    1. 设备读取前 · 客户机程序

      客户机准备读取设备寄存器，EAX 还保留旧值。 这里固定一条需要用户态处理的 MMIO 读；普通 RAM 与 KVM 内核设备访问另有路径。

      QEMU 10.2：KVM_RUN 调用与 MMIO 分派 · Linux 6.18：用户态 I/O 必须重新进入 KVM_RUN 完成
    2. 转入内核设备访问处理 · 物理处理器 → KVM

      EPT 访问触发退出，KVM 分析并模拟这条设备读取。 本例无可用的设备 RAM 映射；KVM 不能在内核中完成读结果，因此建立待完成 I/O。首次访问可以是 EPT violation；已有 MMIO 标记时还可能经 EPT misconfiguration 识别。

      Linux 6.18：EPT violation 与 MMIO 缓存退出入口 · Linux 6.18：MMU 退出转入指令模拟 · Linux 6.18：用户态 I/O 必须重新进入 KVM_RUN 完成
    3. 返回 MMIO 请求 · KVM → QEMU

      第一次 KVM_RUN 返回，QEMU 读取共享区中的地址、方向与长度。 本次请求还没完成客户机读指令；EAX 和后续执行仍需等待设备数据。

      Linux 6.18：填写 KVM_EXIT_MMIO 请求 · Linux 6.18：用户态 I/O 必须重新进入 KVM_RUN 完成
    4. 读取设备模型 · QEMU → MemoryRegion

      address_space_rw 根据 GPA 找到设备区，读取回调返回 0x12345678。 x86 小端格式下，共享 data 中的 4 字节依次是 78 56 34 12。此刻 KVM 尚未消费读结果。

      QEMU 10.2：KVM_RUN 调用与 MMIO 分派 · QEMU 10.2：按读写方向选择地址空间访问 · QEMU 10.2：翻译地址并进入 MemoryRegion 读路径 · QEMU 10.2：检查访问并分派设备读回调
    5. 再入并完成读指令 · QEMU → KVM

      第二次 KVM_RUN 先调用 complete_userspace_io，消费共享区结果。 内核把结果写入客户机 EAX，并完成这条两字节 mov eax, [rbx]；完成之前不能把客户机状态当成已执行完本次读取。

      Linux 6.18：complete_userspace_io 再入处理 · Linux 6.18：复制返回读值并完成 MMIO · Linux 6.18：恢复原指令模拟
    6. 继续客户机执行 · KVM → 客户机

      处理器进入客户机，下一条指令可以使用 EAX 的新值。 exit_reason 是上次正常用户态返回的记录，不能把其残留值当成新的待处理请求。这里的第二次 KVM_RUN 仍在执行。

      Linux 6.18：complete_userspace_io 再入处理 · QEMU 10.2：KVM_RUN 调用与 MMIO 分派
    HLT 等待与唤醒

    客户机空闲时执行 HLT，KVM 让宿主 vCPU 线程睡眠；可接受的中断到达后再唤醒并继续。

    • Intel VMX 拦截 HLT；KVM 管理 LAPIC，APICv 关闭
    • halt-poll 预算为 0，展示阻塞等待；Guest IF = 1，向量 0x51 优先级允许
    • 没有待处理中断，随后后端完成事件通过软件 LAPIC 路径到达
    1. 执行 HLT 前 · 客户机空闲线程

      客户机暂时没有可运行任务，准备执行 HLT。 整台虚拟机仍在运行；此处只跟踪一个 vCPU 的空闲等待。

      Linux 6.18：HLT 模拟与 mp_state
    2. 记录客户机等待状态 · KVM · kvm_emulate_halt

      HLT 退出后，KVM 跳过该指令，把无可用事件的 vCPU 记为 HALTED。 内核 LAPIC 模式下，HLT 的常规等待留在内核；本例没有 KVM_EXIT_HLT 用户态返回。

      Linux 6.18：HLT 模拟与 mp_state · Linux 6.18：vcpu_run 的执行与等待分支
    3. 发布等待者并复查 · KVM · kvm_vcpu_block

      KVM 发布 rcuwait 等待者，设置 TASK_INTERRUPTIBLE，再检查事件。 先发布等待者再复查，避免事件在检查与休眠之间到达造成丢失唤醒。此时还未调用 schedule。

      Linux 6.18：rcuwait 发布、条件复查与 schedule
    4. 宿主线程休眠 · Linux 调度器

      没有可运行事件，schedule 让出物理 CPU。 这里发生宿主任务调度切换；它晚于 HLT 的 VM Exit，并未结束 KVM_RUN。

      Linux 6.18：rcuwait 发布、条件复查与 schedule
    5. 发布中断并唤醒 · 事件源 → LAPIC → 调度器

      完成事件设置 IRR[0x51]，KVM kick 找到等待线程并唤醒。 TASK_RUNNING 表示可以被调度；宿主繁忙时，线程还需要等待物理 CPU。

      Linux 6.18：LAPIC IRR 与事件请求 · Linux 6.18：vCPU wake 与 kick
    6. 线程重新获得 CPU · Linux 调度器 → KVM

      vCPU 线程继续内核等待循环，复查后撤销等待者。 本例的中断可被客户机接受，因此 x86 运行路径把 mp_state 恢复为 RUNNABLE。其他信号或维护请求未必使客户机立即可运行。

      Linux 6.18：rcuwait 发布、条件复查与 schedule · Linux 6.18：等待结束后的事件与可运行状态复查
    7. 恢复客户机并处理事件 · KVM → 客户机

      满足注入条件后，KVM 进入客户机的中断处理入口。 HLT 之后的执行随后由客户机中断返回继续。完整 IRR、ISR、EOI 变化见中断传递；这里的 KVM_RUN 仍未返回。

      Linux 6.18：等待结束后的事件与可运行状态复查 · Linux 6.18：LAPIC 中断接受时清 IRR 并设置 ISR
    定时休眠 · 继续执行其他任务

    任务 A 休眠 1 ms 后，客户机调度任务 B。对照宿主抢占、定时到期和任务 A 恢复执行，区分客户机任务等待与 vCPU 停止运行。

    • 单 vCPU 的 x86-64 Linux 6.18 客户机，QEMU 10.2.0 / KVM，普通非 PREEMPT_RT 内核；A 和 B 固定在该 vCPU。
    • A 调用 nanosleep({0, 1000000}, NULL)，无信号打断。D 表示 Guest 根据当前时间、1 ms 请求和 timer slack 最终排定的本次 clockevent 时刻；不假定精确在 1 ms 后返回。
    • Guest 高分辨率定时器与 TSC-deadline clockevent 已启用，本次事件成为下一到期事件。KVM 使用宿主软件 hrtimer，不启用 VMX 硬件定时辅助、APICv 或 posted timer；定时器提前量取 0。
    • LVT 定时器未屏蔽；需要递送时 Guest IF、interrupt shadow 和 APIC 优先级允许接受。省略无关周期事件、迁移和时钟调整。
    • A 离开 CPU 后 B 可以运行。演示在 D 之前安排一次宿主抢占并重新调度；Guest 无需因此执行自己的任务切换。A 到期后最终得到 Guest 调度，不指定具体调度延迟。
    1. 任务 A 准备休眠 · Guest 用户态 · 任务 A

      A 即将请求休眠 1 ms，B 也具备运行条件。 Guest 内核调度 A、B；宿主内核调度承载整个 vCPU 的 QEMU 线程。两层有各自的任务状态和运行队列。

      Linux 6.18：nanosleep 的等待状态、定时器与 schedule · QEMU 10.2：KVM_RUN 调用与 MMIO 分派
    2. 建立任务等待对象 · Guest 内核 · do_nanosleep

      Guest 为 A 建立 hrtimer_sleeper，task 指向 A，并设置可中断等待标志。 源码设置 TASK_INTERRUPTIBLE | TASK_FREEZABLE，随后启动定时器；此刻 A 仍在内核执行，到 schedule 才让出 CPU。信号与冻结处理不在本次成功路径内。

      Linux 6.18：nanosleep 的等待状态、定时器与 schedule
    3. 安排虚拟定时事件 · Guest clockevent → KVM → 宿主 hrtimer

      Guest 选定下一事件 D 并写 TSC deadline；KVM 安排对应的宿主软件定时器。 TSC deadline 写入由 KVM 处理。start_sw_tscdeadline() 将剩余 Guest TSC 计数换算成宿主等待间隔；处理完成后继续 Guest 调用路径。Guest 的 sleeper 与宿主 hrtimer 是两个不同对象。

      Linux 6.18：客户机 clockevent 写入 TSC deadline · Linux 6.18：KVM 保存客户机 deadline 并启动定时 · Linux 6.18：软件 deadline、pending 与 UNBLOCK 请求
    4. 客户机切换到任务 B · Guest 调度器

      A 调用 schedule 离开运行队列，Guest 选择 B 继续计算。 A 阻塞后，vCPU 仍有客户机指令可以执行，mp_state 保持 RUNNABLE。本次任务切换由 Guest 内核完成，宿主没有因 A 的 nanosleep 而把 vCPU 线程挂到等待队列。

    三、执行路径的差异

    每个例子都可以沿三条边界判断：是否从客户机退出到 KVM，是否结束本次 KVM_RUN 返回 QEMU，以及宿主调度器是否切换了正在运行的线程。它们对应不同的状态和开销。

    例子VM Exit返回 QEMU关键状态
    普通 ADD示例中无退出不需要Guest EAX 与 RIP 前进
    Guest SYSCALL权限切换本身不要求退出不需要Guest CPL 3 → 0 → 3，使用客户机 LSTAR
    CPUID有，进入内核 CPUID 处理常规路径不需要KVM 写回虚拟 CPU 信息并推进 RIP
    QEMU 模拟 MMIO 读有，分析设备访问需要一次请求交接kvm_run.mmio 传递读请求；再入后完成指令
    内核 LAPIC 下的 HLT本例拦截 HLT常规等待不需要mp_state 与宿主 task 状态分别变化

    CPUID 的结果由虚拟 CPU 配置决定，KVM 在内核中完成查询。MMIO 示例需要设备模型提供读结果：第一次 KVM_RUN 返回请求，QEMU 填入数据，第二次进入内核才消费数据并完成指令。CPUID 处理与用户态 I/O 继续处理分别体现了这两种分工。

    在 HLT 场景中，客户机已进入空闲，宿主线程可以继续短暂轮询，也可以进入睡眠。后端事件到达后，线程先变为可运行，随后才有机会被调度。TASK_RUNNING 同时覆盖运行队列中的等待者和当前执行者，分析延迟时还要观察调度事件。

    1. 任务休眠与两层调度

    定时休眠示例中，任务 A 请求等待 1 ms。Guest 内核创建 hrtimer_sleeper，登记到期回调，再把 A 交给调度器等待。如果任务 B 可以运行，Guest 就选择 B，vCPU 继续执行指令；没有其他可运行的普通任务时，Guest 进入 idle，本例通过 HLT 把等待机会交给 KVM。这样，同一个应用请求会对应两条不同的 vCPU 路径。

    2. 从定时到期到应用继续执行

    两个示例使用 Guest TSC-deadline clockevent 和 KVM 的宿主软件 hrtimer 分支。Guest 选定下一次时钟事件 D，KVM 将虚拟 LAPIC 的 deadline 转为宿主定时器。宿主回调到期后，先增加 lapic_timer.pending 并请求唤醒；vCPU 执行循环随后把事件提交给虚拟 LAPIC。客户机接受定时中断、运行自己的 hrtimer 队列后，hrtimer_wakeup() 才清除 sleeper 中的任务指针并唤醒 A。宿主定时器与 pending 标记、Guest 到期回调对应这两端的处理。

    在 HLT 场景中，宿主线程被唤醒后，mp_state 仍可暂时为 HALTED。线程先恢复 KVM 执行，把待处理定时事件转为 LAPIC 中断，再由运行循环检查可接受事件、恢复 RUNNABLE。接着才是 Guest 中断处理、A 进入 Guest 运行队列以及 A 获得 CPU 开始执行。演示把这些阶段分开，便于区分“到期”“可运行”和“正在执行”。

    1 ms 是应用提交的休眠时长。实际 clockevent D 还受 Guest 当前时间、timer slack 和定时器安排影响；D 之后，宿主运行队列等待、虚拟中断递送和 Guest 调度还可能继续增加返回延迟。本例不加入信号打断，最终返回值为 0。播放速度只控制讲解节奏，不模拟这些延迟的实际长度。

    四、退出处理与优化

    硬件辅助虚拟化把大量客户机代码交给处理器直接执行，同时把需要控制的操作交回宿主。KVM 把 CPU、内存和中断的高频处理放在内核，QEMU 保留机器与设备模型。这个分工让 CPUID 等常见操作只经过内核，设备回调仍可复用完整的用户态实现。

    设备通知还可以缩短路径。virtio 驱动先把描述符放入共享队列，再写 doorbell 提醒后端。匹配 ioeventfd 的通知写入可由 KVM 直接触发事件，省去一次通用用户态 MMIO 回调；它通常仍需要 VM Exit。后端完成方向的 irqfd 则把 eventfd 接到 KVM 中断路由。同步设备寄存器读取仍需返回实际值，不能直接替换成无数据的通知。

    空闲等待可以使用有限 halt polling，以宿主 CPU 时间换取较低的短等待延迟；长时间等待应及时睡眠。优化前先按路径区分 VM Exit、用户态返回和调度等待，再对齐请求延迟与 CPU 消耗，避免仅根据退出次数判断收益。

    定时事件也有不同实现：硬件定时辅助、定时器提前量和中断加速可以减少部分处理或交付延迟，但不能保证宿主与 Guest 调度器立即选中相应任务。定位定时唤醒抖动时，可以沿宿主定时回调、vCPU 唤醒与切入、Guest 中断、任务 A 唤醒与切入逐段对齐时间，再判断延迟主要来自哪一层。
