一、场景与边界

GPU 作业从 Guest 用户态提交，经过驱动组织命令、硬件搬运数据和完成通知，最后由应用取得结果。下面以作业 G1 为例，分别展示整卡直通的上传与读回，以及受宿主管理的 mdev 提交。上传与读回指缓冲区之间的数据复制。

VFIO PCI 路径采用 AMD Vega10 / SDMA 4.0 与公开 AMDGPU 驱动，观察 Guest RAM 和 VRAM 之间的 4 KiB 复制。mdev 路径采用 Skylake 的 Intel GVT-g / i915 execlists，观察共享系统内存中的 BLT 复制；该历史实现仅适用于相应的 Intel 平台，不代表 NVIDIA vGPU 或其他 Intel GPU 的实现。两组场景均从设备初始化、BO 分配和基础映射完成后开始。

图中按职责分为 Guest、KVM、QEMU、Host kernel 和物理 GPU。KVM 运行在宿主内核，负责 vCPU 与中断虚拟化；同属宿主内核的 VFIO、i915/GVT-g 负责设备管理。提交、数据访问和完成通知各有自己的路径，后文分别展开。

源码版本：QEMU 10.2.0、Linux 6.18。

当前场景配置与源码版本

    源码版本：QEMU 10.2.0、Linux 6.18。

    以下按场景列出处理顺序。启用 JavaScript 后可逐步观察结构与状态变化。

    上传 · Guest RAM → VRAM

    跟踪作业 G1：应用提交一条 4 KiB SDMA 复制命令，从 Guest RAM / GTT 搬运到 GPU VRAM，等待 fence 后再使用结果。

    • 固定 Linux 6.18 / QEMU 10.2.0，x86 KVM，整块 AMD Vega10 / SDMA 4.0 GPU 经 vfio-pci 直通；不是 SR-IOV VF 或 mdev。
    • Guest 使用公开 AMDGPU DRM CS ioctl 提交合法 SDMA IB，未启用 Guest vIOMMU。GTT 与 VRAM BO、GPU VA、Guest RAM 的宿主 IOMMU 映射和 MSI 路由均已准备；不模拟设备初始化、缺页、复位、迁移或竞争作业。
    • 宿主这块 PCI 设备绑定 vfio-pci，而非 amdgpu；AMDGPU 作业驱动运行在 Guest。SDMA ring 由 Guest 驱动在 GTT 分配，本例 IB1 也固定在 GTT 系统内存，不将所有 GPU 命令缓冲区泛化为 Guest RAM。
    • 示例限定 use_doorbell=true，doorbell BAR 子区间允许 VFIO mmap，且 CPU EPT 映射已建立。Guest CPU 的写指针写入直接到物理 BAR，不需每次退出后由宿主 VFIO 或 QEMU 转发；需捕获的寄存器及 MSI-X 表等区域不能据此推断为直映。
    • 使用正常 MSI→VFIO eventfd→KVM irqfd 软件递送，关闭 posted interrupt；中断未屏蔽，Guest 可接受。本例不用超时、信号打断和错误分支。
    • G1、IB1、fence 42 和示意 GPU VA 用于关联对象，不是真实采样。软件发布与硬件完成分开；用户缓冲区可见性需遵守 DRM 映射与同步约定。
    1. 准备 G1 · Guest 用户态

      源和目标 BO 已建立，应用准备一次 4 KiB 复制。 GPU VA 是 GPU 页表中的地址；CPU 门铃的 BAR 映射与设备访问系统内存的 IOMMU 映射是两条不同路径。

      初始化：将允许映射的 BAR 区域暴露给 Guest · 初始化：建立 Guest 后备页的设备 DMA 映射 · Guest：解析 CS、BO 与 VM 依赖
    2. 提交命令与对象 · Guest 内核 · amdgpu_cs_ioctl

      驱动读取 CS chunks，核验 BO、上下文、VM 更新和依赖。 数据 BO 不会随 ioctl 被整体复制到 QEMU。CS 的 IB 指向 DMA 可访问的命令缓冲区；本例参数合法、BO 已驻留。

      Guest：解析 CS、BO 与 VM 依赖 · Guest：提交前 GPU VM 更新与依赖检查
    3. 作业进入调度队列 · Guest 内核 · amdgpu_cs_submit

      G1 被交给 DRM 调度器，建立供用户态等待的完成关系。 提交和执行是异步的。这里选择 ioctl 先返回、GPU 稍后执行的一种合法时序，不承诺所有负载都按相同延迟运行。

      Guest：把作业交给 DRM 调度器
    4. 提交调用返回 · Guest 用户态

      应用获得本次提交的句柄，尚不能把它当作 GPU 已完成。 本演示随后等待该句柄关联的 fence；不把 ioctl 返回和硬件完成合并成一步。

      Guest：解析 CS、BO 与 VM 依赖 · Guest：等待 CS fence，返回完成状态
    5. 调度并写入 ring · Guest 内核 · DRM 调度回调

      依赖满足后，驱动把 IB 执行命令及 fence/TRAP 序列写入 SDMA ring。 amdgpu_ib_schedule 组织 VM 刷新、IB 和 fence。软件写入 fence 命令不等于 GPU 已把完成序号写回。 本例 ring 与 IB1 位于 Guest RAM 的 GTT 后备页；CPU 写命令内存与随后写 doorbell 是两个动作。

      Guest：依赖满足后的调度回调 · Guest：组织 IB、VM 刷新与 fence · Guest：在 SDMA ring 中写入 IB 命令 · Guest：建立 ring fence · Guest：顺序发出 FENCE 与 TRAP 包 · Guest 初始化：在 GTT 系统内存分配 SDMA ring
    6. 发布 ring 并通知 GPU · Guest 内核 → 物理 GPU

      Guest AMDGPU 执行 ring commit 并写 WDOORBELL64。CPU 经已建立的 EPT 映射写物理 doorbell BAR，GPU 得知新的 ring 写指针。 命令在 ring / IB 内存中，门铃只发布写指针，不携带 4 KiB 载荷。这次 BAR 写既不调用宿主 amdgpu，也不逐请求进入 VFIO 驱动或以 KVM_EXIT_MMIO 返回 QEMU；VFIO、KVM 和 QEMU 已在初始化建立访问、隔离与路由。其他需捕获的 region 仍可走模拟路径。

      Guest：提交 ring 的写指针 · Guest：WDOORBELL64 通知 SDMA · 初始化：将允许映射的 BAR 区域暴露给 Guest
    7. SDMA 获取 IB1 · 物理 GPU · SDMA

      GPU 读取 ring 和 IB1，解析源、目标 GPU VA 与 4096 B 长度。 GPU VA 可以映射到本地 VRAM 或系统内存。本地 VRAM 访问留在 GPU 内部；系统内存 DMA 经过 PCIe 和宿主 IOMMU。SDMA 通过 GPU 页表 / GTT 及预建的宿主 IOMMU 映射读取系统内存，VFIO 负责事先建立设备访问条件。

      Guest：在 SDMA ring 中写入 IB 命令 · 硬件包格式：参考驱动中的内核副本生成器
    8. 读取系统内存 · 物理 GPU · SDMA

      SDMA 从 Guest RAM / GTT 取得 G1 的源数据。 此帧表示该次传输正在进行；目标尚未被标记为可供应用使用，fence 42 仍未完成。

      硬件包格式：参考驱动中的内核副本生成器
    9. 目标显存已写入 · 物理 GPU · SDMA

      本次复制的数据已到达 GPU VRAM。 数据移动完成和软件观察到 fence 是两个阶段。应用必须遵守完成与映射同步约定，此时不应提前复用仍受作业保护的缓冲区。

      硬件包格式：参考驱动中的内核副本生成器 · 硬件包格式：驱动中的写回与通知字段定义
    10. 写回 fence 序号 · 物理 GPU → Guest RAM

      按 ring 顺序执行 FENCE，将完成序号从 41 更新为 42。 FENCE 与后面的 TRAP 是不同包：写回提供完成证据，通知只促使软件尽快检查；这里没有 virtio used ring。

      硬件包格式：驱动中的写回与通知字段定义
    11. 发出物理完成通知 · GPU → 宿主 VFIO

      SDMA TRAP 产生设备中断，宿主 VFIO MSI handler 触发绑定的 eventfd。 本例采用普通 MSI/eventfd 路径，不是硬件 posted interrupt。通知不携带 4 KiB 数据；QEMU 已预先建立路由但不在这次中断处理链中。

      硬件包格式：驱动中的写回与通知字段定义 · 宿主：物理 MSI/MSI-X 触发 eventfd
    12. KVM 记录待处理中断 · Host VFIO → KVM

      物理 MSI 触发的 eventfd 唤起 KVM irqfd，按缓存路由将向量递送目标 vLAPIC。 这一步建立 pending，不等于 Guest 已执行中断处理。IOMMU 的 DMA 映射和 KVM 的虚拟中断递送是不同职责；QEMU 无需为本次通知逐条转发。

      宿主：eventfd 到 KVM 的缓存中断路由 · KVM：按 irqfd 路由递送 MSI · KVM：向量记入目标 vLAPIC
    13. 注入中断并进入 Guest handler · 宿主 KVM → Guest 内核

      目标 vCPU 检查可注入条件，VMX 准备外部中断信息并成功 VM-entry，Guest AMDGPU handler 随后处理 SDMA trap。 普通软件递送路径分为 eventfd、vLAPIC pending、实际注入与 Guest 处理；不能把 irqfd 唤起当成注入完成。本例已满足接受条件，未启用 posted interrupt。完整 IRR/ISR/EOI 细节见中断演示。

      KVM：目标 vCPU 检查可注入事件 · KVM：准备 VM-entry 中断信息 · KVM：进入 Guest 并递送中断 · Guest：AMDGPU 中断入口 · Guest：SDMA trap 分派
    14. Guest 确认完成 · Guest 内核 · amdgpu_fence_process

      驱动读取写回序号 42，signal 对应硬件 fence，作业完成关系随之推进。 硬件写回在前，Guest 软件确认在后。软件轮询也可观察完成；本场景选择中断驱动的检查路径。

      Guest：读取写回序号并 signal fence · Guest：等待 CS fence，返回完成状态
    15. 等待完成并使用结果 · Guest 内核 → 用户态

      wait 返回成功且 status=0，应用在相应的映射同步约定下使用复制结果。 wait 的 ioctl 返回 0 仅表示调用成功，还必须看 out.status：本例为 0，表示不再忙；超时路径不在本次演示中。GPU 作业完成不等于显示器已呈现。

      Guest：等待 CS fence，返回完成状态

    GVT-g · BLT 缓冲区复制

    跟踪 G1：Skylake GVT-g 客户机提交一次 4 KiB BLT 复制，经宿主审核与影子上下文调度，完成后发布虚拟 GPU 事件并由 Guest 确认结果。

    • 使用 Guest i915 的 GEM_EXECBUFFER2 提交合法 BLT batch。A、B 与命令缓冲区均位于受管理的共享系统内存，已完成对象分配和 GPU 映射；不要把它们标成离散 GPU 的独立 VRAM。
    • 本例选择需要捕获的 ELSP 寄存器写：VM-exit 先进入 KVM，无法在内核完成时以 KVM_EXIT_MMIO 返回 QEMU，再经 VFIO region 回调进入宿主 i915/GVT-g。图形 aperture 等可直接映射的区域并非每次都经过此路径。
    • Host i915/GVT-g 的审核、影子页表和调度与 Guest 驱动是不同执行域。物理执行成功，无 GPU hang、复位、迁移、页故障或其他 vGPU 的抢占。
    • 虚拟 MSI 未屏蔽，已配置 VFIO eventfd / KVM irqfd，采用软件递送；应用在 Guest 完成并按 GEM CPU 访问同步约定后使用 B。动画只说明先后，不模拟调度公平性或真实延迟。
    1. 准备复制 G1 · Guest 用户态

      应用已经准备 A、B 和一条复制 4 KiB 的合法 BLT batch。 此处两份数据都在受管理的系统内存中。mdev 的实例建立和资源分配已经完成，不放到每次命令的数据路径中。

      Guest：提交 i915 batch 与对象依赖 · 宿主 GVT-g：建立独立 workload
    2. Guest 提交 batch · Guest 内核 · i915

      GEM_EXECBUFFER2 核验对象与依赖，准备请求、上下文及 batch。 应用通过 GPU 提交接口交出一个合法 BLT 请求，随后由驱动和设备处理缓冲区复制。显示扫描输出独立于这次请求。

      Guest：提交 i915 batch 与对象依赖
    3. 写入虚拟提交端口 · Guest i915 → KVM

      Guest i915 写入虚拟 ELSP 寄存器，访问落入本例需捕获的 MMIO 区域，硬件 VM-exit 先进入 KVM。 KVM 识别需要设备模拟的门铃访问，无法在内核完成时，以 KVM_EXIT_MMIO 返回 QEMU。硬件 VM-exit 先将控制权交给 KVM，KVM_RUN 返回才进入用户态处理。

      Guest：写 execlist 提交端口 · KVM：未在内核满足的访问形成 KVM_EXIT_MMIO
    4. 交给 QEMU 的 VFIO region · KVM → QEMU 用户态

      KVM_RUN 返回 KVM_EXIT_MMIO，QEMU 按虚拟 BAR 地址分派并写 VFIO region fd。 QEMU 转交的是寄存器访问，不在这里执行 GPU batch 或复制 4 KiB 数据。宿主 GVT-g 将收到该 region 写并解析 ELSP。

      QEMU：接收 KVM_EXIT_MMIO 并分派设备访问 · 被捕获的 MMIO：写入 VFIO region fd
    5. 宿主收齐 ELSP 描述符 · 宿主 mdev / GVT-g

      VFIO write 进入 GVT-g 的 MMIO 处理，ELSP 写处理器收齐描述符并提交 execlist。 elsp_mmio_write 收集四个 dword 后调用 intel_vgpu_submit_execlist；此时不代表实际 GPU 已接受该虚拟上下文。

      宿主 mdev：VFIO region 写入口 · 宿主 GVT-g：分派被捕获寄存器写 · 宿主 GVT-g：收集 ELSP 描述符 · 宿主 GVT-g：解析提交上下文
    6. 建立并排队 workload · 宿主 GVT-g

      宿主为 G1 创建 workload，等待 GVT-g 调度。Guest 提交已经可以返回。 宿主排队时间与 Guest ioctl 返回是不同边界；图中选择提交先返回、之后才获得物理引擎的一种合法时序。

      宿主 GVT-g：建立独立 workload · Guest：提交 i915 batch 与对象依赖 · Guest：等待 GEM 对象的请求完成
    7. 审核命令与影子状态 · 宿主 GVT-g 调度线程

      dispatch_workload 扫描 workload，并准备宿主控制的 shadow context、命令和地址映射。 Guest 原始上下文不能不经处理直接作为宿主物理上下文使用；具体审核与重定位由选定 GVT-g 实现决定，不能推广为所有厂商 vGPU 内部。

      宿主：审核、建立 shadow context 并交给 i915 · 宿主：扫描命令与建立影子状态 · 宿主：填充受宿主管理的影子上下文 · 宿主：准备物理 i915 请求的命令与上下文
    8. 交给物理 GPU 执行 · 宿主 GVT-g → Host i915

      宿主将准备好的 i915_request 加入物理引擎，G1 获得执行机会。 宿主为该虚拟工作负载建立新的物理请求，并控制它的执行。这里跟踪单次成功提交；多个 vGPU 并行运行时，还需处理调度与抢占。

      宿主：审核、建立 shadow context 并交给 i915 · 宿主：在 dispatch_workload 中提交 i915 请求的调用点
    9. 读取源缓冲区 A · 物理 GPU · BLT

      硬件沿受宿主管理的映射读取 batch 与源缓冲区 A。 影子映射指向真实后备页。此处表达硬件执行与数据方向，不把物理 GPU 工作伪装成 C 函数，也不假设每字节经 QEMU。

      宿主：扫描命令与建立影子状态 · 宿主：审核、建立 shadow context 并交给 i915
    10. 目标 B 已更新 · 物理 GPU · BLT

      本次复制的数据已经写入目标 B。 目标内容已改变仍不意味着 Guest 驱动已观察完成；应用继续等待请求的完成关系，不提前使用仍由 GPU 访问的缓冲区。

      宿主：审核、建立 shadow context 并交给 i915 · 宿主：确认物理请求完成并更新 Guest context
    11. 宿主确认物理请求完成 · Host i915 → GVT-g

      物理请求和 shadow context 退出达到完成条件，GVT-g 收尾当前 workload。 硬件报信后，complete_current_workload 还要等待影子上下文不再活跃，满足这些条件后才能结束并释放该 workload。

      宿主：确认物理请求完成并更新 Guest context
    12. 发布 Guest context 与事件 · 宿主 GVT-g

      更新 Guest context，并把 workload 中的 pending events 交给虚拟中断逻辑。 宿主请求对象和 Guest 完成状态分别维护。物理请求结束后，还需更新虚拟设备状态，再由 Guest 驱动完成自己的请求。

      宿主：确认物理请求完成并更新 Guest context · 宿主：发布虚拟 GPU 事件并检查屏蔽状态
    13. 虚拟事件进入 KVM 路由 · Host i915/GVT-g → KVM

      虚拟 MSI 已启用且未屏蔽，GVT-g 触发 eventfd，KVM irqfd 路由到目标 vLAPIC，记录待处理中断。 宿主 GVT-g 决定何时发布虚拟完成事件；不能把事件记录、eventfd 唤起和 Guest handler 画成同一动作。本例无 posted interrupt，仍需目标 vCPU 在允许时注入。

      宿主：发布虚拟 GPU 事件并检查屏蔽状态 · 宿主：获准通知后触发 MSI eventfd · 宿主：eventfd 到 KVM 的缓存中断路由 · KVM：按 irqfd 路由递送 MSI · KVM：向量记入目标 vLAPIC
    14. 注入 Guest 完成中断 · KVM → Guest i915

      目标 vCPU 检查可注入条件，准备 VM-entry 外部中断信息；成功进入 Guest 后，Guest i915 才处理通知。 Host i915 完成物理请求、GVT-g 更新虚拟 context、KVM 注入以及 Guest i915 确认请求，是四个不同层级的事件。

      KVM：目标 vCPU 检查可注入事件 · KVM：准备 VM-entry 中断信息 · KVM：进入 Guest 并递送中断
    15. Guest 确认请求完成 · Guest i915

      Guest 驱动观察更新后的请求状态，等待 G1 的完成条件得到满足。 虚拟中断提示 Guest 检查完成状态，4 KiB 数据通过前面的缓冲区访问传输。Guest 也可以轮询完成状态；本场景采用中断驱动路径。

      Guest：等待 GEM 对象的请求完成 · 宿主：确认物理请求完成并更新 Guest context
    16. 应用使用复制结果 · Guest 内核 → 用户态

      等待调用成功返回，应用按 GEM 的 CPU 映射与同步约定读取 B。 本次完成表示缓冲区复制已经结束。显示扫描输出有自己的同步条件；其他 mdev 实现也需要按各自的设备模型和驱动分析。

      Guest：等待 GEM 对象的请求完成

    G1、IB1、地址和 fence 序号为示例值，用于关联同一次操作。播放间隔只控制讲解节奏，不能用于推断 GPU 或虚拟化开销。

    三、提交、数据与完成的边界

    观察点已经发生不能据此推断
    提交 ioctl 返回驱动已接受作业或建立异步完成关系GPU 已执行完毕，或应用已经可以复用所有缓冲区
    doorbell / ELSP 发布相应执行者可以处理新的命令门铃携带整个数据载荷，或每个访问都由 QEMU 处理
    数据写入目标硬件完成了本笔数据移动Guest 驱动已经观察到完成，或应用已经满足 CPU 访问同步条件
    fence / 请求完成软件可以确认对应作业的完成关系显示器已呈现某一帧，或所有其他 GPU 作业都已经结束
    等待成功并满足映射同步约定应用可以按该缓冲区的接口约定使用结果所有 GPU、mdev 和厂商驱动使用完全相同的完成协议

    AMDGPU 的 CS 提交路径先核验上下文、对象和 GPU VM，再把作业交给 DRM 调度器。调度回调组织 IB、fence 与 ring 发布；SDMA 硬件随后执行。等待接口同时提供 ioctl 返回值和输出状态，应用需要检查两者，确认对应作业是否完成。

    四、地址转换与宿主参与

    整卡直通时，宿主这块 PCI 设备绑定 vfio-pci；Guest 内的 AMDGPU 驱动接收应用 CS ioctl，组织 GPU 作业。宿主 VFIO 管理设备资源、DMA 隔离和中断接口，QEMU 预先配置虚拟设备、BAR 与中断路由，KVM 维护 vCPU 的二级地址转换并递送虚拟中断。它们不代替 Guest 驱动逐条解释或转发 GPU 命令。参见 Linux VFIO 文档。

    本例先在 Guest RAM / GTT 写好 IB 与 SDMA ring，再由 Guest CPU 向可 mmap 的 doorbell BAR 写入新写指针。这个 CPU 访问沿 Guest VA → GPA → 已建立的 EPT → 物理 BAR，直接让 GPU 看见门铃；门铃不是 4 KiB 数据载荷，也不需要每次调用宿主 VFIO 或返回 QEMU。GPU 随后自己读取 ring 和 IB：访问系统内存经过 GPU 地址转换与宿主 IOMMU 的预建映射，访问本地 VRAM 则不等于一次系统内存 DMA。SDMA ring 在该驱动中分配于 GTT，本例用户 IB1 也选择 GTT；不是所有 GPU 命令缓冲区都必须放在系统内存。

    数据复制及 fence 写回完成后，物理 MSI 由宿主 VFIO 触发 eventfd，KVM irqfd 把向量路由到目标 vLAPIC；目标 vCPU 在允许时注入，Guest AMDGPU 才处理完成并唤醒应用。演示把 pending 与实际注入分开。未直接映射、需要捕获或特殊处理的 BAR 区域仍可能进入 KVM / QEMU 的 VFIO region 回调，不能用“直通”推导全部寄存器访问都不退出。

    GVT-g 由宿主 i915/GVT-g 管理物理 GPU。本例 ELSP 写先由 KVM 捕获，经 QEMU 的 VFIO region 进入宿主 GVT-g，再审核 workload、建立影子上下文并调度真实引擎；完成后由 GVT-g 发布虚拟事件，KVM 负责递送。部分图形内存可直接访问，数据传输无需逐字节经过 QEMU 模拟。本例集成 GPU 的 A、B 和 batch 均使用系统内存后备页。参见 GVT-g 的访问与地址空间说明。

    VFIO 是设备访问、DMA 和中断的框架；mdev 是 mediated 实例及厂商设备实现，SR-IOV VF 是硬件提供的虚拟功能，virtio-gpu 则是另一种前后端协议。它们不能直接互换。闭源厂商调度与固件内部不在这两个可核验实现的范围内。
