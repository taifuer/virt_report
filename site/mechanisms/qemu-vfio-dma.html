前言

设备直通把物理设备的功能交给客户机驱动使用。驱动向设备提交缓冲区地址后，设备可以通过 DMA 读写客户机内存。宿主机需要把这些地址转换成实际的物理页，同时限制设备能够访问的范围。VFIO 管理设备访问与 DMA 资源，宿主 IOMMU 执行地址转换和权限检查。

本文分析 x86 / KVM 下普通 PCIe 设备访问客户机 RAM 的过程：客户机不配置虚拟 IOMMU，设备使用 GPA 作为 DMA 地址，宿主启用 IOMMU 隔离；内存采用常规可固定的 RAM。本例不涉及 PCIe 对等访问、ATS、PASID 和可恢复页故障。设备寄存器与中断仅作为请求提交和完成的上下文。

源码版本：QEMU 10.2.0、Linux 6.18。

四种地址与两条转换路径

同一块客户机内存，客户机 CPU、QEMU 进程和物理设备使用的地址不同。建映射时，QEMU 提供设备侧地址与用户态内存位置；运行时，IOMMU 根据设备所属的转换域处理 DMA。

地址含义本例中的用途
GPA客户机物理地址客户机 RAM 中缓冲区的位置
IOVA设备发出的 I/O 虚拟地址交给宿主 IOMMU 转换；本例数值等于 GPA
HVAQEMU 进程的宿主虚拟地址向内核描述 RAM 的后备内存
HPA宿主物理地址DMA 最终访问的宿主物理页

EPT / NPT 负责客户机 CPU 的第二阶段地址转换，具体建图过程见KVM 内存映射与 EPT 缺页处理。PCIe 设备发起的普通 DMA 使用宿主 IOMMU 的转换上下文，QEMU 的 HVA 不随 DMA 请求发送。两条路径需要指向相同的客户机后备页，但页表管理、权限和缓存失效是各自的机制。

例如，客户机缓冲区位于 GPA 0x00400080，设备发出同值的 IOVA；映射覆盖 0x00400000–0x00400fff，对应宿主页 HPA 0x21000000。IOMMU 保留页内偏移 0x80，得到 HPA 0x21000080。QEMU 映射这块页时可以使用完全不同的 HVA。连续的 IOVA 区间也可以对应多个不连续的宿主物理页。

客户机配置虚拟 IOMMU 后，IOVA 与 GPA 可以不同，宿主还需跟踪客户机的 DMA 映射变化或使用硬件嵌套转换。QEMU 的内存监听代码为 IOMMU 区域和普通 RAM 分别处理；本文沿普通 RAM 分支继续。IOMMU 与 RAM 的映射分支

配置路径设置转换关系；正常数据访问由设备与 IOMMU 硬件处理。示例地址用于展示页号和偏移，不对应实际机器。故障仅表示本次数据访问被阻止，不模拟特定设备的错误恢复。

  1. QEMU 向内核提供 IOVA、后备内存与访问权限，建立硬件映射。
  2. 客户机驱动提交缓冲区地址，设备发出 DMA。
  3. IOMMU 检查映射和权限，通过后访问 HPA 对应的 RAM。
  4. 正常请求完成后，驱动消费或回收缓冲区；缺失映射和越权写入不能产生正常数据完成。

启用 JavaScript 可切换权限和方向，逐步查看状态变化。

配置阶段

  1. 建立 DMA 所有权。VFIO 检查设备所在 IOMMU group 的所有权，并把设备接入受控的 I/O 地址空间。传统接口通过 group 与 container 建立关系，IOMMUFD 路径通过设备文件描述符绑定并附着 IOAS 或硬件页表。
  2. 接收内存布局。QEMU 的 MemoryListener 获得可访问的 RAM 区间，计算设备侧 IOVA、进程侧 HVA、长度和只读属性。
  3. 建立映射。内核验证范围、权限与页粒度，固定相应后备页，在设备关联的 IOMMU domain 中建立 IOVA 到 HPA 的映射。硬件随后可缓存转换结果。

无客户机 IOMMU 时，常规配置通常映射可 DMA 访问的客户机 RAM，映射生命周期长于单个 I/O 请求。客户机驱动每次填写一个缓冲区地址，并不会使 QEMU 重新执行一遍 DMA map ioctl。

数据阶段

  1. 客户机驱动准备缓冲区和设备所需的描述符，按照设备协议与内存顺序要求提交请求。寄存器访问可通过受支持的 BAR 映射或 VFIO 访问路径到达设备。
  2. 物理设备发出携带 DMA 地址的读写事务，宿主根据设备标识选择对应 IOMMU 转换上下文。
  3. IOMMU 检查映射及读写权限。转换成功时访问目标宿主页；本例缺失映射或写只读页时产生故障，目标数据访问被阻止。
  4. 正常完成的数据请求由设备按其协议报告完成，驱动随后回收或消费缓冲区。DMA 故障后的错误报告、超时或恢复过程依赖设备及平台，不能当作成功完成。

读写权限以设备视角命名：设备读取 RAM 使用 READ，设备把接收数据写入 RAM 使用 WRITE。驱动的“发送”通常包含设备读，“接收”通常包含设备写。内核的权限解释

隔离与映射生命周期

为什么还需要 IOMMU group

I/O 页表限制设备到内存的访问，但实际隔离还取决于 PCIe 拓扑。某些多功能设备、桥或缺少合适 ACS 能力的路径，可能允许事务在到达 IOMMU 前发生重定向。内核据此把无法独立隔离的设备归入同一 IOMMU group，作为 DMA 所有权的边界。

按单个设备打开文件描述符，不能改变硬件隔离粒度。IOMMUFD 的设备 cdev 接口仍检查 group 所有权；同组设备不能分配给相互独立的 DMA 所有者。拥有设备的权限也不等于能任意选择宿主物理地址：映射接口接收用户态能够提供的后备内存，并由内核验证与固定。VFIO group 与设备 cdev

撤销映射为何要协调设备

释放或复用 DMA 缓冲区前，需要确保设备已经停止使用它。删除 I/O 页表项还要与硬件转换缓存失效配合，避免缓存中的旧转换继续指向被回收的页。设备队列停止、在途事务处理与映射撤销共同决定安全的回收顺序；单纯删除 QEMU 的用户态指针并不完成这些工作。

QEMU 收到 RAM 区域删除通知后会调用后端的 DMA unmap。内核负责撤销其维护的 IOMMU 映射并释放固定页的引用。大范围映射可减少频繁的 map / unmap，但长期固定内存会约束内存回收、气球回收和热插拔；频繁更新小范围映射则会增加页表管理与 IOTLB 失效开销。区域删除、RAM discard 与固定页的关系

设备 DMA 写入的脏页还需要独立跟踪。vCPU 的 KVM 脏页日志无法覆盖物理设备绕过 CPU 发出的全部内存写入。因此，直通设备热迁移同时依赖设备状态保存、DMA 停止与设备或 IOMMU 的脏页跟踪能力，不能仅凭 CPU 内存迁移成功判断设备可迁移。

从 VFIO Container 到 IOMMUFD

以 group 和 container 组织 DMA

传统 VFIO 将设备访问、硬件隔离组和 IOMMU 管理组织成 device、group、container 三层。应用先把 group 加入 container，再配置 IOMMU 后端，最后通过 group 获取设备文件描述符。多个可兼容的 group 可以共享 container 中的映射，减少重复的页表维护。

这种结构支撑了长期使用的设备直通路径，但 I/O 地址空间管理与 VFIO container 接口紧密绑定。随着嵌套转换、不同硬件页表类型和更细粒度设备绑定的需求出现，用户态需要更直接地表达地址空间、硬件页表及它们与设备的关联。

把地址空间管理交给 IOMMUFD

IOMMUFD 通过 /dev/iommu提供通用 I/O 地址空间接口。IOAS 保存用户态建立的地址映射；HWPT 表示关联的硬件页表。设备经 VFIO cdev 绑定 IOMMUFD，再附着到 IOAS 或 HWPT。向 IOAS 附着时，内核可以复用兼容的 HWPT，也可以新建 HWPT；同一个 IOAS 的映射可以同步到多个硬件页表。VFIO 继续提供设备区域、配置空间和中断访问，DMA 地址空间管理则使用 IOMMUFD 的对象与操作。

QEMU 在 2023 年合入 IOMMUFD 后端实现。公共 VFIO 内存监听逻辑保留，后端分别完成传统 container 或 IOMMUFD 的绑定与 map / unmap。现在的 iommufd_cdev_connect_and_bind()与 iommufd_cdev_attach_ioas_hwpt()对应绑定和附着两个步骤。绑定实现、附着实现

接口拆分为后续页表能力提供了扩展位置，同时引入对象生命周期、能力协商和多种页表关系的管理。切换后端不会改变设备的 DMA 协议，也不会自动补齐设备迁移、复位或硬件隔离能力。比较两条路径时，应分别检查地址空间管理能力与具体设备支持的功能。

与其他设备虚拟化方式的关系

SR-IOV 让一个物理功能提供多个 VF，VF 可以再通过 VFIO 分配；mdev 由宿主设备驱动提供受管理的设备实例；vDPA 则面向 virtio 数据面加速。它们分别解决功能划分、设备实例管理或 virtio 加速的问题。此处讨论的物理 PCIe 设备 DMA 路径，不能不加区分地套用到所有 mdev 或 vDPA 实现。
