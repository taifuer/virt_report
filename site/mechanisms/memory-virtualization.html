一、客户机地址空间与宿主内存

内存虚拟化为每台客户机提供独立的物理地址空间，并将它映射到宿主的后备内存。两台虚拟机都可以从物理地址零开始使用内存，而不读写彼此的数据。客户机应用还有自己的虚拟地址，客户机内核通过页表把它们映射到自己认识的物理页；宿主再决定每个客户机物理页实际由哪块宿主内存承载。

内存虚拟化需要同时满足三个条件：客户机页表的含义保持不变，访问被限制在获准的宿主页内，宿主仍能分配、迁移和回收这些页面。本文以普通、可由宿主访问的 RAM 和 x86 KVM 为例，从一次读取推导影子页表与 EPT/NPT 的解决办法。

客户机内核维护自己的页表，QEMU 在宿主用户态准备 RAM 后备范围，KVM 在宿主内核维护第二级映射，处理器完成实际遍历。下文沿同一条 load 比较影子页表和 EPT，再跟踪宿主后备页变化时的映射重建。

源码版本：QEMU 10.2.0、Linux 6.18。

二、GVA、GPA、HVA 与 HPA 的对应关系

设客户机执行 load [0x400120]，页大小为 4 KiB。客户机页表把虚拟页 0x400000 映射到客户机物理页 0x20000，偏移 0x120 保持不变，因此需要访问的客户机物理地址是 0x20120。

名称本例作用
GVA，客户机虚拟地址0x400120程序使用的地址，由客户机页表解释
GPA，客户机物理地址0x20120客户机认为存在的 RAM 或设备地址
HVA，宿主虚拟地址B + 0x20120QEMU 进程访问后备内存的位置
HPA，宿主物理地址0x920120本次数据实际位于的宿主内存位置

QEMU 用内存槽向 KVM 登记一段 GPA 与 HVA 的对应关系。这里假定槽从 GPA 0 开始，映射到 QEMU 的基址 B；对应宿主页基址为 0x920000。KVM 建图时先按槽内偏移找到 HVA，再向 Linux 内存管理取得当前宿主页。另一个虚拟机的同一 GPA 可以落到不同 HPA。隔离依赖宿主控制这份映射和访问权限，客户机不能通过修改自己的页表取得任意宿主页。KVM 地址空间与后备内存

三、从软件合成映射到硬件两级转换

1. 影子页表把两次转换合成一次

传统页表硬件只负责虚拟地址到物理地址的一次转换。虚拟机监控器（VMM）可以读取客户机页表，再结合宿主的页面分配，把本例直接合成为 GVA 0x400000 → HPA 0x920000，形成影子页表供硬件使用。客户机仍维护自己看到的 GVA→GPA 关系，VMM 维护实际执行所用的合成结果。

现在客户机内核把同一虚拟页改为指向 GPA 0x30000，这页由 HPA 0xb60000 承载。客户机完成必要的 TLB 维护后，同一条 load 应读取 HPA 0xb60120。旧影子项仍指向 0x920000，因此 KVM 还要跟踪客户机页表变化，使依赖旧关系的影子项失效或更新，再维护转换缓存。影子页表可以延后或合并部分同步工作，相关状态仍需在重新使用时保持一致。影子页表同步与延后同步

2. EPT/NPT 分开客户机页表与宿主映射

Intel EPT（扩展页表）、AMD NPT（嵌套页表）增加第二级硬件转换。客户机页表仍把 GVA 变为 GPA，KVM 管理的第二级页表把 GPA 变为 HPA。在上面的改映射例子中，若 GPA 0x30000 的 EPT 项已经有效，客户机更新自己的页表并完成 TLB 维护后，硬件就会沿新 GPA 找到 HPA 0xb60000；KVM 无需再维护一份依赖 GVA 的合成结果。

两种方案中，load 的结果都必须来自客户机当前指定的页。区别是维护工作的位置：影子模式需要追踪客户机映射与宿主后备两侧的变化；EPT/NPT 把客户机页表的常规维护留给客户机，KVM 主要维护第二级映射。宿主替换 HPA 时，两种方案仍须撤销旧映射，EPT 没有消除这一责任。

两级转换的新增成本来自硬件遍历：客户机页表本身也在 GPA 空间中，读取每一级表项都要经过 EPT/NPT；最后的数据访问同样需要第二级转换。TLB 保存最终转换，页表遍历缓存复用中间结果，因此一次 load 的实际访存开销取决于缓存命中情况。

这里有两类后续优化：大页让一个转换项覆盖更多地址，减少遍历与缓存压力；KVM 的并行页表管理则减少多个 vCPU 同时建图的锁争用。前者改变映射粒度，后者改变宿主的软件实现。它们都以地址和权限仍然正确为前提，具体条件放到大页与 EPT 专篇展开。

四、一次读取中的建图、访问与映射失效

1. 缺少 EPT 项时的映射建立

回到最初 GVA 0x400120 → GPA 0x20120 的映射。假设客户机页表有效，相关页表页已可访问，只有数据页 GPA 0x20000 的 EPT 项尚缺。硬件转换失败后退出，KVM 从内存槽找到 HVA B + 0x20000，取得宿主页 HPA 0x920000，检查权限并安装 EPT 项。客户机重试同一条 load，最终读取 0x920000 + 0x120。

取得宿主页时，Linux 可能还需分配或调入内存，这属于宿主缺页；客户机自己的页表无效则可能引发客户机 #PF，由客户机内核处理。普通 RAM 的 EPT 建图通常在 KVM 内完成，不必把每次访问交给 QEMU。

2. 宿主页变化与旧映射失效

后续访问可使用有效页表和 TLB。假设宿主将该页移到 HPA 0xa30000，HVA 可以不变，但旧 EPT 项和缓存必须撤销。Linux 通过 MMU notifier 这套内存变更通知机制告知 KVM 受影响的范围，KVM 使旧转换失效，并防止并发缺页把旧物理页重新写回。下一次重建后，同一 load 读取的是 0xa30120，内容随宿主页迁移得到保留。

3. MMIO 访问与脏页跟踪

GPA 若属于设备寄存器，就需要相应设备模型完成访问，不能照 RAM 路径随意分配页面。迁移期间还需记录客户机写过哪些 RAM 页：写保护可以让首次写入进入 KVM 处理，硬件也可提供辅助脏标记；bitmap 或 dirty ring 再把记录交给用户态。记录方式不同，目标都是让迁移器知道哪些内容需要重新发送。

性能现象可用改进代价与边界
TLB 未命中和页表遍历多大页、合适的地址布局碎片、对齐与细粒度写保护可能限制大页

影子页表用软件维护合成关系，EPT/NPT 用额外硬件转换换取更清晰的分工；两者最终都依赖宿主后备页的生命周期。评价时把转换未命中、缺页建图、真实内存访问和脏页跟踪分开，再观察吞吐、尾延迟与内存占用，才能判断优化发生在哪一层。

七、小实验：对照首次触碰与重复访问

在 Linux 客户机里运行下面的单线程程序。它申请 32 MiB 匿名内存，按基础页大小写两遍，并分别统计本进程的 minor fault。第一次写入需要客户机建立匿名页映射；第二遍通常可以复用。程序只调整自己的映射，不需要 root，也不修改系统的大页配置。

将代码保存为 first-touch.c。MADV_NOHUGEPAGE 用于排除本段映射的透明大页合并；系统不支持该建议时，程序报错退出，不把不同粒度的结果混在一起。

#define _GNU_SOURCE
#include <stdio.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <unistd.h>

int main(void)
{
    const size_t bytes = 32UL * 1024 * 1024;
    long page = sysconf(_SC_PAGESIZE);
    struct rusage before = {0}, after = {0};
    long faults[2] = {0};
    if (page <= 0) return 1;
    void *mapping = mmap(NULL, bytes, PROT_READ | PROT_WRITE,
                         MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (mapping == MAP_FAILED) { perror("mmap"); return 1; }
    if (madvise(mapping, bytes, MADV_NOHUGEPAGE) != 0) {
        perror("madvise"); munmap(mapping, bytes); return 1;
    }
    volatile unsigned char *p = mapping;
    for (int pass = 0; pass < 2; pass++) {
        if (getrusage(RUSAGE_SELF, &before) != 0) {
            perror("getrusage"); munmap(mapping, bytes); return 1;
        }
        for (size_t offset = 0; offset < bytes; offset += (size_t)page)
            p[offset] = (unsigned char)(pass + 1);
        if (getrusage(RUSAGE_SELF, &after) != 0) {
            perror("getrusage"); munmap(mapping, bytes); return 1;
        }
        faults[pass] = after.ru_minflt - before.ru_minflt;
    }
    printf("page_bytes=%ld first_minor=%ld second_minor=%ld\n",
           page, faults[0], faults[1]);
    return munmap(mapping, bytes) == 0 ? 0 : 1;
}
cc -std=c11 -O2 -Wall -Wextra -Werror first-touch.c -o first-touch
./first-touch

在 4 KiB 基础页、无明显内存压力的条件下，32 MiB 包含 8192 页，首次写入的 minor fault 应接近这一数量；第二遍通常明显减少。统计覆盖整个进程，少量额外缺页可能来自程序或运行库，不要求恰好得到 8192 和 0。getrusage 的统计口径、透明大页与 madvise。

这两个数只说明客户机进程的缺页情况。一次 Guest #PF 的处理可能伴随多个 GPA 的访问，宿主是否需要补建 EPT/NPT 又取决于既有映射。因此不能从 first_minor 推算 VM-Exit 次数，更不能把第二遍缺页少解释成 TLB 全部命中。需要分析后两者时，要在宿主另采 KVM 事件或硬件计数，并对齐同一运行窗口。

实测：两遍访问的缺页计数

实测日期：2026-11-08。环境为 AMD Ryzen 5 5600G、Windows 11（26300.9818）→ WSL2 → KVM；WSL 内核为 6.18.54.1-microsoft-standard-WSL2，QEMU 为 10.1.50（v10.1.0-2213-g9febfa94b6），客户机内核为 6.18.60-0-virt。

测试机使用 2 个 vCPU、1 GiB 普通匿名 RAM，以最小 initramfs 启动，无磁盘、无网卡、未配置 swap。宿主 RAM 后备在启动时预分配（prealloc=on），balloon 的空闲页报告关闭（free-page-reporting=off）；QMP query-kvm 返回 enabled=true、present=true。本次二级转换使用 AMD NPT；页首的 QEMU 10.2.0 / Linux 6.18 仍是正文源码基线，与这组实测版本分开记录。

宿主已经为这台 VM 预分配了 RAM 后备，Guest 中新进程的匿名页映射仍要按需建立：32 MiB / 4 KiB = 8192，第一遍逐页写入触发缺页，第二遍复用这些映射。这组结果把宿主的后备分配与 Guest 应用的缺页区分开；也说明 mmap 成功后，页面未必已经全部准备好。
