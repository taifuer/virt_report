一、客户机地址空间与宿主内存

内存虚拟化为每台客户机提供独立的物理地址空间，并将它映射到宿主的后备内存。两台虚拟机都可以从物理地址零开始使用内存，而不读写彼此的数据。客户机应用还有自己的虚拟地址，客户机内核通过页表把它们映射到自己认识的物理页；宿主再决定每个客户机物理页实际由哪块宿主内存承载。

内存虚拟化需要同时满足三个条件：客户机页表的含义保持不变，访问被限制在获准的宿主页内，宿主仍能分配、迁移和回收这些页面。本文以普通、可由宿主访问的 RAM 和 x86 KVM 为例，从一次读取推导影子页表与 EPT/NPT 的解决办法。

客户机内核维护自己的页表，QEMU 在宿主用户态准备 RAM 后备范围，KVM 在宿主内核维护第二级映射，处理器完成实际遍历。下文沿同一条 load 比较影子页表和 EPT，再跟踪宿主后备页变化时的映射重建。

三、从软件合成映射到硬件两级转换

1. 影子页表把两次转换合成一次

传统页表硬件只负责虚拟地址到物理地址的一次转换。虚拟机监控器（VMM）可以读取客户机页表，再结合宿主的页面分配，把本例直接合成为 GVA 0x400000 → HPA 0x920000，形成影子页表供硬件使用。客户机仍维护自己看到的 GVA→GPA 关系，VMM 维护实际执行所用的合成结果。

现在客户机内核把同一虚拟页改为指向 GPA 0x30000，这页由 HPA 0xb60000 承载。客户机完成必要的 TLB 维护后，同一条 load 应读取 HPA 0xb60120。旧影子项仍指向 0x920000，因此 KVM 还要跟踪客户机页表变化，使依赖旧关系的影子项失效或更新，再维护转换缓存。影子页表可以延后或合并部分同步工作，相关状态仍需在重新使用时保持一致。影子页表同步与延后同步

2. EPT/NPT 分开客户机页表与宿主映射

Intel EPT（扩展页表）、AMD NPT（嵌套页表）增加第二级硬件转换。客户机页表仍把 GVA 变为 GPA，KVM 管理的第二级页表把 GPA 变为 HPA。在上面的改映射例子中，若 GPA 0x30000 的 EPT 项已经有效，客户机更新自己的页表并完成 TLB 维护后，硬件就会沿新 GPA 找到 HPA 0xb60000；KVM 无需再维护一份依赖 GVA 的合成结果。

两种方案中，load 的结果都必须来自客户机当前指定的页。区别是维护工作的位置：影子模式需要追踪客户机映射与宿主后备两侧的变化；EPT/NPT 把客户机页表的常规维护留给客户机，KVM 主要维护第二级映射。宿主替换 HPA 时，两种方案仍须撤销旧映射，EPT 没有消除这一责任。

两级转换的新增成本来自硬件遍历：客户机页表本身也在 GPA 空间中，读取每一级表项都要经过 EPT/NPT；最后的数据访问同样需要第二级转换。TLB 保存最终转换，页表遍历缓存复用中间结果，因此一次 load 的实际访存开销取决于缓存命中情况。

这里有两类后续优化：大页让一个转换项覆盖更多地址，减少遍历与缓存压力；KVM 的并行页表管理则减少多个 vCPU 同时建图的锁争用。前者改变映射粒度，后者改变宿主的软件实现。它们都以地址和权限仍然正确为前提，具体条件放到大页与 EPT 专篇展开。

四、一次读取中的建图、访问与映射失效

1. 缺少 EPT 项时的映射建立

回到最初 GVA 0x400120 → GPA 0x20120 的映射。假设客户机页表有效，相关页表页已可访问，只有数据页 GPA 0x20000 的 EPT 项尚缺。硬件转换失败后退出，KVM 从内存槽找到 HVA B + 0x20000，取得宿主页 HPA 0x920000，检查权限并安装 EPT 项。客户机重试同一条 load，最终读取 0x920000 + 0x120。

取得宿主页时，Linux 可能还需分配或调入内存，这属于宿主缺页；客户机自己的页表无效则可能引发客户机 #PF，由客户机内核处理。普通 RAM 的 EPT 建图通常在 KVM 内完成，不必把每次访问交给 QEMU。

2. 宿主页变化与旧映射失效

后续访问可使用有效页表和 TLB。假设宿主将该页移到 HPA 0xa30000，HVA 可以不变，但旧 EPT 项和缓存必须撤销。Linux 通过 MMU notifier 这套内存变更通知机制告知 KVM 受影响的范围，KVM 使旧转换失效，并防止并发缺页把旧物理页重新写回。下一次重建后，同一 load 读取的是 0xa30120，内容随宿主页迁移得到保留。

3. MMIO 访问与脏页跟踪

GPA 若属于设备寄存器，就需要相应设备模型完成访问，不能照 RAM 路径随意分配页面。迁移期间还需记录客户机写过哪些 RAM 页：写保护可以让首次写入进入 KVM 处理，硬件也可提供辅助脏标记；bitmap 或 dirty ring 再把记录交给用户态。记录方式不同，目标都是让迁移器知道哪些内容需要重新发送。

    • 普通 HVA 后备 RAM，4 KiB 页；匿名宿主页已换出，相关 EPT 已通过失效机制撤销。
    • Guest 页表页和内核所需页面均驻留，本例只跟踪目标 RAM 数据页。
    • Guest 未启用 KVM 异步缺页协议，本例使用允许等待 I/O 的同步取页路径。
    • 换入成功、无信号和硬件错误；换入后的示例 PFN 为 0x21000，原数据值为 0x12345678。
    1. 访问前 · Guest 用户态

      Guest 地址仍合法，宿主已经将目标后备页换出并撤销相关 EPT。 Guest 页表与宿主页的驻留状态由不同层管理。页面换出不要求 Guest 删除自己的 PTE。

      Linux 6.18 · KVM MMU 地址空间与两级转换
    2. EPT 退出到 KVM · CPU 硬件 → KVM

      读取命中缺失的 EPT 映射，KVM 接手处理 GPA 0x00403080。 此时 Guest 没有收到 #PF。故障地址是第二级映射对应的 GPA，随后才会查找宿主 HVA。

      Linux 6.18 · handle_ept_violation · Linux 6.18 · kvm_tdp_mmu_page_fault
    3. 非等待取页无法完成 · KVM → 宿主内存管理

      KVM 用 HVA 取页，FOLL_NOWAIT 尝试发现页面需要 I/O。 返回 KVM_PFN_ERR_NEEDS_IO 后，KVM 检查能否走异步缺页。本例未启用相应 Guest 协议，继续同步慢路径。

      Linux 6.18 · 后备页需要 I/O 时的同步与异步路径 · Linux 6.18 · HVA、GUP 与后备 PFN
    4. 等待宿主换入 · 宿主内存管理

      KVM 去掉 FOLL_NOWAIT 后再次取页，宿主读取交换后备并等待页面可用。 同一 vCPU 线程仍处于 KVM_RUN 的宿主内核调用中，等待期间可以被调度出去；这种等待不等于返回 QEMU 用户态。其他 vCPU 的运行取决于其自身状态。

      Linux 6.18 · 后备页需要 I/O 时的同步与异步路径 · Linux 6.18 · HVA、GUP 与后备 PFN
    5. 后备页重新驻留 · 宿主内存管理 → KVM

      页面内容恢复，宿主返回当前 PFN 0x21000。 换入后的 PFN 可以不同于换出前的 PFN；本例显示本次返回值。KVM 仍需核对失效条件后才能发布 EPT。

      Linux 6.18 · 后备页需要 I/O 时的同步与异步路径 · Linux 6.18 · kvm_tdp_mmu_page_fault
    6. 恢复 EPT 并重试 · KVM → CPU 硬件

      KVM 建立新的 EPT 叶子，重新进入 Guest。原读取沿 HPA 0x21000080 完成。 成功后 EAX 得到 0x12345678。宿主缺页带来的主要额外成本是取页与等待，Guest 页表没有因此被改写。

    MMIO · QEMU 设备读取

    地址落在 QEMU 模拟设备寄存器。KVM 返回 MMIO 退出，QEMU 填回读值，再次 KVM_RUN 后完成待决指令。

    • Guest 内核读取 32 位 MMIO 寄存器；GVA 0xffffc90070001000 映射到 GPA 0xf0001000。
    • 对应设备由 QEMU 模拟，内核设备不能处理该访问；该区域不作为普通 RAM memslot 映射。
    • 一次 4 B 读取，不跨页、不拆分；设备回调返回 0x12345678。
    • 未涉及直通设备 BAR、内核 LAPIC 或 ioeventfd 门铃写入。
    1. 访问前 · Guest 驱动

      Guest 已映射设备寄存器，准备执行 4 B 读取。 Guest 页表中的地址有效，GPA 落在模拟设备区域。这里没有可供普通 RAM 读取使用的宿主页。

      Linux 6.18 · MMIO 数据与重新进入 KVM_RUN · QEMU 10.2 · KVM_EXIT_MMIO 与 address_space_rw
    2. 退出并识别设备访问 · CPU 硬件 → KVM

      访存引起 EPT 退出，KVM 进入指令模拟路径。 KVM 无法用普通 RAM 映射或内核设备满足该读取，保留尚未完成的指令状态，准备请求用户态设备处理。

      Linux 6.18 · handle_ept_violation · kvm_mmu_page_fault() · emulator_read_write_onepage()
    3. 返回 QEMU · KVM → QEMU

      KVM_RUN 返回 KVM_EXIT_MMIO，并在共享结构中填写地址、长度与方向。 phys_addr=0xf0001000，len=4，is_write=0。KVM_RUN 在这里从宿主内核返回 QEMU 用户态。

    4. 执行设备读回调 · QEMU 设备模型

      QEMU 调用 address_space_rw()，在 MemoryRegion 地址空间中定位设备。 设备模型按寄存器语义返回 0x12345678。真实设备可能有读清除等副作用，本示例使用固定值寄存器。

    5. 填回 MMIO 读值 · QEMU

      共享区 data[0..3] 填入小端字节 78 56 34 12。 Guest EAX 此时仍未更新，待决读指令也尚未完成。设备回调结束与客户机指令完成处在两个不同阶段。

      QEMU 10.2 · KVM_EXIT_MMIO 与 address_space_rw · Linux 6.18 · MMIO 数据与重新进入 KVM_RUN
    6. 重新进入并完成待决读 · QEMU → KVM → Guest

      QEMU 再次调用 KVM_RUN，KVM 消费返回字节，完成指令模拟后恢复 Guest。 EAX 现在成为 0x12345678，执行位置前进。演示合并了内核完成待决操作与后续 VM-entry；KVM 会先完成待决操作，再处理可能阻止 Guest 继续运行的信号等事件。

    脏页记录 · EPT 写保护

    这是已有 EPT 映射的权限处理，不是缺少后备页。Guest PTE 允许写入，KVM 为脏页跟踪撤掉 EPT 写权限；本例首次写入退出后恢复权限、记录脏页并重试。

    • 普通 RAM，4 KiB EPT 叶子，Guest 用户态写入 0x12345678。
    • memslot 启用 KVM_MEM_LOG_DIRTY_PAGES，使用位图；未启用 Dirty Ring 或硬件 PML。
    • 本轮已对目标 EPT 叶子写保护并完成所需失效，Guest PTE、宿主页及 KVM 软件记录都允许最终恢复写权限。
    • 固定为成功的 fast_page_fault 修复路径，无并发 SPTE 改动、页跟踪或其他写保护原因。
    1. 访问前 · Guest 用户态

      客户机允许写入该页，EPT 暂时禁止写入，以捕获本轮第一次写访问。 槽从 GFN 0x400 起始，因此 GFN 0x403 对应脏位图中的槽内页号 3。

    2. 写权限检查触发退出 · CPU 硬件 → KVM

      Guest PTE 的写权限通过，但 EPT W=0，写入在修改数据前触发 EPT violation。 这次写保护由 KVM 为脏页记录设置；不会因此向 Guest 抛出权限 #PF。目标内存仍是 0x00000000。

      Linux 6.18 · handle_ept_violation · Linux 6.18 · 写保护快速修复与脏页记录

      KVM 确认映射允许恢复写权限，原子更新 SPTE。 本例沿 fast_pf_fix_direct_spte() 的顺序展示：先成功更新 SPTE，随后记录脏页，再返回 Guest。这里只展示一个 vCPU 的成功路径，不将图中分步视为可供其他线程观察的同步屏障。

      mark_page_dirty_in_slot() 将槽内页号 3 标记为脏。 该记录按页表示需要重新同步的数据范围。它可以保守地早于实际写入完成；这里仍未执行 Guest 的原写指令。

      Linux 6.18 · 写保护快速修复与脏页记录 · Linux 6.18 · mark_page_dirty_in_slot

      重新进入 Guest 后，同一条写指令通过两级权限检查，将 0x12345678 写入 RAM。 此次处理不返回 QEMU。本轮内该页后续写入通常无需再次因这项写保护退出；开始新一轮记录时还需按脏页 API 的规则重新建立跟踪条件。

    KVM 内核 LAPIC 读取

    Guest 读取 xAPIC ID 寄存器，访问退出到 KVM 后由内核 LAPIC 返回结果，不交给 QEMU。

    • x86-64 / Intel VMX，Linux 6.18 与 QEMU 10.2.0；仅跟踪所选设备访问
    • 硬件 VM-exit 与 KVM_RUN 返回用户态是两个不同边界；没有其他异步退出
    • 内核 LAPIC、xAPIC MMIO 模式；关闭 APIC-access / APIC-register virtualization 等相关硬件加速
    • Guest LAPIC 基址 0xfee00000，ID 寄存器偏移 0x20；示例 APIC ID = 1，32 位读取值为 0x01000000
    1. 读取前 · Guest 内核

      驱动即将读取 LAPIC ID。 QEMU 只在准备阶段配置虚拟机；本次寄存器读由内核设备处理。

      apic_mmio_read()
    2. 设备访问退出到 KVM · 处理器 → KVM

      所选配置下，该 MMIO 访问使处理器退出 Guest。 这是硬件 VM-exit，不是 KVM_RUN 返回 QEMU。

      Linux 6.18 · handle_ept_violation · vcpu_mmio_read()
    3. 优先检查内核 LAPIC · KVM · vcpu_mmio_read

      KVM 先把地址交给内核 LAPIC，apic_mmio_read 命中此地址。 内核处理成功就不再为这部分访问创建 KVM_EXIT_MMIO。

      vcpu_mmio_read() · apic_mmio_read()
    4. 读取虚拟 APIC ID · KVM · apic_mmio_read

      内核 LAPIC 返回 0x01000000。 返回值先交给指令模拟器，Guest 原目标寄存器随后才更新。

      apic_mmio_read() · emulator_read_write_onepage()
    5. 完成读指令并继续 Guest · KVM → Guest

      模拟器写回目标寄存器并推进原指令，随后恢复客户机。 整个访问没有把 KVM_RUN 交回 QEMU 用户态；不需要一次额外用户态读回调。

      emulator_read_write_onepage() · vcpu_mmio_read()
    ioeventfd 队列门铃写入

    Guest 发布队列后写门铃，KVM 匹配 ioeventfd 并发出通知；vCPU 不经通用用户态 MMIO 返回。

    • x86-64 / Intel VMX，Linux 6.18 与 QEMU 10.2.0；仅跟踪所选设备访问
    • 硬件 VM-exit 与 KVM_RUN 返回用户态是两个不同边界；没有其他异步退出

      共享队列已经发布，驱动准备写队列号 0。 发布数据和门铃通知是两个动作；先发布，再判断是否需要 kick。

    VFIO BAR 已建立直接映射

    CPU 经 Guest 页表与 EPT，把 Guest BAR GPA 转换为宿主 MMIO HPA，再由 PCIe 访问设备。HPA 是设备窗口地址，不是先访问一份宿主 RAM；本例稳态读取不退出。

    • x86-64 / Intel VMX，Linux 6.18 与 QEMU 10.2.0；4 KiB 页，只跟踪一次 4 B CPU 读取。
    • 固定可 mmap 的 BAR0 区间，VFIO 映射、KVM memslot 与有效 EPT 均已建立；本例不发生额外 VM-exit。
    • Guest BAR0 基址 GPA 0xf0000000，宿主 BAR0 的 CPU 物理资源基址 HPA 0xd0000000；访问 offset 0x1000，得到 GPA 0xf0001000 / HPA 0xd0001000。
    • 本例固定宿主桥的 CPU 物理地址与 PCI 总线地址恒等；其他平台可能由宿主桥换算。BAR offset 是区域内偏移，不是额外一级页表。
    • 不包括 MSI-X 表、需模拟寄存器、首次建图故障、权限变更、设备复位和映射撤销；内存类型与顺序满足设备要求。
    • 本例观察 CPU 对设备 BAR 的读取，不是设备 DMA；设备发起的 IOMMU 翻译不串入这条 CPU 路径。普通 Guest RAM 仍映射宿主 RAM，不因启用 VFIO 就指向 BAR。
    • QEMU 的 HVA 仅参与 mmap / memslot 配置与 KVM 后备解析；本次 CPU 稳态转换不逐次查询 HVA。所有地址和读值为教学示例。

      驱动已识别并映射 Guest BAR0，准备读取 offset 0x1000。 QEMU/VFIO 事先建立宿主映射，KVM 已配置 GPA 0xf0001000 → HPA 0xd0001000。Guest 驱动知道自己访问设备资源，但不需要知道宿主 BAR 的地址。

    共享内存 BAR · ivshmem

    ivshmem BAR2 暴露宿主共享 RAM。Guest 经页表与 EPT 直接读同一后备页；没有物理 PCIe 设备或 VFIO。BAR 是客户机资源窗口的形式，不代表落点一定是设备寄存器。

    • x86-64 / Intel VMX，QEMU 10.2.0、Linux 6.18；固定 ivshmem-plain，memdev 指向 share=on 的宿主共享内存后备。
    • 只读 BAR2 中 offset 0x1000 的 4 B 数据；不访问 BAR0 控制寄存器，不使用 ivshmem-doorbell、MSI-X、通知或任何设备 DMA。
    • Guest 驱动已枚举并映射 BAR2；GVA 0xffffc900f0001000 → GPA 0xf0001000。BAR2 的 Guest 基址为 0xf0000000。
    • 对应宿主共享页已驻留，示例 HPA 0x21001000，EPT 有效且允许读。该页的示意值已预先写为 0x12345678；本例没有并发写入。
    • QEMU 已将共享后备的 MemoryRegion 注册为 BAR2，并由 MemoryListener 发布 memslot。HVA 只用于准备与后备解析，不是硬件逐次访问的一层。
    • 同一个共享对象可以被宿主或其他 VM 映射，但不同地址空间的虚拟地址和 Guest BAR 基址无需相同；本例不展开多方同步协议。
    • 与 VFIO 场景复用 Guest 示意地址便于对照，二者是不同配置，不在同一地址空间重叠。这里的 HPA 指向共享 RAM 页，不是物理设备 BAR，也不保证整个 BAR2 在宿主物理内存中连续。

      驱动准备读取 BAR2 + 0x1000，所访问的共享页已驻留。 QEMU 用宿主共享内存对象作为 BAR2 后备，而不是模拟一次寄存器读取。BAR0 的控制接口属于另一片区域，不能把整个设备都说成无退出。

      Guest 页表给出 BAR2 GPA 0xf0001000；EPT 将它映射到共享页 HPA 0x21001000。 Guest 仍把这片区域视为 PCI BAR 资源，但实际落点是宿主 RAM，不是物理设备寄存器。相同的 Guest 示意地址在不同配置下可以有不同后备，硬件不会根据 MOV 指令猜测用途。

    3. 直接读取共享后备页 · CPU · 宿主 RAM

      CPU 读取 HPA 0x21001000 对应的共享内存数据。 没有经过物理 PCIe 设备、VFIO 或逐次 QEMU 设备回调；也没有额外复制到一份 Guest 专用缓冲区。地址转换与 CPU 数据缓存是不同层次，本例不模拟缓存时延。

    4. 返回共享页中的读值 · 共享 RAM → CPU

      CPU 取得共享页中预先存在的 0x12345678。 数据来自共享后备页，不是 QEMU 合成的寄存器响应。跨进程或跨 VM 使用共享内存时仍需同步协议，本例固定没有并发写入。

      CPU 更新 EAX 并继续执行；本次没有 VM-exit，KVM_RUN 没有返回。 这提供了非 VFIO 的直接映射对照：BAR2 背后是共享 RAM。普通 Guest RAM、共享 BAR 与物理 MMIO 可以使用相似的 CPU 转换链，但资源语义和最终落点不同。

    六、地址空间与访问分派

    1. Guest 资源语义与硬件地址转换

    Guest 内核从固件内存图获知 RAM 范围，通过 PCI 枚举和 BAR 资源获知设备窗口。驱动选择适当的映射、缓存属性与访问接口，例如 ioremap()、readl() / writel()；它通常知道自己在访问 RAM、设备寄存器还是设备暴露的内存，但无需知道宿主 HPA。普通应用也不必了解这些后备细节。Linux 设备访问接口

    在本例 x86 环境中，RAM 与 MMIO 都由普通访存指令触达。CPU 按地址转换、权限和内存属性执行：Guest 页表得到 GPA，EPT 得到 HPA，物理地址译码再选择内存或设备窗口。缓存属性约束访问行为，资源类型由映射与平台地址布局共同确定。

    2. QEMU 配置地址空间，KVM 处理退出

    QEMU 用 MemoryRegion 建立客户机物理地址布局：普通 RAM、共享后备和需要设备回调的区间具有不同属性。MemoryListener 将可映射的 GPA 区间及 HVA 后备注册为 KVM memslot。VFIO 可映射设备区域也可使用 RAM-device 接口，因此“存在 memslot”不等于“物理落点必然是普通 RAM”。memslot 注册、RAM-device 后备接口

    EPT 缺项或权限问题使处理器退出到 KVM。普通 RAM 缺项由 KVM 取得后备 PFN 并补建 EPT，必要时由宿主内存管理先提供页面。需要模拟的访问先尝试内核 LAPIC / MMIO 总线；不能在内核完成的部分通过 KVM_EXIT_MMIO 返回 QEMU，由地址空间分派找到设备回调。EPT 由 KVM 管理，QEMU 负责相应设备操作；未分配的地址空洞也可能没有可处理的设备。EPT 建图、模拟访问分派、用户态 MMIO 请求

    3. HPA 可以指向 RAM，也可以指向设备窗口

    访问对象Guest GPAEPT 输出的 HPA实际落点

    十、小实验：对照首次触碰与重复访问

    在 Linux 客户机里运行下面的单线程程序。它申请 32 MiB 匿名内存，按基础页大小写两遍，并分别统计本进程的 minor fault。第一次写入需要客户机建立匿名页映射；第二遍通常可以复用。程序只调整自己的映射，不需要 root，也不修改系统的大页配置。

    将代码保存为 first-touch.c。MADV_NOHUGEPAGE 用于排除本段映射的透明大页合并；系统不支持该建议时，程序报错退出，不把不同粒度的结果混在一起。

    #define _GNU_SOURCE
#include <stdio.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <unistd.h>

int main(void)
{
    const size_t bytes = 32UL * 1024 * 1024;
    long page = sysconf(_SC_PAGESIZE);
    struct rusage before = {0}, after = {0};
    long faults[2] = {0};
    if (page <= 0) return 1;
    void *mapping = mmap(NULL, bytes, PROT_READ | PROT_WRITE,
                         MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (mapping == MAP_FAILED) { perror("mmap"); return 1; }
    if (madvise(mapping, bytes, MADV_NOHUGEPAGE) != 0) {
        perror("madvise"); munmap(mapping, bytes); return 1;
    }
    volatile unsigned char *p = mapping;
    for (int pass = 0; pass < 2; pass++) {
        if (getrusage(RUSAGE_SELF, &before) != 0) {
            perror("getrusage"); munmap(mapping, bytes); return 1;
        }
        for (size_t offset = 0; offset < bytes; offset += (size_t)page)
            p[offset] = (unsigned char)(pass + 1);
        if (getrusage(RUSAGE_SELF, &after) != 0) {
            perror("getrusage"); munmap(mapping, bytes); return 1;
        }
        faults[pass] = after.ru_minflt - before.ru_minflt;
    }
    printf("page_bytes=%ld first_minor=%ld second_minor=%ld\n",
           page, faults[0], faults[1]);
    return munmap(mapping, bytes) == 0 ? 0 : 1;
}
    cc -std=c11 -O2 -Wall -Wextra -Werror first-touch.c -o first-touch
./first-touch

    在 4 KiB 基础页、无明显内存压力的条件下，32 MiB 包含 8192 页，首次写入的 minor fault 应接近这一数量；第二遍通常明显减少。统计覆盖整个进程，少量额外缺页可能来自程序或运行库，不要求恰好得到 8192 和 0。getrusage 的统计口径、透明大页与 madvise。

    这两个数只说明客户机进程的缺页情况。一次 Guest #PF 的处理可能伴随多个 GPA 的访问，宿主是否需要补建 EPT/NPT 又取决于既有映射。因此不能从 first_minor 推算 VM-Exit 次数，更不能把第二遍缺页少解释成 TLB 全部命中。需要分析后两者时，要在宿主另采 KVM 事件或硬件计数，并对齐同一运行窗口。
