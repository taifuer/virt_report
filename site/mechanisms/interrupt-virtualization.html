一、中断的作用与虚拟化边界

中断用于将设备完成、定时器到期等事件通知处理器，使操作系统及时执行相应的处理程序。中断虚拟化为每台客户机维护独立的中断控制器状态、路由和处理入口，并在客户机允许接收时交付事件。以网卡收包为例，报文先进入接收缓冲区，通知路径再促使客户机驱动检查队列；数据传输与中断交付是相互关联的两个过程。

1. 轮询与中断：主动检查，或等待通知

一种办法是让 CPU 反复检查接收队列，这叫轮询。检查足够频繁时，响应可以很快；没有包到达时，也要消耗 CPU 时间。另一种办法由设备在有工作时发出中断，CPU 平时继续计算或进入空闲，收到通知后转入操作系统的处理入口。代价是保存与恢复执行现场，以及处理通知本身的开销。高流量网络常把两者结合：中断启动处理，再通过轮询批量收包。

2. 一次中断需要完成三件事

设备先保存数据和完成状态，再发出通知；中断系统决定通知哪个 CPU、使用哪个入口；CPU 在允许接受中断时保存必要的执行现场，经中断描述符表（IDT）进入内核，驱动再读取队列或设备状态。处理结束后，系统恢复先前的执行。网络包保存在缓冲区中，中断携带的是处理入口等控制信息。

本文围绕 x86 的一次 virtio-net 收包展开：后端填好缓冲区，通知指定 vCPU，客户机驱动读取结果。先建立这条完整路径，再解释中断控制器、内核注入与硬件辅助分别改善了哪一段。

源码版本：QEMU 10.2.0、Linux 6.18。

二、一次收包的数据路径与通知路径

设客户机已给接收队列 0 提供空缓冲区，后端收到一个 1500 字节以太网帧。客户机把这个队列的通知配置到 vCPU 1，对应中断向量 0x51；向量是客户机查找中断处理入口的编号。处理分为四步：

  1. 保存结果。后端把网络头和帧写入客户机缓冲区，再发布 used 完成记录。驱动今后据此找到数据与实际长度。
  2. 提交通知。通知条件满足时，设备按配置发出中断消息。多个完成可以合并为一次通知，帧内容仍保存在内存里。
  3. 等待并交付。虚拟中断控制器记录待处理向量。目标 vCPU 获得执行机会、客户机允许接收时，处理器才转入客户机的中断入口。
  4. 消费数据。客户机驱动检查队列，安排 NAPI 批量处理，把帧交给网络栈，并补充新的接收缓冲区。

从后端写完数据到客户机消费数据，还可能经历通知合并、客户机屏蔽、宿主调度和驱动轮询等等待。下面沿同一个帧，分别说明路由、等待状态与减少交接成本的方案。

三、从中断线到消息：PIC、APIC 与 MSI-X

1. PIC：集中处理设备的中断请求

早期 PC 使用 8259 PIC（可编程中断控制器）汇集设备的中断线，记录请求、处理屏蔽和优先级，再通知 CPU。单片有 8 个输入，传统 PC 用两片级联得到 15 个可供外部使用的输入。设备增加、多个设备共享中断线时，CPU 还要询问相关设备，才能确定谁需要处理；固定的输入与目标也难以满足多处理器分工。

2. APIC：把路由与每个 CPU 的接收状态分开

APIC 把工作拆开：I/O APIC 汇集外部中断线，并按路由表选择目标；每个逻辑 CPU 的 Local APIC（LAPIC）负责本地的待处理中断、优先级、定时器和处理器间中断。这样，操作系统可以把设备工作分配到不同 CPU。

在物理机器上，I/O APIC 属于平台的中断路由设施，LAPIC 则与逻辑 CPU 关联。例如启用全部线程的 16 核、32 线程 x86 服务器有 32 个逻辑 CPU，各自具有 LAPIC 状态。虚拟机看到的是自己的拓扑：一台 4 vCPU 的客户机有 4 份虚拟 LAPIC 状态，宿主调度这些 vCPU 时维护其归属。

其中两个编号尤其重要：APIC ID 选择目标 CPU，中断向量选择该 CPU 的中断入口。例如“发给 APIC ID 1，向量 0x51”，表示让目标 CPU 按 IDT 中的 0x51 号入口处理。操作系统的 IRQ 号、设备队列号和向量属于不同编号空间，由配置关联起来。

3. MSI/MSI-X：设备用消息表达通知

传统 PCI INTx 中断线可能被多个设备共用。MSI 改用设备向特定地址发出一次写事务，地址与数据编码中断目的地和向量。MSI-X 进一步提供可独立配置地址、数据和屏蔽状态的表项，方便把不同队列分配给不同 CPU。消息最终仍交给目标 LAPIC 接收和排队；这条路径不需要经过 I/O APIC 的引脚路由。Linux MSI 文档

MSI-X 改善了多队列分工，却没有消除中断处理成本。向量数量有限，队列也可能共用一个表项；设备每完成一个包就发一次中断，在高吞吐场景仍可能让 CPU 忙于通知，所以还需要合并和批量处理。

四、QEMU/KVM 的虚拟中断状态与交付

1. 每台虚拟机独立的控制器状态

客户机同样会配置 APIC、屏蔽某些中断、设置优先级，并在自己的 IDT 注册处理入口。宿主必须保存每台虚拟机的这些状态，保证网卡 A 的通知只进入指定虚拟机。同时，vCPU 是宿主调度的执行线程，通知到达时它未必正在占用物理 CPU。

软件模拟可以在 QEMU 中保存 PIC、I/O APIC 和 LAPIC 的寄存器及待处理位。设备产生事件后，模拟控制器选择向量，再由 CPU 模拟或虚拟化执行路径交给客户机。这种方式便于兼容不同机器，但客户机访问控制器、产生通知和确认中断都可能引入软件处理。

2. 把高频控制器逻辑移入 KVM

KVM 的 in-kernel irqchip 把虚拟中断控制器放进内核。客户机已经在 KVM 中执行，中断状态检查和许多控制器访问可以直接在内核完成，减少返回 QEMU 的往返。设备模型仍可能在 QEMU 中，设备事件仍需要送达 KVM。

QEMU 在宿主用户态模拟设备，KVM 在宿主内核维护对应的虚拟中断状态。x86 的两种内核 irqchip 配置将控制器分配如下：

kernel-irqchip 配置PIC 与 I/O APIC每 vCPU 的 LAPIC
on：完整内核 irqchipKVM，宿主内核KVM，宿主内核；可结合硬件辅助
split：split irqchipQEMU，宿主用户态KVM，宿主内核；可结合硬件辅助

split 把传统引脚控制器留在用户态，缩小内核负责的控制器范围，代价是相应引脚路径需要用户态参与。两种配置都保留内核 LAPIC。QEMU 8.0 已移除带 LAPIC 的 KVM 客户机使用用户态 LAPIC 的模式，前文的完整软件控制器路径用于说明模拟原理与历史演进。KVM irqchip 接口、QEMU 的接口演变

回到向量 0x51：虚拟 LAPIC 先记录“已有请求等待”，满足屏蔽与优先级条件后再转入“正在服务”。软件注入路径安排下一次进入客户机时交付该向量；客户机通过自己的 IDT 找到处理入口。IRR、ISR 等位图分别保存这些状态，具体字段与转换留在中断注入专篇中展开。

客户机发出的 EOI（中断结束应答）结束 APIC 层面的服务状态。驱动消费报文是另一项工作，Linux 还可以把它交给 NAPI 后续轮询。因此 EOI 不代表这个 1500 字节帧已经交给网络栈，used 也不会因 EOI 被自动回收。

五、irqfd、APICv 与直通中断的优化层次

1. irqfd：把后端通知直接接到 KVM

如果后端已经完成收包，却需要先唤醒 QEMU，再由 QEMU 调用注入接口，通知会多一次用户态中转。irqfd 允许 QEMU 事先把一个 eventfd 与 KVM 中断路由绑定。后端触发 eventfd 后，KVM 可以直接按路由投递中断；设置和更新路由仍由管理路径完成。

本例仍向 vCPU 1 交付 0x51：后端触发已绑定的 eventfd，KVM 按预先配置的路由处理。报文与完成记录保存在共享内存中，eventfd 只传递通知。相反方向的 ioeventfd 则连接客户机的设备通知写入与后端唤醒：

接口通知方向减少的中转
ioeventfd客户机写设备通知地址 → KVM → 后端 eventfd这次通知写入可由 KVM 处理，无需返回 QEMU 的 vCPU 线程做设备访问分派
irqfd后端 eventfd → KVM 路由 → 客户机中断完成事件无需先唤醒用户态监听者，再调用中断注入接口

ioeventfd 路径仍可能产生硬件 VM Exit，只是 KVM 可以在内核完成匹配和通知；irqfd 的交付同样受客户机中断状态与 vCPU 调度限制。两者在同一设备上分别服务于请求与完成方向。KVM eventfd 实现

2. APICv / AVIC：减少控制器访问与虚拟中断交付的退出

把控制器移入内核后，部分 APIC 寄存器访问和虚拟中断交付仍需退出客户机再由软件处理。Intel APICv 用虚拟 APIC 状态与执行控制，让硬件接管部分访问、优先级判断和中断交付；AMD AVIC 也沿硬件辅助方向降低开销，但使用不同的数据结构和通知机制。

以 Intel posted interrupt 为例，KVM 可以先把向量记入 Posted Interrupt Descriptor 的 PIR 位图，再按需发送通知。目标 vCPU 正在合适的运行状态时，处理器可同步待处理向量并向客户机交付，避免为这段交付专门退出。客户机的屏蔽和优先级规则仍然有效。irqfd 的投递也可以进入这条路径，因此 irqfd 与 APICv 可以配合使用。KVM 的 posted 与软件回退路径

3. 直通设备的 interrupt posting：再减少宿主软件转发

对于直通设备，CPU 已能辅助接收虚拟中断，但物理设备的通知仍可能先由宿主中断处理再转发。支持 Intel VT-d interrupt posting 的硬件可把设备中断经中断重映射单元直接写入目标 vCPU 的 posted 描述符，在符合条件时省去这段宿主软件转发。

这需要设备分配、IOMMU、CPU 和内核配置共同支持。vCPU 阻塞时仍需宿主唤醒线程；vCPU 被抢占时要保存待处理状态，等待重新调度。硬件能够减少投递开销，不能替宿主调度器分配 CPU 时间。AMD 的 AVIC/中断重映射有自己的实现，不能套用 Intel 描述符字段。阻塞与调度处理

六、中断机制的演进与实现取舍

这段演进有三条相互配合的线：设备从中断线转向消息；虚拟控制器从用户态移入内核；高频访问与交付逐步获得硬件辅助。下表按这些变化的形成顺序梳理，今天的系统中仍可能同时存在多条路径。

阶段原有问题与改进仍需承担的工作
PIC → APIC / I/O APIC从集中、有限的中断输入，发展到多 CPU 路由与每 CPU 状态管理引脚分配、路由配置、优先级与应答
PCI INTx → MSI / MSI-X消息与独立表项改善共享中断辨源和多队列分工向量资源、亲和性与通知频率
QEMU 软件控制器 → KVM 内核 irqchip减少控制器处理时的用户态往返内核中的模拟、事件检查及可能的 VM Exit
irqfd（2009 年提出）把 eventfd 后端通知连接到 KVM 路由，省去用户态注入中转eventfd 与路由生命周期、屏蔽同步
APICv / AVIC硬件辅助 APIC 操作与虚拟中断交付，减少部分退出硬件能力、不能加速的操作与回退处理
IOMMU interrupt posting把设备中断直接送到虚拟中断状态，减少直通设备的宿主软件转发平台能力、vCPU 调度迁移、阻塞唤醒与隔离

irqfd 的原始提案说明了 eventfd 连接中断的设计。后来增加的 APICv/AVIC 并没有使 irqfd 失去作用：前者着重减少控制器与 CPU 交付的开销，后者把后端事件接入 KVM。

还有一条客户机与宿主协作的路线：PV EOI 用共享应答状态减少部分 EOI 写入造成的退出；PV IPI 用半虚拟化调用向一组 vCPU 发送处理器间通知，减少逐个写 APIC 的开销。这些方案需要客户机配合。比较方案时，应明确其减少的访问、退出或转发步骤，以及硬件和客户机支持条件。

七、中断配置、计数与延迟观察

可以先在客户机检查网卡采用的中断方式，再观察相应处理次数。下面的 0000:00:03.0 是示例 PCI 地址，应替换为 lspci -nn 中实际网卡的地址；读取完整配置空间可能需要管理员权限。

# 在客户机执行，只查询状态
lspci -nn
lspci -vv -s 0000:00:03.0
cat /proc/interrupts

MSI-X: Enable+ 表示客户机已启用该设备的 MSI-X。收包前后对照 /proc/interrupts 中网卡相关行，可以看到客户机各 CPU 的中断处理计数变化。多个包可以共用一次通知，后续还可能由 NAPI 轮询处理，因此这些计数既不等于报文数量，也不能证明宿主启用了 irqfd 或 APICv。宿主的 /proc/interrupts 则反映宿主自身的中断处理，须与客户机视图分开。

报文到达后仍长时间未被客户机处理，可以按顺序检查以下阶段：

  1. 结果发布。查看缓冲区、used 索引和驱动消费位置。后端尚未完成时，优化中断注入没有帮助。
  2. 通知产生与路由。检查通知抑制、MSI-X 屏蔽与 pending、目标 CPU 和向量，区分没有发出与已经等待。
  3. 客户机接受与执行。区分中断屏蔽、优先级等待、vCPU 阻塞和宿主 CPU 竞争。投递变快不会自动消除调度延迟。
  4. 驱动消费。中断处理可能只启动 NAPI，后续批量大小、网络栈与应用调度继续影响尾延迟。

中断优化的目标是以合理的 CPU 成本及时处理工作。降低中断次数可能提高吞吐，也可能让低负载报文等得更久；增加轮询可缩短等待，却占用 CPU。比较时同时记录吞吐、尾延迟、每次通知的处理量和 CPU 占用，才能判断优化是否对实际负载有效。
