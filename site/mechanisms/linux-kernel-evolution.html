一、内核的位置与基本分工

同一台机器可以一边编译程序，一边保存文件、接收网络请求。CPU 和内存是有限的，磁盘和网卡又按自己的节奏工作。Linux 内核负责把这些资源组织成应用可使用的进程、地址空间、文件和 socket：决定谁获得 CPU，维护地址与权限，把 I/O 交给设备，并在结果就绪时让等待者继续。

Linux 内核与 Shell、C 库、systemd 等用户空间软件共同组成发行版。应用通常通过库封装的系统调用请求内核服务，普通计算和已映射内存访问则由处理器直接执行。

系统调用切换执行权限：线程执行 read 时，由同一线程进入内核并使用自己的内核栈；等待或抢占可能引发任务切换。设备中断处理、内核工作线程也是执行内核代码的方式。

Linux 采用单体内核结构：调度、内存、文件系统和大量驱动在内核权限下协作，可直接调用彼此的接口。可加载模块方便按需装载和维护，模块与其余内核代码共享权限和地址空间，模块故障也可能影响整个系统。

源码版本：Linux 6.18。

二、从早期 PC 到通用内核

1991 年的 Linux 0.01 面向 i386 AT 机器。Linus 的原始发布说明列出有限的磁盘、屏幕、键盘和串口支持，部分系统调用还未实现，主要用于阅读和实验。随着机器、设备和工作负载增多，内核逐步完善功能，并调整数据结构以应对并发、规模和可靠性需求。

阶段机器与需求的变化对内核设计的影响
1991—1994：从 0.01 到 1.0从少量 PC 上的实验走向可用系统逐步完善进程、虚拟内存、文件系统、网络和驱动支持；稳定的应用接口开始承载越来越多软件
1996：Linux 2.0 与 SMP一台机器上不止一个处理器，需要同时执行多个任务共享内核数据必须正确同步；“可以在多个 CPU 上运行”不等于共享路径已经能线性扩展
2003 起：2.6 系列服务器、桌面与嵌入式负载并存，多核和大内存逐渐普及每 CPU 运行队列、内核可抢占性、细粒度同步和 NUMA 管理持续发展；同一系列内也会替换重要算法
此后的持续演进更多核、更快设备、虚拟化与多租户共用机器多队列 I/O、批处理、资源控制与虚拟化进入核心路径；优化重点从单项操作延迟扩展到并行、局部性与尾延迟

1.0、2.0、2.6.0 的时间可核对 kernel.org 的 1994 年归档、1996 年归档和2003 年起的归档。2.0 源码包内的 Documentation/SMP.txt 已说明多处理器支持，也列出调度与中断分配等待改进项；多核扩展能力在后续版本中继续完善。

从一把共享锁到分散状态

单 CPU 上，只要处理好中断和任务切换，共享结构相对容易推理。到了 SMP，两颗 CPU 可以同时修改同一条队列；一把大锁容易保证互斥，却也让其他 CPU 排队。缩小锁的保护范围、按 CPU 或队列拆分状态可以减少争用，但又需要处理负载不均、跨 CPU 唤醒和状态汇总。新增的复杂度，是换取并行能力的成本。

调度器的每 CPU 运行队列、块层与网卡的多队列、内存分配器的每 CPU 缓存，都通过拆分状态减少共享路径上的争用。跨队列操作和全局状态仍需同步。

三、多核与高速设备带来的改变

1. CPU：从挑选任务到公平与响应

早期扫描任务的办法容易理解，任务多了却会增加选择工作。2002 年的 O(1) 设计利用每 CPU 优先级数组减少这类开销；Linux 2.6.23 的 CFS 用权重归一化的运行时间衡量服务份额；Linux 6.6 起的 EEVDF 再把“有没有资格获得服务”与“谁的虚拟截止时间更早”分开。目标从来不只是跑得多：交互任务希望早点响应，长期运行任务希望得到公平份额，频繁切换又会消耗 CPU。算法和数值例子见公平调度与资源约束。

2. 内存：容量变大后，距离与管理成本也变重要

虚拟地址让程序不必直接管理物理页，按需分页和 COW 把分配、复制推迟到需要时。多核大机器中，NUMA 使不同内存位置的访问代价不同；大量映射与页面也增加查找、加锁和回收成本。Maple Tree 管理地址区间，folio 调整页面管理粒度，MGLRU 改善回收时的冷热判断。详见地址空间、缺页与页面回收。

3. I/O：设备越快，软件交接越显眼

机械盘的寻道很贵，调整请求顺序可能省下大量等待；SSD/NVMe 减少这部分成本后，队列锁、跨核访问和提交开销更容易成为瓶颈。blk-mq 把软件提交与硬件队列关联，允许多核并行推进。网络则面对小包带来的高事件率，NAPI 用“通知启动、按预算批量处理”摊薄每包开销。二者共同引出的取舍是：批量越大，平均开销可能越低，但某个短请求也可能等待更久。

io_uring 用共享 SQ/CQ 交接应用请求与结果，具体操作仍交给文件系统、块层等子系统执行。原始实现在 Linux 5.1 源码可见。异步提交允许应用继续其他工作，相关缓冲区仍须按接口约定保持有效。

四、容器、虚拟机与资源管理

多个工作负载共用机器时，需要隔离资源视图并控制用量。namespace 隔离 PID、挂载点和网络等资源视图，cgroup 控制器负责资源记账、分配和限制。容器还组合 capability、seccomp 等机制限制权限与系统调用；隔离效果取决于具体配置和威胁模型。

容器应用的系统调用进入宿主内核，Guest 应用的系统调用进入自己的 Guest 内核。Guest 内核使用 vCPU、Guest 物理地址和虚拟设备。KVM 接入硬件虚拟化，QEMU 组装机器并提供设备模型，宿主调度器给 vCPU 线程分配 CPU。

Linux 2.6.20 的 KVM 配置已通过 /dev/kvm 暴露硬件虚拟化能力；2.6.24 的 cgroups 文档解释了按资源需求组织任务的设计。两者可以组合使用：QEMU 进程能受宿主 cgroup 限制，Guest 内部也可以运行容器。

例如 Guest 应用等待虚拟磁盘读取，可能既有 Guest 设备队列等待，也有宿主存储排队；完成后 Guest 任务虽然可运行，vCPU 线程仍可能没拿到物理 CPU。排查时必须标明自己观察的是哪一层，不能把 Guest 的 CPU 利用率直接当成宿主调度结果。继续对照虚拟化基础与KVM vCPU 执行。

五、一次文件读取串起五个子系统

以本地普通文件的 4 KiB 缓存读取为例，假设元数据已就绪、数据未命中页缓存，且本次仅提交所需区间的设备读。数据处理与线程等待按下列顺序衔接。

数据沿 I/O 路径走，线程沿调度状态走

文件描述符 fd 是进程文件表中的索引，表项引用 struct file，后者保存打开方式、文件偏移和操作接口，并关联 inode 等文件对象。普通文件的页缓存按文件对象与偏移组织，多次打开同一文件可以访问同一份缓存；各次打开的文件偏移却可以独立。任务通过这些引用进入文件系统，文件系统再把数据页与设备请求联系起来。

  1. 系统调用与文件系统：应用提供文件描述符、缓冲区和长度。内核定位文件区间、检查缓存；命中时可复制并返回，本次根本不需要设备读取。
  2. 内存与块层：缓存未命中时准备接收数据的内存，文件系统把文件偏移映射到块位置，块层组织 bio/request，驱动设置 DMA 和设备命令。物理地址与 DMA 地址不能随意互换。
  3. 调度：线程登记等待并重查条件。数据仍未就绪才睡眠，让 CPU 可以执行其他任务；睡眠并没有停止设备。
  4. 中断与完成：设备更新完成状态，驱动通过中断或轮询发现结果。完成回调更新页状态、记录错误、释放资源，并唤醒等待者。一次通知可能覆盖多个完成项。
  5. 恢复执行：线程重新可运行，等获得 CPU 后检查结果、复制数据到用户缓冲区，再从系统调用返回。唤醒不等于已经返回。

源码可以沿 generic_file_read_iter() 的读取选择、blk_mq_end_request() 的请求完成和try_to_wake_up() 的任务唤醒分别观察。这些路径通过数据结构、完成回调和等待状态衔接，可以在不同 CPU 上执行。

排查读取延迟时，可分别统计 CPU 执行、设备等待和调度等待。设备完成较慢时关注存储路径，完成后仍迟迟无法运行时关注 CPU 竞争。

网络接收又有一个重要不同：外部报文可以先到，驱动预先准备 RX 缓冲区；recv 是从 socket 取数据或等待数据，并不命令远端发送特定报文。发送完成也首先描述本地资源可回收，不代表远端已收到。五篇详解分别展开调度、内存、中断、存储和网络。

六、版本演进与长期维护

现代内核按发布周期滚动演进：补丁先经子系统评审、集成测试，再在约两周的合并窗口进入主线；随后若干 rc 版本集中修复问题，正式版之后由 stable 或长期维护分支继续接收适合回移的修复。5.x 到 6.x 等主版本号变化也延续这套流程。依据见内核开发过程。

实际行为取决于发行版回移的补丁、内核配置、运行参数、驱动与硬件能力。上线评估需要同时核对这些条件。文章以固定源码基线解释机制，并用旧版源码标注历史变化。

兼容性也有边界：内核重视已有用户空间程序继续工作，但内部驱动接口并非永久不变。发行版的模块 ABI 承诺还可能与上游不同。LTS 表示一条维护线，不意味着每个新功能都会回移，更不表示所有硬件和工作负载都应采用同一内核配置。

七、只读观察与阅读路径

下面命令只读取信息；路径和权限因发行版、内核配置及容器可见性而异。

观察入口对应问题解释边界
uname -r、lscpu正在运行的内核与 CPU/NUMA 拓扑在 VM 中看到的可能是 Guest 视图；版本字符串不是完整补丁清单
ps -eLo pid,tid,psr,stat,comm哪些线程可运行、睡眠，最近在哪个 CPU 上执行一次快照不能解释整段延迟，R 也不保证此刻正在执行
/proc/meminfo、/proc/vmstat驻留、缓存、回收与缺页活动缓存不是自动等同泄漏；许多计数需要比较时间窗口内的增量
/proc/interrupts、/proc/diskstats、ip -s link通知、块设备与网络工作量三者处于不同统计层次，不能期待中断数、请求数和包数一一对应

对应原理可分开追踪：阻塞后恢复执行解释线程的去向；缺页与 COW解释地址和物理页的关系；通知与完成解释事件交接；写入与持久化、网络发送与回收则对比两种不同的完成语义。

八、源码与延伸阅读

  • 早期材料：Linux 0.01 发布说明；2.0 源码与 SMP 说明。这些用于还原当时的约束，不作为现代调参指南。
  • 演变依据：O(1) 设计、CFS、EEVDF、blk-mq、NAPI。
  • 资源与虚拟化：cgroup v2、KVM API；开发与兼容性：开发流程、内核内部接口的边界。
