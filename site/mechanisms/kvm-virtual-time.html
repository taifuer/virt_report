一、虚拟机怎样计时，又怎样按时获得通知

客户机安排一个 1 ms 后执行的任务，需要先知道当前时间，再设置一个到期通知。虚拟化使这两步有了不同的困难：vCPU 可能被宿主抢占，恢复时应能读出已经经过的时间；定时事件即使已经到期，处理线程也可能还没有得到 CPU。迁移到另一台服务器后，物理计数器的起点和频率还可能改变。

Linux 将提供时间读数的机制称为 clocksource，将产生定时中断的机制称为 clockevent。本文以 x86 客户机的 KVM pvclock 和 Intel TSC-deadline 定时器为例，沿“读出当前时间—设置截止时刻—接收到期中断”说明两条路径。示例使用内核虚拟 LAPIC。

源码版本：QEMU 10.2.0、Linux 6.18。

二、TSC 偏移与缩放建立客户机的计数坐标

TSC 是处理器提供的计数器，客户机可通过 RDTSC 等指令读取。具有 invariant TSC 能力的处理器使用稳定的计数频率；这个频率与程序当前执行指令的速度不同，不能用计数增量直接当作已执行的指令数。

物理 TSC 的起点属于宿主。KVM 为客户机配置偏移来选择起点，在支持硬件 TSC scaling 时还可配置比例来选择计数频率。Intel VMX 的比例采用 48 位小数，概念上的变换为：

guest_tsc = ((host_tsc × tsc_multiplier) >> 48) + tsc_offset

偏移可使迁移目的端从客户机原来的计数位置接续；比例可使不同物理 TSC 频率呈现同一个客户机频率。两者都不改变客户机获得多少 CPU 时间。常见的非嵌套 VMX 路径不拦截每次 RDTSC，处理器直接完成上述变换；配置更新才由 KVM 写入 VMCS。VMCS 字段、RDTSC 退出控制

三、pvclock 用共享时间基准减少读取开销

客户机仍需知道计数怎样换成纳秒，并处理 vCPU 调度、宿主计数器条件和时钟基准变化。pvclock 让 KVM 把换算参数写入客户机内存；客户机读取共享数据和当前 TSC，自己计算时间。它不需要为了每次查询时间都向宿主发起调用。

客户机为每个 vCPU 登记一份 32 字节的 pvclock_vcpu_time_info，通过 MSR_KVM_SYSTEM_TIME_NEW 提交其客户机物理地址并启用。KVM 更新的是参考点和换算关系，读取之间的时间增量由 TSC 提供，更新共享结构的频率不等于时钟的分辨率。

字段大小读取时的作用
version4 B检查本次读取是否跨过一次更新
tsc_timestamp8 B参考点的客户机 TSC
system_time8 B同一参考点的纳秒时间
tsc_to_system_mul、tsc_shift4 B、1 B将 TSC 增量换成纳秒
flags1 B稳定性、宿主暂停通知等标志

其余 6 字节为填充。写入方先把 version 改为奇数，再发布字段，最后改为偶数；两处写屏障保证顺序。读取方在参数与 TSC 采样前后检查版本，只有同一偶数版本才接受结果，并以读屏障约束字段读取；否则重试。这样可避免把旧参考点和新比例拼成一个错误时间。KVM 发布协议、客户机读取协议

四、从 5.002 秒安排一次 1 毫秒后的通知

设客户机 TSC 频率为 2 GHz，已一致读到下列参考点。移位为 0、乘数为 231，因此每个 tick 对应 0.5 ns。

tsc_timestamp     = 20,000,000 ticks
system_time       = 5,000,000,000 ns
tsc_shift         = 0
tsc_to_system_mul = 2,147,483,648  // 2^31
current_tsc       = 24,000,000 ticks

delta_ns = ((24,000,000 - 20,000,000) × 2^31) >> 32
         = 2,000,000 ns
now_ns   = 5,000,000,000 + 2,000,000 = 5.002 s

一般情况下先按 tsc_shift 左移或右移 TSC 增量，再乘 tsc_to_system_mul 并右移 32 位。这里的定点运算和实际接口一致，不涉及浮点计算。结构与换算公式

若此时要安排 1 ms 后的事件，截止 TSC 为 24,000,000 + 2,000,000 = 26,000,000，对应同一时间轴上的 5.003 s。客户机将 LAPIC 定时器配置为 TSC-deadline 模式、指定中断向量，再向 IA32_TSC_DEADLINE 写入这个绝对计数。时钟读数回答“现在到哪里”，deadline 指定“何时通知”。

五、截止时刻如何变成客户机中断

KVM 保存客户机写入的 deadline，再选择当前可用的定时方式。先看软件定时分支：start_sw_tscdeadline() 读取当前客户机 TSC，将剩余 ticks 按客户机频率换成纳秒，以宿主 hrtimer 安排到期。先不计编程耗时与注入提前量，上述例子剩余 2,000,000 ticks，换算后是 1,000,000 ns；实际安排会根据采样时刻和提前量调整。

通用到期路径增加 lapic_timer.pending，设置 KVM_REQ_UNBLOCK，由定时器回调触发 kick。阻塞中的 vCPU 被唤醒；获得 CPU 后，KVM 将定时器向量交给虚拟 LAPIC。客户机允许中断、优先级满足条件时才接受它，随后执行定时处理并安排就绪任务。到期与软件 deadline

这条路径中有三个时间点：deadline、客户机进入中断处理程序、应用任务实际开始运行。它们之间可夹着宿主排队、客户机屏蔽中断以及客户机调度。时钟保持连续，只保证能够计量经过的时间；到期通知和任务执行仍可能迟到。

运行中的硬件定时与阻塞后的切换

支持且适用时，VMX 后端可用 VMX preemption timer 辅助实现虚拟 LAPIC 定时器。它按换算后的宿主计数安排 VM exit，再由 KVM 处理到期；客户机写入的 deadline 并非直接独占宿主物理 LAPIC 定时器。计数范围等条件不满足时会回退到 hrtimer。vCPU 将要阻塞时，KVM 把正在使用的硬件定时切换为软件定时，避免依赖只在 VMX non-root 环境中倒计时的机制。VMX 换算、阻塞前后的切换

APICv 与 posted timer interrupt 还可减少部分事件交接。后者有配置、APICv 和 IN_GUEST_MODE 等条件，不能据此推断宿主已经阻塞的 vCPU 总能直接收到硬件投递。投递条件

七、暂停与迁移怎样接续时间

从源端搬到目的端，不能直接沿用宿主 TSC 原值。QEMU 保存客户机 TSC、频率、deadline 等状态，在目的端恢复；KVM 根据新宿主建立偏移和可支持的比例。QEMU 通过 KVM_GET_CLOCK / KVM_SET_CLOCK 保存、重建 kvmclock 参考点，跨宿主频率不兼容时还需检查 TSC 控制能力。客户机频率设置

具体停顿怎样计入取决于恢复策略。QEMU 10.2 的 kvmclock 设备在停止时保存读数，恢复时用保存值重新设置基准；迁移运行中的 VM 时，pre_save 会再取一次读数，把停止到保存之间的末批传输时间计入。已经显式暂停的 VM 则保留之前的基准。这能减少迁移丢失的时间，但不意味着所有停机区间都会自动补全。状态变化、迁移保存

还要区分经过时间与日期。pvclock 的纳秒读数配合 wallclock 基准可提供日期参考；客户机操作系统在其上维护 CLOCK_MONOTONIC、CLOCK_REALTIME 等接口，后者还受设置日期和 NTP 校时影响。MONOTONIC 不随手工设置日期直接跳变，也不等于 vCPU 累计执行时长。宿主暂停、客户机自行挂起和迁移是不同事件，不能仅凭某个时钟名称推断它们都采用同一种停顿语义。

PVCLOCK_GUEST_STOPPED 用于告知客户机发生过宿主暂停，让看门狗避免据此误判锁死；这个标志本身不负责补齐墙钟。暂停通知接口

九、总结：时间读数、到期事件与执行机会

TSC 变换建立客户机的计数坐标，pvclock 将计数转换为一致的时间读数，虚拟 LAPIC 定时器把截止时刻变成中断。事件到达后，宿主和客户机两级调度共同决定任务何时运行。理解这三层，才能判断一个“定时不准”的问题究竟来自时间基准、事件投递，还是执行机会不足。
