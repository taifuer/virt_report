一、用共享队列交接缓冲区

驱动提交磁盘请求或网络报文时，需要告诉设备缓冲区在哪里、长度多少、能否写入。设备处理后，还要让驱动找到原来的请求并安全复用内存。virtqueue 把这些交接规则放在共享内存中；数据留在描述符指向的缓冲区，通知负责提示另一方检查队列。

Split 把描述符、可用链头和完成记录分开放置，双方各自发布进度。Packed 将发布与完成状态放到同一个描述符环，用状态位和 wrap 区分不同轮次。两种格式都要完成同一轮交接：准备缓冲区 → 发布请求 → 设备处理并发布完成 → 驱动回收。从发布到回收，驱动不能随意改写正在使用的描述符与缓冲区。

本文先讲 Split，再对照 Packed。交互示例使用 4 个槽位，每项请求只占一个描述符，设备按提交顺序完成；不启用 IN_ORDER 的合并完成。队列格式依据 VIRTIO 1.2，只有协商 VIRTIO_F_RING_PACKED 才使用 Packed。协议演进和启用队列的步骤见Virtio 协议演进与设备初始化。

源码版本：QEMU 10.2.0、Linux 6.18。

规范依据：VIRTIO 1.2 CS01。规范版本记录

二、Split：描述缓冲区，分别发布请求和完成

共享区域保存内容更新方
描述符表 desc每项 16 B：addr / len / flags / next。NEXT 连接描述符，WRITE 允许设备写缓冲区驱动准备，设备读取
可用环 availablering[N] 中每项为 16 位链头编号；idx 发布新增请求的进度驱动写入，设备读取
已用环 usedring[N] 中每项为 {id:32, len:32}；idx 发布完成进度设备写入，驱动读取

available 和 used 都是循环使用的数组，存的是链头和完成信息。报文、块请求头及数据位于 desc.addr 指向的环外内存。WRITE 从设备角度解释：磁盘读取或网卡接收需要设备写入缓冲区，磁盘写入或网卡发送通常需要设备读取数据。

驱动还会在自己的内存中保存链头到请求上下文的对应关系。设备归还 used.id 后，驱动据此找回请求、释放描述符及缓冲区引用。QEMU 后端也有解析后的 iovec、设备消费位置等私有状态；这些对象不能直接写进共享环让另一侧解引用。描述符地址属于设备可访问的 DMA 地址空间，本例按 GPA 理解；开启 IOMMU 或平台访问约束时还要经过相应映射。

三、一次 Split 请求的发布、完成与回收

设队列大小 N=4，索引都从 0 开始。驱动选中空闲描述符 2，提供容量 256 B 的可写缓冲区；设备本次实际写入 64 B。描述符编号 2 与 available 的槽 0 分属两个数组，可以不同。

  1. 准备：驱动填写 desc[2] = {addr, len:256, flags:WRITE}，记录本次请求。此时设备还不能使用这项请求。
  2. 发布：将链头 2 写入 avail.ring[0]，完成必要内存屏障后令 avail.idx: 0 → 1。设备看到新索引时，必须能够读取完整描述符。
  3. 设备处理：设备比较私有消费位置与 avail.idx，读出链头 2，解析权限和长度，再写入缓冲区。本例把取得请求与处理完成合成一次演示操作。
  4. 发布完成：设备写入 used.ring[0] = {id:2, len:64}，保证数据及完成项可见后令 used.idx: 0 → 1。used.len 表示设备写入的长度，desc.len 仍表示提供的容量。
  5. 回收：驱动观察到 used.idx 前进，读取 used.id=2，找回原请求并回收资源，推进自己的回收位置。旧环项可以留在内存中，是否为新项由索引判断。

索引与数组槽位也要分开：idx % N 用于定位槽位，16 位 idx 按 65536 回绕，不会每绕一圈数组就清零。设备消费位置、驱动回收位置各自私有；它们与对方发布的索引比较，判断有没有新工作。第 4 次发布后 avail.idx=4，下一次使用槽 0；只要描述符尚未回收，驱动仍不能重复提交同一缓冲区。

多缓冲区请求通过链头交接

一个块读取常用“请求头 → 数据区 → 状态字节”三段直接链，例如 desc[2] → desc[0] → desc[3]。available 只发布链头 2；used 也用 id=2 归还整条链。此时一项请求占三个描述符，四槽队列只能再用一个空闲描述符。协商 INDIRECT_DESC 后，可以让主表的一项指向环外间接表，减少主表占用；间接表内仍使用 Split 的 addr/len/flags/next 布局。

两端不要求一提交就通知。驱动发布后检查设备是否需要 kick；设备发布完成后检查驱动是否需要中断。未协商 EVENT_IDX 时用抑制标志，协商后按对方填写的事件索引判断是否越过通知点。队列索引承载事实，门铃和中断用于唤醒处理；即使通知被合并，接收方仍可通过索引读取全部新增项。

四、Packed：一个描述符环，加两个事件抑制结构

Split 的区域划分清楚，但处理一项请求需要在 available、描述符表和 used 之间访问元数据。Packed 随 VIRTIO 1.1 引入，将发布和完成状态放回描述符环，减少部分分散访问。交接规则仍然成立，只是“有没有新项”的判定从两个共享索引改成描述符状态位和各方进度。

区域组成职责
Descriptor RingN 个 16 B 描述符：addr:64 / len:32 / id:16 / flags:16驱动发布缓冲区，设备写入完成记录
Driver Event Suppressionoff_wrap:16 / flags:16，共 4 B驱动告诉设备何时需要完成通知
Device Event Suppression相同的 4 B 格式设备告诉驱动何时需要可用缓冲区通知

三个区域分别由队列配置地址定位，均用于交换队列元数据。报文或块请求数据位于 addr 指向的缓冲区，门铃位于设备通知接口。id 是驱动为请求分配的标识，完成时用它找回上下文：槽位编号定位环内记录，Buffer ID 关联请求资源。

以 N=4 计算，描述符环为 64 B，加两个事件结构共 72 B，未计外部对齐填充与请求数据。split 在不带 EVENT_IDX 时对应三个区域合计 112 B。这个小例子展示的是元数据布局差别，不能直接换算成相同比例的吞吐提升。packed 的队列大小也不要求是 2 的幂；选 4 只是为了方便观察回绕。

五、AVAIL、USED 与 wrap 的状态判定

flags 的 bit 7 为 AVAIL，bit 15 为 USED。发布、设备消费、完成和驱动回收分别维护所需的环位置与一位 wrap，初始 wrap 为 1，描述符内存清零。某个进度越过最后一个槽位时，对应的 wrap 翻转；不同进度不要求同时翻转。下方演示将设备消费与完成合为一步，展示发布、完成和回收三个进度。

当前期望 wrap驱动发布后的 A / U设备完成后的 A / U
1，第一圈1 / 01 / 1
0，第二圈0 / 10 / 0

以槽 0 为例：初始化的 0/0 表示没有新工作；第一圈发布后成为 1/0，设备据此读取缓冲区；完成后成为 1/1，驱动据此归还资源。再次绕回槽 0 时，双方期待的 wrap 已变成 0，旧的 1/1 就不会被误判为新完成。

设备判断可用时检查 A == expected_wrap && U != expected_wrap；驱动判断完成时，典型条件是 A、U 均等于回收位置的 expected_wrap。wrap 给相同位组合加上轮次：初始 0/0 与期望的 wrap=1 不匹配，第二圈的 0/0 才与 wrap=0 的完成状态匹配。

驱动回收完一个请求后，不需要把槽位清零。旧 flags 留在内存里，下一圈根据翻转后的 wrap 区分新旧。驱动根据已回收的描述符数量限制继续发布；Buffer ID 和数据缓冲区必须等对应请求完成后才能复用。完成记录可以位于不同于原请求的位置，环上槽位与请求资源的生命周期需要分开。wrap 解决代际识别，不能代替空闲数量和所有权管理。QEMU 的可用状态判断

六、切换两种布局，观察同一轮交接

每次“发布”提供一个容量 256 B 的设备可写缓冲区；设备完成时写入 64 B。切换布局会保留当前请求进度：Split 用描述符编号 2、0、3、1，Packed 用相同序列作为 Buffer ID。两种格式分别维护自己的数据结构，展示相同操作下的差别；实际设备在初始化时选定一种格式，不能运行中直接切换。

可以先发布四项，再完成两项但暂不回收。此时仍不能发布新请求；驱动回收后才恢复容量。继续操作到第二圈，观察 Split 的 idx 与 Packed 的 wrap 如何识别新旧记录。

蓝色表示已发布，绿色表示完成待回收，空白表示可用。演示仅包含单描述符、顺序完成，不模拟 DMA 时延、通知抑制、乱序完成和 IN_ORDER 批量归还。Packed 的 A/U 显示状态位，非完整 flags 数值；旧值保留不代表有新工作。

发布时先写地址、长度、ID 和数据准备，再以必要内存顺序发布 flags。设备观察到可用状态后才能读取请求；完成时先写数据及完成字段，再发布完成状态。CPU 或编译器若把状态写提前，另一方就可能看见“已就绪”却读到旧内容。通知只是唤醒提示，不能代替这两个发布边界。

七、描述符链沿相邻槽位前进，ID 负责找回请求

1. 直接链使用连续槽位

split 描述符含 next 字段，可以把不相邻槽位串起来；packed 没有 next 字段。设置 NEXT 后，链的下一项就是环中的下一槽，越过末尾便从槽 0 继续。一个请求占槽 3、0、1 时，驱动需要按各位置所属的 wrap 填好所有状态，最后才发布槽 3 这个链头，防止设备读到半条链。

直接链的 Buffer ID 放在最后一个描述符中。设备处理完整条链后，只为整项缓冲区写一个完成描述符；驱动用完成 ID 找回私有上下文和该链占用的描述符数，然后跳过相应槽位继续回收。used 中 NEXT 是保留位，不能拿它来重新遍历提交时的链。

2. 完成记录的位置与原请求的位置可以不同

未协商 IN_ORDER 时，设备可以按不同于提交的顺序完成请求，但完成记录仍沿完成位置在环中依次写入。此时不能根据“used 记录位于槽 0”推断完成的是原来在槽 0 提交的请求；应读 Buffer ID，并查询驱动保存的链长度及缓冲区关联。单描述符且顺序完成的教学例子刚好原位覆盖，不代表一般规则。

协商 INDIRECT_DESC 后，还可以让主环一项指向环外的间接描述符表，减少主环占用。packed 的间接项使用 packed 描述符布局，顺序遍历，内部仅 WRITE 标志有效；不能直接拿 split 的 next 索引规则解释。协议要求与特性选择必须在初始化时就一致。QEMU 沿环取下一项、读取直接链和间接表

八、事件位置减少通知，复查关闭竞态窗口

每个事件结构含 off_wrap 和 flags。off_wrap 的低 15 位为描述符位置，高 1 位为该位置所属 wrap。flags 可以要求启用通知、禁用通知，或者在协商 EVENT_IDX 后按指定位置触发通知。不能只比较裸索引大小：从槽 3 到槽 0 虽然数字变小，队列实际上继续前进了。

两个事件结构由等待方填写：驱动用 Driver Event 请求完成通知，设备用 Device Event 请求新工作通知。发布方先让描述符状态可见，再读取对方的事件配置，按进度变化判断是否通知。等待方从轮询切回通知时，重新检查切换窗口内到达的工作。

如果等待方先看到没有工作，发布方恰好在通知仍被抑制时发布，等待方随后直接睡眠，就可能错过唤醒。packed 改变共享队列布局，没有消除生产者与消费者并发产生的通知竞态。内存屏障、通知抑制和最后复查仍共同构成正确交接。

九、QEMU 的链长度记录与完成发布

virtqueue_packed_pop() 从 last_avail_idx 读取链，建立可读与可写 iovec，保存 Buffer ID 和 ndescs。后者对普通直接链是占用的主环描述符数量，对间接表则为 1。I/O 完成后，fill 暂存 ID、长度和 ndescs，flush 根据完成顺序写回记录并推进 used_idx。

  解析链或间接表，保存 element.index 与 element.ndescs

  virtqueue_packed_fill()：暂存完成结果
  virtqueue_packed_flush()：按 ndescs 推进完成位置

驱动读取完成 ID，找回上下文与链长度，归还资源

批量 flush 会先准备后续完成，再带发布顺序约束地写出首项，使读者不会越过尚未完整写出的批次。IN_ORDER 还允许一条记录表示一批按序处理的缓冲区，这需要额外的批次推导；不能只删除逐项完成写入而保持驱动逻辑不变。完成字段与 flags、链长度与完成位置推进

十、两种布局的取舍与适用边界

比较项SplitPacked
发布与完成available / used 分开，分别更新 idx同一描述符环，更新 AVAIL / USED
槽位复用16 位 idx 前进，idx % N 定位环槽位置越过末尾，独立的一位 wrap 翻转
直接链next 指定下一描述符，可不相邻沿相邻槽位前进，可跨环尾
找回请求used.id 是描述符链头编号完成记录携带 Buffer ID，由驱动找回私有上下文
完成长度used.len 与 desc.len 分开完成字段复用环中描述符的 len 等字段
通知控制环内抑制字段，可选 EVENT_IDX独立事件抑制结构，可选按 off_wrap 判断
兼容关系Legacy 与 Modern 都可使用Modern，且双方协商 RING_PACKED

packed 随 VIRTIO 1.1 引入，使高吞吐设备可以用更紧凑的共享元数据交换请求。它减少某些路径上的环间跳转和内存占用，但双方都会写描述符环，也可能带来缓存行共享；实际收益依赖后端实现、批量大小、队列深度和 CPU 拓扑。

相对于 split，packed 的实现增加了 wrap、Buffer ID、跨尾部的链、完成位置及事件偏移之间的配合。双方在特性协商时选定共同布局，运行期间按这一布局访问队列；迁移目标也需支持客户机已经选定的格式。实现和验证的工作主要集中在资源归属与各方进度的对应关系上。

检查演示时，可以先发布四项，再完成两项但暂不回收：驱动仍不能继续发布，直到回收释放相应资源。这个状态把“设备已处理”与“驱动可继续提交”分开，也说明 wrap 判断必须配合空闲容量管理。评价时可以在相同报文或块请求负载下对比每核吞吐、尾延迟、缓存未命中与通知次数。小队列更省元数据，并不代表能容纳同样多的复杂请求；直接链与间接表的占用也要固定。split 仍有成熟兼容性与清晰的生产者区域，packed 提供另一种局部性取舍。
