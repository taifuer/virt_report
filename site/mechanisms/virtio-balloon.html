一、Guest 页面与宿主后备内存

virtio-balloon 让客户机主动交出暂时不用的页面，供宿主回收对应的后备内存。虚拟机仍保持原来的 RAM 地址布局，客户机内的气球驱动负责占住这些页，避免应用继续使用。负载增长后，管理端可以缩小气球，驱动再把页交还客户机分配器。

以配置了 8 GiB RAM 的虚拟机为例：管理端希望客户机暂时只使用其中的 6 GiB，于是要求气球占用 2 GiB。这个操作要经过“设置目标 → Guest 收集页 → 队列提交 → 宿主处理 → Guest 报告结果”。管理端不能仅根据宿主看到的地址范围，随意丢弃客户机还在使用的数据。

这里有三个需要分别观察的量：虚拟机配置的 RAM、气球驱动持有的页，以及 QEMU 后备内存的实际驻留量。前两个量决定客户机可管理的范围；后一个量还受宿主内存分配、共享页、大页和内存后端影响。

源码版本：QEMU 10.2.0、Linux 6.18。

规范依据：VIRTIO 1.2 CS01 · Memory Balloon Device。规范版本记录

二、目标、页列表与共享队列

在本例中，QMP balloon 的 value 是希望留下的字节数：6 GiB，即 6442450944。设备配置中的 num_pages 表示希望气球占用的 4 KiB 页数，因此应为 (8 − 6) × 2³⁰ / 4096 = 524288。驱动完成调整后写回 actual，报告已经占用的页数。QMP query-balloon 也有一个名为 actual 的字段，但它报告扣除气球后的字节数，不能和设备配置里的同名字段混用。

结构保存内容更新者与用途
config.num_pages / actual目标与实际气球页数，单位均为 4 KiBQEMU 设置目标；Guest 驱动回报进度
inflateq / deflateq描述符指向 32 位 PFN 数组驱动提交将交出或归还的页；设备处理后发布 used
Guest 气球页链表由驱动持有的 struct page让普通分配器无法再次分配这些页，并支持后续归还
RAMBlock 与后备页对应 GPA 的宿主映射QEMU 定位区域后请求宿主处理后备内存

PFN 是按 4 KiB 单位编码的页号，例如 0x200 对应 GPA 0x200000。队列描述符指向的是 PFN 数组，数组再指向目标页。提交 256 个 PFN 需要 1024 B 的数组，所描述的页面共 1 MiB；页面数据本身无须通过这条队列拷贝。Linux 驱动分批提交并等待完成，不会用一个巨大请求交接全部 2 GiB。

    四、内存压力与回收边界

    inflate 时，驱动从 Guest 分配器取得页面并持有，提交 PFN 后等待设备处理。QEMU 找到对应 RAMBlock，尝试丢弃后备页；Guest 仍保留这些地址，但业务不能使用被气球持有的页。deflate 时，Linux 驱动先通过 deflateq 告知设备，再把本批页释放给分配器。QEMU 对后备地址发出 MADV_WILLNEED 提示，实际物理页何时重新驻留仍由宿主管理。

    回收目标过大时，Guest 可能需要回收缓存、换出页面，甚至无法分配足够的气球页。管理端应观察 actual 的推进、可用内存、换页和业务延迟，逐步调整目标。协商 DEFLATE_ON_OOM 后，Linux 可在 OOM 路径主动缩小气球；这是缓解机制，不能代替容量规划，也不保证业务一定避免 OOM。

    宿主侧还有另一组限制：部分迁移阶段会禁止并发 discard；后备页大于 4 KiB 时，交出的子页可能不足以组成可丢弃的完整宿主页；discard 也可能失败。QEMU 仍可完成相应队列交接。判断收益时，应同时观察 Guest 的实际气球大小、QEMU RSS/PSS 与内存后端指标，不能只看目标已到达。

    五、统计、空闲页优化与内存热插拔

    基础气球协议解决了运行中回收和归还页面的问题，后续扩展改善了管理端的信息和空闲页处理。它们可以组合使用，控制的对象与完成条件各不相同。

    机制用途完成后页面的状态
    statsqGuest 提供可用内存、换页和缺页等统计，帮助管理端决定目标不直接回收页。QEMU 轮询间隔为 0 时不继续请求；应同时检查 last-update，旧值可能仍能读取
    FREE_PAGE_HINTQEMU 预拷贝迁移中，通过命令 ID 标识一轮空闲页提示，减少无用页面传输按该协议的持有和结束规则处理；QEMU 会停止、结束相应轮次。不能把它当成持续降低 RSS 的接口
    PAGE_REPORTINGGuest 暂时隔离空闲页，经 reporting_vq 让宿主尝试丢弃后备页队列完成后重新允许 Guest 分配；num_pages / actual 不因报告而增大
    virtio-mem按设备内存块执行 plug / unplug，并配合 Guest 内存上线、下线调整可用设备内存块，回收仍可能受页面迁移和不可移除页限制
    DIMM 热插拔以 DIMM 设备及其地址范围为管理单位涉及设备增删、固件通知和 Guest 内存热插拔流程

    PAGE_REPORTING 的描述符直接指向可丢弃区域，和 inflateq 的 PFN 数组格式不同。QEMU 的属性名为 free-page-reporting，源码特性常量使用 VIRTIO_BALLOON_F_REPORTING。使用前要确认两端协商成功，不能仅根据设备名称假定这些扩展都已启用。

    气球适合在已配置 RAM 内灵活回收空闲容量，部署相对直接；它依赖 Guest 配合，并可能挤压缓存与业务工作集。需要调整设备内存容量时，可结合 virtio-mem 的内存添加与回收比较。两者的统计口径、页面所有权与失败处理都应分开理解。

    六、小实验：同时观察目标、actual 与 RSS

    为降低实验的资源占用，本节把前面演示的 8 GiB → 6 GiB 按比例缩小为 1 GiB → 768 MiB → 1 GiB：先回收 256 MiB，再恢复初始容量。使用一台可丢弃的 Linux 测试虚拟机，由 QEMU 直接启动，已加载 virtio_balloon 驱动，不运行重要业务，也不开启自动气球调节。确认 Guest 有足够余量交出 256 MiB；可用内存不足或出现换页、业务延迟升高时，停止收缩并恢复原目标。不要在生产虚拟机或 libvirt 管理的实例上绕过管理器发送这些调节命令。

    在宿主用 LAB_DIR=$(mktemp -d) 建立私有目录。测试机采用以下相关启动选项，内核或磁盘的启动参数沿用自己的测试镜像；已有 machine、内存后端或 balloon 配置时替换对应项，不重复添加。记录该 QEMU 的 PID。QMP 使用私有 Unix socket，不开放 TCP 管理端口。

    -machine q35,accel=kvm,memory-backend=ram
-cpu host -smp 2 -m 1024
-object memory-backend-ram,id=ram,size=1G,prealloc=on
-device virtio-balloon-pci,free-page-reporting=off
-qmp unix:${LAB_DIR}/qmp.sock,server=on,wait=off

    prealloc=on 让宿主在启动时先准备 1 GiB 后备页，便于观察后续回收的变化；宿主也要有足够余量。关闭 free-page-reporting 可避免空闲页报告引入另一条回收路径。若省略预分配，部分后备页可能尚未驻留，同样的 balloon 调整未必带来相同的 RSS 降幅。

    在宿主的监控终端中，将 LAB_DIR 设置为刚才创建的目录，将 QEMU_PID 设置为这台测试机的 QEMU 进程号。执行 socat STDIO UNIX-CONNECT:"${LAB_DIR}/qmp.sock"，看到 QMP greeting 后先发送下面两行。保存 query-balloon 返回的初始 actual；本例应为 1073741824 字节，即未充气的 1 GiB。若值不同，先查清初始配置，不套用后面的恢复值。

    {"execute":"qmp_capabilities"}
{"execute":"query-balloon"}

    满足上述前提后，请求留下 768 MiB，即 805306368 字节，再隔一段时间查询。balloon 返回成功只代表已发出请求；驱动处理、BALLOON_CHANGE 事件与查询响应可以异步出现。实际值未推进时应检查驱动和 Guest 内存压力，不连续加大收缩幅度。

    在请求前、actual 稳定后、恢复后各记录一次。这三组量能区分“驱动已交出页”和“宿主实际减少驻留内存”。若页面原本尚未驻留，或后备大页无法完整丢弃，actual 已变化也未必观察到 RSS 等量下降。

    本例结束时恢复初始的 1 GiB 目标，继续查询实际值。恢复后 RSS 不必立刻上升：后备页可以等待后续访问再驻留。如需观察下一次访问，应先确认 Guest 可用内存，再分配一段有余量的测试映射逐页写入，释放这段映射后记录 RSS。最后退出 QMP 连接、正常关闭测试虚拟机，再移除它的 QMP socket 与私有目录。

    实测：容量恢复与页面重新驻留

    实测日期：2026-11-08。环境为 AMD Ryzen 5 5600G、Windows 11（26300.9818）→ WSL2 → KVM；WSL 内核为 6.18.54.1-microsoft-standard-WSL2，QEMU 为 10.1.50（v10.1.0-2213-g9febfa94b6），客户机内核为 6.18.60-0-virt。

    测试机使用 2 个 vCPU、1 GiB 普通匿名 RAM，以最小 initramfs 启动，无磁盘、无网卡、未配置 swap。宿主 RAM 后备在启动时预分配（prealloc=on），balloon 的空闲页报告关闭（free-page-reporting=off）；QMP query-kvm 返回 enabled=true、present=true。本次二级转换使用 AMD NPT；页首的 QEMU 10.2.0 / Linux 6.18 仍是正文源码基线，与这组实测版本分开记录。

    初始值、收缩完成、恢复完成分别采样；后两次先等待 query-balloon 达到目标，再等 1 秒。第四次采样前，Guest 申请 512 MiB 匿名内存，使用 MADV_NOHUGEPAGE 并每隔 4096 B 写入一次，释放这段映射后再读取统计。表中 Guest 总量取自 /proc/meminfo 的 MemTotal，QEMU RSS 取自宿主 /proc/<QEMU_PID>/status 的 VmRSS；各列在同一采样阶段依次读取。

    收缩后，Guest 的 MemTotal 减少 262144 KiB，QEMU RSS 也下降约 256 MiB；恢复后，QMP actual 和 Guest MemTotal 已回到初始值，RSS 仍保持低位。直到后续逐页写入，RSS 才回到约 1066 MiB。Guest 的 munmap 将页面交还自己的分配器；本例关闭了空闲页报告，释放这段 Guest 映射后，宿主仍可保留已驻留的后备页。

    QMP actual 表示扣除气球后的逻辑字节数；Guest MemTotal 还受客户机保留内存等因素影响；QEMU RSS 则包含 RAM 后备和进程的其他映射，因此三列不能直接等同。后续访问的页面由 Guest 分配器选择，其他环境下 RSS 的回升幅度也可能不同。

    收缩完成时，Guest 的 MemAvailable 仍有 627608 KiB。四次采样的 oom_kill 均为 0；该客户机未配置 swap，pswpin、pswpout 也为 0。实验结束前已恢复初始目标并正常关闭测试机。这组数据验证了气球交页、宿主回收和再次驻留的关系；没有对内存压力、共享后备、大页后备或迁移并发场景做比较，也不作为性能基准。首次触碰实验可对照 Guest 进程自身的缺页行为。
