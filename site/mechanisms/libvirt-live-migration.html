一、把运行中的虚拟机从 A 交给 B

Libvirt 热迁移协调两端资源，让客户机在保留内存、CPU 和设备状态的情况下更换宿主。QEMU 负责传输与恢复运行状态，Libvirt 负责准备、推进迁移、确认接管和清理源实例。客户机在大部分内存复制期间继续运行，最后短暂停止，再从目的端继续执行。

本文用共享存储上的虚拟机 demo 演示预拷贝迁移。A、B 分别运行 Libvirt 守护进程和 QEMU；操作者连接 A 发起任务。先说明命令与前提，再跟踪任务在两端的执行过程。

源码版本：Libvirt 12.0.0、QEMU 10.2.0。

二、迁移前准备：计算、存储与网络

资源需要满足的条件
计算与虚拟硬件B 支持客户机正在使用的 CPU 特性、机器类型和设备状态版本，并有足够的内存与配额。host CPU 模型尤其需要核对双端能力。
磁盘本例两端以相容路径、权限访问同一份共享存储，锁管理配置允许安全交接。非共享磁盘需要另外配置数据复制。
网络B 提供对应的虚拟网络或桥，迁移后的 MAC、IP 和连接有可接管的网络路径。
管理与传输A 的 Libvirt 能认证并连接 B；QEMU 迁移网络、防火墙与 TLS 配置就绪。
直通设备与后端支持所需的状态迁移，并能在 B 配置等价资源；普通整卡直通不自动获得迁移能力。

预拷贝会消耗 CPU、内存带宽和链路容量。正式操作前，应在相同软件、CPU 和设备配置的测试环境验证兼容性、停机目标与迁移期间的业务延迟。

三、命令示例与常用参数

在 A 上执行以下命令。demo 是源虚拟机名称，host-b 是目的宿主名。SSH 权限与非交互认证须提前配置给执行迁移的源端守护进程。

virsh -c qemu:///system migrate \
  --live --p2p --persistent --verbose \
  demo qemu+ssh://host-b/system

-c qemu:///system 选择源端系统级 Libvirt。末尾的 URI 选择目的端管理服务，前面的 demo 指定迁移对象。

参数作用与条件
--live客户机在预拷贝期间继续执行，最终交接仍有短暂停顿。
--p2p源端 Libvirt 连接目标并协调迁移，任务不依赖 virsh 持续在线。
--persistent在 B 保留持久域定义，客户机关机后仍可管理和再次启动。
--undefinesource成功后删除 A 的持久定义；本例默认保留。此选项不删除磁盘数据。
--verbose显示迁移进度。
--bandwidth 256设置迁移带宽上限，单位 MiB/s；影响传输时间与收敛。
--tls要求原生 QEMU 迁移传输使用 TLS，需预先配置双端证书。
--tunnelled配合 p2p，让状态流经 Libvirt 连接传输；增加软件参与，并有功能组合限制。
--copy-storage-all完整复制非共享磁盘数据；预先准备目标镜像、容量与权限。
--copy-storage-inc增量复制顶层，要求两端存在一致的基础镜像。

若 B 已配置 TCP 管理监听和认证，也可使用 virsh -c qemu:///system migrate --live --p2p --persistent demo qemu+tcp://host-b/system。TCP URI 本身不承诺加密，仅用于已有安全控制的环境，勿暴露未认证的管理端口。

非共享存储增加磁盘复制路径。是否复制、目标如何准备、哪些磁盘参与，应在执行前确定；存储复制选项不会自动建立任意布局的目标存储。

四、控制连接与状态传输走不同通道

p2p 的控制路径是 virsh → A 的 Libvirt → B 的 Libvirt，两端通过 QMP 控制各自 QEMU。原生数据路径是 A 的 QEMU → B 的 QEMU，承载 RAM、CPU 和设备状态；域 XML、迁移 cookie 和阶段结果走管理连接。

SSH 保护 Libvirt 控制连接，原生迁移流需单独配置 TLS 或隔离网络。tunnelled 模式才让状态流经 Libvirt 隧道传输。--p2p 决定协调者，--tunnelled 决定数据路线。

省略 p2p 时，常用的 managed direct 由客户端同时连接 A、B，交替推进阶段。p2p 使用 A 的守护进程凭据访问 B，因此运维电脑能登录 B，不能代替 A 到 B 的认证检查。

五、从准备目标到清理源端

Libvirt 的版本 3 迁移协议用五个阶段衔接成功路径。本例由源端守护进程协调，两端 QEMU 传输状态。

阶段A 与 B 的工作
Begin · A检查配置，生成迁移 XML 与 cookie，建立作业保护；客户机继续运行。
Prepare · B准备存储、网络、安全标签和 incoming QEMU，返回接收地址。
Perform · A预拷贝 RAM、重传脏页，最终暂停 vCPU、收尾设备，传出余页及 CPU、设备状态。
Finish · B验证接收完成，处理持久定义，恢复客户机并返回结果；A 保持停止。
Confirm · A成功则清理旧 QEMU 与资源；按参数保留或删除源持久定义。

预拷贝时 Guest 写入会让已发送页面再次变脏。切换时要让最后的 RAM、寄存器、定时器和设备队列对应同一个执行点；能修改 RAM 的设备与异步后端也需收尾。QEMU 传完状态、B 恢复执行、A 清理结束是相互关联的三个完成点。

六、查看进度与迁移结果

以下命令只查询状态，在有双端权限的管理机执行：

virsh -c qemu+ssh://host-a/system domjobinfo demo
virsh -c qemu+ssh://host-a/system domjobinfo demo --completed --keep-completed
virsh -c qemu+ssh://host-a/system domstate demo --reason
virsh -c qemu+ssh://host-b/system domstate demo --reason
virsh -c qemu+ssh://host-b/system dominfo demo

--completed 读取保留的完成统计，--keep-completed 保留本次读取后的记录；失败统计可结合 --anystats 查询。活动作业消失后，还要核对同一 UUID 的双端状态。未使用 --undefinesource 时，A 留下关闭的持久定义属于正常结果。

验收同时检查 B 正在运行、A 已停止、网络与应用恢复，并分别记录迁移总时间、客户机停顿和业务不可用时间。

七、失败时先确认执行位置

目标准备失败通常还未影响源客户机执行；传输出错时，Libvirt 根据阶段取消作业并清理未完成的目标。切换附近的连接错误需要核对两端：B 可能已恢复客户机，但 Finish 的成功响应没有返回 A。

先检查运行状态、迁移日志和共享存储锁。保留的暂停源进程可能只是在等确认，直接恢复会造成双端写同一磁盘。网络分区时遵循已有集群隔离与存储仲裁流程。p2p 让任务脱离客户端生命周期，源端守护进程、网络和存储仍是迁移依赖。

八、源码中的管理流程

managed direct 的入口为 virDomainMigrateVersion3Full()；p2p 在源端驱动的 qemuMigrationSrcPerformPeer2Peer3() 中组织调用。vm->job 保存作业与阶段，qemuMigrationCookie 交换身份、锁、能力和统计等管理信息。

目的端 qemuMigrationDstFinishFresh() 核对接收结果并推进 CPU 恢复，源端 qemuMigrationSrcConfirmPhase() 根据目标结果结束作业。管理信息帮助协调，RAM 和寄存器仍通过 QEMU 状态流传输。
