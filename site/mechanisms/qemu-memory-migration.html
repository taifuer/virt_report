一、预拷贝如何缩短停机

预拷贝迁移在虚拟机运行期间复制内存，最后暂停虚拟机，传输剩余脏页及处理器、设备状态。复制期间客户机仍会写入内存，已经传过的页可能需要重传。QEMU 通过脏页跟踪记录这些修改，并根据剩余数据量和传输速率决定切换时机。本文分析这两个过程及其对停机时间的影响。

以 8 GiB 内存、1000 MiB/s 的有效传输速率为例，停机后再复制全部内存，仅数据传输就约需 8.2 秒。预拷贝先在运行期间完成大部分复制，再把停机阶段的剩余量压到可接受范围。下面先看两端如何交接，再跟踪一页被重新写脏后的重传，最后讨论何时停止迭代，以及停机超出目标时应检查什么。

以下分析以 x86 / KVM、普通 RAM 的预拷贝路径为例，假定两端机器配置兼容、存储已就绪，不涉及磁盘复制、VFIO 或机密虚拟机。

源码版本：QEMU 10.2.0、Linux 6.18。

二、运行中复制与停机交接

暂停虚拟机后复制全部内存，可以在停止修改的条件下传送一致状态，停机时间也会包含整个内存传输过程。预拷贝将大部分复制工作移到运行阶段：先建立目的端内存副本，再重复传输发生修改的页，最后暂停客户机并完成状态交接。重复传输增加了流量，同时减少了暂停期间需要处理的数据量。

Libvirt 协调目的端准备和迁移任务；QEMU 保存、传送和恢复状态；KVM 提供客户机执行及脏页记录能力。目的端 QEMU 边接收边填充内存，但客户机尚未运行。运行阶段得到的副本不要求任意时刻都一致，最终一致性依靠停止修改、最后一次脏页同步和状态交接建立。

暂停后不仅要补齐 RAM，还要保存寄存器、中断控制器、设备队列处理位置等状态。普通预拷贝路径先完成 RAM 等可迭代状态，再同步 vCPU 并保存非迭代状态；目的端恢复完成且允许启动后才执行。字节流的组织方式另见《QEMU 迁移流格式与状态恢复》。

三、脏页位图如何驱动重传

1. 迁移位图与脏页记录

QEMU 为各个 RAMBlock维护迁移位图 bmap，表示哪些页还需要发送。初始化时将相应位设为 1，使首次扫描覆盖需要迁移的内存；与此同时开启脏页跟踪，记录运行期间的新修改。初始化代码还会排除符合条件的丢弃页，缩小首次扫描的待传集合。

KVM 的 dirty bitmap 或 dirty ring 记录客户机写脏的页；QEMU 内存子系统汇总相关记录，再由 migration_bitmap_sync()合入迁移位图。原来为 0、此次变为 1 的页增加待传数量，已经为 1 的页不会重复计数。同一页在两次发送之间反复写入，合入位图后仍只需安排一次重传。位图合并、同步入口

2. 页面重传与跟踪顺序

假设页 P 已传到目的端，随后客户机又修改了 P。底层脏页跟踪记录这次写入；下次同步把 P 重新标入待传集合，目的端旧内容便会被覆盖。发送任务完成后，跟踪仍持续到最终同步阶段。

migration_bitmap_clear_dirty()在发送前处理底层脏标记的清除，再清除迁移位图中的该页。相关页的跟踪必须在读取、发送之前重新有效：若发送之后才清标记，两者之间的新写入就可能被一并清除。手动 dirty-log 模式允许按块推迟清除操作，前提是仍在读页之前恢复跟踪。清除顺序、页面发送

运行阶段的页复制与客户机写入可能交错，因此单次复制不保证得到整页的原子快照。期间发生修改的页会再次同步。最后暂停客户机并静止相关 I/O 后，ram_save_complete()再次汇总脏页并发送剩余内容，形成恢复所需的最终内存。用户态设备或 DMA 的写入还需要对应的脏页记录路径，KVM 脏页日志的覆盖范围取决于写入来源。

3. 扫描轮次与发送批次

ram_save_iterate()从上次扫描位置继续寻找待传页；达到限速或时间预算时返回，下次调用再继续发送。外层为一次调用写出一个 SECTION_PART，一次完整扫描可以跨越多个 PART。扫描位置、位图同步次数和 PART 数分别描述扫描进度、记录收集与传输批次。扫描游标、迭代回调

四、带宽与写脏速率决定收敛

用一个简化的轮次模型可以说明重传的代价。设内存量为 M，第 n 轮待传量为 Rn，有效内存传输速率为 B，按脏页粒度去重后的新增数据速率为 D。在速率稳定、没有压缩和其他开销的近似下：

本轮耗时      Tₙ ≈ Rₙ / B
下一轮待传量  Rₙ₊₁ ≈ min(M, D × Tₙ)
                    = min(M, Rₙ × D / B)

例如 M 为 8 GiB、B 为 1000 MiB/s、D 为 256 MiB/s，待传量大致按 8192 → 2097.152 → 536.871 → 137.439 → 35.184 MiB 下降；下方演示以这组参数开始，可切换 4、8、16 GiB 内存或修改带宽。D/B 越接近 1，每轮减少得越少；达到或超过 1 时，这个模型就不能靠继续迭代收敛。实际负载的热页集合、突发写入、扫描顺序和带宽变化，会使曲线偏离几何级数。

D 按脏页粒度统计：修改一页中的少量字节，也可能需要重传整页；同一统计周期内反复修改同一页会被合并。B 使用当前路径处理内存的有效速率，与网卡标称带宽可能有明显差异。压缩或零页编码启用后，还需分别统计逻辑内存字节数与链路字节数。

内存迭代与停机时间

调整传输带宽、脏页速率或停机目标，观察剩余内存何时达到切换条件，以及减少迭代会怎样改变停机阶段的工作量。

  1. 首次复制8192 MiB（8 GiB）内存，以 1000 MiB/s 传输需 8.192 秒；期间以 256 MiB/s 产生约 2097.152 MiB 待重传脏页。
  2. 迭代重传继续重传，待传量约按 2097.152 → 536.871 → 137.439 → 35.184 MiB 下降；完成 4 轮运行中复制后，低于 100 MiB 的切换阈值。
  3. 暂停并完成最终内存传输约需 35.184 毫秒，加上示例中的状态保存传输与恢复共 40 毫秒，模型停机时间约为 75.184 毫秒。

增加迭代通常能减少暂停后的剩余工作，但也会延长迁移、消耗网络与主机资源。QEMU 根据预计暂停期间的工作量判断切换时机，剩余量达到阈值后即可进入完成阶段，无需等待脏页归零。

五、从剩余量估算停机时间

1. 从时间目标换算剩余量阈值

migration_update_counters()使用近期观测带宽，或配置的 avail-switchover-bandwidth，计算切换阈值。固定版本中的关键表达式为：

s->threshold_size = expected_bw_per_ms * migrate_downtime_limit();

随后 migration_iteration_run()先读取各状态处理器报告的剩余量估计；当它低于阈值时，再请求更精确的剩余量。对 RAM 来说，后一步会重新同步脏页，避免只看已经过时的位图。最终剩余量不超过阈值，并且切换条件满足，才进入完成阶段。启用 switchover-ack时，还需目的端确认。阈值、判断逻辑、精确剩余量

2. 停机目标与实际停机时间

剩余内存除以带宽，只解释暂停阶段的一部分。实际还要停止 vCPU 和相关 I/O、汇总最终脏页、提取与序列化 CPU 和设备状态、完成传输，并在目的端完成装载、存储激活和恢复执行。其中部分发送与接收可以重叠，不能简单把所有函数耗时相加。设备状态、带宽突变、线程调度及同步等待都可能让实际停顿超过目标。

参数或指标含义
downtime-limit用于切换决策的时间目标，单位为毫秒；不是业务 SLA。
expected-downtime迁移活动期间报告的估计值，随脏页同步和带宽估计更新，不是已经发生的停机。
downtime成功完成后报告的停机统计；需结合源端计时点与启用的协议理解。
total-time整个迁移过程的耗时，包含运行期间的迭代，不能与停机时间混用。

在本文的预拷贝实现中，源端在 migration_stop_vm()调用停止操作前开始计时，在源端完成处理时结束；是否等待返回通道也影响这个区间。因此 QMP 的 downtime不是一次直接测量“源端最后一条客户机指令到目的端第一条指令”的跨主机计时。业务侧还会受到网络切换、连接重试和应用调度影响，应另行测量请求中断与尾延迟。计时开始、完成流程、计时结束

六、源码：迭代与最终状态保存

迁移线程负责判断是否继续迭代，RAM 处理器负责维护待传集合，两者通过状态保存回调连接。初始化、迭代和最终保存的主要调用关系如下：

migration_thread
  qemu_savevm_state_setup
    ram_save_setup → ram_init_bitmaps
  migration_iteration_run
    pending_estimate / pending_exact → 必要时同步脏页
    qemu_savevm_state_iterate
      ram_save_iterate → ram_find_and_save_block
        ram_save_host_page → ram_save_target_page
  migration_completion_precopy
    migration_stop_vm
    qemu_savevm_state_complete_precopy
      ram_save_complete → 最终脏页同步、发送余页
      complete_precopy_non_iterable → 同步 vCPU、保存设备

savevm_ram_handlers注册了初始化、迭代、完成和装载回调。暂停阶段的最终保存流程先完成可迭代处理器，再通过 cpu_synchronize_all_states()读取所需的 CPU 状态，并保存各非迭代处理器。CPU 与具体设备的保存次序由处理器注册顺序决定。

观察一次实际迁移时，可同时记录 query-migrate中的 ram.remaining、dirty-pages-rate、dirty-sync-count、pages-per-second与时间指标；页速率须结合 page-size换算。再用 migration_bitmap_sync_end、migrate_pending_exact和 vmstate_downtime_checkpoint等 trace 事件区分“剩余量降不下来”和“暂停后的处理太慢”。单看链路吞吐或完成时间，无法分辨这两类问题。

七、并行、限速与后拷贝的取舍

预拷贝的主要开销来自内存传输、脏页跟踪与重传，以及暂停阶段的状态保存和恢复。不同优化机制针对其中的不同环节，也各自需要额外的计算、内存或同步资源。

1. 传输能力不足：并行化

当单一路径的页面处理或传输成为瓶颈时，MultiFD 使用多个工作线程和通道处理内存；QAPI 的 multifd能力自 QEMU 4.0 提供。它有机会提高有效 B，但会增加线程、缓冲区和同步开销；若已受网络总带宽或内存带宽限制，增加通道不会按比例提速。MultiFD 实现、能力版本

多通道的任务分发和同步过程见《QEMU MultiFD 的任务分发与跨通道同步》。

2. 写脏速度过高：从统一限速到按 vCPU 限制

QEMU 1.6 的 auto-converge通过限制客户机 CPU 执行降低写脏速度。这会降低迁移期间的业务性能，也会影响写内存较少的 vCPU。QEMU 8.1 的 dirty-limit利用 KVM dirty ring 观察各 vCPU 的写脏活动，对超过配额的 vCPU 施加等待。它依赖相应 KVM 能力，并以受限 vCPU 的执行时间换取较低的写脏速率；设备写入仍需由相应路径处理。自动收敛、Dirty limit 设计

3. 跟踪本身有开销：缩短清除与读页的间隔

传统整槽位同步、清除与重新写保护，在大内存客户机上可能持锁较久；而过早重新保护，还会记录一些随后本就会随当前页一起传走的修改。KVM 的手动 dirty-log 保护把“获取记录”和“清除并重新保护”分开，允许按较小范围、更接近发送时刻处理。它减少无效工作，却增加了顺序要求：必须在读页前恢复跟踪。dirty ring 则以队列收集脏页，带来回收、满环处理及内存顺序方面的新约束。手动保护的设计动机、Dirty ring 约束

脏页记录的收割、重置与发布顺序见《KVM 脏页日志：位图与 Dirty Ring》。

4. 减少流量与控制收尾成本

零页识别避免发送整页零值；XBZRLE 在适合的重传场景中编码与已缓存页面的差异；压缩以 CPU 工作换取链路字节减少。实际收益取决于页面内容、缓存命中和处理能力。内存剩余量已经很小而停机仍长时，需要进一步分析设备保存、目的端装载和 I/O 交接的耗时。放宽停机目标可以更早切换，也会把更多工作留在暂停阶段。

后拷贝允许目的端在内存尚未传完时开始执行，剩余页面由后台传输，并在访问缺失页时优先请求。它减少了预拷贝阶段的重复传输，同时引入远程缺页延迟和两端状态依赖。预拷贝与后拷贝的选择还需结合业务延迟要求、网络稳定性和故障恢复条件。后拷贝设计

缺页请求、页面安装与恢复执行的过程见《QEMU 后拷贝迁移的缺页处理与页面传输》。
