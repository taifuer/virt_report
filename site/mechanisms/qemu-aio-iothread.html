前言

磁盘请求的大部分时间可能花在等待上。QEMU 需要让等待中的请求保留进度，同时继续处理其他队列、完成通知和管理事件。AioContext 组织事件分发，协程保存请求的执行过程，IOThread 提供独立的事件循环线程；三者共同决定 I/O 在何处运行、何时恢复。

本文沿 Linux 宿主上的 virtio-blk 写请求，跟踪 raw 文件后端的 aio=threads 路径，再讨论多队列映射、同步与调优。客户机描述符和完成通知的格式见virtio-blk 的请求处理与写入完成。

源码版本：QEMU 10.2.0。

线程、事件循环与协程

结构关键字段含义

AioContextaio_handlers / bh_list / notifier / tlg文件描述符处理器、延迟回调、跨线程唤醒和定时器。
Coroutineentry / caller / ctx / scheduled协程入口、调用关系、挂起时所属上下文与调度标记。

iothread_run() 设置当前线程的 AioContext，随后反复执行 aio_poll(ctx, true)。一次循环检查待处理事件，必要时等待，再分发 BH、就绪的文件描述符和定时器。Linux 上的等待实现可以使用 io_uring、epoll 或 poll；这层事件监控与磁盘的 aio=threads/native/io_uring 参数是两个不同的选择。

同一个 AioContext 的事件分发不能由两个线程并发执行。一个 IOThread 内可以交错推进许多请求，但同一时刻只执行其中一段代码。协程在 yield 时保存调用栈，恢复后从原位置继续；coroutine_fn 标记函数需要在协程中调用，本身不会创建线程或自动把阻塞调用异步化。

一次写请求的挂起与恢复

假设队列 0 已映射到 IOThread A，客户机提交一个 4 KiB 写请求，数据经映射得到一个连续 iovec，后端使用 raw 普通文件、writeback 缓存和 aio=threads。请求到达后，IOThread A 处理队列，调用 blk_aio_pwritev()。

blk_aio_prwv() 创建 BlkAioEmAIOCB，保存偏移、向量、完成函数等信息，再创建并进入写协程。协程沿块图下行到 raw_co_prw()，构造栈上的 RawPosixAIOData，交给线程池：

RawPosixAIOData
  aio_fildes = 文件 fd
  aio_offset = 本次写入的字节偏移
  aio_nbytes = 4096
  io.iov     = 映射后的客户机数据向量
  io.niov    = 1

ThreadPoolElementAio
  func = handle_aiocb_rw
  arg  = &RawPosixAIOData
  state: THREAD_QUEUED → THREAD_ACTIVE → THREAD_DONE

thread_pool_submit_co() 记录当前 Coroutine，将任务加入当前 AioContext 的线程池，然后执行 qemu_coroutine_yield()。协程栈仍然存在，因此栈上的请求参数保持有效；提交端也必须让 iovec 和数据缓冲区存活到完成。IOThread 返回事件循环，继续处理其他请求。

worker 从队列取出任务，执行 handle_aiocb_rw()。本例只有一个 iovec，进入 pwrite 循环；多个合适的 iovec 才尝试 pwritev。worker 返回后先保存结果，再发布 THREAD_DONE，通过 qemu_bh_schedule(completion_bh) 通知所属事件循环。它不直接修改客户机 used ring。

IOThread A 执行 thread_pool_completion_bh()，找到完成任务，调用 thread_pool_co_cb()。该函数保存返回值并通过 aio_co_wake() 恢复协程。原来的 submit_co 从 yield 后返回，结果沿块层回到 blk_aio_complete()，最后调用 virtio-blk 的完成函数，写状态、更新 used ring，并按通知规则告知客户机。

即使某条块路径立即完成，异步接口也不能在提交函数返回前提前调用外部完成函数。has_returned 配合完成 BH 保证这一点。上述 raw 写入成功只表示该次文件操作成功；writeback 下数据可能仍在宿主页缓存，持久化还取决于后续 flush、存储设备及其保证。

例如请求 A 先提交后挂起，请求 B 随后进入另一 worker 并先完成。IOThread 可以先恢复 B，再恢复 A。每个请求拥有自己的参数、协程和返回值，完成顺序不必等于提交顺序；应用需要的写入先后关系必须由客户机块层、协议中的 flush 等约束建立。增加 IOThread 不会替应用推导依赖关系。

BH 与跨线程调度

BH 是用户态的延迟回调。调度操作设置标志并把它加入所属 AioContext 的待处理链表，必要时通过 EventNotifier 唤醒事件循环。回调在目标线程运行，不在调用 qemu_bh_schedule 的线程内执行。线程池中的锁保护工作队列，结果发布与读取还使用内存屏障，避免看到 DONE 却读到旧结果。

aio_co_enter() 根据调用位置选择恢复方式：目标上下文不同，先把协程放入 scheduled_coroutines 并调度 co_schedule_bh；同上下文且当前不在协程中，可以直接进入；当前也在协程中，则加入唤醒队列，在安全的切换点处理。一个协程不能同时在两条线程上运行，也不能被重复入队。

跨线程执行普通函数通常用 aio_bh_schedule_oneshot(ctx, cb, opaque)。但把指针交给 BH 不会自动延长对象寿命，调用者仍需安排引用、完成等待和删除顺序。虚拟机关闭、设备移除及后端切换时，遗漏这些约束就可能使回调访问已释放的状态。

通知只表示有工作需要处理，实际结果存放在任务结构中。线程池共用一个 completion_bh，多次调度可以合并，回调扫描完成任务后逐一交付。因此不能把一次唤醒当成一个请求，也不能从通知次数推算吞吐量。取消同样有边界：尚在队列中的任务可以移除并返回取消错误，已经执行的阻塞文件操作则不能靠删除 BH 强行终止。

多队列如何分配到 IOThread

创建多个 virtqueue，只提供多个提交入口。若它们都映射到同一个 AioContext，请求解析和完成处理仍由同一条事件循环线程推进。下面的磁盘配置片段将四个队列分给两个 IOThread；disk.raw 需已存在：

-object iothread,id=io0 \
-object iothread,id=io1 \
-drive if=none,id=disk0,file=disk.raw,format=raw,aio=threads,cache=writeback \
-device '{"driver":"virtio-blk-pci","drive":"disk0","num-queues":4,"iothread-vq-mapping":[{"iothread":"io0","vqs":[0,2]},{"iothread":"io1","vqs":[1,3]}]}'

vq_aio_context[i] 保存队列 i 的映射，队列的 host notifier 挂到相应事件循环。显式映射要求队列全部覆盖、没有重复、索引合法；所有条目都省略 vqs 时则轮询分配。iothread 和 iothread-vq-mapping 不能同时设置，transport 还必须支持所需通知接口与 ioeventfd。

每个 IOThread 可以服务多个队列或磁盘；一个磁盘也可以由多个 IOThread 处理。aio=threads 的 worker 承担阻塞调用，不消费 virtqueue、不代替 IOThread 的事件分发。换成内核异步后端会改变请求提交与完成机制，也不会自动增加队列处理线程。

数据面并行与管理操作

IOThread 的数据路径通常不持有 BQL。设备配置、复位和管理操作仍有各自的同步要求。块层的 I/O API 可以跨线程调用，块图的修改需要图锁与相应的全局状态上下文；设备的共享请求链表等状态则由自己的锁保护。多条线程能够遍历同一块图，不意味着可以同时任意更改节点关系。

管理侧需要停止接收并等待已有请求完成时使用 drain。virtio-blk 的 drained_begin 会暂时摘下各队列的 host notifier，drained_end 再挂回。已有请求仍需由事件循环推进到完成，不能简单把 IOThread 停住再等它完成工作。drain 也不等于磁盘 flush，两者分别处理活动请求与持久化语义。

容量变更提供了一个具体的跨线程例子：virtio_blk_resize() 用 BH 把配置通知安排到主 AioContext，后者调用 virtio_notify_config()。把需要 BQL 的控制操作直接塞进普通 IOThread 回调，会破坏既有锁和上下文约束。

从单一事件循环到队列级并行

2014 年引入的 IOThread 对象让事件循环可以独立配置，减少数据路径与主循环、BQL 的竞争。协程让异步等待仍能保持顺序代码的结构；线程池为阻塞文件接口提供执行位置，但线程切换、排队和缓存局部性也随之成为成本。

2023 年末，块层移除了广泛使用的 AioContext acquire/release 锁定，改由明确的 API 分类、块图锁和对象级同步承担职责。本文版本仍有 AioContext.lock 字段，不能据此沿用旧式块层锁模型，也不能把这次改动解读成所有路径都无锁。

QEMU 9.0加入同一 virtio-blk 磁盘的队列到多 IOThread 映射，使单盘请求解析与完成处理能够使用多核。收益取决于客户机是否真正使用多个队列、宿主 CPU 余量以及后端并行能力；对低队列深度负载，增加线程可能只增加调度和跨核通信。

现象优先观察调整的代价
IOThread 单核忙，后端尚有余量客户机队列分布、映射和请求解析开销增加 IOThread 会增加共享状态竞争与 CPU 占用。
线程池排队时间长worker 数量、阻塞调用耗时、文件系统与存储队列放宽线程池可能只把拥塞推向下游。
低负载尾延迟偏高事件唤醒、线程调度、CPU 亲和性与 NUMA增大 poll-max-ns 可减少部分睡眠唤醒，但会消耗更多 CPU。

测量时至少分开客户机提交、队列处理、后端服务和完成回送，并同时记录吞吐、尾延迟与 CPU 使用率。IOThread 数量、worker 数量、virtqueue 数量和磁盘硬件队列数量分别控制不同层次，不能按一个统一比例机械配置。
