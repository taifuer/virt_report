一、场景与边界

从虚机内的应用开始：程序对虚拟磁盘的块设备执行 pread(fd, buf, 4096, 1048576) 或 pwrite()，读取或写入偏移 1 MiB 处的 4 KiB 数据。设备已用 O_DIRECT 打开。在演示顶部选择设备接口、后端与读写操作，观察对应的系统调用、Guest 内核、共享队列、后端处理与 KVM 中断注入，直到结果返回应用。

为看清设备路径，本例不经过 Guest 文件系统与页缓存：缓冲区已按 4 KiB 对齐，固定为一个页面、一个 bio 和一个块请求 R1，不发生拆分、合并或错误。Guest 内核固定用户页并建立 I/O 映射；读取时后端填充这份内存，写入时后端读取其内容，各层通过映射访问同一份缓冲区。普通文件读写的差异见后文。

共同前提是 x86 / KVM、modern virtio PCI 与 split ring；队列大小为 8，本次使用 3 个直接描述符，未启用 Guest vIOMMU。不同后端采用各自的执行上下文、通知与完成路径；具体配置随选择一起更新。本地文件可能命中宿主页缓存，SPDK 场景固定为轮询与 NVMe 后端，Ceph 展示到 QEMU / librbd 的异步接口边界，不展开集群内部协议。

演示从设备已就绪开始。队列建立过程见设备初始化与特性协商，另一种队列布局见 Packed virtqueue。

选择本地写入时可以进一步观察完成保证：写后 FLUSH 沿用应用起点，后续显式提交刷新 F1；FUA 则从已携带该要求的块请求 R1 开始，止于上层块请求完成，不推断应用的系统调用方式。

启用 JavaScript 后可逐步查看；完整流程也可直接阅读：

  1. 应用发起

    同步 pread 进入 Guest 内核，映射用户页并提交一个 bio。

  2. 准备请求

    Guest 为 R1 准备命令、结果缓冲区与描述符链。

  3. 发布队列

    先写描述符和 available 项，再发布 avail.idx。

  4. 通知后端

    本次需要 kick，KVM ioeventfd 唤醒 QEMU 队列处理。

  5. 解析请求

    QEMU 消费链头并建立本地请求与 iovec 视图。

  6. 异步读取

    块后端读取数据，原请求及缓冲区保持有效。

  7. 发布完成

    先写数据和状态，再发布 used 完成记录。

  8. 中断注入

    irqfd 路由到 LAPIC，设置待处理向量，经 VM-entry 注入后 Guest 才执行回调。

  9. 回收请求

    Guest 取回原上下文，归还描述符、完成 bio 与块请求。

  10. 返回应用

    原调用线程完成同步等待、释放页面引用，pread 返回 4096。

这是固定配置下的成功路径，不是运行中的虚拟机追踪，也不模拟真实时间、CPU 内部微操作或物理设备行为。完成发布与完成通知是不同步骤；通知的发送取决于协商能力和抑制条件。

中断展示固定为 x86 VMX 软件注入路径，不启用 APICv / posted interrupt。irqfd 通知、虚拟 APIC 中断挂起、VM-entry 注入与 Guest 执行处理函数是不同阶段。

地址为教学示例：应用 buf 是 Guest 虚拟地址，数据描述符 0x2000 是其后备页的 Guest 物理地址，后端通过宿主虚拟地址访问同一份后备内存。WRITE 标志指设备可写 Guest 内存，不表示磁盘写入。

    三、缓存与持久化

    写请求和读请求一样，需要向 Guest 交付完成状态。后端写入状态并发布 used，驱动通过中断提示或轮询发现完成记录，检查成功或失败，解除数据映射、回收描述符并结束块请求，再唤醒等待者或交付异步完成。中断本身不是成功标志，也不保证每个请求对应一次中断；普通写完成仍不等于掉电后数据可恢复。

    演示覆盖块设备直接读写，不代表所有应用 I/O。普通文件、缓存与持久化还涉及以下区别：

    场景Guest 内部设备与完成语义
    块设备直接读（本例）固定用户页，经 bio / blk-mq 提交。一次应用调用形成一个 R1 是本例的前提。数据描述符带 WRITE，设备把 4096 B 结果写入 Guest 缓冲区；完成结构与 used.len 随设备接口和实现变化，见关键结构视图。
    普通文件缓冲读先经过 VFS、文件系统和 Guest 页缓存。命中可能不发起设备 I/O；缺页读取、预读及请求拆分可能产生多个请求。设备通常先填充 Guest 缓存页，随后由内核向用户缓冲区交付所需数据，不能等同于本例的直接映射。
    块设备直接写应用先准备数据，内核固定缓冲区并提交写请求；完成前不能任意复用。数据描述符不带 WRITE，设备从 Guest 读取数据；virtio-blk 使用 OUT 与状态字节，virtio-scsi 使用 SCSI CDB 与响应结构。
    普通文件缓冲写写入可能先完成于 Guest 页缓存，设备 I/O 由后续回写触发。write() 返回、设备请求完成与掉电后仍可恢复是不同边界，持久化还需看同步操作、flush/FUA 及后端约定。

    进一步阅读：virtio-blk 写入、完成与持久化。原理文章解释协议与设计取舍，本页用于观察一次请求的状态变化，两者互相补充。

    四、写入完成与持久化

    在上方同一演示中选择“写入”，再选择“写入完成要求”：本地 virtio-blk 提供普通写与写后 FLUSH，本地 virtio-scsi 提供普通写与 FUA。R1、队列、源码和当前完成保证在同一个工作区连续展示，不需要另开播放器。RBD/SPDK 目前只展示其已核验的普通读写，不套用本地文件的刷新语义。

    本地场景使用 raw 文件、aio=threads、writeback=on 与 no-flush=off。写后 FLUSH 在普通 O_DIRECT 写返回后发起 fsync()，形成独立请求 F1；FUA 从已经携带 REQ_FUA 的块请求开始，到上层请求完成，不冒充完整应用同步写路径（后者还可能包含额外刷新）。缓存状态表达接口契约，不推断物理设备内部时序或真实耗时。

    1. 区分缓存路径与同步要求

    配置或操作控制范围完成保证
    Guest O_DIRECT本次 I/O 绕过 Guest 页缓存单独使用不保证掉电持久化，也不控制宿主页缓存
    QEMU cache.direct=on尽量绕过宿主页缓存设备仍可能有易失写缓存；direct 不等于同步持久化
    writeback=on 的普通 WRITE允许下层在缓存接受数据后报告完成应用可回收本次缓冲区，稳定存储状态尚未由该操作确认
    WRITE 完成后执行 FLUSH确认此前已完成、属于刷新范围的写入刷新成功后，这些数据达到下层承诺的稳定存储边界
    WRITE FUA约束本次写的完成条件本次数据持久化后才完成，不自动保证所有前序写入
    QEMU cache.no-flush=on允许跳过向存储落实的刷新；也会清除下传的 FUA 要求不能沿用本演示的持久化保证

    cache=none 对应 writeback=on、direct=on、no-flush=off，仍需要 Guest 正确发起同步。cache=unsafe 则允许忽略刷新。这些参数和 Guest 打开文件时的标志属于不同层，不能只凭“direct”或“无缓存”的名称判断数据安全。QEMU 缓存模式定义。

    2. FUA 在两种设备接口中的实现

    Linux 6.18 的块设备同步直接写可产生 REQ_FUA。virtio-scsi 在目标支持时把它编码到 SCSI WRITE 的 FUA 位；QEMU scsi-hd 再转换成 BDRV_REQ_FUA。本例的 raw threads 后端先完成文件写入，再执行刷新，最后才向 Guest 完成这条 SCSI 命令。其他后端可以直接支持 FUA，具体实现需分别检查。文件后端实现。完整系统调用还可能安排其他同步：例如同步块设备写在 write_iter 末尾还会经过 generic_write_sync()，不能把这里的一条命令直接当作完整调用的全部设备请求。Linux 调用边界。

    virtio-blk 的普通 OUT 命令没有这里的原生 FUA 位。固定版本的 Linux 驱动声明写缓存能力而不声明 BLK_FEAT_FUA，块层会为需要 FUA 的写入安排写后 FLUSH。它与应用先完成普通写、再显式调用 fsync() 的外部调用顺序不同；共同要求是同步操作不能在所需刷新完成前成功返回。驱动能力、块层 POSTFLUSH。

    需要同时约束前序数据和当前写时，上层可以组合 PREFLUSH 与 FUA。FUA 的契约只覆盖该写；某个后端用较大范围刷新来实现它，也不应让应用依赖额外的前序顺序保证。持久化还不同于原子性：本例不保证一组写入整体生效，也不涵盖文件创建、目录项或跨设备事务。Linux 写缓存控制契约。

    五、源码与相关内容

    “源码路径”按执行上下文列出关键函数路径，并高亮当前步骤涉及的函数，辅助调用已省略。Guest 与宿主通过共享队列和通知协作；异步提交与完成回调分开展示。示例中的 R1 用来关联两端各自保存的请求对象，具体源码随设备与后端选择更新。

    • SPDK vhost_blk.c：轮询共享队列，提交块请求并回写完成。
    • SPDK vhost_scsi.c：消费 SCSI 命令队列并建立后端任务。
