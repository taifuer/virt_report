网络 I/O 收发过程

本演示由 OpenAI Codex (GPT-6-Astra) 辅助编写。

一、场景与边界二、逐步演示三、缓冲区与完成语义四、后端演进与取舍五、源码与相关内容

一、场景与边界

客户机应用调用 sendto() 后，UDP/IP 协议栈把用户数据封装为网络帧，再由 virtio-net 驱动交给后端。接收方向则从后端写入 RX 缓冲区开始，经过驱动、协议栈和 socket 排队，最后由 recvfrom() 把 UDP 载荷复制给应用。QEMU、内核 vhost-net、DPDK vhost-user 与硬件 vDPA 使用相同的客户机设备接口，数据处理位置和缓冲区交接方式各有不同。

示例发送 ASCII 字符串 virt-report-demo01，共 18 B。加上 8 B UDP 头、20 B IPv4 头和 14 B Ethernet 头，得到 60 B 帧 P1；virtio-net 另外使用 12 B 网络头，设备 RX 的实际写入量为 72 B。接收应用提供 128 B 缓冲区，成功时 recvfrom() 返回 18。

队列按 8 个槽位展示，使用直接描述符。发送选取头部不能直接压入 skb 的分支，desc[0] → desc[2] 分别指向 12 B 网络头和 60 B 帧；接收采用 add_recvbuf_small()，desc[2] 提供 12 + GOOD_PACKET_LEN = 1530 B 可写空间。本次实际写入仍为 72 B。页片段还会分配 headroom 和 skb 元数据，分配大小不等于描述符向设备暴露的长度。

演示采用 x86 + KVM、QEMU 10.2.0、Linux 6.18；DPDK 路径采用 24.11。设备为 modern virtio-net，使用 split ring 和一个队列对：队列 0 接收，队列 1 发送。路由、邻居、设备协商与内存映射已经就绪；使用普通 UDP 复制路径，关闭分段、校验和卸载、合并 RX 缓冲区、UDP cork 和零拷贝发送。报文不带 IP 选项或 VLAN，也无需分片。

源码版本：QEMU 10.2.0、Linux 6.18、DPDK 24.11。

先选择后端及 TX / RX，再逐步观察处理者与字段变化。流程总览从应用调用开始，包含协议栈、队列、后端和返回；关键结构展示描述符的地址、长度、权限和 next，以及 available / used 的环项、发布索引、消费位置和缓冲区。填写环项与发布索引分成不同步骤，源码路径则按执行上下文列出关键函数。额外两个场景演示 TAP 背压与 RX 空间不足。

当前场景配置与源码版本

    源码版本：QEMU 10.2.0、Linux 6.18、DPDK 24.11。

    以下按场景列出处理顺序。启用 JavaScript 后可逐步观察结构与状态变化。

    QEMU + TAP · TX

    18 B UDP 载荷经客户机协议栈形成 60 B 帧，交给 virtio-net 与所选后端；分别观察 sendto 返回、队列归还与本地发送。

    • x86 + KVM；QEMU 10.2.0 / Linux 6.18；modern virtio-net、split ring、单队列对。
    • P1 为 60 B 以太网帧（不含 FCS），virtio-net 基础头为 12 B；不启用分段、校验和卸载、合并 RX 缓冲区或间接描述符。
    • QEMU 设备与 TAP FD 已连接。
    • Guest 回收与宿主后续转发可以并行；播放顺序展示一种可观察的执行顺序。
    • UDP/IPv4 小数据报：用户载荷 virt-report-demo01 为 18 B；8 B UDP + 20 B IPv4 + 14 B Ethernet，共 60 B 帧；virtio-net 另加 12 B 头。无 IP 选项、VLAN 或分片。
    • 普通 sendto(..., 18, 0, ...)，无 UDP_CORK、MSG_MORE 或 MSG_ZEROCOPY；路由、邻居及 socket 已就绪，发送预算与客户机 TX 队列均有空间，本次直接走到驱动。
    • virtqueue 发布后，Guest 返回与后端处理可并发。本次先展示 sendto 返回；后端也可能更早消费队列，TX used、线路发送与返回没有固定总顺序。
    • 队列固定为 8 槽 direct descriptors；地址是示意 GPA / IOVA。TX 选择 xmit_skb 的 can_push=false 且 skb 无分片分支，形成 12 B 头 + 60 B 帧两项；RX 选择 add_recvbuf_small，设备可写长度 12 + GOOD_PACKET_LEN = 1530 B，不等于页片段的实际分配大小。
    1. 初始状态 · 队列与后端

      应用持有 18 B 载荷，网络设备和队列已就绪，本次 sendto 尚未调用。 队列、socket 与用户缓冲区分别显示初始状态；没有处理者正在推进本次数据报。

      VIRTIO 1.2：split virtqueue（§2.7）
    2. 调用 sendto · Guest 用户态应用

      应用用 U0 提交 18 B UDP 载荷，目标地址交给 socket 层。 __sys_sendto() 导入用户缓冲区并构造 msghdr，随后分派到 IPv4 UDP。系统调用改变客户机内的执行特权级；本步不要求退出到 QEMU 处理。

      Linux · __sys_sendto()
    3. 构造 UDP/IP 报文 · Guest UDP/IP 协议栈

      普通复制路径把 18 B 用户数据复制入 skb，并完成 UDP、IPv4 与链路层封装。 UDP 无 cork 路径通过 ip_make_skb() 构建 skb；ip_generic_getfrag() 执行用户数据复制。邻居已解析，本例在客户机发送路径形成 14 + 20 + 8 + 18 = 60 B 帧。U0 与 skb 数据是不同的存储对象。

      Linux · udp_sendmsg() · Linux · ip_generic_getfrag() · Linux · ip_finish_output2()
    4. 交给 virtio-net · Guest 网络发送路径

      网络层把 skb S1 交给 virtio-net 的 start_xmit()。 本例 qdisc 与驱动队列有空间，当前调用推进到驱动提交。start_xmit() 通过 xmit_skb() 组织 virtio 网络头与 skb 分散表。其他配置下，skb 可以先在客户机排队，系统调用返回并不要求每次都已发布 virtqueue。

      Linux · start_xmit() · Linux · xmit_skb()
    5. 准备描述符 · Guest virtio-net 驱动

      将 12 B 网络头和 60 B 帧 P1 组织为链 0 → 2。 desc[0] 的 NEXT 指向 desc[2]，两个缓冲区均为设备可读。此时 avail.idx 尚未增加，后端不能据此消费本次请求。 这里的 60 B 来自 S1，virtio 网络头是设备接口附加的 12 B，不会交给远端 UDP 应用。

      Linux · xmit_skb() · Linux · virtnet_add_outbuf() · Linux · virtqueue_add_outbuf() · Linux · virtqueue_add_split() · VIRTIO 1.2：网络设备与收发队列（§5.1）
    6. 填写 available 环项 · Guest virtio-net 驱动

      avail.ring[0] = 0，索引仍为 0。 环项保存描述符链头，不保存报文。尚未推进 avail.idx，设备不能仅因槽位已有数字就消费这条链。

      Linux · virtqueue_add_split()
    7. 发布 TX 链 · Guest virtio-net 驱动

      描述符与环项写入完成后，通过发布屏障再令 avail.idx = 1。 内存顺序保证后端观察到新索引时可以读取完整的链。驱动在发布索引后检查通知条件，按协商的通知抑制规则决定是否 kick。

      Linux · virtqueue_add_split() · Linux · virtqueue_kick_prepare() · Linux · virtqueue_notify()
    8. sendto 返回 · Guest 系统调用返回路径

      本次 sendto 成功返回 18，应用可以继续执行并复用 U0。 18 是提交的 UDP 载荷字节数，未包含协议头。成功不保证交付；本例只确认本机发送路径接受请求，不等待 TX used、本地物理发送或远端接收。Guest 返回与后端消费从发布处分成两条分支，这里展示返回先发生的一种调度顺序。

      Linux · udp_sendmsg() · Linux · xmit_skb() · Linux send(2)：成功返回不保证网络交付
    9. 取得描述符链 · QEMU 用户态

      后端读取 available，取得链头 0 并检查设备可读区域。 virtio_net_flush_tx() 调用 virtqueue_pop()，解析可读 iovec 与网络头。

      QEMU · virtio_net_flush_tx()
    10. 交给 TAP · QEMU 用户态

      QEMU 网络层将 P1 通过 TAP FD 交给宿主网络。 qemu_sendv_packet_async() 经 TAP 后端调用 writev()；本例立即成功接受。返回 0 的异步排队情况另见 TX 背压场景。

      QEMU · virtio_net_flush_tx() · QEMU · tap_write_packet()
    11. 填写 used 完成项 · QEMU 用户态

      used.ring[0] = { id: 0, len: 0 }；used.idx 仍为 0。 设备已写好完成项，但尚未发布新索引。驱动仍必须按 used.idx 判断哪些记录可消费，TX 的 len=0 表示未向设备可写描述符写入字节，不表示发送帧长为零。

      QEMU · virtqueue_fill()
    12. 发布 TX 完成 · QEMU 用户态

      先完成数据与 used 环项写入，再发布 used.idx = 1；驱动现在可以消费。 used = {id: 0, len: 0} 表示设备已经结束对本链的使用。驱动观察到完成后可以回收原缓冲区；这一记录不能证明远端已经收到 P1。

      QEMU · virtqueue_flush()
    13. 提示客户机 · QEMU 用户态

      按通知条件提示客户机检查 used ring。 QEMU 的 virtio_notify() 检查通知条件，经已配置的虚拟中断路径通知 Guest。

      QEMU · virtio_net_flush_tx() · VIRTIO 1.2：split virtqueue（§2.7）
    14. 回收 TX 链 · Guest virtio-net 驱动

      驱动消费 used 项，找到链头 0 并释放本次发送引用。 回收位置更新为 1。Guest 链和原始发送缓冲区现在可以复用；描述符槽中的旧值无需清零，是否有效由环索引决定。 应用 U0 早已独立可用。socket 发送计账可能随 skb_orphan() 提前解除，也可能在 skb 释放时回收，不能与 used.idx 简单等同。

      Linux · __free_old_xmit() · Linux · virtqueue_get_buf() · Linux · virtqueue_get_buf_ctx_split() · VIRTIO 1.2：split virtqueue（§2.7） · Linux · xmit_skb()
    15. 继续网络转发 · 宿主网络

      P1 沿本地出口继续发送，虚拟队列已可承接下一帧。 路径中的排队、交换、丢包和远端处理不由本次 used 项报告。演示展示本地交付边界，未模拟对端协议栈或确认报文。 此处整理出口状态，与 Guest 返回及回收可交错；演示未收到对端确认，UDP 本身也不提供可靠交付确认。

      QEMU · virtio_net_flush_tx() · VIRTIO 1.2：网络设备与收发队列（§5.1）
    QEMU + TAP · RX

    从 RX 空缓冲区开始，跟踪 UDP 帧进入客户机协议栈、socket 接收队列，直到 recvfrom 把 18 B 载荷交给应用。

    • x86 + KVM；QEMU 10.2.0 / Linux 6.18；modern virtio-net、split ring、单队列对。
    • P1 为 60 B 以太网帧（不含 FCS），virtio-net 基础头为 12 B；不启用分段、校验和卸载、合并 RX 缓冲区或间接描述符。
    • QEMU 设备与 TAP FD 已连接。
    • 用一条 1530 B 可写描述符链表示接收空间；实际驱动可把头与数据分散在多个描述符中。
    • UDP/IPv4 小数据报：用户载荷 virt-report-demo01 为 18 B；8 B UDP + 20 B IPv4 + 14 B Ethernet，共 60 B 帧；virtio-net 另加 12 B 头。无 IP 选项、VLAN 或分片。
    • 普通阻塞 recvfrom(..., 128, 0, ...)，无 MSG_PEEK、MSG_TRUNC；socket 已绑定，路由、校验与接收内存预算满足本次报文，应用缓冲区容量足够。
    • 本例只收一帧，received 小于 NAPI budget；GRO_NORMAL 普通列表尚未达到提前刷新条件。驱动先 refill，随后在 NAPI 完成阶段将列表交给协议栈；补充空间无需等待 recvfrom 返回。
    • 队列固定为 8 槽 direct descriptors；地址是示意 GPA / IOVA。TX 选择 xmit_skb 的 can_push=false 且 skb 无分片分支，形成 12 B 头 + 60 B 帧两项；RX 选择 add_recvbuf_small，设备可写长度 12 + GOOD_PACKET_LEN = 1530 B，不等于页片段的实际分配大小。
    1. 初始状态 · 队列与后端

      应用有 128 B 接收空间，socket 和网络设备已就绪，本次数据报尚未到达。 队列、socket 与用户缓冲区分别显示初始状态；没有处理者正在推进本次数据报。

      VIRTIO 1.2：split virtqueue（§2.7）
    2. 等待 UDP 数据报 · Guest 用户态应用 / UDP socket

      应用调用 recvfrom(fd, U1, 128, 0, ...)，当前 socket 无数据，进入等待。 __sys_recvfrom() 导入可写用户缓冲区；udp_recvmsg() 从 UDP 接收队列取报文。阻塞调用暂时睡眠，驱动和后端仍可接收、回收并补充队列。

      Linux · __sys_recvfrom() · Linux · __skb_recv_udp() · Linux recv(2)：阻塞接收与返回长度
    3. 准备 RX 描述符 · Guest virtio-net 驱动

      desc[2] 指向一块 1530 B 设备可写空间。 固定 non-mergeable small-buffer 路径，长度为 12 B virtio 头 + GOOD_PACKET_LEN（1518 B）。页片段实际分配还包括 headroom 和 skb 元数据，不能把分配容量当作描述符长度。此时尚未发布 available。

      Linux · add_recvbuf_small() · Linux · virtqueue_add_inbuf_premapped() · Linux · virtqueue_add_split()
    4. 填写 available 环项 · Guest virtio-net 驱动

      avail.ring[0] = 2，索引仍为 0。 环项保存描述符链头，不保存报文。尚未推进 avail.idx，设备不能仅因槽位已有数字就消费这条链。

      Linux · virtqueue_add_split()
    5. 发布 RX 空间 · Guest virtio-net 驱动

      描述符与环项写入完成后，通过发布屏障再令 avail.idx = 1。 RX 描述符带 WRITE，允许设备写入头和报文。空缓冲区在来包之前提供；available 记录表示空间已准备好，不代表里面已经有新帧。

      Linux · virtqueue_add_split() · Linux · virtqueue_kick_prepare() · Linux · virtqueue_notify()
    6. 报文到达 · 宿主网络

      P1 经宿主网络送到 TAP，后端获得一个待交付的帧。 TAP 读事件触发 tap_send()，读取报文后将其交给 QEMU 网络层。

      QEMU · virtio_net_receive_rcu() · QEMU · tap_send()
    7. 取得可写链 · QEMU 用户态

      后端观察到 avail.idx = 1，取出 head 2 并检查容量和 WRITE 权限。 virtio_net_has_buffers() 确认空间，virtqueue_pop() 取出可写描述符。本例 1530 B 足以容纳 72 B 头与帧。

      QEMU · virtio_net_receive_rcu() · QEMU · virtio_net_has_buffers()
    8. 写入报文 · QEMU 用户态

      向 Guest 缓冲区写入 12 B 网络头和 P1 的 60 B 帧内容。 QEMU 通过 iovec 复制头和报文，写入量为 12 + 60 = 72 B，余下容量不属于本帧。

      QEMU · virtio_net_receive_rcu()
    9. 填写 used 完成项 · QEMU 用户态

      used.ring[0] = { id: 2, len: 72 }；used.idx 仍为 0。 设备已写好完成项，但尚未发布新索引。驱动仍必须按 used.idx 判断哪些记录可消费，RX 的 len=72 是实际写入量，不是 1530 B 空间容量。

      QEMU · virtqueue_fill()
    10. 发布 RX 完成 · QEMU 用户态

      先完成数据与 used 环项写入，再发布 used.idx = 1；驱动现在可以消费。 完成记录包含本次实际写入量 72 B，容量仍是 1530 B。数据写入必须先于完成进度对驱动可见，驱动据此判断缓冲区可读。

      QEMU · virtqueue_flush()
    11. 提示 Guest 接收 · QEMU 用户态

      在需要通知的条件下，提示客户机 RX 队列有完成。 通知路径可经过 call eventfd 与配置的虚拟中断；具体是否发送取决于队列通知规则。used 内容独立保存完成记录。

      QEMU · virtio_net_receive_rcu() · VIRTIO 1.2：split virtqueue（§2.7）
    12. 回收 RX 链并交给 NAPI · Guest virtio-net / NAPI

      驱动消费 head 2，去掉 12 B virtio-net 头，将 60 B 帧交给 NAPI 接收处理。 驱动回收描述符后，napi_gro_receive() 接管接收 skb。本例单帧走 GRO_NORMAL，普通接收列表尚未达到提前刷新条件，UDP socket 此时仍为空。描述符槽可以复用，旧数据页继续由接收路径持有。

      Linux · virtnet_poll() · Linux · virtnet_receive() · Linux · virtnet_rq_get_buf() · Linux · virtqueue_get_buf_ctx() · Linux · virtqueue_get_buf_ctx_split() · Linux · receive_buf() · Linux · virtnet_receive_done() · Linux · gro_skb_finish()
    13. 重新关联 RX 空间 · Guest virtio-net 驱动

      已回收的 desc[2] 改指向另一块 1530 B 缓冲区。 旧 P1 仍由接收 skb 引用。这里复用的是描述符槽，不是提前覆盖仍被协议栈引用的旧报文页。

      Linux · try_fill_recv() · Linux · add_recvbuf_small() · Linux · virtqueue_add_inbuf_premapped()
    14. 填写下一 available 环项 · Guest virtio-net 驱动

      avail.ring[1] = 2，avail.idx 暂时仍为 1。 新一代链仍使用 head 2，但指向新的缓冲区；已经消费的 slot 0 和 used slot 0 保留旧值。

      Linux · virtqueue_add_split()
    15. 补充下一块 RX 空间 · Guest virtio-net 驱动

      发布屏障之后令 avail.idx = 2，向设备交出新 RX 空间。 virtnet_receive() 消费当前批次后检查空闲描述符并调用 try_fill_recv()。本例分配成功，示意一条新链写入 slot 1，使 avail.idx = 2；实际驱动可批量补入更多缓冲区。旧 P1 仍由 NAPI 接收路径持有，新空间无需等待 socket 入队或 recvfrom 返回。

      Linux · try_fill_recv() · Linux · virtqueue_add_split() · Linux · virtqueue_kick_prepare()
    16. 送入 UDP socket · Guest IPv4 / UDP 协议栈

      本轮 NAPI 完成后，普通列表交给 IPv4 / UDP 协议栈，校验并分发 P1，将 18 B 载荷排入目标 socket。 本例 received 小于 budget，virtnet_poll() 经 virtqueue_napi_complete() 调用 napi_complete_done()，由 gro_flush_normal() 刷新普通列表。UDP 根据地址和端口查找 socket，接收预算足够时排队并通知等待者。Linux 6.18 可能经 producer queue 归并，再由 reader_queue 供 recvmsg 消费；这里显示逻辑上一个待收数据报。唤醒只使线程可运行。

    三、缓冲区与完成语义

    普通发送会把用户数据复制到客户机内核的 skb。应用缓冲区 U0、内核 skb S1、设备描述符，以及 DPDK 路径中的宿主 mbuf 是不同对象。sendto() 返回后，应用可以复用 U0，已经复制出的数据仍可沿后续路径转发。UDP 发送内存预算用于约束本地资源使用；普通无 cork UDP 不会像 TCP 那样保留可靠重传队列。

    TX 发布的是已准备好的帧，后端获得设备可读的缓冲区；RX 提前发布空闲空间，后端获得设备可写的缓冲区。两种方向都先写内容或描述符，再发布索引。通知只提示另一端检查队列，完成记录由 used 保存，多个报文可以共用一次通知。

    avail.ring[n] 保存链头编号，不保存报文本身；描述符的 addr 才指向缓冲区。used.ring[n] 保存链头与本次设备写入长度。槽位已有数据不代表已发布：只有观察到新的索引，另一端才能消费。TX 的 used.len = 0 表示设备没有向可写描述符写入字节，不是帧长为零；RX 的 used.len = 72 则不等于空间容量 1530 B。

    TX used设备结束对该 Guest 链的使用，驱动可回收缓冲区本地网络排队、链路发送与远端接收可能尚未结束
    本地网卡 TX 完成网卡结束对相应发送缓冲区的使用远端协议栈与应用接收仍需独立确认；UDP 自身不提供可靠送达确认
    RX used帧已写入 Guest 可写空间，实际写入量可见客户机还要消费队列、处理协议，再交给应用

    Guest RX 回收描述符槽可重新关联可用空间旧数据页可能仍被 skb 引用，补充空间要遵守引用生命周期

    发送在队列发布后分成并行的两条路径：Guest 沿系统调用返回，宿主后端消费已发布的链。本页展示先返回、后处理的一种调度顺序，后端也可能更早运行。图中返回边直接连接客户机协议栈和应用，设备完成不会作为 sendto() 返回的前置条件。真实系统若先把 skb 排入客户机 qdisc，返回还可能早于 virtqueue 发布。

    RX 演示选取单帧接收路径：驱动回收 used 链，把 skb 交给 NAPI；GRO_NORMAL 普通列表尚未达到提前刷新条件，驱动先补充新 RX 空间。本轮处理量小于 budget，随后在 NAPI 完成阶段由 gro_flush_normal() 把普通列表交给协议栈。IPv4 / UDP 校验与分发完成后，数据才进入 socket。批量阈值或处理预算不同，协议交付与 refill 可以交错；补充新空间始终不以应用读完旧数据为前提。

    数据进入 socket 后，等待的应用变为可运行；获得 CPU 后才能复制载荷并返回。设备完成也不保证数据能进入 socket：协议校验、接收预算和应用消费速度都可能成为后续限制。本例选择空间充足、校验通过的一条成功路径。

    DPDK 的普通同步路径有两份独立存储。TX 将 Guest 帧复制为 mbuf，归还 Guest 链后仍可继续转发这个 mbuf；RX 则从 mbuf 复制到 Guest 空间，成功返回后应用可释放宿主 mbuf。rte_vhost_dequeue_burst() 从 Guest 取包，rte_vhost_enqueue_burst() 向 Guest 送包。两个名字以 vhost 接口为视角。

    队列空间和网络交付能力也应分别观察。TX 的 TAP 暂不可写时，QEMU 保留异步请求，写入恢复后才归还链。RX 没有可写缓冲区时，QEMU 等待 refill 并暂停上游交付；本例演示恢复成功，持续超载仍受有限队列约束，可能丢包。有关 NAPI、缓冲区补充与竞态的细节见virtio-net 接收路径。

    四、后端演进与取舍

    这些路径保留相同的客户机设备接口，把不同部分放到更合适的执行位置。优化应同时观察吞吐、尾延迟、CPU 消耗，以及迁移和维护能力，单看少经过一个进程无法判断最终效果。

    后端数据面变化代价与适用条件
    QEMU + TAPQEMU 解析队列，并通过 TAP 连接宿主网络路径集中、易于观察；逐包处理和跨用户态边界会消耗 CPU
    内核 vhost-net队列处理接入宿主内核，减少 QEMU 的逐包往返仍受内核调度、网络栈、内存访问与 CPU 亲和性影响
    DPDK vhost-user独立用户态进程通过轮询、批处理和 PMD 组织数据面需要配置数据线程、内存及 NUMA；持续轮询消耗 CPU，普通路径仍有复制
    硬件 vhost-vDPA设备通过 DMA 处理 Guest 队列，减少宿主软件逐包参与依赖硬件能力、映射和设备状态管理；迁移与可观测性需要额外支持

    vhost-user 的 Unix socket 负责共享内存、队列和通知配置，逐包数据通过共享内存访问。vDPA 也包括软件实现；本页固定为硬件 direct 模式，关闭 Shadow Virtqueue（SVQ）。启用 SVQ 后，QEMU 会参与队列转接，不能沿用本页的直接访问路径。对应实现分别见vhost-net 与 vhost-user、DPDK 网络转发和vhost-vDPA 与 SVQ。
