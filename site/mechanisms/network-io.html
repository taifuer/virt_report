一、场景与边界

发送由客户机应用调用 sendto()，UDP/IP 协议栈封装网络帧，再由 virtio-net 驱动交给后端。接收则由驱动预置空 RX 缓冲区，外部报文可以主动到达；经过设备、驱动和协议栈后，数据进入已绑定的 socket，应用再用 recvfrom() 读取。收包不由某次 recvfrom 发起，也不是让网卡去获取指定报文。

QEMU、内核 vhost-net、DPDK vhost-user 与硬件 vDPA 使用相同的客户机设备接口，但数据处理位置和缓冲区交接方式不同。本页分别观察应用调用、Guest 队列、完成中断与宿主处理；它们的“完成”不代表同一件事。

示例发送 ASCII 字符串 virt-report-demo01，共 18 B。加上 8 B UDP 头、20 B IPv4 头和 14 B Ethernet 头，得到 60 B 帧 P1；virtio-net 另外使用 12 B 网络头，设备 RX 的实际写入量为 72 B。接收应用提供 128 B 缓冲区，成功时 recvfrom() 返回 18。

队列按 8 个槽位展示，使用直接描述符。发送选取头部不能直接压入 skb 的分支，desc[0] → desc[2] 分别指向 12 B 网络头和 60 B 帧；接收采用 add_recvbuf_small()，desc[2] 提供 12 + GOOD_PACKET_LEN = 1530 B 可写空间。本次实际写入仍为 72 B。页片段还会分配 headroom 和 skb 元数据，分配大小不等于描述符向设备暴露的长度。

演示采用 x86 + KVM、QEMU 10.2.0、Linux 6.18；DPDK 路径采用 24.11。设备为 modern virtio-net，使用 split ring 和一个队列对：队列 0 接收，队列 1 发送。路由、邻居、设备协商与内存映射已经就绪；使用普通 UDP 复制路径，关闭分段、校验和卸载、合并 RX 缓冲区、UDP cork 和零拷贝发送。报文不带 IP 选项或 VLAN，也无需分片。

源码版本：QEMU 10.2.0、Linux 6.18、DPDK 24.11。

规范依据：VIRTIO 1.2 CS01。规范版本记录

    QEMU + TAP · TX

    18 B UDP 载荷形成 60 B 帧，提交宿主网络栈后归还 TX 链；完成通知表示缓冲区可回收，不是对端收包确认。

    • x86 + KVM；QEMU 10.2.0 / Linux 6.18；modern virtio-net、split ring、单队列对。
    • P1 为 60 B 以太网帧（不含 FCS），virtio-net 基础头为 12 B；不启用分段、校验和卸载、合并 RX 缓冲区或间接描述符。
    • QEMU 设备与 TAP FD 已连接。
    • Guest 回收与宿主后续转发可以并行；播放顺序展示一种可观察的执行顺序。
    • UDP/IPv4 小数据报：用户载荷 virt-report-demo01 为 18 B；8 B UDP + 20 B IPv4 + 14 B Ethernet，共 60 B 帧；virtio-net 另加 12 B 头。无 IP 选项、VLAN 或分片。
    • 普通 sendto(..., 18, 0, ...)，无 UDP_CORK、MSG_MORE 或 MSG_ZEROCOPY；路由、邻居及 socket 已就绪，发送预算与客户机 TX 队列均有空间，本次直接走到驱动。
    • virtqueue 发布后，Guest 返回与后端处理可并发。本次先展示 sendto 返回；后端也可能更早消费队列，TX used、线路发送与返回没有固定总顺序。
    • 队列固定为 8 槽 direct descriptors；地址是示意 GPA / IOVA。TX 选择 xmit_skb 的 can_push=false 且 skb 无分片分支，形成 12 B 头 + 60 B 帧两项；RX 选择 add_recvbuf_small，设备可写长度 12 + GOOD_PACKET_LEN = 1530 B，不等于页片段的实际分配大小。
    • 通知路径启用 KVM ioeventfd；本例首次发布新链时后端请求 kick，未协商 VIRTIO_F_NOTIFICATION_DATA。notify 区写入队列编号，由 KVM 触发预先注册的 eventfd；发送载荷保存在 Guest RAM。
    • 完成中断固定为 MSI-X，表项未屏蔽，队列允许本次通知；未协商 EVENT_IDX。使用 KVM 内核 LAPIC 与 VMX 软件注入，未启用 APICv / posted interrupt；目标 vCPU 的 IF=1、无中断阴影且优先级允许接受向量 0x51。Guest 开启 TX NAPI，TX 回调安排后续 NAPI 回收。
    • 本例展示一次队列完成提示从发起到 Guest 接受的过程，不把 eventfd、vLAPIC 待处理与注入计为多次通知。实际中断可以合并或抑制，驱动也可轮询完成记录；一份报文不保证对应一次中断。
    1. 初始状态 · 队列与后端

      应用持有 18 B 载荷，网络设备和队列已就绪，本次 sendto 尚未调用。 队列、socket 与用户缓冲区分别显示初始状态；没有处理者正在推进本次数据报。

      VIRTIO 1.2：split virtqueue（§2.7）
    2. 调用 sendto · Guest 用户态应用

      应用用 U0 提交 18 B UDP 载荷，目标地址交给 socket 层。 __sys_sendto() 导入用户缓冲区并构造 msghdr，随后分派到 IPv4 UDP。系统调用改变客户机内的执行特权级；本步不要求退出到 QEMU 处理。

      Linux · __sys_sendto()
    3. 构造 UDP/IP 报文 · Guest UDP/IP 协议栈

      普通复制路径把 18 B 用户数据复制入 skb，并完成 UDP、IPv4 与链路层封装。 UDP 无 cork 路径通过 ip_make_skb() 构建 skb；ip_generic_getfrag() 执行用户数据复制。邻居已解析，本例在客户机发送路径形成 14 + 20 + 8 + 18 = 60 B 帧。U0 与 skb 数据是不同的存储对象。

      Linux · udp_sendmsg() · Linux · ip_generic_getfrag() · Linux · ip_finish_output2()
    4. 交给 virtio-net · Guest 网络发送路径

      网络层把 skb S1 交给 virtio-net 的 start_xmit()。 本例 qdisc 与驱动队列有空间，当前调用推进到驱动提交。start_xmit() 通过 xmit_skb() 组织 virtio 网络头与 skb 分散表。其他配置下，skb 可以先在客户机排队，系统调用返回并不要求每次都已发布 virtqueue。

      Linux · start_xmit() · Linux · xmit_skb()
    5. 准备描述符 · Guest virtio-net 驱动

      将 12 B 网络头和 60 B 帧 P1 组织为链 0 → 2。 desc[0] 的 NEXT 指向 desc[2]，两个缓冲区均为设备可读。此时 avail.idx 尚未增加，后端不能据此消费本次请求。 这里的 60 B 来自 S1，virtio 网络头是设备接口附加的 12 B，不会交给远端 UDP 应用。

    6. 填写 available 环项 · Guest virtio-net 驱动

      avail.ring[0] = 0，索引仍为 0。 环项保存描述符链头，不保存报文。尚未推进 avail.idx，设备不能仅因槽位已有数字就消费这条链。

      Linux · virtqueue_add_split()
    7. 发布 TX 链 · Guest virtio-net 驱动

      描述符与环项写入完成后，通过发布屏障再令 avail.idx = 1。 发布屏障使描述符和 available 环项先于新索引可见。后端依据 avail.idx 判断可消费的范围。

      Linux · virtqueue_add_split()
    8. 通知后端 · Guest virtio-net 驱动

      驱动确认需要通知，vp_notify() 向 notify 区写入队列号 1。KVM 匹配 ioeventfd 注册项，触发对应 eventfd。 QEMU 事件循环读取并清除 eventfd，调用队列处理函数；TX handler 调度 bottom half，随后读取 available。这次门铃写由 KVM 内核处理，不必让 KVM_RUN 以 MMIO 退出返回 QEMU。

    9. sendto 返回 · Guest 系统调用返回路径

      本次 sendto 成功返回 18，应用可以继续执行并复用 U0。 18 是提交的 UDP 载荷字节数，未包含协议头。成功不保证交付；本例只确认本机发送路径接受请求，不等待 TX used、本地物理发送或远端接收。Guest 返回与后端消费从发布处分成两条分支，这里展示返回先发生的一种调度顺序。

      Linux · udp_sendmsg() · Linux · xmit_skb() · Linux send(2)：成功返回不保证网络交付
    10. 取得描述符链 · QEMU 用户态

      后端观察 available 新索引，取出链头 0，检查设备可读缓冲区。 virtio_net_flush_tx() 通过 virtqueue_pop() 取得 iovec，解析 virtio-net 头；报文仍在 Guest RAM，下一步交给 TAP。

      QEMU · virtio_net_flush_tx()
    11. 提交宿主网络栈 · QEMU 用户态

      报文经 TAP 交给宿主网络栈；本例采用普通复制路径，宿主已有独立的报文存储。 qemu_sendv_packet_async() 经 tap_write_packet() 调用 writev()；成功返回后，QEMU 才发布 TX used。这表示宿主已接受报文，不表示物理网卡发完或远端收到；后续转发不等待 Guest 回收。

      QEMU · virtio_net_flush_tx() · QEMU · tap_write_packet()
    12. 填写 used 完成项 · QEMU 用户态

      used.ring[0] = { id: 0, len: 0 }；used.idx 仍为 0。 设备已写好完成项，但尚未发布新索引。驱动仍必须按 used.idx 判断哪些记录可消费，TX 的 len=0 表示未向设备可写描述符写入字节，不表示发送帧长为零。

      QEMU · virtqueue_fill()
    13. 发布 TX 完成 · QEMU 用户态

      先完成数据与 used 环项写入，再发布 used.idx = 1；驱动现在可以消费。 used = {id: 0, len: 0} 表示设备已经结束对本链的使用。驱动观察到完成后可以回收原缓冲区；这一记录不能证明远端已经收到 P1。 TX used 表示设备不再使用这份 Guest 缓冲区；驱动还需回收资源，不是物理网卡或远端的发送确认。

      QEMU · virtqueue_flush()
    14. 发起本次完成中断 · QEMU 用户态

      QEMU 检查队列通知条件和 MSI-X 屏蔽状态，通过 KVM_SIGNAL_MSI 提交本次完成中断。 固定 QEMU 主事件循环持有 BQL 的设备处理路径：virtio_irq() 经 MSI-X 设备通知进入 KVM。此时 used 已发布，Guest 尚未执行中断处理；使用 IOThread 的设备可另走 guest notifier / irqfd。 这是本次 used 完成的提示；随后 KVM 注入与 Guest 处理的是同一次中断，不是再次通知。

      QEMU · virtio_notify() · QEMU · virtio_should_notify() · QEMU · virtio_irq() · QEMU · msix_notify() · QEMU · kvm_irqchip_send_msi()
    15. 本次中断等待 vCPU 接受 · KVM · MSI 路由与 vLAPIC

      KVM 按 MSI 地址与数据选中目标 vCPU，在其虚拟 LAPIC 中记录向量 0x51。 IRR 记录待处理状态，并请求目标 vCPU 处理事件；必要时唤醒或踢出正在运行的 vCPU。此时尚未跳转到 Guest 中断入口。

      Linux · kvm_set_msi() · Linux · vmx_deliver_interrupt()
    16. 准备注入同一次中断 · KVM · 目标 vCPU 线程

      目标 vCPU 线程检查中断接受条件，应答 LAPIC 请求，并准备下一次 VM-entry 的中断注入字段。 本例 IF、优先级和中断阴影检查均通过。vmx_inject_irq() 填写 VMCS；设置注入字段还没有执行 Guest 指令。若当前不可接受，KVM 保留待处理状态，等待合适窗口。

      Linux · vmx_interrupt_allowed() · Linux · kvm_apic_ack_interrupt() · Linux · vmx_inject_irq()
    17. Guest 接受本次完成中断 · Guest 内核 · IRQ 与 virtio 回调

      VM-entry 成功后，CPU 按 Guest IDT 转入中断入口；virtio 队列回调安排 NAPI。 本例开启 TX NAPI，skb_xmit_done() 安排发送完成清理。中断入口的 APIC 应答只更新中断服务状态；NAPI 随后依据 used.idx 回收队列，两个进度各自维护。

      Linux · vmx_inject_irq() · Linux · handle_edge_irq() · Linux · vring_interrupt()
    18. 回收 TX 链 · Guest virtio-net 驱动

      驱动依据 used.idx 取得链头 0，回收描述符并释放发送 skb 的设备引用。 回收位置推进到 1，缓冲区可复用；槽位旧值可保留。应用 U0 在 sendto 返回时已独立可用；socket 计账可能在 skb_orphan() 时提前解除，与 TX used 无固定对应关系。

    三、缓冲区与完成语义

    普通发送会把用户数据复制到客户机内核的 skb。应用缓冲区 U0、内核 skb S1、设备描述符，以及 DPDK 路径中的宿主 mbuf 是不同对象。sendto() 返回后，应用可以复用 U0，已经复制出的数据仍可沿后续路径转发。UDP 发送内存预算用于约束本地资源使用；普通无 cork UDP 不会像 TCP 那样保留可靠重传队列。

    TX 发布的是已准备好的帧，后端获得设备可读的缓冲区；RX 提前发布空闲空间，后端获得设备可写的缓冲区。两种方向都先写内容或描述符，再发布索引。通知只提示另一端检查队列，完成记录由 used 保存，多个报文可以共用一次通知。

    “发布完成”与“Guest 处理中断”不是通知两次。本例先发布 used，再发起一次完成提示；KVM 记录 vLAPIC 待处理中断，目标 vCPU 随后接受它，Guest 回调安排 NAPI。提交、待处理、注入和处理是同一次中断的不同位置。驱动依据 used 消费完成记录，不根据中断次数判断完成了几个报文；实际通知也可以被抑制或由轮询替代。

    avail.ring[n] 保存链头编号，不保存报文本身；描述符的 addr 才指向缓冲区。used.ring[n] 保存链头与本次设备写入长度。槽位已有数据不代表已发布：只有观察到新的索引，另一端才能消费。TX 的 used.len = 0 表示设备没有向可写描述符写入字节，不是帧长为零；RX 的 used.len = 72 则不等于空间容量 1530 B。

    观察点已经完成后续工作
    sendto 返回 18本例的本机发送路径接受了 18 B UDP 载荷，应用可复用用户缓冲区不保证交付，不等待 TX used、物理发送或远端响应
    TX used设备结束对该 Guest 链的使用，驱动可回收缓冲区本地网络排队、链路发送与远端接收可能尚未结束
    本地网卡 TX 完成网卡结束对相应发送缓冲区的使用远端协议栈与应用接收仍需独立确认；UDP 自身不提供可靠送达确认
    RX used帧已写入 Guest 可写空间，实际写入量可见客户机还要消费队列、处理协议，再交给应用
    DPDK TX 提交返回数量对应的 mbuf 交给 PMD网卡完成使用后，PMD 才能清理这些 mbuf
    Guest RX 回收描述符槽可重新关联可用空间旧数据页可能仍被 skb 引用，补充空间要遵守引用生命周期
    recvfrom 返回 1818 B UDP 载荷已复制到应用的 128 B 缓冲区应用继续处理数据；新的 RX 缓冲区可以早已发布

    发送在队列发布后分成并行的两条路径：Guest 沿系统调用返回，宿主后端消费已发布的链。本页展示先返回、后处理的一种调度顺序，后端也可能更早运行。图中返回边直接连接客户机协议栈和应用，设备完成不会作为 sendto() 返回的前置条件。真实系统若先把 skb 排入客户机 qdisc，返回还可能早于 virtqueue 发布。

    QEMU + TAP 的普通 TX 路径在 writev() 成功返回后发布 used，再判断完成通知条件。此时宿主已经接受了帧，网络转发可以独立推进；Guest 侧依次处理虚拟中断和队列回收。宿主转发可能在写 TAP 的调用内部就已开始，两条路径之间没有“Guest 回收后才发送”的依赖。TAP 暂不可写时则保留请求，等待重试成功后发布 used。QEMU 发送与完成、TAP 写入

    RX 演示选取单帧接收路径：NAPI poll 从 used 取回链，构造 skb 并交给 GRO；GRO_NORMAL 普通列表尚未达到提前刷新条件，驱动先补充新 RX 空间。本轮处理量小于 budget，随后在 NAPI 完成阶段由 gro_flush_normal() 把普通列表交给协议栈。IPv4 / UDP 校验与分发完成后，数据才进入 socket。批量阈值或处理预算不同，协议交付与 refill 可以交错；补充新空间始终不以应用读完旧数据为前提。

    本例数据先进入 socket，应用随后调用 recvfrom，直接读取已有数据。若应用先调用、socket 尚无数据，阻塞调用会等待；入队时再唤醒等待者，线程获得 CPU 后才能复制载荷。非阻塞调用在无数据时返回 EAGAIN。这是同一接收机制下调用时机的区别，不需要另选一种收包模式。设备完成也不保证数据能进入 socket：协议校验、接收预算等可能导致后续丢弃。

    DPDK 的普通同步路径有两份独立存储。TX 将 Guest 帧复制为 mbuf，在发布 used 并检查通知条件后返回；应用取得 mbuf，即可交给 PMD，无需等待 Guest 执行中断或回收描述符。RX 则从 mbuf 复制到 Guest 空间；rte_vhost_enqueue_burst() 成功返回后，应用可释放已复制报文对应的宿主 mbuf，Guest 的 NAPI 与协议栈继续处理自己的副本。rte_vhost_dequeue_burst() 从 Guest 取包，rte_vhost_enqueue_burst() 向 Guest 送包，两个名字以 vhost 接口为视角。

    硬件 vDPA 直接访问 Guest 缓冲区。设备必须结束对本次发送链及其数据的使用，才可发布 TX used；DMA 刚开始或报文刚进入硬件处理流程都不足以满足这一条件。内部缓存、流水线和发送完成策略由具体设备实现，通用 virtio 接口只保证 used 之后可以归还缓冲区。演示保留这条保证，不把设备完成解释为远端收包确认。

    队列空间和网络交付能力也应分别观察。TX 的 TAP 暂不可写时，QEMU 会保留异步请求；RX 没有可写缓冲区时，也可能暂停上游交付。持续超载受有限队列约束，仍可能丢包。默认演示固定空间充足的成功路径，不额外设置“正常/缓冲区不足”选择。有关 NAPI、缓冲区补充与竞态的细节见virtio-net 接收路径。

    这些路径保留相同的客户机设备接口，把不同部分放到更合适的执行位置。优化应同时观察吞吐、尾延迟、CPU 消耗，以及迁移和维护能力，单看少经过一个进程无法判断最终效果。
