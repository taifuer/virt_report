一、保留 virtio 接口，改变队列处理位置

virtio-net 驱动通过 virtqueue 提交网络请求。同一套客户机接口，可以由 QEMU 处理，也可以连接宿主内核中的 vhost-net 或独立进程中的 vhost-user 后端。后端位置改变后，队列地址、内存访问权限和通知通道需要重新安排，设备初始化和报文处理也由不同组件承担。

本文沿用 网卡模拟与 virtio-net 发包路径中的 split virtqueue，分析 x86 / KVM 下单个发送请求。QEMU 和 vhost-net 路径使用 TAP；vhost-user 部分分析协议定义的共享内存和 eventfd 路径，网络出口由外部后端实现。示例不配置客户机 IOMMU，也不展开分段卸载、多队列和异常重试。

三条路径都处理同一个动作：从 available 取出报文 P1 的描述符，读取缓冲区，把报文交给出口，再发布 used。差别集中在“谁读队列”和“怎样把它唤醒”。先看后端如何获得内存与队列访问权，再比较一次发包经过哪些进程或内核上下文，最后评价减少中转所带来的收益及新的管理成本。

源码版本：QEMU 10.2.0、Linux 6.18。

二、QEMU、vhost-net 与 vhost-user 的分工

一个 TX virtqueue 包含描述符表、available ring 和 used ring。客户机驱动把网络头与报文放在客户机 RAM 中，发布描述符链；后端读取链上的数据，处理完成后写回 used ring。队列位于客户机内存，处理它的代码可以运行在不同的宿主执行环境中。

1. 内存如何被后端访问

vhost-net 接收内存区域表和队列地址，内核据此访问客户机的描述符及数据缓冲区。vhost-user 还需要跨进程建立映射：QEMU 发送区域描述和可共享内存的文件描述符，外部后端执行映射，并建立客户机地址、QEMU 地址与自身映射地址之间的对应关系。双方映射同一份内存，虚拟地址可以不同。共享映射的建立不会把全部客户机 RAM 复制一遍。

vhost-user 的内存消息描述客户机地址、区域长度、QEMU 用户地址和文件偏移；队列地址则用于定位描述符表与索引。后端必须验证访问范围。配置客户机 IOMMU 后，还需要处理 IOTLB 映射及失效，不能直接套用本例的地址转换。地址转换与 IOTLB

  1. QEMU 配置设备；内核后端通过 ioctl，外部后端通过 Unix socket 获得内存、队列及通知信息。
  2. 客户机发布 available 项，按需 kick；选定消费者读取同一份描述符和报文。
  3. QEMU 或 vhost-net 交给 TAP；外部后端使用自身的网络出口。
  4. 后端回写 used，按条件通知客户机，驱动随后回收缓冲区。

启用 JavaScript 可切换处理位置，并逐步观察初始化与发送过程。

本例采用 eventfd 通知，假定 kick 和完成通知均需要发送，后端发送成功；每步表示逻辑阶段。外部后端以协议职责表示，不限定其线程或网络实现。切换后端会重置过程。

1. 初始化：把队列交给后端

  1. 协商能力。QEMU 查询后端支持的 virtio 特性，再结合设备配置与客户机协商结果设置生效特性。vhost-user 另有协议特性，用于协商多队列、内存管理等控制能力。
  2. 配置内存。内核路径使用 VHOST_SET_MEM_TABLE；外部路径可通过 VHOST_USER_SET_MEM_TABLE传递区域表与内存文件描述符。后续内存变化也需要同步。
  3. 配置队列。设置队列大小、描述符和 available / used 的地址，以及恢复消费所需的索引。队列编号使后端能够区分 RX、TX 及不同队列对。
  4. 连接通知。设置 kick 与 call 文件描述符，分别用于提交唤醒和完成通知。QEMU 关联客户机通知地址、KVM ioeventfd 和中断路由。
  5. 允许处理。在设备与队列状态满足条件后启用数据处理。内核网络路径还要绑定 TAP 对应的后端文件描述符；vhost-user 按协商结果管理队列启停。

图中按职责归纳初始化阶段，实际调用会因功能协商、队列就绪顺序和中断屏蔽状态交错执行。正常发包时，这些关系已经建立，无需每发一包重新发送整套配置。队列配置、设备启动

2. 数据处理：读取同一份描述符链

  1. 客户机准备 P1 的网络头和报文缓冲区，填写描述符链；完成内存顺序操作后更新 available ring。
  2. 需要唤醒时，驱动写队列通知地址。启用 ioeventfd 的路径由 KVM 触发 kick eventfd，对应的队列消费者获得处理机会。
  3. 后端读取 available 项、验证描述符并定位 P1。QEMU 构造自己的队列元素，vhost-net 由内核解析，外部后端则访问已映射的共享内存。
  4. QEMU 将 P1 写入 TAP；vhost-net 将数据交给 TAP 对应的内核 socket；外部后端按其网络实现进行转发。
  5. 当本次请求的缓冲区可以归还时，后端发布 used 项，并按通知条件告知客户机。驱动检查完成记录后回收描述符和缓冲区。

used 的含义是本地请求完成和缓冲区可以回收，远端应用是否收到报文需要由网络协议确认。下层拥塞、异步发送和零拷贝会影响归还时刻，后端不能在仍有引用时提前让客户机复用缓冲区。

四、kick 唤醒后端，call 通知客户机

1. 控制消息、kick 与报文数据

vhost-user 的 Unix socket 承载控制消息，并通过 SCM_RIGHTS传递内存、kick 和 call 等文件描述符。常规 eventfd 模式下，kick 提示后端检查队列，报文内容通过共享内存访问；socket 中的 payload是控制消息体，例如内存区域描述，并不表示以太网报文。协议职责、文件描述符传递

部分后端持续轮询队列，或通过通知抑制减少唤醒。协议也定义了协商后使用的带内通知扩展。因此检查实际配置时，需要区分 eventfd、轮询与带内通知；改变通知方式仍不会让普通报文自动经控制 socket 逐包传输。带内通知

存储后端的具体实现见SPDK vhost-user-blk 的请求处理路径，其中继续跟踪共享队列、控制器线程、bdev 和 NVMe 完成回调。

2. 完成记录先于完成通知

后端先写 used 项，再更新 used 索引，最后判断是否需要通知。vhost-net 的 vhost_add_used_n()和 vhost_signal()分别承担发布和通知检查；call eventfd 可连接 KVM irqfd，形成宿主后端到客户机中断的路径。中断屏蔽、路由能力和回退配置会影响具体实现，详见irqfd 的通知路径。

kick 与 call 的方向相反：kick 面向后端，call 面向客户机。批量请求可合并通知，驱动也可主动检查 used ring，故报文数、kick 数和中断数应分别统计。ioeventfd 减少通知 MMIO 返回 QEMU 处理的往返，CPU 进入 KVM 的硬件 VM-exit 仍可能发生。KVM_IOEVENTFD 与 KVM_IRQFD、完成发布与条件通知

六、缩短数据路径的收益与管理代价

1. 从 QEMU 报文处理到内核 vhost-net

QEMU 用户态模型把设备逻辑、队列处理和网络后端连接起来，便于统一管理。高报文率场景中，队列通知、用户态调度及向 TAP 提交等环节会积累开销。vhost-net 将网络队列处理放到宿主内核，保留客户机 virtio 接口，并由 QEMU 配置运行所需的资源。

处理路径缩短后，宿主仍需执行队列检查、内存访问和网络转发。性能会受到 vhost 工作项调度、CPU 亲和性、NUMA、批量大小和网络栈的影响。Linux 的发送实现同时保留复制与零拷贝分支，说明“启用 vhost”本身不足以判断复制次数。零拷贝条件

2. 从内核接口到外部用户态后端

用户态交换机等组件需要直接处理 virtqueue 时，vhost-user 把内核 ioctl 的控制职责扩展为跨进程协议。QEMU 在 2014 年引入 vhost-user 后端，通过控制消息对应 vhost 操作，并传递共享资源的文件描述符。QEMU 提供设备配置、队列位置和共享内存，外部进程可以使用自己的调度与网络数据面，例如接入 DPDK 构建的用户态交换机。

独立进程便于分离设备控制与数据处理，也增加了内存映射、文件描述符生命周期、协议兼容及后端失联处理。迁移时还要跟踪后端对客户机内存的写入，并协调队列停止与状态恢复。QEMU 10.2 的协议包含脏页日志和后端状态迁移约定，各后端的可用能力需要通过协商确认。迁移与后端状态

三种处理方式仍各有适用场景。比较时应固定客户机队列、报文大小、卸载配置及出口，再观察 CPU 消耗、延迟、吞吐和部署复杂度。轮询可减少等待唤醒的延迟，但会持续消耗 CPU；拆分进程可独立安排数据面资源，也需要额外维护状态交接和故障处理。

物理设备执行 DMA 时的映射与隔离见《VFIO 设备直通的 DMA 地址转换与隔离》。
