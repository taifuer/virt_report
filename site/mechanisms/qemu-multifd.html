前言

MultiFD 将迁移数据分派给多个工作线程，通过独立通道并行发送和接收。它可以分担页面处理、压缩和传输工作，但也引入了一个顺序问题：主迁移流已经走到同步点时，其他通道上的页面可能仍在途中。

本文分析普通 socket 迁移中未压缩 RAM 数据的分发与同步。示例采用默认同步方式：在 RAM 扫描轮次边界通过主流的 RAM_SAVE_FLAG_MULTIFD_FLUSH 协调数据通道。旧机器兼容模式、文件迁移及压缩路径在后文分别说明。

源码版本：QEMU 10.2.0。

内存迭代与停机切换见《QEMU 预拷贝迁移的内存迭代与停机控制》；主迁移流的记录格式见《QEMU 迁移流格式与状态恢复》。

基本原理

主迁移流与数据通道

主迁移流继续承担流头、配置、RAMBlock 布局、状态分段和同步控制；RAM 页面可以交给额外的 MultiFD 通道。每条通道各有发送线程和接收线程，同一通道内保持字节顺序，不同通道可以同时推进，抵达顺序由各自的处理和传输进度决定。

源端先把同一 RAMBlock 的页偏移收集成批，再寻找空闲发送线程。目的端根据包头中的 RAMBlock 名称与偏移数组，把数据写入对应内存位置。数据批次因而可以在不同通道上独立处理，无须按地址从低到高抵达。

并行通道必须在必要的边界上重新建立顺序。假设页面 P 在上一轮发送了旧内容，下一轮又被写脏并发送新内容：如果两次传输走不同通道，旧内容晚到就可能覆盖新内容。同步点保证上一组传输完成装载之后，接收端才越过相应边界。

两端各有一个完成条件

  • 发送端：工作线程完成已有任务，并按要求把 SYNC 包写入各自通道，主线程才能继续发出主流同步标记。
  • 接收端：主流读到同步标记后，等待全部数据通道读到 SYNC；各接收线程此前已经处理了该通道上排在 SYNC 前的页面。

发送函数返回只说明本地写入完成，数据仍可能位于 socket 缓冲区或网络中。发送端无需为每个同步点等待一条远端确认消息；跨通道的接收顺序由目的端屏障保证。同步请求定义、接收端屏障

    页面如何分给线程

    multifd_queue_page() 收集同一个 RAMBlock 的页偏移。当前批次满了，或扫描进入另一个 RAMBlock 时，它把已有批次交给 multifd_send()。同步前也会提交尚未满的批次。默认批量上限按 MULTIFD_PACKET_SIZE = 512 KiB 计算；采用 4 KiB 页时可容纳 128 个页偏移。入队实现、批量大小

    分发函数等待 channels_ready，从上次位置之后循环寻找 pending_job == false 的线程。交接通过交换数据对象指针完成，随后以 release 语义发布任务并唤醒线程。页面并没有在入队时整体复制成一份不可变快照；普通未压缩路径由工作线程准备 iovec 并执行写入，迁移期间的新写入仍由脏页跟踪和后续轮次处理。

    通道上的包长什么样

    MultiFD 通道先交换初始化信息，包括 magic = 0x11223344、版本、虚拟机 UUID 和通道 ID。后续 RAM 包携带批次元数据与页内容。它有自己的包格式，与主迁移流的 START / PART / END section 分层处理。

    公共头magic · version · flags 批次信息pages_alloc · normal_pages
    next_packet_size · packet_num
    zero_pages · reserved     内存定位ramblock[256]
    offset[]     普通页内容page 0 · page 1 · …

    整数按协议规定转换成大端序。普通页的偏移排在 offset[] 前部，零页偏移位于其后；零页由目的端填零，无需携带整页内容。packet_num 是包序号，接收线程按各自通道直接装载页面，并不会先汇集全部通道再按包序号排序。包结构、页接收和头部解析

    跨通道同步

    发送端：完成任务，再排入 SYNC

    multifd_ram_flush_and_sync() 先提交残留页批次，随后调用 multifd_send_sync_main(MULTIFD_SYNC_ALL)。主线程为每个工作线程设置 pending_sync 并唤醒它，再逐个等待完成信号。

    工作线程先处理 pending_job，再处理同步请求。发送 SYNC 使用与页面相同的有序通道，因此接收端不会先读到 SYNC、再读到它前面的页内容。全部线程完成这一步后，主线程写出主流的 RAM_SAVE_FLAG_MULTIFD_FLUSH。

    接收端：汇合所有通道

    MultiFD 接收线程读到 SYNC 时，先通知公共同步信号量，再阻塞于自己的 sem_sync。主流处理函数 ram_load() 读到 FLUSH 后进入 multifd_recv_sync_main()，收齐全部通道的通知，然后释放这些接收线程。

    FLUSH 可能早于某条数据通道上的 SYNC 到达，某些 SYNC 也可能先于 FLUSH 到达。两种情况都由同一个汇合条件处理。接收线程在屏障处暂停，可以防止后续轮次的数据提前覆盖当前阶段仍在使用的状态。

    本页交互为了逐步查看，等目的端完成同步后才生成下一组任务。实际源端完成本地同步并发出 FLUSH 后即可继续工作，下一组数据可以在通道中排队；目的端接收线程仍须通过屏障才能继续装载。同步发起、发送线程、接收线程等待

    RAM EOS 与同步点

    默认配置下，RAM EOS 结束本次 RAM section 载荷，专门的 FLUSH 则触发跨通道同步；两者用途不同。一轮 RAM 扫描可能跨越多个 PART，不能把 PART 的数量当作预拷贝轮数。使用旧机器兼容配置时，接收端在每个 RAM EOS 上同步，发送端也必须配对发送各通道的 SYNC。RAM 标记分派

    环节入口与关注点
    收集页面multifd_queue_page()：同一 RAMBlock、批次容量、未满批次的提交。
    交接任务multifd_send()：空闲线程、数据对象交换与 acquire / release。
    发送工作multifd_send_thread()：准备包头与 iovec、发送、归还任务槽，再处理同步。
    页装载multifd_nocomp_recv()：构建目的地址 iovec，读取普通页并处理零页。
    同步两端multifd_recv_sync_main()：等待所有接收线程，再统一释放。

    源码中的本地同步和远端同步由 MultiFDSyncReq 区分。MULTIFD_SYNC_LOCAL 只等本地工作线程；MULTIFD_SYNC_ALL 还要求各通道写出 SYNC，并与主流同步标记配合。mapped-ram 文件迁移使用不同的数据定位与同步方式，不能把其完成条件直接套用到网络迁移。

    实现演进与性能取舍

    从串行处理到并行批次

    当页扫描、编码和发送集中在一个路径上时，CPU 处理能力可能先于网络带宽成为限制。MultiFD 把批次处理分给工作线程，让发送、接收及可选压缩获得并行机会。QMP 的 multifd-channels 参数自 4.0 提供，压缩方法参数自 5.0 提供；具体收益取决于 CPU、内存带宽、网络及负载。

    从逐 section 同步到扫描轮次同步

    早期协议在每个 RAM section 结束时同步全部通道。主流为了限速和迭代调度产生多个 PART 时，也会反复触发屏障，已经空闲的通道需要等待其他通道。QEMU 8.1 引入按完整 RAM 扫描轮次同步的方式，并增加 FLUSH 标记，把跨通道同步与 section 结束解耦。旧机器兼容设置仍保留逐 section 行为。同步粒度调整提交、8.0 兼容属性

    同步减少后，工作线程可以连续处理更多批次，但协议仍需要在页面可能跨轮重复发送及阶段切换的位置建立顺序。QEMU 10.2.0 的 multifd_ram_sync_per_section() 与 multifd_ram_sync_per_round() 明确区分两种路径。演进改变的是同步频率和标记位置，顺序约束始终存在。

    通道数为什么需要测量

    增加通道会增加线程、连接和缓冲区，也可能提高内存访问竞争。当网卡带宽已经耗尽，更多线程不能增加物理链路容量；当目的端解压或写内存较慢时，发送端的并行度也无法单独解决瓶颈。一个明显较慢的通道还会拉长屏障等待。

    评估配置时，应同时记录实际传输吞吐、两端工作线程 CPU 利用率、内存带宽、停机时间和迁移总时长，并观察 multifd_send_sync_main_wait、multifd_recv_sync_main_wait 等 trace 事件。通道数与压缩方式需要结合业务写脏速率测试，交互示例的逻辑步数不对应实际耗时或性能倍数。
