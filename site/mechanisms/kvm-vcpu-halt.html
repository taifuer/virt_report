一、空闲 vCPU 如何兼顾响应时间与 CPU 占用

客户机没有工作可做时，空闲循环可以执行 HLT，等待中断。宿主却仍需决定：继续占用当前 CPU，短暂等待即将到来的事件，还是把承载 vCPU 的线程交给调度器休眠？前者消耗 CPU 时间，后者可能增加再次运行的等待。KVM 的 halt polling 就放在这个交界处。

KVM 采用“先检查事件 → 有预算时短暂轮询 → 仍无工作则阻塞 → 事件到达后唤醒”的处理顺序。短等待争取避免休眠与重新调度，长等待归还 CPU；每次等待结束后，再根据耗时调整下一轮预算。收益应以业务延迟衡量，代价则是轮询消耗的宿主 CPU 时间。

本文用一次网络请求等待完成事件为例，跟踪 x86、内核 LAPIC、HLT 被截获后的路径。客户机 HLT、宿主线程睡眠和整台虚拟机暂停是不同状态；硬件直接处理 HLT、posted interrupt 与客户机内部 haltpoll 驱动有各自的路径。

源码版本：Linux 6.18、QEMU 10.2.0。

二、一个例子：请求完成前等待 30 µs

客户机已经提交网络请求，没有其他可运行任务，空闲循环执行 HLT。假设后端的完成事件在 30 µs 后到达；当前 vCPU 轮询预算为 50 µs。KVM 在轮询中观察到事件，直接回到运行循环，不必先把宿主线程挂起、再等待它重新取得 CPU。

事件何时到达KVM 的处理收益与成本
30 µs，落在 50 µs 窗口内轮询观察到事件，结束等待避免一次睡眠往返，同时占用约 30 µs CPU
120 µs，超过 50 µs 窗口先轮询，随后准备等待、休眠；完成事件唤醒线程这轮轮询未避免睡眠，已付出约 50 µs CPU 成本
等待很久，例如 10 ms到预算即停止轮询，把 CPU 交给其他任务有界等待限制空转成本；预算应随这种负载缩小

这些时间是教学输入，忽略退出、检查和注入开销。后面的交互还单列“准备休眠”和“已唤醒、等待调度”两段：完成事件已经到达，线程仍可能因宿主繁忙而晚些运行。增大轮询预算只能覆盖一部分短等待，无法消除后端处理时间，也不能保证获得物理 CPU。

接下来依次解释三个动作：如何识别可以继续运行的事件，如何安全入睡与唤醒，以及如何判断轮询预算是否值得保留。

三、等待状态：客户机活动状态与宿主任务状态

上例中，“客户机执行到 HLT”和“承载它的宿主线程进入睡眠”之间还有轮询阶段。KVM 分别保存客户机状态、等待者和预算，才能在不睡眠的情况下发现短期事件，也能在真正睡眠后找到需要唤醒的任务。

对象与字段用途
kvm_vcpu.arch.mp_state客户机的活动状态，如 HALTED、RUNNABLE；不等同于宿主任务状态
kvm_vcpu.halt_poll_ns这个 vCPU 当前学习到的轮询预算，单位纳秒
kvm_vcpu.wait（rcuwait）发布等待者任务指针，供唤醒端找到正在阻塞的线程
kvm_vcpu.requestsKVM 内部请求位图；EVENT、UNBLOCK 等请求有各自语义
kvm.max_halt_poll_ns、override_halt_poll_ns虚拟机显式覆盖的轮询上限；否则采用模块参数

通用字段见 kvm_vcpu，架构字段见 LAPIC 与 mp_state；上限选择见 kvm_vcpu_max_halt_poll_ns()。中断向量由 LAPIC 的待处理中断状态保存；requests 只表达需要处理的工作，不能把它当成中断向量队列。

四、进入等待：HLT 处理与有限轮询

1. HLT 如何进入 KVM 等待路径

VMX 的 HLT 退出处理调用 kvm_emulate_halt()，跳过已模拟的指令。内核管理 LAPIC 时，__kvm_emulate_halt() 检查已有事件：已经可以继续运行，就保留 RUNNABLE；否则记录 HALTED。运行循环随后进入 vcpu_block()，由它调用通用的 kvm_vcpu_halt()。VMX 分发表、HLT 模拟

这条路径通常不退出到 QEMU。若 LAPIC 由用户态管理，KVM 才以 KVM_EXIT_HLT 返回，把等待事件交给用户态；QEMU 的 x86 退出处理会进入 kvm_handle_halt()。因此不能看到一次 HLT 就推断发生了一次用户态往返。QEMU 的 HLT 分支

2. 何时继续轮询，何时归还 CPU

轮询期间反复执行 kvm_vcpu_check_block()：检查架构可运行条件、待处理定时器、宿主信号与 UNBLOCK 请求。cpu_relax() 之间还检查期限、need_resched() 和当前 CPU 是否只有一个可运行任务；有调度需要便提前结束轮询。预算为零时直接进入阻塞流程。事件检查、轮询循环、轮询继续条件

五、事件到达：从休眠、唤醒到重新运行

kvm_vcpu_block() 先发布 rcuwait 等待者，把当前任务设为 TASK_INTERRUPTIBLE，再检查一次阻塞条件。只有条件仍不满足才调用 schedule()；返回后循环复查，最后撤销等待者。一次唤醒可能只是宿主信号或维护请求，x86 路径还会判断 vCPU 是否真正可运行，不能无条件把 mp_state 改回 RUNNABLE。阻塞循环、架构侧复查

以 VMX 的普通中断软件回退路径为例，vmx_deliver_interrupt() 先记录 LAPIC IRR，再设置 EVENT 请求并调用 kvm_vcpu_kick()。已经睡眠的线程经 rcuwait 唤醒；正在客户机模式执行的 vCPU 则可能需要 IPI 促使其退出。线程得到唤醒后只具备被调度的条件，何时取得 CPU 还受宿主负载影响。中断交付、wake 与 kick

待处理的可屏蔽中断还要满足架构允许条件；“有中断记录”不保证立即注入。定时器也有独立入口：常规软件 LAPIC 定时器增加 pending 并请求 UNBLOCK。x86 在阻塞前把仅在客户机运行时计时的硬件定时器切换为软件定时器，避免退出客户机模式后失去唤醒来源。事件资格与定时器切换、定时器到期

六、正确性：如何避免入睡前丢失唤醒

如果只在轮询结束时检查一次，然后直接睡眠，事件可能在两步之间到达：发送方没有看到等待者，接收方又错过事件，造成丢失唤醒。KVM 的等待顺序是“发布等待者 → 设置任务状态 → 再检查条件 → schedule”。事件先到达，复查会阻止休眠；事件较晚到达，唤醒端能找到已发布的任务。

这个顺序还需要内存屏障。set_current_state() 与 rcuwait_wake_up() 中的屏障配合，约束等待者发布与事件条件观察的次序。若事件发生在最终检查之后、schedule 之前，唤醒会把任务恢复为可运行状态，后续调度不会让它因为这次等待永久睡下。它仍可能因其他任务而让出 CPU。等待端、唤醒端与屏障配对说明

源码统计也保留了这一区别：轮询循环已经结束，但在阻塞前复查命中事件、没有调用 schedule，仍可计为成功轮询。因此分析 trace 时，应同时看 poll、wait 和唤醒事件，不能仅凭一次成功计数推断事件一定在预算内到达。成功条件

七、自适应预算：短等待增长，长等待缩小

轮询预算按 vCPU 保存，上限默认取 halt_poll_ns；用户态可用 KVM_CAP_HALT_POLL 为整台虚拟机覆盖上限。一次 halt 返回后，KVM 用包含轮询、阻塞和重新调度在内的总耗时调整下一轮预算。它观察过去的等待，不能预知下一次中断。

1. 对上例的下一轮有什么影响

设当前预算 50 µs、上限 200 µs：事件在 30 µs 到达并被轮询捕获，预算保持 50 µs。若总等待为 160 µs，超过当前预算但低于上限，默认增长系数为 2，下一轮预算可增至 100 µs；若总等待达到 1 ms，默认缩小为 25 µs。若总耗时恰等于上限，则不进入增长或缩小分支。

2. 源码中的边界条件

在允许轮询的 x86 路径中，总耗时未超过当前预算就保持不变；超过上限且当前预算非零则缩小；当前预算和总耗时都小于上限，且没有命中前述保持条件时才增长。总耗时恰等于上限时，不触发这两个严格不等式分支。通用代码还为支持无效唤醒分类的架构保留单独的缩小分支，本文 x86 基线的 vcpu_valid_wakeup() 恒为 true。调整条件、有效唤醒分类

6.18 的增长系数与缩小除数默认均为 2，增长起点为 10000 ns。增长取“乘积与起点中的较大值”；缩小后低于起点便归零，除数为零也直接归零。增长结果可以暂时超过上限，下一次进入 halt 时再裁剪。长期空闲与密集短等待交替时，预算会反复调整；需要结合负载观测，不能把更大的窗口当成通用优化。默认参数、增长与缩小

八、交互验证：改变到达时间、预算与调度等待

事件到达与轮询窗口

从进入 halt 路径的 0 µs 开始，改变事件到达时刻和本轮预算，观察是否休眠，以及下一轮有效预算。

事件取 0—1000 µs 整数；调度等待取 0—200 µs 整数；预算取 0—200 µs，最多三位小数。调度等待是自选模型输入，不是实测延迟。

    九、效果评价：降低了多少延迟，消耗了多少 CPU

    比较同一业务负载下的三组结果：关闭轮询、较小窗口、较大窗口，保持 vCPU 绑定、后端线程布局、并发和宿主负载一致。每组都观察稳定运行阶段，同时保留短突发与空闲阶段；只测高负载吞吐容易掩盖空闲轮询成本。

    现象核对的证据可尝试的方向
    短请求 p99 延迟降低成功轮询增加、睡眠往返减少；同时核对 vCPU CPU 时间若 CPU / 功耗成本在目标内，保留能取得收益的较小窗口
    CPU 增多，业务延迟基本不变halt_poll_fail_ns 增长，或成功轮询耗时很高但未改善业务减小上限或关闭轮询，确认后端实际完成时间
    完成事件已到，vCPU 仍迟迟不运行将 sched_wakeup 与 sched_switch 对齐，检查 runnable 等待检查超分、CPU 绑定、其他任务争用；单纯增大窗口无法解决调度拥塞
    事件本身到达得晚后端队列延迟、设备处理时间、定时器或中断合并策略先缩短事件产生路径；KVM 轮询不能提前完成尚未做完的 I/O

    KVM 的 halt_poll_success_ns、halt_poll_fail_ns、halt_wait_ns 及直方图给出等待路径的分解；结合 kvm_vcpu_wakeup trace 与业务延迟，才能区分节省的调度时间和新增的空转。统计中的“成功”包括准备休眠时复查命中、实际没有 schedule 的情形。统计字段

    成本可以先做量纲检查：若每秒有 10000 次等待，每次白耗 50 µs，累计便是 0.5 秒 CPU 时间，约半个 CPU 的处理时间。多 vCPU 还会累加。这个估算不含真实调度与提前退出，适合检查预算数量级，不代替实测。轮询的合理目标是以可接受的 CPU 成本满足延迟要求。

    十、演进与局限：从固定窗口到按 vCPU 调整

    2015 年引入 halt_poll_ns 的提交针对短等待后的调度往返，在休眠前增加可配置轮询。空闲 vCPU 同样会消耗这段时间，后来采用每 vCPU 的自适应预算；当前算法把短等待留下的经验用于下一轮，又对长等待缩小窗口。

    2020 年增加的 KVM_CAP_HALT_POLL允许不同虚拟机选择不同上限；随后启用默认缩小除数的提交把缩小行为从直接清零改为默认减半，仍保留低于增长起点时归零。参数选择始终涉及延迟、宿主 CPU 占用及功耗的取舍。

    如今 kvm_vcpu_halt() 负责轮询与预算调整，kvm_vcpu_block() 单独负责等待循环。两者共用事件检查，轮询结束后仍会在入睡前重查条件。两个入口的实现

    自适应算法减少了人工选择固定窗口的负担，但它使用过去的总等待预测下一轮；业务突变、后端批处理和宿主调度拥塞都会影响判断。进一步优化应根据证据选择方向：短且稳定的等待关注轮询窗口，长等待关注事件源，已唤醒后的延迟关注调度。客户机 haltpoll、硬件中断加速等机制还改变了等待或通知发生的位置，评估时应把它们与 KVM 的宿主侧轮询分开。
