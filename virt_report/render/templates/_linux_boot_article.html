从固件交接到应用运行

Linux 启动逐步建立可供应用使用的执行环境：固件提供最初的机器初始化，引导程序准备内核映像和参数，内核接管 CPU、内存与设备，首个用户进程组织系统服务，最后启动登录程序与业务应用。每一阶段给下一阶段留下明确的代码入口和资源信息。

本文以 x86-64 Linux 和使用 systemd 的常见发行版为例。BIOS、UEFI 影响前面的引导方式，发行版决定 initramfs 和服务组织；内核的核心职责保持一致。虚拟机中，固件与 Linux 在 vCPU 上执行，磁盘、网卡和中断控制器由虚拟平台提供。

固件与引导程序的资源准备

CPU 从平台定义的复位入口执行固件。固件准备基础硬件，提供内存布局和 ACPI 等平台信息，并按启动配置选择设备或可执行映像。传统 BIOS 硬盘引导从启动扇区转入后续引导程序；UEFI 可加载 EFI System Partition 中的 EFI 程序。

GRUB 等引导程序读取 Linux 内核映像、可选的 initramfs 和内核命令行，再按启动协议交接。UEFI 也可加载带 EFI stub 的 Linux 映像，或使用封装内核及其他启动资源的统一内核映像，具体取决于系统配置。

交接内容用途
内核映像与入口提供启动代码；磁盘上的文件偏移、加载地址和最终内核虚拟地址是不同的坐标。
内存布局、启动参数告诉内核哪些范围可用、哪些需保留，以及平台和引导信息。
命令行例如 root=、console=，控制根设备选择、日志输出及其他初始化行为。
initramfs提供早期用户空间、驱动模块和挂载真实根所需的工具。

内核早期入口：让内核代码能够运行

x86 bzImage 的启动入口取决于引导程序采用的协议。压缩映像的启动代码准备栈和临时页表，建立所需执行模式，解压并重定位内核，再跳入解压后内核的架构入口。支持的 64 位入口已有相应模式前提，不必重复所有 32 位入口步骤。

arch/x86/boot/compressed/head_64.S 和 arch/x86/kernel/head_64.S 分属压缩映像与最终内核。后者继续建立早期映射和 CPU 状态，逐步进入通用 C 初始化流程。此时还没有完整的文件系统、普通用户进程或全功能驱动环境；初始化代码依赖事先保留的空间和早期分配机制。

接收平台内存图后，内核用 memblock 等早期管理手段预留自身、initramfs 和其他保留区，再建立正式页管理。启动参数中的物理地址需要按对应阶段的映射访问。

start_kernel：建立通用内核环境

start_kernel() 串起架构设置、命令行处理、内存管理、调度、中断、时钟、RCU 与 VFS 等基础初始化。许多步骤有先后依赖：可以创建任务前要有调度基础，可以接收常规事件前要准备相应中断与计时状态。

主启动路径最初由引导 CPU 执行。其他 CPU 在后续 SMP 初始化中启动，并建立各自的内核栈、每 CPU 数据、调度和中断状态。它们随后共同承担内核工作和用户线程；增加在线 CPU 是建立并行执行条件，具体任务仍由调度器分配。

rest_init() 创建执行 kernel_init() 的 PID 1 任务及 kthreadd。原始启动任务转入 boot CPU 的 idle 路径；PID 1 此时仍执行内核代码，继续 SMP、驱动和 initcall 等初始化，之后才装载第一个用户程序。

驱动发现设备，准备访问根文件系统

平台信息与总线枚举提供设备描述，驱动匹配设备并执行 probe，建立寄存器映射、队列、DMA 和中断连接。内建驱动可在内核初始化期间工作；模块驱动需要后续用户空间加载。probe 可能异步执行或因依赖未就绪而推迟，某个初始化函数返回不意味着所有设备已经可用。

例如根文件系统在 virtio-blk 磁盘上，系统必须能使用 virtio 总线、块驱动和对应文件系统。驱动若编成模块且只存在于尚未挂载的根目录，就形成依赖闭环；initramfs 把这些早期必需的模块和工具提前带入内存。

网卡驱动加载完成后，接口的 IP、路由与业务配置通常仍由用户空间完成。本地磁盘启动一般无需等待网卡联网；网络根文件系统则需要在挂载根之前准备相应网络条件。

initramfs、真实根与首个用户程序

initramfs 是可解包到 rootfs 的文件归档，可随内核内建或由引导程序提供。存在可执行的早期 /init 时，内核通过 run_init_process() → kernel_execve() 让 PID 1 执行它，进入用户态。这个程序可以加载模块、激活 LVM、解锁加密卷或准备网络根。

真实根就绪后，早期用户空间挂载它，再通过 switch_root 等流程切换根并执行真实根内的 init。通常是同一个 PID 1 换入新的程序映像，进程号保持不变；switch_root 操作由早期用户空间组织。

没有可用的早期 /init 时，内核走自身的根挂载流程，并按配置执行指定 init 或尝试 /sbin/init 等路径。这要求必需驱动和文件系统已经可用。真实根也不一定是磁盘分区，嵌入式系统可以继续使用内存中的根文件系统。

exec 装入代码、数据、用户栈和入口；动态链接程序还要先运行解释器。CPU 从内核态返回用户态后，才执行新用户程序的指令。PID 1 的创建、进入用户态、启动服务分别发生在不同阶段。

PID 1 与服务、应用的启动

在本例发行版中，systemd 作为 PID 1 读取 unit 配置，按依赖与顺序关系组织挂载、设备、socket 和服务。可并行的任务共同推进；某个服务可能要等待文件系统、设备或其他服务。系统并不是从头到尾串行执行一张固定脚本表。

启动目标通常由 default.target 指向多用户或图形环境。到达目标表示其组织的启动工作达到相应状态，但业务还应有自己的健康检查。网卡存在、地址配置完成、远端服务可访问，也各有独立的完成条件。

普通应用随后由服务管理器或登录 Shell 启动，获得进程、地址空间和文件描述符，再通过系统调用使用内核资源。启动阶段建立的调度器、页管理和驱动由此转入长期运行。

按阶段定位启动问题

下面是只读观察命令。日志访问可能需要权限；systemd 命令只适用于使用该服务管理器的系统。

cat /proc/cmdline
dmesg
findmnt /
ps -p 1 -o pid,comm,args
systemd-analyze time
systemd-analyze critical-chain
journalctl -b -k
现象优先核对
固件找不到引导项启动设备、EFI/BIOS 模式、引导程序和磁盘内容。
看不到内核日志入口和映像兼容性、console= 及实际显示/串口配置；日志不可见本身不足以证明内核未运行。
无法挂载根或停在早期 Shellroot=、UUID、必需驱动、initramfs、解密或卷激活。
内核启动后等待很久驱动探测、挂载、unit 依赖与服务自身的初始化。

启动耗时应分为固件、引导、内核、早期用户空间和服务阶段。systemd-analyze 的可见范围取决于平台提供的时间信息；critical-chain 也不是所有后台工作和业务延迟的完整记录。
