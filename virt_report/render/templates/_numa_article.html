绑了 vCPU，访问内存为什么仍然慢

一台双路服务器上，虚拟机的 4 个 vCPU 都在 NUMA 节点 1 的物理 CPU 上运行，客户机 RAM 却大部分分配在节点 0。每次访问这些页，都可能跨越处理器互连。绑定线程解决了“在哪执行”，内存位置仍需单独安排。

NUMA 的含义是不同 CPU 访问不同内存位置时，延迟和可用带宽可能不同。虚拟机又增加了客户机拓扑：客户机认为自己的 CPU 和内存属于哪个节点，与真实页位于哪个宿主节点，是两套独立关系。要获得局部性，需要让客户机的工作分配、宿主线程放置和实际物理页分布相互配合。

从内存映射到物理页分配

QEMU 创建 RAM 后端时，先获得一段宿主虚拟地址映射。使用按需分配的匿名内存时，许多物理页在后续缺页时才真正分配。分配位置取决于适用的 NUMA 内存策略、允许的节点集合以及当时的资源状况；默认局部分配下，触发分配的线程所在节点会影响结果。

这解释了为什么“启动完成后再绑核”可能晚了一步：预分配线程或启动过程中运行的线程已经让页落在别的节点。单纯调整线程亲和性不会把这些页一起搬走。共享内存、文件后端和大页还有各自的分配约束，也不宜用一个 first touch 规则概括所有情况。

HostMemoryBackend 保存 RAM 区域、host_nodes、policy 和 prealloc 等属性。QEMU 的 Linux 路径先通过 mbind() 为后端应用节点策略，再执行预分配，避免预分配先发生而策略尚未生效。内存策略与预分配的顺序

常见策略适用思路取舍
bind / Libvirt strict把分配约束在指定节点集合内，维持明确的局部性节点内存不足时可能分配失败，不能假定其他节点有空闲就一定能启动
preferred优先使用指定节点，必要时允许回退更容易满足容量，但运行时页分布可能偏离理想位置
interleave将页分散到一组节点，利用多节点带宽和容量单个 CPU 访问时包含远端页，不等于最低访问延迟

cpuset/cgroup 的允许节点约束也参与决定最终放置。预分配能在启动阶段更早暴露容量问题并减少运行时首次缺页，代价是更长启动时间和更早占用内存；大页还需要检查目标节点的大页池，而非只检查全机空闲内存。

4 个 vCPU 与 8 GiB RAM 的放置例子

假设宿主节点 1 包含逻辑 CPU 8—15，有足够空闲内存；这些编号只是例子，实际应先通过 lscpu -e=CPU,NODE,SOCKET,CORE 和 numactl --hardware 确认。客户机只暴露一个节点，包含 4 个 vCPU 和 8 GiB RAM。

QEMU 内存与虚拟拓扑部分可以表示为：

-m 8G -smp 4,sockets=1,cores=4,threads=1
-object memory-backend-ram,id=ram0,size=8G,host-nodes=1,policy=bind,prealloc=on
-numa node,nodeid=0,cpus=0-3,memdev=ram0

nodeid=0 是客户机节点，host-nodes=1 是宿主节点。这段配置将 RAM 约束到宿主节点 1，但尚未设置 vCPU 亲和性。由 Libvirt 管理时，可以在既有 domain XML 中同时表达客户机 CPU/NUMA 拓扑、vcpupin 和 numatune，例如以下相关片段：

<cputune>
  <vcpupin vcpu='0' cpuset='8'/>
  <vcpupin vcpu='1' cpuset='9'/>
  <vcpupin vcpu='2' cpuset='10'/>
  <vcpupin vcpu='3' cpuset='11'/>
  <emulatorpin cpuset='12-13'/>
</cputune>
<numatune>
  <memory mode='strict' nodeset='1'/>
  <memnode cellid='0' mode='strict' nodeset='1'/>
</numatune>

这里假设客户机节点 0 已在 CPU 的 numa 配置中定义。若使用 IOThread，还要为已创建的线程配置 iothreadpin；若使用独立 vhost-user 后端，则在那个进程及其工作线程上配置。CPU 8—11 是否属于不同物理核、是否与其他任务争抢，仍需检查，四个逻辑 CPU 不保证有四份独立核心资源。

这是单节点内存密集型负载的放置例子。超过单节点容量的大 VM，可能更适合暴露多个客户机节点，让每组 vCPU 靠近自己的 RAM；此时应用也要理解 NUMA，避免把全部数据集中到一个节点后由其他节点反复远程访问。

I/O 路径也要计入局部性

一次 virtio 请求可能先由 vCPU 准备描述符和缓冲区，再由 QEMU IOThread、内核 vhost 或独立用户态后端读取，最后交给网卡或存储设备。共享缓冲区没有变，读取它的 CPU 却可能跨了节点。后端线程放得很远时，绑好 vCPU 和 RAM 仍会留下远端访问及缓存交接成本。

物理设备也有所在节点。把后端靠近网卡可以缩短设备侧路径，但若客户机 RAM 在另一节点，缓冲区访问又会跨节点。合理选择取决于数据量、批大小、共享方式和队列分配；不能用“所有线程都绑到同一个 CPU”解决局部性，否则可能增加执行排队。

多队列可以把请求分配给多组工作线程，使处理并行化，也可能提高跨节点共享和通知数量。评价时要把每个队列的消费者、缓冲区位置和设备位置对应起来，再决定是否拆分队列或调整线程亲和性。

验证配置是否变成了实际放置

以下命令只读取状态，其中 PID 和 DOMAIN 应替换为目标虚拟机的实际标识。重点是交叉核对配置与结果，而非只看 XML。

virsh vcpupin DOMAIN
virsh emulatorpin DOMAIN
virsh numatune DOMAIN
numastat -p PID
less /proc/PID/numa_maps
ps -L -p PID -o pid,tid,psr,comm

psr 是采样时看到的处理器，不是允许 CPU 集合；线程亲和性还应结合 /proc/PID/task/TID/status 的 Cpus_allowed_list。numastat -p 汇总进程内存，包含 QEMU 自身开销，不能把所有页都直接算成客户机 RAM；numa_maps 可进一步按映射区间核对。

先固定业务负载，再比较放置调整前后的吞吐、延迟分布、CPU 消耗和内存节点分布。节点间缓存共享、带宽竞争与调度排队可能同时存在，不能仅凭远端页数推导业务会快多少。迁移后应重新验证目的端放置；客户机拓扑保持不变，不代表目的端自动沿用正确的物理资源映射。

从默认分配到按内存对象管理

默认调度与局部分配无需细致配置，适合资源动态共享；当虚拟机跨多个节点、使用大页或接入高吞吐设备后，默认策略可能难以保持稳定局部性。显式 NUMA 拓扑和每节点内存后端把客户机视图与宿主分配策略分开，使控制更精确，也增加了容量规划和迁移时重建映射的责任。

Linux 的自动 NUMA 平衡可以根据访问情况调整部分工作和页的位置，适用效果受策略、页类型和运行环境影响；严格绑定、大页或固定高吞吐后端不能期待它自动修正全部放置。进一步出现的异构内存描述也让“节点距离”超出了单纯双路服务器：延迟、带宽和容量可能不同，需要让客户机了解适合其负载的信息。

最实用的判断顺序是：先确认线程和页究竟在哪里，再识别访问最频繁的共享数据，最后选择局部绑定、分区或跨节点分散。局部性是数据访问关系的结果，单独增加绑定项并不能证明已经优化。
