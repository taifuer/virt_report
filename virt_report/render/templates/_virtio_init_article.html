virtio 设备初始化的阶段与约束

客户机驱动与 virtio 设备通过共享内存交接请求。第一次 I/O 前，驱动先找到设备的控制区域，与设备选定共同支持的功能，再分配队列并公布地址。设备确认这些约定后，才能按相同格式读取描述符、访问缓冲区并归还结果。

本文跟踪现代 virtio-pci 接口上的一个 virtio-blk 队列。例子采用 4 个描述符、split 格式，普通 RAM，无客户机 IOMMU 地址转换；队列地址以 GPA 表示。开启平台访问约束时，需要使用相应 DMA 映射，不能沿用这里“地址就是 GPA”的假设。协议依据 VIRTIO 1.2，实例由 QEMU 与 Linux 驱动实现。

这次初始化依次经过：发现设备 → 复位并选择特性 → 确认共同格式 → 配置队列内存 → 允许处理 → 发布读取请求。特性确认决定队列的解释方式；队列地址和设备状态决定何时可以开始访问。阅读数据路径时，可先在这里确认队列何时可用，再进入磁盘 I/O 演示或网络 I/O 演示观察请求的交接。

Virtio 从早期虚拟设备接口逐步发展为可扩展的设备规范。下文先沿现代设备的初始化建立一个完整例子，再在协议演进中对照 0.8.7、0.9.5 与 1.0–1.4 的变化。队列运行期间的通用规则集中在Split 与 Packed 的请求与完成，这里侧重双方如何开始使用同一套规则。

通过 PCI 能力找到控制与通知区域

PCI 枚举先识别设备，再遍历能力链。现代 virtio 使用 vendor-specific capability 描述控制区域所在的 BAR、偏移和长度，驱动据此映射寄存器。virtio_pci_cap 的 cfg_type 标识区域用途，bar / offset / length 给出位置与范围。这些控制区域由设备接口呈现，日常请求使用的 virtqueue 则分配在客户机 RAM 中。

区域本次初始化中的作用与队列内存的区别
Common configuration读写特性、device_status、队列大小和地址保存控制字段，不存每次请求的数据
Notify驱动写门铃，提示某队列有新工作通知不携带整条描述符或数据缓冲区
ISR传统引脚中断下读取队列/配置事件原因不代替 used 中的完成记录；MSI-X 有独立向量路由
Device configuration读取块设备容量等设备特有配置布局由设备类型和已协商特性决定

Common 中的 config_generation 用于检查设备配置读取的一致性。例如读取跨多个访问的容量值时，前后读取 generation，发生变化就重试，避免拼出一次更新前后的混合值。设备配置空间、PCI 配置空间和客户机 RAM 中的 virtqueue，是三类不同位置。能力结构与公共配置字段

先选择特性，再让设备确认

特性选择包含依赖，不能只取交集

设备公布它支持的 feature bits，驱动选择自身支持并准备启用的特性子集。公共配置用 device_feature_select 选择每组 32 位，再从 device_feature 读取；驱动以对应的 driver_feature_select / driver_feature 写回选择。QEMU 头文件把后两者称为 guest_feature，表达的是同一组寄存器。

本例选择 VIRTIO_F_VERSION_1，使用现代接口；不选择 RING_PACKED，所以采用 split 队列，也不选择 EVENT_IDX、RING_RESET、通知数据扩展。VERSION_1 位说明采用现代协议，不能据此断言设备实现了某个文档版本的所有可选功能。

选择还要满足依赖与环境要求。比如 virtio-net 的 HOST_TSO4 要求 CSUM，不能只打开分段能力而忽略其校验和前提。平台要求设备使用受控 DMA 地址时，ACCESS_PLATFORM 也可能是运行条件。Linux 因而在初步交集后继续进行传输层和设备驱动验证。现代 PCI 路径还明确检查 VERSION_1。驱动特性筛选、现代 PCI 验证与写回

把 4 个描述符的队列放入客户机内存

驱动选择 queue_select = 0，确认该队列存在且尚未启用，读取支持的大小。设其上限至少为 4，本例写 queue_size = 4。split 队列大小为 2 的幂；它表示描述符表和环的容量，不表示始终可以同时提交 4 个任意大小的请求。

公共配置字段本例 GPA本例内存结构与最小占用
queue_desc0x1000004 × 16 B 描述符，共 64 B；16 B 对齐
queue_driver0x101000available 的 flags、idx、4 个链头，共 12 B；2 B 对齐

本例没有 EVENT_IDX，所以没有额外的 used_event、avail_event 字段。分开保留三页是为了让地址关系清楚，实际分配可以更紧凑。每个描述符由 addr:64 / len:32 / flags:16 / next:16 构成；现代接口的这些多字节字段采用小端。驱动初始化环和索引，设备就能按相同布局访问它们。

选用 packed 时，queue_desc 指向 packed 描述符环，queue_driver 和 queue_device 指向双方的事件抑制结构；它们不再是上表的 available/used 环。双方必须先对 RING_PACKED 达成一致，再按对应格式分配与访问，不能在运行中只切换一个标志来改造已有队列。

启用队列，再发出第一个读取请求

完成地址、大小、中断等必要配置后，驱动写 queue_enable = 1，再完成设备级准备并设置 DRIVER_OK。前者说明这个队列已配置，后者说明驱动能够接收结果；仅有 queue_enable 不能越过 DRIVER_OK 提前通知或消费请求。

例子从磁盘偏移 1 MiB 读取 4 KiB，采用直接链 0 → 1 → 2。描述符 0 指向 GPA 0x200000 的 16 B 请求头，类型 IN、sector 2048；描述符 1 指向 0x201000 的 4096 B 可写数据区；描述符 2 指向 0x202000 的 1 B 可写状态区。第 4 个描述符空闲。WRITE 表示设备写入客户机内存，所以磁盘读取的数据区需要这个标志。

desc[0]: addr=0x200000, len=16,   flags=NEXT,       next=1
desc[1]: addr=0x201000, len=4096, flags=NEXT|WRITE, next=2
desc[2]: addr=0x202000, len=1,    flags=WRITE

avail.ring[0] = 0
按发布顺序完成内存写入，再令 avail.idx: 0 → 1
成功完成后：used.ring[0] = {id: 0, len: 4097}, used.idx: 0 → 1

通知地址由 BAR 基址 + notify capability.offset + queue_notify_off × notify_off_multiplier 得到，queue_notify_off 不是字节偏移。本例未启用通知扩展，驱动向该地址写 16 位队列号 0；数据仍留在描述符指向的 RAM。发布所需的内存屏障不能被门铃写入替代，是否需要通知还应遵守队列抑制规则。通知区域计算

设备检查 available，读取请求并完成块操作，再写数据、状态和 used。初始化至此才接入日常数据路径。具体处理见virtio-blk 请求与完成，两种布局的环槽复用可在Split / Packed 对照演示中逐步观察。

协商失败处理与设备复位

设备复位重新开始整轮协商

驱动遇到无法恢复的初始化错误时，标记 FAILED 并停止继续初始化。FAILED 本身不是“设备已停止访问内存”的证明；重试需要复位。设备报告 DEVICE_NEEDS_RESET 时，在途请求可能已经完成，也可能尚未完成，驱动不能据此推断结果或盲目重放。

现代 PCI 的设备复位通过向 device_status 写 0 发起，读取到 0 才确认完成；此时设备不再访问旧队列或发送相应通知。驱动还需停止自己的提交与回调，之后才能安全拆除队列、释放缓冲区，并从 ACKNOWLEDGE 重新协商。复位不会替应用证明一次磁盘写入是否持久化，设备特有状态仍遵循对应协议。PCI 复位等待

队列复位是独立的可选功能

只有先协商 RING_RESET，驱动才可使用 queue_reset。选中队列后写 1，等待读回 queue_reset=0 且 queue_enable=0，再回收该队列资源、重新配置并启用。其他队列和设备级特性协商不随之重置；队列复位不能用来更换全设备的 split/packed 格式。本例没有选择 RING_RESET，不能走这条路径。

现代 PCI 传输通过已协商的队列复位或整设备复位停止队列。其 queue_enable 用于启用，QEMU 的公共配置写处理只接受 queue_enable=1；写 0 没有关闭队列的效果。MMIO 传输的寄存器操作另有约定。队列启用与复位、Linux 队列复位等待

从早期草案到 1.4：接口与队列逐步演进

2007 年，Rusty Russell 已在公开邮件中讨论统一的 virtio 驱动接口。不同虚拟化实现如果各自定义网络、磁盘前后端协议，客户机就要维护多套驱动；共享队列与统一设备约定让驱动和后端可以分别演进。2007 年 Virtio draft II 原始邮件记录了这段早期设计，早于这里收录的编号规范。

经典文档背景与变化对理解现有设备的意义
0.8.7 草案，2010将早期 virtio PCI 接口、共享环和设备约定整理成文档可用于追溯 Legacy 设计。封面有可核验日期，但不能据此称它为第一版
0.9.5 草案，2012OASIS 标准化前的经典接口基线；后续规范保留其 Legacy 兼容说明旧 PCI 寄存器布局、32 位特性空间及环地址约定，与 Modern 初始化要分开理解
1.0，Modern 接口明确字节序、扩展特性空间，引入 VERSION_1、FEATURES_OK 与现代 PCI 能力区域本文的“协商后确认，再放行运行”建立在这套接口上；transitional 设备兼容两种接口
1.1，2019引入可选 Packed virtqueue，在元数据布局和缓存访问之间作新取舍需协商 RING_PACKED。Modern 设备继续使用 Split 完全符合规范
1.2，2022加入可选单队列复位等机制，缩小队列恢复时影响的范围RING_RESET 需两端支持；停止旧访问、回收和重新启用仍有严格顺序
1.3 CSD01，2023委员会规范草案中加入 administration virtqueue 等管理机制管理命令与常规 I/O 队列的职责分开；草案阶段按原始文档标注
1.4 CS01，2026扩展设备状态管理与 device parts，加入 SUSPEND 等约定，并扩充设备类型状态交接逐步拥有协议级表达；能否使用仍取决于驱动、前端和后端共同实现

这些修订解决的是不同阶段的需求：先统一设备接口，再明确兼容边界，随后改善队列效率、恢复与管理能力。版本号标识一份规范文档，运行时启用的是协商后的特性集合。看到“QEMU 支持 Virtio”或 VIRTIO_F_VERSION_1，都还不足以判断某项 1.4 新能力是否可用；应继续检查设备类型、驱动和实际后端的特性实现。

Legacy、Modern 和 Split、Packed 是两个维度。Modern 可以使用 Split；Packed 需要额外协商。virtio-win 0.1.xxx 又属于 Windows 驱动包编号，不对应 0.9.5 或 1.x 规范号。目前缺乏可核验的全行业部署比例，不能认定某个小版本“用得最多”。选型时更实用的记录是接口模式、队列格式、已协商特性以及 QEMU/Linux/后端版本。

完整文档日期、批准阶段与 PDF 见Virtio 版本记录。本文源码仍固定在所列 QEMU/Linux 基线；新增规范发布后，不会自动改变前面初始化例子的技术前提。

排查“设备可见却没有 I/O”，可依次核对特性选择及依赖、FEATURES_OK 读回、三个队列地址与大小、queue_enable、DRIVER_OK，最后检查 available 与门铃。初始化成功只表明接口约定成立，吞吐和延迟仍取决于队列深度、通知策略与实际后端。
