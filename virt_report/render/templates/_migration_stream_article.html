前言

QEMU 将内存、处理器和设备状态组织为迁移流，由目的端顺序解析和装载。外层记录标识状态处理器，内部载荷保存内存布局、页面或设备字段。理解这两层格式及各自的结束标记，才能把发送顺序、接收解析和最终恢复执行对应起来。

{% include '_mechanism_baselines.html' %}

以下以 x86 / KVM、普通 RAM 的单流预拷贝为主，机器与设备已在目的端创建，存储另行准备。内存为什么反复传输、何时进入停机阶段，见《QEMU 预拷贝迁移的内存迭代与停机控制》；这里沿一条流分析格式、解析与恢复。

整体结构

QEMUFile提供顺序读写接口；迁移框架在流中标识状态处理器，RAM、CPU 和设备各自负责载荷。左侧按发送顺序排列整条迁移流，右侧展开相应记录的字段。RAM 载荷内部的 EOS、section 尾部的 footer 和整条状态流的 EOF 属于不同层次。

下面以 pc.ram及其中四个页面为例，观察同一组数据从源端编码、经过迁移通道，到目的端解析和更新的过程。字段条与十六进制内容对应当前记录；页面再次写入后，可比较两端版本的变化。

{% include '_migration_stream_lab.html' %}

在源端运行期间，框架写入流头、配置摘要、RAM 初始化和多个迭代批次。暂停后，最终 RAM 保存先于非迭代状态保存；后者先同步 CPU 状态，再遍历设备处理器。目的端从流开始就解析和装载，而非收到 EOF 后才统一拷贝。最终保存顺序

流头、分段与边界

流格式版本不等于设备状态版本

流头是两个大端 32 位整数：QEMU_VM_FILE_MAGIC = 0x5145564d与QEMU_VM_FILE_VERSION = 3，完整字节为 51 45 56 4d 00 00 00 03。前者是 magic，后者是流格式版本。每个 CPU、RAM 或设备处理器还拥有自己的状态版本，解决各自字段演进的问题，两者不能混用。格式常量

默认随后写入 CONFIGURATION 0x07：机器名称长度为 BE32，名称本身按字节写入，不带终止 NUL；条件子段补充页大小、能力等兼容性信息。这不是虚拟机定义，目的端不能只凭它创建完整设备。配置字段、发送入口

两种 section 头

外层类型常量以 QEMU_VM_SECTION_为前缀：START、PART、END、FULL分别为 0x01至 0x04；QEMU_VM_SECTION_FOOTER为 0x7e。图表使用简称，源码可按完整宏名查找。

记录线上字段，按顺序
START / FULL类型 1 B → section ID 4 B → 名称长度 1 B → 名称 N B → 实例 ID 4 B → 状态版本 4 B
PART / END类型 1 B → section ID 4 B
Section Footer0x7e 1 B → section ID 4 B

这些 4 字节整数均为大端。START建立可迭代处理器的关联，PART/END只引用 section ID；FULL一次传输一个处理器的完整状态。名称和实例决定目的端匹配哪个已注册对象，section ID 则是本次流中的引用，不是设备永久编号。头与 footer 的实现

例如假设 RAM 的 section ID 为 1，其 START 头为：

01                 # SECTION_START
00 00 00 01        # section ID（本例取 1）
03 72 61 6d        # 名称长度 3；"ram"
00 00 00 00        # instance ID = 0
00 00 00 04        # RAM 状态版本 = 4

默认每次 START、PART、END、FULL 的载荷之后都有 5 字节 footer。它用于核对处理器是否准确消费载荷，不是可以扫描寻找的分隔符：页面内容本身也可能出现 0x7e。正确做法是先按处理器格式读完载荷，再校验 footer 的标记和 ID。默认设置、footer 校验

内存记录的编码

布局先于页面

ram_save_setup()先写 BE64 的“总 RAM 字节数 OR MEM_SIZE 0x004”，随后逐块写名称长度（1 B）、名称、块长度（BE64）。目的端用块名寻找本机 RAMBlock，并按长度累计扣减总量，读完布局后遇到 RAM EOS。块名不是宿主进程地址，页面也通过“块＋块内偏移”定位。布局发送、布局接收

偏移与标志共用八字节

页记录的首个 BE64 保存块内页偏移，低位存放标志。普通页用 PAGE 0x008，零页用 ZERO 0x002。首次发送某块或切换 RAMBlock 时，还要发送名称长度和名称；同一块的后续记录可加 CONTINUE 0x020，复用上次块名。

普通页（4 KiB 页、同一 RAMBlock，偏移 0x2000）：
00 00 00 00 00 00 20 28     # 0x2000 | PAGE | CONTINUE
[4096 字节页面内容]

零页（同一 RAMBlock，偏移 0x3000）：
00 00 00 00 00 00 30 22     # 0x3000 | ZERO | CONTINUE
00                          # 零填充值，不传整页

本批 RAM 载荷结束：
00 00 00 00 00 00 00 10     # RAM_SAVE_FLAG_EOS
7e [4 字节 section ID]      # 外层 footer，不属于 RAM 载荷

普通页长度由目标页大小决定，并无逐页长度字段。零页在此版本只允许零填充，接收端会拒绝非零填充值。CONTINUE表示沿用块名，不表示延续上一页的数据，也不是“继续下一轮迁移”。标志定义、页头、零页与普通页

边界具体含义
RAM EOS · BE64 0x10RAM 处理器结束本批载荷，返回外层解析器。
SECTION_END · 类型 0x03本条外层记录是可迭代处理器的最终阶段，载荷仍在其后。
Section Footer · 0x7e＋ID校验刚消费完的 section；每批都可以有，不等于整个 RAM 完成。
EOF · 0x00结束主状态记录循环，不等于网络连接立即关闭。

ram_save_iterate()每次调用可以只传输部分待传页，首次扫描本身就可能跨多个 PART。停机后 ram_save_complete()做最终脏页同步，再用相同的页编码发送余页。流里没有统一的轮次序号；分析抓取数据时，不宜把 PART 个数当作预拷贝轮数。

处理器与设备状态

源端暂停后，默认还会发送切换通知：08 00 0b 00 00，分别是 COMMAND、SWITCHOVER_START = 11和长度 0。接收端据此分派 switchover_start回调；它并不是命令目的端暂停或启动。COMMAND 的长度属于这种记录自身的格式，普通设备 section 仍没有统一载荷长度。命令编码、发送时机

完成 RAM 后，cpu_synchronize_all_states()把 KVM 维护的寄存器状态同步进 QEMU 对象，再保存非迭代状态。CPU、设备及其他处理器按注册顺序写 FULL，不保证“全部 CPU 在前、全部设备在后”。标记 early_setup的状态还可以在初始化阶段提前保存。

VMStateDescription规定要保存的字段、类型、版本条件以及保存前和装载后回调。x86 CPU 的状态表以这些字段开始：

VMSTATE_UINTTL_ARRAY(env.regs, X86CPU, CPU_NB_REGS),
VMSTATE_UINTTL(env.eip, X86CPU),
VMSTATE_UINTTL(env.eflags, X86CPU),

在 x86-64 目标中，它们使用 64 位目标字宽；后面的 FPU、段寄存器、控制寄存器等继续按类型保存。序列化不是把 C 对象连同指针和填充直接复制出去。接收端必须理解对应状态版本及字段顺序。CPU 状态表、字段遍历

i8259 的 irr、imr、isr分别用 UINT8 保存中断请求、屏蔽和服务中状态。virtio 除客户机 RAM 中的队列描述符，还需要交接设备状态、协商特性、last_avail_idx等设备侧处理位置。否则 RAM 虽然一致，设备仍可能从错误位置继续工作。i8259、virtio

条件子段用 SUBSECTION 0x05＋名称长度（1 B）＋名称＋版本（BE32）＋子段载荷表达。它属于相应 VMState 的内部格式，不是另一条顶层 FULL，也不自带统一长度或 section footer。父处理器读取完字段与子段之后，才返回框架校验外层 footer。子段保存与装载

接收解析与恢复执行

qemu_loadvm_state_main()先取一个外层类型字节。START/FULL 读取名称和实例，找到目的端处理器并检查版本；PART/END 复用之前建立的 section ID 关联。然后进入 RAM、VMState 或旧式设备的专用装载函数。找不到对象或无法理解版本，应当报错，而不是从流中猜出并创建一个设备。

qemu_loadvm_state_header     校验流头、装载配置摘要
qemu_loadvm_state_main       按外层类型分发
  START/FULL                按名称和实例匹配处理器
  PART/END                  按 section ID 找回处理器
    ram_load / vmstate_load 消费其自身格式的载荷
    check_section_footer    核对尾标记与 section ID
  COMMAND                   按命令号执行协议处理
  EOF                       离开主状态记录循环

EOF 后可能跟随 VMDESCRIPTION 0x06＋JSON 字节长度（BE32）＋JSON。它供调试工具分析字段，不是恢复虚拟机所需的一份完整描述。普通预拷贝接收端按条件读完它，再完成装载收尾与 CPU 状态同步。处理器匹配、装载收尾

cpu_synchronize_all_post_init()使恢复的 CPU 对象状态同步到 KVM vCPU；真正开始执行还需要后续运行状态检查。process_incoming_migration_bh()考虑原运行状态、autostart 与存储激活，满足条件才调用 vm_start()。因此 EOF、装载完成和客户机恢复执行是三个不同的时刻。目的端运行决策

格式的演进与兼容

早期设备分别手写保存与装载函数，字段顺序与条件容易在两端产生偏差。2009 年引入的声明式 VMState集中字段类型与读写逻辑，降低重复维护的成本，但旧式处理器仍然存在。已经发布的线格式也不会因此自动兼容：字段顺序、版本号与条件子段都必须谨慎设计。

二进制流本身没有为每个字段携带名称；离线分析通常需要对应设备代码。后来增加的VM Description在 EOF 后附加诊断 JSON，改善可观察性，同时避免重写既有状态编码。它解决的是分析便利性，而非跨任意 QEMU 版本、机器类型和设备组合迁移的问题。

MultiFD、后拷贝与设备并行传输进一步改变通道与时序：部分页面不再经过这条主流，执行权交接和同步点也有所不同。但“框架识别处理器、处理器解释载荷、兼容性由两端实现保证”的分工仍然重要。阅读新分支时，应先识别哪些数据离开了主流，再分析新增的同步条件，而不是只在单流图中增加一个箭头。
