迁移流如何恢复运行状态

目的端 QEMU 已经创建了机器与设备，但还不知道源端哪些页被修改、CPU 停在哪条指令、设备处理到了哪个请求。迁移流把这些运行状态交给对应的接收处理器：先识别流格式和机器配置，再建立 RAM 布局并更新页面，暂停后交接 CPU 与设备状态，最后检查是否可以恢复执行。

这条路径由两层格式配合完成：外层 section 选择处理器并校验边界，内层载荷描述页面或设备字段。以下用同一组四个内存页贯穿完整流示例，再逐层展开头部、RAM 编码、VMState 和接收流程。

以下以 x86 / KVM、普通 RAM 的单流预拷贝为例，机器与设备已在目的端创建，存储另行准备。内存重传和停机切换条件见《QEMU 预拷贝迁移的内存迭代与停机控制》。

完整示例：从流头到状态恢复

QEMUFile提供顺序读写接口；迁移框架在流中标识状态处理器，RAM、CPU 和设备各自负责载荷。左侧按发送顺序排列整条迁移流，右侧展开相应记录的字段。RAM 载荷内部的 EOS、section 尾部的 footer 和整条状态流的 EOF 属于不同层次。

下面以 pc.ram及其中四个页面为例，观察同一组数据从源端编码、经过迁移通道，到目的端解析和更新的过程。字段条与十六进制内容对应当前记录；页面再次写入后，可比较两端版本的变化。

在源端运行期间，框架写入流头、配置摘要、RAM 初始化和多个迭代批次。暂停后，最终 RAM 保存先于非迭代状态保存；后者先同步 CPU 状态，再遍历设备处理器。目的端从流开始就解析和装载，而非收到 EOF 后才统一拷贝。最终保存顺序

流头、分段与边界

流头与配置摘要

流头是两个大端 32 位整数：QEMU_VM_FILE_MAGIC = 0x5145564d与QEMU_VM_FILE_VERSION = 3，完整字节为 51 45 56 4d 00 00 00 03。前者是 magic，后者是流格式版本。各 CPU、RAM 或设备处理器另有独立的状态版本，用于管理各自字段的兼容性。格式常量

默认随后写入 CONFIGURATION 0x07：机器名称长度为 BE32，名称本身按字节写入，不带终止 NUL；条件子段补充页大小、能力等兼容性信息。目的端用这些字段检查已创建的机器，完整机器与设备配置仍需在迁入前准备。配置字段、发送入口

两种 section 头

外层类型常量以 QEMU_VM_SECTION_为前缀：START、PART、END、FULL分别为 0x01至 0x04；QEMU_VM_SECTION_FOOTER为 0x7e。图表使用简称，源码可按完整宏名查找。

记录流中的字段，按顺序
START / FULL类型 1 B → section ID 4 B → 名称长度 1 B → 名称 N B → 实例 ID 4 B → 状态版本 4 B
PART / END类型 1 B → section ID 4 B
Section Footer0x7e 1 B → section ID 4 B

这些 4 字节整数均为大端。START建立可迭代处理器的关联，PART/END只引用 section ID；FULL一次传输一个处理器的完整状态。名称和实例用于匹配目的端已注册的对象，section ID 的引用范围限定在本次迁移流中。头与 footer 的实现

例如假设 RAM 的 section ID 为 1，其 START 头为：

01                 # SECTION_START
00 00 00 01        # section ID（本例取 1）
03 72 61 6d        # 名称长度 3；"ram"
00 00 00 00        # instance ID = 0
00 00 00 04        # RAM 状态版本 = 4

默认每次 START、PART、END、FULL 的载荷之后都有 5 字节 footer，用于核对处理器是否准确消费载荷。接收端按处理器格式读完载荷后，再校验 footer 的标记和 ID。由于页面内容本身也可能出现 0x7e，扫描该字节无法确定载荷边界。默认设置、footer 校验

内存记录的编码

布局先于页面

ram_save_setup()先写 BE64 的“总 RAM 字节数 OR MEM_SIZE 0x004”，随后逐块写名称长度（1 B）、名称、块长度（BE64）。目的端用块名寻找本机 RAMBlock，并按长度累计扣减总量，读完布局后遇到 RAM EOS。后续页记录通过“块＋块内偏移”定位，使用目的端对应 RAMBlock 的本地映射。布局发送、布局接收

偏移与标志共用八字节

页记录的首个 BE64 保存块内页偏移，低位存放标志。普通页用 PAGE 0x008，零页用 ZERO 0x002。首次发送某块或切换 RAMBlock 时，还要发送名称长度和名称；同一块的后续记录可加 CONTINUE 0x020，复用上次块名。

普通页（4 KiB 页、同一 RAMBlock，偏移 0x2000）：
00 00 00 00 00 00 20 28     # 0x2000 | PAGE | CONTINUE
[4096 字节页面内容]

零页（同一 RAMBlock，偏移 0x3000）：
00 00 00 00 00 00 30 22     # 0x3000 | ZERO | CONTINUE
00                          # 零填充值，不传整页

本批 RAM 载荷结束：
00 00 00 00 00 00 00 10     # RAM_SAVE_FLAG_EOS
7e [4 字节 section ID]      # 外层 footer，不属于 RAM 载荷

普通页长度由目标页大小决定，并无逐页长度字段。零页在此版本只允许零填充，接收端会拒绝非零填充值。CONTINUE只控制块名复用；每条页记录仍携带自己的偏移、编码标志和相应载荷。标志定义、页头、零页与普通页

边界具体含义
RAM EOS · BE64 0x10RAM 处理器结束本批载荷，返回外层解析器。
SECTION_END · 类型 0x03本条外层记录是可迭代处理器的最终阶段，载荷仍在其后。
Section Footer · 0x7e＋ID校验刚消费完的 section；每批都可以有，不等于整个 RAM 完成。
EOF · 0x00结束主状态记录循环，不等于网络连接立即关闭。

ram_save_iterate()每次调用可以只传输部分待传页，首次扫描本身就可能跨多个 PART。停机后 ram_save_complete()做最终脏页同步，再用相同的页编码发送余页。流里没有统一的轮次序号；分析抓取数据时，不宜把 PART 个数当作预拷贝轮数。

暂停后保存 CPU 与设备状态

源端暂停后，默认还会发送切换通知：08 00 0b 00 00，分别是 COMMAND、SWITCHOVER_START = 11和长度 0。接收端据此分派 switchover_start回调，后续仍需完成内存与设备状态装载，才能进入运行状态检查。COMMAND 的长度属于这种记录自身的格式，普通设备 section 仍没有统一载荷长度。命令编码、发送时机

完成 RAM 后，cpu_synchronize_all_states()把 KVM 维护的寄存器状态同步进 QEMU 对象，再保存非迭代状态。CPU、设备及其他处理器按注册顺序写 FULL，不保证“全部 CPU 在前、全部设备在后”。标记 early_setup的状态还可以在初始化阶段提前保存。

VMStateDescription规定要保存的字段、类型、版本条件以及保存前和装载后回调。它与状态处理器和字段定义共同完成序列化：

本地结构关键字段如何参与编码与装载
SaveStateEntryidstr / instance_id / version_id / section_id / load_section_id关联状态处理器；接收 START / FULL 后记录源端 section ID，后续 PART / END 可据此找回处理器
VMStateDescriptionname / version_id / minimum_version_id / fields / subsections定义可接受版本、字段列表及条件子段，组织保存与装载回调
VMStateFieldoffset / size / num / info / flags / version_id在本地对象中定位字段，由类型的 put / get 函数写入或读取线格式

这些结构描述如何访问对象。offset是本地 C 对象中的字段偏移，不直接作为迁移流中的字段地址发送；接收端根据自己的状态描述找到对应成员。SaveStateEntry、VMState 字段与描述

x86 CPU 的状态表以这些字段开始：

VMSTATE_UINTTL_ARRAY(env.regs, X86CPU, CPU_NB_REGS),
VMSTATE_UINTTL(env.eip, X86CPU),
VMSTATE_UINTTL(env.eflags, X86CPU),

在 x86-64 目标中，它们使用 64 位目标字宽；后面的 FPU、段寄存器、控制寄存器等继续按类型保存。VMState 按声明逐个序列化字段，编码独立于 C 对象中的指针和填充布局。接收端按对应状态版本及字段顺序装载。CPU 状态表、字段遍历

i8259 的 irr、imr、isr分别用 UINT8 保存中断请求、屏蔽和服务中状态。virtio 除客户机 RAM 中的队列描述符，还需要交接设备状态、协商特性、last_avail_idx等设备侧处理位置。否则 RAM 虽然一致，设备仍可能从错误位置继续工作。i8259、virtio

条件子段用 SUBSECTION 0x05＋名称长度（1 B）＋名称＋版本（BE32）＋子段载荷表达。它嵌在相应 VMState 内部，没有统一长度或独立的 section footer。父处理器读取完字段与子段之后，返回框架校验外层 footer。子段保存与装载

接收解析与恢复执行

qemu_loadvm_state_main()先取一个外层类型字节。START/FULL 读取名称和实例，找到目的端处理器并检查版本；PART/END 复用之前建立的 section ID 关联。然后进入 RAM、VMState 或旧式设备的专用装载函数。对象缺失或状态版本不受支持时，装载返回错误。

EOF 后可能跟随 VMDESCRIPTION 0x06＋JSON 字节长度（BE32）＋JSON，供调试工具分析状态字段；实际恢复使用前面已装载的二进制状态。普通预拷贝接收端按条件读完诊断描述，再完成装载收尾与 CPU 状态同步。处理器匹配、装载收尾

cpu_synchronize_all_post_init()使恢复的 CPU 对象状态同步到 KVM vCPU；真正开始执行还需要后续运行状态检查。process_incoming_migration_bh()考虑原运行状态、autostart 与存储激活，满足条件才调用 vm_start()。因此 EOF、装载完成和客户机恢复执行是三个不同的时刻。目的端运行决策

沿这条路径排查失败，可先按层定位：magic 或格式版本错误发生在流入口；名称、实例或版本不匹配发生在处理器选择；RAM 范围和设备字段错误发生在载荷装载；数据全部读完后仍未运行，再检查 autostart、存储激活与原运行状态。这样可以把传输损坏、配置不兼容和有意保持暂停区分开。

格式的演进与兼容

早期设备分别手写保存与装载函数，字段顺序与条件容易在两端产生偏差。2009 年引入的声明式 VMState集中字段类型与读写逻辑，降低重复维护的成本，但旧式处理器仍然存在。已经发布的线格式也不会因此自动兼容：字段顺序、版本号与条件子段都必须谨慎设计。

二进制流本身没有为每个字段携带名称；离线分析通常需要对应设备代码。后来增加的VM Description在 EOF 后附加诊断 JSON，便于工具还原字段含义，并保留已有二进制编码。跨版本迁移仍受机器类型、设备字段及双方能力约束。

MultiFD 将部分内存数据移到并行通道，后拷贝调整执行权交接与页面传输的先后顺序，设备并行传输也会引入独立通道。这些路径需要额外的同步协议，保证目的端恢复时各部分状态已经就绪。外层框架继续负责识别状态处理器，具体处理器负责解析载荷和检查版本兼容性。
