写入完成与持久化

同样写入 4 KiB 数据，普通 WRITE、写后 FLUSH 和 WRITE FUA 的完成条件不同。下面沿用偏移 1 MiB 的块设备写入，把旧值 A 更新为 B，分别观察应用返回、Guest 队列完成、宿主缓存和稳定存储。原有读写演示用于查看完整设备路径，这里集中展示同步要求如何改变完成边界。

三种场景固定使用 QEMU 的 raw 文件后端、aio=threads 和 writeback 模式。普通 WRITE 与写后 FLUSH 从应用的 O_DIRECT 块设备写入开始，宿主仍使用自己的页缓存；FUA 对照从已经带 REQ_FUA 的块请求开始，只观察这一命令。WRITE 后 FLUSH 场景另外提交一条刷新命令。缓存状态用于解释接口契约，不表示真实硬件内部时序或耗时。

区分缓存路径与同步要求

配置或操作控制范围完成保证
Guest O_DIRECT本次 I/O 绕过 Guest 页缓存单独使用不保证掉电持久化，也不控制宿主页缓存
QEMU cache.direct=on尽量绕过宿主页缓存设备仍可能有易失写缓存；direct 不等于同步持久化
writeback=on 的普通 WRITE允许下层在缓存接受数据后报告完成应用可回收本次缓冲区，稳定存储状态尚未由该操作确认
WRITE 完成后执行 FLUSH确认此前已完成、属于刷新范围的写入刷新成功后，这些数据达到下层承诺的稳定存储边界
WRITE FUA约束本次写的完成条件本次数据持久化后才完成，不自动保证所有前序写入
QEMU cache.no-flush=on允许跳过向存储落实的刷新；也会清除下传的 FUA 要求不能沿用本演示的持久化保证

cache=none 对应 writeback=on、direct=on、no-flush=off，仍需要 Guest 正确发起同步。cache=unsafe 则允许忽略刷新。这些参数和 Guest 打开文件时的标志属于不同层，不能只凭“direct”或“无缓存”的名称判断数据安全。QEMU 缓存模式定义。

FUA 在两种设备接口中的实现

Linux 6.18 的块设备同步直接写可产生 REQ_FUA。virtio-scsi 在目标支持时把它编码到 SCSI WRITE 的 FUA 位；QEMU scsi-hd 再转换成 BDRV_REQ_FUA。本例的 raw threads 后端先完成文件写入，再执行刷新，最后才向 Guest 完成这条 SCSI 命令。其他后端可以直接支持 FUA，具体实现需分别检查。文件后端实现。完整系统调用还可能安排其他同步：例如同步块设备写在 write_iter 末尾还会经过 generic_write_sync()，不能把这里的一条命令直接当作完整调用的全部设备请求。Linux 调用边界。

virtio-blk 的普通 OUT 命令没有这里的原生 FUA 位。固定版本的 Linux 驱动声明写缓存能力而不声明 BLK_FEAT_FUA，块层会为需要 FUA 的写入安排写后 FLUSH。它与应用先完成普通写、再显式调用 fsync() 的外部调用顺序不同；共同要求是同步操作不能在所需刷新完成前成功返回。驱动能力、块层 POSTFLUSH。

需要同时约束前序数据和当前写时，上层可以组合 PREFLUSH 与 FUA。FUA 的契约只覆盖该写；某个后端用较大范围刷新来实现它，也不应让应用依赖额外的前序顺序保证。持久化还不同于原子性：本例不保证一组写入整体生效，也不涵盖文件创建、目录项或跨设备事务。Linux 写缓存控制契约。
