中断的作用与虚拟化边界

中断用于将设备完成、定时器到期等事件通知处理器，使操作系统及时执行相应的处理程序。中断虚拟化为每台客户机维护独立的中断控制器状态、路由和处理入口，并在客户机允许接收时交付事件。以网卡收包为例，报文先进入接收缓冲区，通知路径再促使客户机驱动检查队列；数据传输与中断交付是相互关联的两个过程。

轮询与中断：主动检查，或等待通知

一种办法是让 CPU 反复检查接收队列，这叫轮询。检查足够频繁时，响应可以很快；没有包到达时，也要消耗 CPU 时间。另一种办法由设备在有工作时发出中断，CPU 平时继续计算或进入空闲，收到通知后转入操作系统的处理入口。代价是保存与恢复执行现场，以及处理通知本身的开销。高流量网络常把两者结合：中断启动处理，再通过轮询批量收包。

一次中断需要完成三件事

设备先保存数据和完成状态，再发出通知；中断系统决定通知哪个 CPU、使用哪个入口；CPU 在允许接受中断时保存必要的执行现场，经中断描述符表（IDT）进入内核，驱动再读取队列或设备状态。处理结束后，系统恢复先前的执行。网络包保存在缓冲区中，中断携带的是处理入口等控制信息。

本文围绕 x86 的一次 virtio-net 收包展开：后端填好缓冲区，通知指定 vCPU，客户机驱动读取结果。全文按“配置目标 → 发布完成 → 发送消息 → Guest 接受与消费”展开，再对比 irqfd、硬件辅助和设备直通。

一次收包的数据路径与通知路径

设客户机已给接收队列 0 提供空缓冲区，后端收到一个 1500 字节以太网帧。客户机把这个队列的通知配置到 vCPU 1，对应中断向量 0x51；向量是客户机查找中断处理入口的编号。处理分为四步：

  1. 保存结果。后端把网络头和帧写入客户机缓冲区，再发布 used 完成记录。驱动今后据此找到数据与实际长度。
  2. 提交通知。通知条件满足时，设备按配置发出中断消息。多个完成可以合并为一次通知，帧内容仍保存在内存里。
  3. 等待并交付。虚拟中断控制器记录待处理向量。目标 vCPU 获得执行机会、客户机允许接收时，处理器才转入客户机的中断入口。
  4. 消费数据。客户机驱动检查队列，安排 NAPI 批量处理，把帧交给网络栈，并补充新的接收缓冲区。

从后端写完数据到客户机消费数据，还可能经历通知合并、客户机屏蔽、宿主调度和驱动轮询等等待。后面的软件基线固定使用 QEMU virtio-net 后端、MSI-X 和 KVM 内核 LAPIC，先跟完这一条路径，再更换后端与递送方式。

先确定队列、中断向量与目标 CPU

本例接收队列 0 关联 MSI-X 表项 2；表项的消息地址与 data 表达 APIC ID 1 和向量 0x51。APIC ID 选择虚拟 CPU，中断向量选择该 CPU 的 IDT 入口。队列号、表项索引、Linux IRQ 号和向量属于不同编号空间。

每个逻辑 CPU 的 Local APIC（LAPIC）维护待处理与正在服务的中断。I/O APIC 路由外部中断线，MSI/MSI-X 用消息直接表达目标与向量，不需要经过 I/O APIC 的引脚路由。传统 PIC 为兼容旧设备提供集中式引脚中断接口。

启用全部线程的 16 核、32 线程物理服务器有 32 个逻辑 CPU，各有 LAPIC 状态；一台 4 vCPU 客户机则有自己的 4 份虚拟 LAPIC 状态。两套编号与路由分别由宿主和客户机管理。

QEMU 的设备模型保存本虚拟机的 MSI-X 表项；KVM 维护每个 vCPU 的 LAPIC；IDT 保存在客户机内存。客户机的 APIC ID 1 指定虚拟 CPU，宿主调度器决定对应 vCPU 线程实际运行在哪个物理 CPU 上。

发布 used 与判定通知

设队列大小为 8，先前 used.idx = 7，本次完成的描述符链头为 3。QEMU 先写完成项，再推进索引。设备写入 1500 字节帧与 12 字节网络头，共 1512 字节，本次记录如下：

used.ring[7 % 8] = { id: 3, len: 1512 }
写屏障：先让完成数据与完成项可见
used.idx = 8

驱动读取：last_used_idx = 7 → 消费 ring[7] → last_used_idx = 8

len 表示设备写入缓冲区的字节数；本例接收记录为 1512，纯发送请求则可以为 0。virtqueue_split_flush() 在更新 used.idx 前执行写屏障；virtio_split_should_notify() 在读取通知条件前执行内存屏障。发布完成和决定通知是两个动作。完成发布、通知判定

未协商 EVENT_IDX 时，设备查看驱动设置的 VRING_AVAIL_F_NO_INTERRUPT。协商后，驱动用 used_event 表示希望被通知的完成位置，设备按 16 位环绕运算判断本次推进是否越过阈值：

need_event = (uint16_t)(new - event - 1) < (uint16_t)(new - old)

old = 7, new = 8, event = 7 → 0 < 1，发出通知
old = 7, new = 8, event = 8 → 65535 < 1 为假，暂不通知

这里假定 QEMU 已有有效的先前通知判定位置；首次尚未建立该记录时，代码会允许通知。通知抑制保留全部 used 记录，供驱动批量消费或轮询。驱动准备停止轮询时，需要重新启用通知并再次检查队列，处理“设备恰好在重新启用期间完成请求”的竞争。单纯打开中断后立即睡眠，可能错过已经发布的工作。

调大批处理范围可以减少通知与唤醒，但请求可能等到下一次轮询或通知才被消费。完成延迟因此同时受后端处理、通知策略和客户机调度影响。只统计中断次数，不能判断 I/O 是否更快。

MSI-X 消息与屏蔽状态

通知被允许后，virtio_pci_notify() 用队列配置的表项索引调用 msix_notify()。假设表项 2 已分配、MSI-X 已启用、功能级和表项级屏蔽均关闭，使用传统 xAPIC 消息格式、物理目的地、fixed delivery、edge trigger，向 APIC ID 1 发送向量 0x51：

MSI-X table[2]：
  address_lo     = 0xfee01000  // 0xfee00000 | (APIC ID 1 << 12)
  address_hi     = 0x00000000
  data           = 0x00000051 // vector = 0x51，fixed、edge
  vector_control = 0x00000000 // bit 0：表项屏蔽位，当前为 0

地址选择中断目的地，data 编码向量和投递属性。这次写入针对客户机的中断消息地址空间，不会把 0x51 写入一页普通客户机 RAM。x2APIC 扩展目的地、逻辑目的地或中断重映射使用不同的编码与转换，不能直接套用这个数值示例。

QEMU 从表项组装 MSIMessage { address, data }，经 PCI 地址空间写入进入 KVM APIC 的 MSI 区域，最终用 KVM_SIGNAL_MSI 提交 struct kvm_msi。这条直接路径把地址和 data 一起交给 KVM，由消息本身指定目标 APIC 与向量。MSI-X 发送、KVM APIC 消息入口

若表项被屏蔽，QEMU 设置 Pending Bit Array 中该表项的 pending 位，暂不发送。取消屏蔽时发现 pending，会清除该位并补发通知。一个 pending 位可以合并多个完成事件；驱动仍通过 used.idx 与 used ring 取得完整的完成记录。

这个屏蔽与 virtqueue 的通知抑制处于不同层。前者已有一次待发送的 MSI-X 通知，后者可能根本没有产生该次通知；LAPIC 接收后暂不能投递，又是第三种等待状态。排查“完成了但客户机没处理”时，需要分别查看。

从 LAPIC 待处理中断到驱动回调

KVM 把 MSI 地址和 data 解码为目的 APIC、向量、投递方式等字段，再送到目标虚拟 LAPIC。以未启用 APICv 的 Intel VMX 路径为例，vmx_deliver_interrupt() 设置 IRR[0x51]，请求事件处理并 kick 目标 vCPU。kick 用于促使 vCPU 及时检查状态，不保证客户机立即执行中断处理函数。

irqfd 的内核中断注入路径

QEMU 为 guest notifier 配置 irqfd 时，先通过 KVM_SET_GSI_ROUTING 建立 GSI 37 到 MSI 地址及 data 的路由，再通过 KVM_IRQFD 绑定 eventfd 与 GSI 37。struct kvm_irqfd 的 fd、gsi、flags 和 resamplefd 均为 32 位字段；本例边沿 MSI 路径不使用电平中断的 resamplefd 应答协议。

后端发出 eventfd 事件后，KVM 的 irqfd_wakeup() 读取事件并尝试用缓存路由直接投递；当前上下文无法完成时，再安排工作队列。原先需要由用户态监听完成事件并调用 MSI 注入接口的场景，可以省去这次中转。进入目标 LAPIC 后，仍按前文的待处理、交付和驱动回收流程继续。eventfd 计数不等于客户机应收到同样次数的中断，请求完成仍以队列为准。

QEMU 10.2 的 virtio_irq() 在 IOThread 中使用 guest notifier；非 IOThread 的普通路径调用 virtio_notify_vector()。vhost 的完成通知也可以接到 eventfd，但其后端执行者已经不同。irqfd 路径必须随 MSI-X 路由修改、屏蔽、解除绑定同步更新，不能绕开这些设备语义。

irqfd 描述的是 eventfd 到虚拟中断的内核接口。消息进入 KVM 后，可以由 KVM 写 PID.PIR，使用 CPU 侧 posted-interrupt processing 加速交付。直通设备还有 VT-d 根据 posted IRTE 直接写 PIR 的路径，设备仍发送 MSI-X，但省去逐次 VFIO / irqfd 转发。两者都受硬件能力、配置及运行条件限制；使用 irqfd 并不自动意味着启用 posted，更不保证没有 VM Exit。

中断路径的开销与加速

先把刚才的流程按开销位置分开。设备完成后，消息要从设备后端进入 KVM；KVM 随后检查虚拟控制器状态并安排客户机接受中断。irqfd 主要改变前一段的通知入口，APICv / AVIC 主要加速后一段的控制器访问与交付。MSI-X 表项决定的目标和向量仍然有效。

irqfd：减少独立后端的用户态通知中转

现在把收包处理从 QEMU 切换到 vhost-net：报文和 used 记录由内核后端填写。如果完成通知还要唤醒 QEMU，再由 QEMU 调用注入接口，就会为通知重新走一趟用户态。irqfd 允许 QEMU 事先把后端的 eventfd 与 KVM 中断路由绑定，使这次交接直接在内核完成。独立的 vhost-user 后端也能使用这一机制，设置和更新路由仍由管理路径负责。

本例仍向 vCPU 1 交付 0x51：后端触发已绑定的 eventfd，KVM 按预先配置的路由处理。报文与完成记录保存在共享内存中，eventfd 只传递通知。若设备后端本身仍在 QEMU 中，收包处理也仍由 QEMU 执行，不能由使用 irqfd 推导出整个 I/O 路径都绕过 QEMU。

与完成方向对应，ioeventfd 用于请求方向，连接客户机的设备通知写入与后端唤醒：

接口通知方向减少的中转
ioeventfd客户机写设备通知地址 → KVM → 后端 eventfd这次通知写入可由 KVM 处理，无需返回 QEMU 的 vCPU 线程做设备访问分派
irqfd后端 eventfd → KVM 路由 → 客户机中断完成事件无需先唤醒用户态监听者，再调用中断注入接口

ioeventfd 路径仍可能产生硬件 VM Exit，只是 KVM 可以在内核完成匹配和通知；irqfd 的交付同样受客户机中断状态与 vCPU 调度限制。两者在同一设备上分别服务于请求与完成方向。KVM eventfd 实现

APICv / AVIC：减少控制器访问与虚拟中断交付的退出

事件进入 KVM 后，前一节的软件路径还要记录 IRR、促使 vCPU 检查事件，并安排 VM Entry 注入；部分 APIC 寄存器访问也会使客户机退出。Intel APICv 用虚拟 APIC 状态与执行控制，让硬件接管部分访问、优先级判断和中断交付；AMD AVIC 也沿硬件辅助方向降低开销，但使用不同的数据结构和通知机制。

以 Intel posted interrupt 为例，KVM 可以先把向量记入 Posted Interrupt Descriptor 的 PIR 位图，再按需发送通知。目标 vCPU 正在合适的运行状态时，处理器可同步待处理向量并向客户机交付，避免为这段交付专门退出。客户机的屏蔽和优先级规则仍然有效。irqfd 的投递也可以进入这条路径，因此 irqfd 与 APICv 可以配合使用。KVM 的 posted 与软件回退路径

直通设备分支：用 interrupt posting 减少宿主转发

前面讨论的是 virtio 软件后端。换成 VFIO 分配的物理设备后，数据与通知由实际设备产生。这里两条直通路径都使用 MSI-X：普通 remapped IRTE 把消息送到宿主 IRQ / VFIO，再经 eventfd / irqfd 转交 KVM；posted IRTE 则由 VT-d IOMMU 直接把 Guest 向量写入目标 vCPU 的 PID，省去逐次宿主转发。MSI-X 是设备消息机制，VT-d posted 是递送加速，两者不是替代关系。普通宿主转发进入 KVM 后，也仍可使用 CPU 侧 APICv posted 交付。

同一网卡、NVMe 控制器或 GPU 都可能走这两条路径，取决于平台和路由，不是设备类型或应用逐次 I/O 的选择。设备 posting 要求 IOMMU / CPU 能力与内核配置支持、VFIO irq-bypass 绑定成功，并能投递给单一 vCPU；未启用或不满足条件时使用宿主转发。广播、多播及 NMI 等不适用这里的 posted 路径；已有路由变为不支持的形式时，KVM 可恢复普通 remapped 模式。单目标路由条件与回退

vCPU 暂时未运行不等于自动切回普通 IRTE。阻塞时可能需要宿主唤醒线程；被抢占时保留 pending、等待调度；迁核时更新 PID 通知目标。硬件能减少投递开销，不能替宿主调度器分配 CPU 时间。AMD 的 AVIC/中断重映射有自己的实现，不能套用 Intel 描述符字段。PID 目标与状态维护、阻塞与调度处理

两种 posted 路径共用 CPU 侧的 posted-interrupt processing，区别在上游是谁写 PIR：一个是 KVM 软件，一个是 VT-d IOMMU。不能把 APICv 与 VT-d posted 看成两种完全并列、互斥的中断方案。演示固定目标 vCPU 正在另一物理 CPU 上运行、IF 与优先级允许等条件，才展示无需为本次交付退出目标 Guest 的路径。

DPDK 的 callfd 是 eventfd 文件描述符，irqfd 是 KVM 对 eventfd 和 GSI 路由的绑定。QEMU 事先建立内存共享、MSI 路由，并经 VHOST_USER_SET_VRING_CALL 把 fd 交给后端；逐次通知由 DPDK 直接写入。SPDK vhost-user 也可使用这类交接方式。

本例只生成一次完成事件。write(callfd) → irqfd → PIR / IRR → Guest handler 是它在不同层的推进；posted notification 是提示目标 CPU 检查 PID 的宿主通知，并非第二次设备完成。快速 irqfd 路由可在 eventfd 写调用内执行，不表示唤醒 QEMU 或另一个用户态监听线程。相比“后端通知 QEMU、QEMU 再转发”，这里省去了用户态中转；相比 QEMU 自己直接提交 MSI，不能只凭箭头数量断言性能高低。

宿主在设备绑定、路由建立或更新时配置 IRTE，IOMMU 按当前表项处理消息。Guest 驱动仍配置 MSI-X 并处理完成，通常无需感知宿主是否使用 posting。表中的宿主转发示例固定关闭 APICv，以完整呈现软件注入；实际配置仍可结合 CPU 侧 posted 交付。

IF 关闭与表项屏蔽发生在不同位置。IF = 0 时，已经到达的向量可以留在 IRR；设备表项被屏蔽时，消息尚未发出，PBA 记录补发需求。恢复 IF 后还要考虑 STI / MOV SS shadow 和 APIC 优先级。只看“中断已发送”无法判断客户机何时执行处理函数。

MSI-X 表项 2、KVM 路由键 GSI 37、APIC ID 1、向量 0x51 各自标识不同对象。直接 MSI 路径每次提交地址和 data；irqfd 路径预先登记路由，再用 eventfd 触发该路由。配置变更时，路由与 notifier 绑定也要保持一致。

中断机制的演进与实现取舍

沿这次收包过程，可以把演进归为三条线：设备接口从中断线走向消息；虚拟控制器处理从用户态移入内核；后端通知与 vCPU 交付逐步减少软件往返。下表汇总每项改进消除的成本，以及仍需承担的工作。

阶段原有问题与改进仍需承担的工作
PIC → APIC / I/O APIC从集中、有限的中断输入，发展到多 CPU 路由与每 CPU 状态管理引脚分配、路由配置、优先级与应答
PCI INTx → MSI / MSI-X消息与独立表项改善共享中断辨源和多队列分工向量资源、亲和性与通知频率
QEMU 软件控制器 → KVM 内核 irqchip减少控制器处理时的用户态往返内核中的模拟、事件检查及可能的 VM Exit
irqfd（2009 年提出）把 eventfd 后端通知连接到 KVM 路由，省去用户态注入中转eventfd 与路由生命周期、屏蔽同步
APICv / AVIC硬件辅助 APIC 操作与虚拟中断交付，减少部分退出硬件能力、不能加速的操作与回退处理
IOMMU interrupt posting把设备中断直接送到虚拟中断状态，减少直通设备的宿主软件转发平台能力、vCPU 调度迁移、阻塞唤醒与隔离

irqfd 的原始提案说明了 eventfd 连接中断的设计。后来增加的 APICv/AVIC 并没有使 irqfd 失去作用：前者着重减少控制器与 CPU 交付的开销，后者把后端事件接入 KVM。

一台虚拟机可以同时使用 MSI-X、内核 LAPIC、irqfd 和 APICv：它们分别承担消息表达、状态维护、事件接入和交付加速。端到端延迟还包含通知合并、宿主调度与驱动批处理，判断配置的效果需要把这些阶段分别观察。

中断配置、计数与延迟观察

可以先在客户机检查网卡采用的中断方式，再观察相应处理次数。下面的 0000:00:03.0 是示例 PCI 地址，应替换为 lspci -nn 中实际网卡的地址；读取完整配置空间可能需要管理员权限。

# 在客户机执行，只查询状态
lspci -nn
lspci -vv -s 0000:00:03.0
cat /proc/interrupts

MSI-X: Enable+ 表示客户机已启用该设备的 MSI-X，不能据此判断宿主采用普通转发还是 VT-d posted。收包前后对照 /proc/interrupts 中网卡相关行，可以看到客户机各 CPU 的中断处理计数变化。多个包可以共用一次通知，后续还可能由 NAPI 轮询处理，因此这些计数既不等于报文数量，也不能证明宿主启用了 irqfd 或 APICv。宿主的 /proc/interrupts 则反映宿主自身的中断处理，须与客户机视图分开。

报文到达后仍长时间未被客户机处理，可以按顺序检查以下阶段：

  1. 结果发布。查看缓冲区、used 索引和驱动消费位置。后端尚未完成时，优化中断注入没有帮助。
  2. 通知产生与路由。检查通知抑制、MSI-X 屏蔽与 pending、目标 CPU 和向量，区分没有发出与已经等待。
  3. 客户机接受与执行。区分中断屏蔽、优先级等待、vCPU 阻塞和宿主 CPU 竞争。投递变快不会自动消除调度延迟。
  4. 驱动消费。中断处理可能只启动 NAPI，后续批量大小、网络栈与应用调度继续影响尾延迟。

中断优化的目标是以合理的 CPU 成本及时处理工作。降低中断次数可能提高吞吐，也可能让低负载报文等得更久；增加轮询可缩短等待，却占用 CPU。比较时同时记录吞吐、尾延迟、每次通知的处理量和 CPU 占用，才能判断优化是否对实际负载有效。
