增加一个 vCPU，需要谁同意

一台虚拟机启动时使用 2 个 vCPU，高峰期希望扩到 4 个。QEMU 可以创建额外的 CPU 对象和执行线程，但客户机还需要发现处理器、初始化本地状态，并让调度器使用它。缩容时更复杂：客户机必须先移走任务、中断和定时器，宿主才能撤销相应执行上下文。

本文沿 x86 PC 机器的 ACPI CPU 热插拔路径，区分最大拓扑、QEMU 中已创建的 vCPU 和客户机 online CPU，再跟踪一个新增 vCPU 的创建与删除。客户机采用支持 ACPI CPU 热插拔的 Linux；CPU 是否自动上线仍取决于客户机配置。

最大数量、设备存在与客户机在线

状态表示什么怎样确认
最大拓扑启动时预留可容纳的 socket、core、thread 位置和数量上限QEMU 的 smp/maxcpus 与 query-hotpluggable-cpus
QEMU 已创建设备某个位置已经关联 CPU 对象及运行资源query-hotpluggable-cpus 中有 qom-path；query-cpus-fast 返回实例
客户机 present客户机已发现这个处理器客户机 /sys/devices/system/cpu/present
客户机 online客户机已完成上线，允许该 CPU 承担调度与中断工作客户机 /sys/devices/system/cpu/online

前三项也各有观察边界。QEMU 创建了设备，客户机可能尚未处理通知；客户机看到了 CPU，也可能按策略保持 offline。把 CPU 在客户机中 offline，通常只是停止使用，QEMU 对象和宿主线程仍可存在；它与从虚拟硬件中移除 CPU 是两件事。

Linux 的 possible 集合用于描述内核预先支持的 CPU 范围，通常在启动阶段确定。它还受客户机自身配置影响，不应机械地认为它一定与 QEMU 的 maxcpus 相等。最大拓扑也不代表预留了同样数量的独占物理核，宿主调度与绑核需要另行规划。

从 2 个 vCPU 扩到 3 个

下面列出示例虚拟机启动配置中与拓扑相关的部分。CPU 模型应已在本机验证可用；其余磁盘、内存、固件和 QMP 配置沿现有虚拟机设置。

-machine pc-q35-10.2,accel=kvm
-cpu Haswell-v4
-smp cpus=2,maxcpus=4,sockets=1,cores=4,threads=1

启动前预留 4 个单线程核心位置，最初只创建其中 2 个。进入 QMP 后先查询：

{"execute":"query-hotpluggable-cpus"}

在返回项中寻找没有 qom-path 的空位，使用该项实际返回的 type 和 props 创建 CPU。例如查询结果中 core-id 为 2 的空位使用下面的类型与拓扑属性：

{"execute":"device_add","arguments":{
  "driver":"Haswell-v4-x86_64-cpu","id":"cpu-extra",
  "socket-id":0,"core-id":2,"thread-id":0
}}
{"return":{}}

不同拓扑可能还返回 die-id 等字段，应完整沿用对应空位的属性，不能只改数量猜测位置。返回成功后，query-cpus-fast 可确认 QEMU 已建立实例；再在客户机读取 present、online 和 lscpu，确认操作系统是否开始使用。

CPU 的 QMP 设备 ID、cpu-index、APIC ID、客户机逻辑 CPU 编号，以及宿主线程 ID 属于不同标识空间。尤其 query-cpus-fast 返回项顶层的 thread-id 是宿主线程 ID，而 props.thread-id 是虚拟拓扑中的线程位置；排查时应通过拓扑和查询结果关联，不能直接认为数字相等。

ACPI 怎样连接设备变化和客户机动作

{{ diagram('cpu-hotplug-acpi-handoff', '创建、上线与异步移除', 'QEMU 创建 CPU 后发出 ACPI 通知，客户机再完成发现和上线；删除请求需要客户机迁走工作并回应 eject，QEMU 才拆除设备并报告完成。') }}

机器模型维护可用 CPU 位置，ACPI 热插拔控制器保存每个位置的 CPU 指针、插入和移除标志。acpi_cpu_plug_cb() 将新 CPU 关联到位置，设置插入标记并发出 ACPI 事件。客户机处理 SCI 后执行固件提供的方法，确认 CPU 存在，进入自身 CPU 注册和上线流程。

移除时，管理程序发送 device_del，QEMU 设置移除标记并通知客户机。Linux 的 CPU hotplug 状态机按顺序执行下线回调，把任务、中断和定时器移到其他可用 CPU，并处理每 CPU 资源。客户机随后通过 ACPI eject 交还设备，QEMU 才能清理该 CPU 对象。CPU 插入与移除通知

如果客户机卡死、热插拔被禁用，或者下线流程无法完成，删除可能停在等待阶段。直接终止对应宿主线程会破坏虚拟机的执行模型，不能作为 CPU 热拔出的替代方案。x86 PC 路径还明确拒绝拔出启动 CPU，因此例子只移除后来添加的 cpu-extra。

怎样确认缩容真正完成

{"execute":"device_del","arguments":{"id":"cpu-extra"}}
{"return":{}}

稍后可能收到完成事件（省略 timestamp）：
{"event":"DEVICE_DELETED","data":{
  "device":"cpu-extra","path":"/machine/peripheral/cpu-extra"
}}

命令成功表示移除请求已受理。管理程序需要持续接收并关联完成事件，也要能处理事件与响应的不同先后顺序。完成后再次查询可插拔 CPU 列表，该位置应不再包含 qom-path，运行实例列表中也不再包含被删除对象。客户机的 online 列表可能更早变化，不能单独用它证明宿主资源已经释放。

Libvirt 的 qemuDomainHotplugDelVcpu() 会标记待移除的别名、发送删除请求并等待设备移除；超时错误明确要求重新检查实际结果。超时与删除失败不是同义词：事件可能稍后到达。重连后应重新查询状态，避免重复创建、错误复用标识或把仍在等待的操作当作已完成。Libvirt 的移除等待

使用 Libvirt 管理的虚拟机，应通过其 vCPU 管理接口操作，使运行状态与持久配置保持一致。--live、--config 和客户机内部 online 控制各有不同对象；不要用旁路 QMP 操作后再假定 Libvirt XML 会自动成为预期配置。

源码：拓扑位置、通知和拆除

入口或结构阅读重点
x86_possible_cpu_arch_ids()按 maxcpus 建立位置列表，把 APIC ID 与拓扑属性联系起来
x86_cpu_pre_plug()检查型号、拓扑和可用位置，阻止重复占用或不匹配的 CPU
AcpiCpuStatus 与通知回调维护插入、移除标记，并发出 SCI 对应的 ACPI 热插拔事件
cpu_hotplug_wr()客户机写入 eject 标志后调用真正的 unplug，再解除对象关系
x86_cpu_unplug_request_cb() / unplug_cb()拒绝启动 CPU、清空位置、unrealize 并更新机器计数

上层的通用设备接口把 CPU 与其他可插拔设备放在一致的生命周期框架中，具体协调仍由机器和 ACPI 实现。不能据此把 PCIe 插槽寄存器的流程直接套到 CPU 上。

从调整数量到管理完整生命周期

早期 CPU 增加接口更强调数量和 CPU 编号。现在的 query-hotpluggable-cpus 配合 device_add/device_del，显式表达空位、设备类型与拓扑，并用异步事件区分请求与完成。ACPI 中保留的旧接口兼容分支也说明，固件描述、机器版本与客户机支持需要一起演进。

在线扩容减少了重启，但不会自动增加应用并行度或宿主可用算力。新增 vCPU 还需要合适的宿主亲和性、NUMA 放置与客户机线程分配。缩容可降低争抢，也可能让剩余 CPU 的排队和尾延迟上升。应同时观察业务吞吐、尾延迟、客户机 online 状态和宿主调度等待。

可用性检查可以分三步：先验证预留位置能否成功创建，再验证客户机是否上线，最后验证移除事件和状态收敛。测试应包含客户机延迟响应或暂不响应的情况；只验证添加命令返回成功，会漏掉最容易出问题的后半段。
