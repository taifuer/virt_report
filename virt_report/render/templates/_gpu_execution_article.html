场景与边界

GPU 作业从 Guest 用户态提交，经过驱动组织命令、硬件执行和完成通知，最后由应用取得结果。整卡直通把相应 PCI 功能交给一个 Guest；共享虚拟化则需要划分可见资源，并协调多个使用者。下面沿同一条提交主线，对照设备归属、门铃访问和完成交接。

AMDGPU 的 CS 提交路径先核验上下文、对象和 GPU VM，再把作业交给 DRM 调度器。调度回调组织 IB、fence 与 ring 发布；SDMA 硬件随后执行。等待接口同时提供 ioctl 返回值和输出状态，应用需要检查两者，确认对应作业是否完成。

地址转换与宿主参与

整卡直通时，宿主这块 PCI 设备绑定 vfio-pci；Guest 内的 AMDGPU 驱动接收应用 CS ioctl，组织 GPU 作业。宿主 VFIO 管理设备资源、DMA 隔离和中断接口，QEMU 预先配置虚拟设备、BAR 与中断路由，KVM 维护 vCPU 的二级地址转换并递送虚拟中断。它们不代替 Guest 驱动逐条解释或转发 GPU 命令。参见 Linux VFIO 文档。

直接映射的门铃与设备 DMA

本例先在 Guest RAM / GTT 写好 IB 与 SDMA ring，再由 Guest CPU 向可 mmap 的 doorbell BAR 写入新写指针。这个 CPU 访问沿 Guest VA → GPA → 已建立的 EPT/NPT → 宿主物理 MMIO 地址 → GPU BAR。QEMU 的用户态映射用于建立这套关系，每次写入无需经过 QEMU 进程或调用宿主 VFIO 驱动。门铃只提供新命令的位置或进度，4 KiB 数据仍在缓冲区中。设备提交单元如何与固件协作取决于具体 GPU。

GPU 随后读取 ring 和 IB：访问系统内存经过 GPU 地址转换与宿主 IOMMU 的预建映射；本地显存访问在 GPU 的地址空间内完成。CPU 的 EPT/NPT 转换和设备的 IOMMU 转换分属两条路径。本例 SDMA ring 与用户 IB1 放在 GTT，其他实现也可选择显存中的命令缓冲区。参见 QEMU BAR 映射与设备 DMA 映射。

数据复制及 fence 写回完成后，物理 MSI 由宿主 VFIO 触发 eventfd，KVM irqfd 把向量路由到目标 vLAPIC；目标 vCPU 在允许时注入，Guest AMDGPU 才处理完成并唤醒应用。演示把 pending 与实际注入分开。未直接映射、需要捕获或特殊处理的 BAR 区域仍可能进入 KVM / QEMU 的 VFIO region 回调，不能用“直通”推导全部寄存器访问都不退出。

GVT-g 的 BAR0 捕获与 BAR2 直映

GVT-g 由宿主 i915/GVT-g 管理物理 GPU。其 BAR0 提供读写接口，没有开放 MMAP；ELSP 写先触发硬件 VM-exit，KVM 处理被捕获的 MMIO，再让 KVM_RUN 返回用户态，kvm_run.exit_reason = KVM_EXIT_MMIO。QEMU 按地址分派到 VFIO region，写设备 fd，宿主 GVT-g 才解释 ELSP、建立 workload 并调度真实引擎。KVM 不解释 ELSP 的 GPU 提交语义。

访问对象直接映射条件本例处理路径
BAR0：ELSP、控制寄存器、GGTT 页表窗口未开放 MMAPVM-exit → KVM → QEMU → VFIO region → GVT-g
BAR2：分配给该 vGPU 的 aperture仅开放稀疏映射声明的窗口映射有效时，Guest CPU 直接访问图形内存窗口
普通 Guest RAM：batch 与数据缓冲区正常 RAM 映射一般访问不逐次退出；额外写保护或页跟踪需另行处理

intel_vgpu_mmap() 只接受 BAR2 中已分配的窗口。因此，同一个 mdev 可以同时具有直映区域和捕获区域；本例 ELSP 的路径则已经由 BAR0 的实现确定。参见区域能力声明、aperture 映射与ELSP 处理。

硬件退出与返回 QEMU

硬件 VM-exit 把控制权交给宿主 KVM；只有需要用户态处理的情形才让 KVM_RUN 返回 QEMU。首次补建二级映射等退出可由 KVM 处理后直接恢复 Guest。即使设备属于直通路径，也要检查访问地址、区域权限和映射状态；MSI-X 表等模拟覆盖区不能按普通 doorbell 推断。KVM API 文档说明了 KVM_EXIT_MMIO 的含义。

PF、VF 与 mdev 的组合关系

SR-IOV：保留 PF 管理，分配 VF

PF 是物理功能，负责建立和管理 VF；每个 VF 有自己的 PCI 身份和寄存器空间。AMD 示例保留宿主 GIM 对 PF 的管理，将一个 VF 绑定 vfio-pci 并分配给 Guest。Guest AMDGPU 提交自己的作业，硬件按该 VF 获得的资源执行。允许直映的门铃无需逐笔交给 PF 驱动；资源分配、复位和管理通信仍有宿主参与。硬件内部怎样共享引擎与显存取决于具体产品，VF 数量也不能直接当成独立 GPU 数量。PCI SR-IOV 文档、AMD PF/VF 部署说明。

SR-IOV + mdev：VF 之上再建立实例

NVIDIA 的一类部署先启用 VF，再在 VF 的 mdev_supported_types 下创建实例，最后把实例 UUID 交给虚拟机。关系是 PF → VF → mdev UUID → VM；所引文档限定每个 VF 创建一个 mdev。VFIO 提供设备访问接口，SR-IOV 提供硬件功能，mdev 提供实例管理，三者可以组合。这里沿公开配置与完成接口展示，厂商内部命令格式、寄存器捕获范围和调度细节保留为未展开区域。NVIDIA 配置文档。

同一文档还区分了厂商 VFIO 路径：某些宿主版本直接通过 VF 的 PCI 地址接入已配置的 vGPU，不再创建 mdev。两种部署不能混用 XML，也不能把承载实例的同一个 VF 再当作独立设备重复直通。另一类“混合使用”是多块 GPU 分别采用不同方案，或一个 VM 分配多个互不冲突的设备；是否支持仍需核对 IOMMU 分组、复位范围与厂商矩阵。

virtio-gpu 使用另一套前后端协议，继续在渲染与编解码演示中说明。以上对比集中于 Guest 使用厂商 GPU 驱动的路径。

libvirt XML 与部署前提

以下是 <domain><devices> 内的独立片段，BDF 和 UUID 均为示例值。XML 只声明分配对象，不会自动启用 SR-IOV、创建 mdev、选择 vGPU profile 或解决驱动兼容。使用前需确认设备归属、IOMMU 隔离、复位能力及宿主/Guest 驱动支持；不要接管正在承载宿主显示的 GPU。libvirt hostdev 文档。

整卡直通：引用物理 PCI 功能

例中 GPU 功能为 0000:65:00.0。managed='yes' 允许 libvirt 在分配前处理驱动解绑，并在释放后恢复绑定。板卡的音频等伴随功能以及同组设备需单独评估；一个 hostdev 条目不自动代表整块板卡的所有功能。

<hostdev mode='subsystem' type='pci' managed='yes'>
  <source>
    <address domain='0x0000' bus='0x65' slot='0x00' function='0x0'/>
  </source>
</hostdev>

GVT-g：引用已创建的 mdev UUID

宿主物理 GPU 继续由 i915 管理，先按该平台实际提供的 mdev 类型创建实例，再引用 UUID。这里仅声明设备分配，显示输出及远程桌面配置需另行添加；历史 GVT-g 不能直接套用于新代 Intel GPU。

<hostdev mode='subsystem' type='mdev' model='vfio-pci'>
  <source>
    <address uuid='11111111-2222-4333-8444-555555555555'/>
  </source>
</hostdev>

AMD SR-IOV：引用 VF 的 PCI 地址

例中 0000:85:00.0 是 PF，仍由 GIM 管理；分配的是 VF 0000:85:02.0。本例假定管理员已将该 VF 绑定 vfio-pci，故采用 managed='no'，生命周期由外部部署流程负责。可通过 VF 的 physfn 关系核对父 PF；XML 中不填写 PF 地址。

<hostdev mode='subsystem' type='pci' managed='no'>
  <source>
    <address domain='0x0000' bus='0x85' slot='0x02' function='0x0'/>
  </source>
</hostdev>

NVIDIA 组合：按实例接口选择一种 XML

采用 SR-IOV + mdev 时，在 VF 上创建实例后填写其 UUID。hostdev 与 GVT-g 的形状相同，但父设备和厂商实现不同，须从宿主实例关系确认。

<hostdev mode='subsystem' type='mdev' model='vfio-pci'>
  <source>
    <address uuid='aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeeeee'/>
  </source>
</hostdev>

采用厂商 VFIO 接口时，引用配置好 vGPU 的 VF BDF，保留厂商驱动绑定。所引 NVIDIA 文档要求 unmanaged 模式；不要为了套用普通直通教程而强制改绑通用 vfio-pci。此片段与上面的 mdev 片段二选一。

<hostdev mode='subsystem' type='pci' managed='no'>
  <source>
    <address domain='0x0000' bus='0x3d' slot='0x00' function='0x4'/>
  </source>
</hostdev>

这里没有在本机执行解绑、创建 VF 或创建 mdev 操作。示例已按 XML 结构与官方接口校核，部署可用性仍需要对应硬件验证。
