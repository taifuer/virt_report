从进程替换到宿主内核更新

QEMU CPR-transfer 替换用户态进程，宿主内核继续运行。更新 KVM 或整个宿主内核则会触及 VM / vCPU、内存映射、中断路由和设备所有权，不能只交接 QEMU 的状态文件。

KVM 热升级有不同范围：修补正在运行的代码、在新旧 KVM 之间接管虚拟机，或保留资源后切换整个宿主内核。Guest 不重启、vCPU 持续执行和业务无停顿是三个不同目标；保留了 RAM，不代表后三者自动成立。

方案更新对象能力与状态边界
Linux livepatch适合热补丁的内核函数，包括模块中的函数主线框架；不等于任意 KVM 版本原地替换
Orthus / Dual KVM经专门改造的 KVM 与 QEMUASPLOS 2019 论文披露的厂商方案；不是主线通用模块升级接口

QEMU cpr-luo利用 KHO / LUO 保留 RAM，重启宿主后恢复虚拟机本文分析 2026-10-12 的补丁版本；Guest 在交接期间暂停，该版禁止 VFIO

下文按固定版本和公开材料的日期说明能力，不把补丁提案、会议计划或厂商实现当作任意发行版已具备的功能。

热补丁：修改代码，保留现有内核对象

Linux livepatch 可以把合适的函数调用切换到修补后的实现，并通过一致性模型协调任务从旧代码过渡到新代码。目标既可以是内核本体，也可以是已加载模块中的函数；VM 和 vCPU 不因此被重新创建。机制见 Linux livepatch 文档。

修复某个 KVM 判断条件，与替换整套 KVM 对象布局并不是同一件事。锁、数据结构和新旧调用关系都要满足补丁的安全条件；不能把任意两个内核版本的差异包装成一个函数替换。运行中直接卸载再加载 KVM，也不提供 VM 状态交接协议。

Dual KVM：在两套实现之间接管虚拟机

Orthus 论文描述了新旧 KVM 并存、逐台接管的设计：将可替换的主要实现集中到经改造的 kvm-intel.ko，保留一个不随此次升级替换的薄 kvm.ko；不同实现通过各自的设备入口提供服务。它还需要符号隔离和硬件资源协调，而不是在普通发行版上重复加载同名模块。参见 Orthus 原论文，ASPLOS 2019。

VM grafting 让新实现接管原有 Guest 内存和执行状态，device handover 处理设备与 DMA 资源的交接；目标是减少整份 RAM 的复制，并缩短接管停顿。这里不应推导出“所有客户机指令都在升级期间持续执行”。论文报告的部署经验，也不是当前主线 KVM 对任意版本组合的兼容保证。厂商发布说明给出了这项方案的背景。

KHO 与 LUO：跨内核保留内存和受支持的资源

kexec 将控制权交给新内核，但普通重启不会自动把旧内核的文件、KVM 对象和设备关联变成新内核可用的对象。Kexec Handover（KHO）保留指定的物理内存，并传递描述这些资源的元数据；新内核使用预留的 scratch 区启动，避免覆盖保留页。它保留的是字节和交接信息，不是让任意旧内核指针在新内核中继续有效。参见 Linux 6.16 KHO 概念文档。

Live Update Orchestrator（LUO）在此基础上组织有名字的会话，由各资源的处理器执行保留、冻结和恢复。新内核重新构建受支持的文件对象，并向新进程返回可用的 fd；fd 数值不必与旧进程相同。Linux 6.19 的接口和 memfd 支持见 LUO 文档及固定源码中的文档入口。

因此有两种需要区分的路径：保留 Guest RAM 后重新创建 KVM VM / vCPU，再加载迁移状态；或者为 KVM 对象本身增加专门的保留与接管协议。后者需要额外实现，不能由“memfd 已能保留”推出。VFIO、IOMMU、PCI 和中断关联同样各有生命周期。

cpr-luo：保留 RAM，暂停后恢复执行

2026-10-12 的 cpr-luo 补丁系列将 CPR 与 KHO / LUO 连接起来：保留 CPR 状态 memfd 和 RAMBlock 的后备 fd，其余 VM 状态继续经迁移框架保存与恢复。它不是 QEMU 10.2 的 cpr-transfer 自带的能力，也不要求 Guest 在宿主切换期间一直执行。

该补丁版本要求共享内存配置和虚拟机标识匹配；旧 QEMU 应保持 postmigrate 直到 kexec，不能提前退出，否则 LUO 会话及其资源会被释放。该版明确阻止 VFIO，作者提到的另行实验不等于这组补丁已支持直通设备。CPR-transfer 的 VFIO 交接支持也不能直接搬来证明跨内核更新可用。

Caretaker：让部分客户机执行跨越宿主重启

Orphaned VMs 尝试让经过准备的 vCPU 留在保留的 CPU 上，在宿主内核切换期间继续运行；Caretaker 在这个窗口中接手有限的 VM-exit 处理。2026-09-20 的 RFC 00/46明确是概念验证，不是生产就绪的通用方案。

Caretaker 不是完整的 KVM 或 QEMU 替代品。遇到其不能处理的退出，vCPU 仍要等待新宿主就绪；依赖用户态设备模型、尚未接管的 I/O 后端或设备资源时，也不能承诺业务继续无停顿。这个限制在 LPC 2026 的 Orphaned VMs 介绍中有明确说明。

它与Idle Passthrough也不是同一个机制：后者讨论正常运行时是否拦截空闲指令，Caretaker 讨论宿主内核暂时不可用时由谁维持客户机执行。减少某类 VM-exit，不能代替完整的升级状态交接。

兼容性与升级验收

2026-10-19 社区会议纪要（10 月 25 日发布）仍在讨论跨子系统状态头、KVM 保留，以及 PCI、VFIO 与 IOMMU 的衔接。这里引用的是该次进展快照；邮件中的目标版本和下一版计划不代表功能已发布。

选型时先核对实际内核配置、资源处理器、新旧状态格式和设备支持，再讨论 downtime。仅仅能加载新内核，或新 QEMU 能启动，都不足以证明原虚拟机被正确接管。Guest 的 RAM、寄存器、中断与 I/O 状态必须对应同一个可恢复的执行点；恢复失败也不意味着能够随时回到旧端。

验收目标测试环境中的观察不能据此推断
Guest 未重启启动标识不变，原进程的内存计数继续递增不能证明期间没有暂停
执行与服务连续性从独立观察端记录请求时延、超时和最长无进展间隔串口计数连续不等于零停顿，平均延迟也不能代表尾延迟
状态与 I/O 完整校验内存内容、应用事务和升级前后的设备行为能恢复 CPU 不等于 DMA、网络或存储已正确交接
失败可控在测试环境验证每个切换阶段的资源归属和故障恢复新端已执行后，旧端不能直接继续运行同一份 Guest 状态

这些是验证建议，不是本文执行过的虚拟机升级测试。实际部署须采用明确支持的版本组合与运维方案；本文不提供可直接在业务宿主上运行的 kexec 或模块卸载命令。
