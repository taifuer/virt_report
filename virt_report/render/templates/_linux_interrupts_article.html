事件与处理上下文

网卡通过 DMA 把数据写入接收缓冲区，再发中断提示驱动检查队列。驱动也可以轮询发现完成。设备状态和队列保存工作结果，中断通知 CPU 开始检查。

以常见 x86 Linux 非实时内核为例：外设中断异步到达，缺页等同步异常由当前指令触发，系统调用则由线程主动请求内核服务。三者各有入口和处理规则。

从共享中断线到多队列与线程化处理

中断机制沿两条主线演进：事件递送关注中断线共享、路由与多核扩展；处理上下文关注高负载开销、并发和响应延迟。MSI-X 属于递送机制，softirq 与 IRQ 线程负责组织后续处理。

发展脉络要解决的问题机制与取舍
早期 PC 到 SMP：PIC、APIC 与共享 INTx有限的硬件中断线，多设备共享与多 CPU 路由控制器提供屏蔽、优先级和路由；共享 IRQ 的驱动仍须辨认是否是本设备的事件
PCI MSI / MSI-X：从电平线到消息共享线带来的处理与扩展限制设备以消息事务通知，MSI-X 便于为不同队列配置向量；实际可分配数量受设备与平台约束
多核与高包速率：softirq、NAPI 与工作队列在硬中断入口处理太多工作，抢占应用 CPU，或频繁进出中断把可延后的工作放到相应上下文，批量推进；仍须控制预算、锁与 CPU 间共享
低延迟与实时需求：线程化 IRQ、PREEMPT_RT长时间不可抢占区段使高优先级任务迟迟不能运行让更多工作成为可调度线程，并调整锁语义；最底层入口与部分关键路径仍不能随意睡眠

一块 MSI-X 网卡可以由 hardirq 调度 NAPI，慢速设备也可能用线程化 IRQ。PREEMPT_RT 调整内核的可抢占性与锁模型，让更多处理在线程上下文执行。依据见 PCI MSI 驱动指南与 PREEMPT_RT 的设计说明。

硬件标识与内核 IRQ

层次含义不能直接等同
MSI / MSI-XPCI 设备通过消息写事务报告事件；MSI-X 可配置多个表项MSI-X 表项编号不是 Linux IRQ 编号
CPU 中断向量经过路由后，CPU 按向量进入相应入口某个向量不永久对应某个应用或数据包
Linux IRQ内核用 irq_desc、irq_chip 与 irqaction 组织控制器操作和驱动处理函数IRQ 号、硬件中断号与 CPU 向量属于不同命名空间

驱动注册处理函数，内核与中断控制器协作配置路由和目标 CPU。IRQ affinity 影响中断在哪里被处理，不等于把后续应用也绑在那个 CPU；网络处理还可能通过队列和跨 CPU 工作分派继续推进。

以 PCI 驱动为例，pci_alloc_irq_vectors() 请求设备可用的向量，pci_irq_vector() 把设备内的向量索引转换为 Linux IRQ，随后 request_irq() 或 request_threaded_irq() 关联处理函数。驱动提供队列等上下文，通用 IRQ 层维护分派关系；设备的向量编号并不直接充当 CPU 的 IDT 下标。

例如，驱动让 RX 队列 2 使用 MSI-X 表项 3，内核分配 Linux IRQ 137，并把消息路由到目标 CPU 的向量 0x51。这些示例编号通过初始化配置关联。CPU 根据向量进入入口，内核找到对应 irq_desc 和处理函数，驱动再根据保存的队列上下文检查 RX 队列 2。

报文已通过 DMA 写入接收缓冲区。CPU 沿图中的通知路径进入驱动，再根据队列完成记录找到数据。IRQ affinity 控制通知目标，应用线程的 CPU 位置由独立的调度配置决定。

中断入口与延后处理

  1. 设备发布完成状态并发出允许的中断，处理器保存必要现场，进入内核架构相关入口。
  2. 通用 IRQ 层调用驱动注册的处理函数，完成必要的状态确认与通知控制。
  3. 驱动可调度延后工作。例如网卡调度 NAPI，在轮询函数中批量处理 RX 和 TX completion；线程化 IRQ 则可唤醒对应的内核线程。
  4. 延后路径更新上层队列、释放资源，必要时唤醒等待任务。应用要等自己被调度后，才继续执行。
上下文典型用途约束
hardirq快速响应与调度后续工作不能任意睡眠，应避免长时间占用 CPU
softirq / 常规 NAPI有预算的批量网络处理等通常也不能睡眠；即使由 ksoftirqd 承接，仍须遵守该回调的上下文约束
IRQ 线程 / 普通 workqueue在可调度线程中完成延后工作可按进程上下文规则阻塞，但持锁与原子区段仍有限制

PREEMPT_RT、threaded NAPI 和 busy polling 会改变部分执行上下文。代码入口可对照 handle_irq_event() 与 request_threaded_irq()。

中断上下文与接收线程

网卡中断到达时，CPU 可能正在执行线程 B。hardirq 在中断上下文执行驱动函数；退出时，内核可能继续处理待办 softirq，并检查是否需要调度。接收应用 A 的等待条件满足后成为可运行任务，随后等待获得 CPU。

线程化 IRQ 具有独立的可调度内核线程。主处理函数返回 IRQ_WAKE_THREAD 时，通用 IRQ 层唤醒该线程执行已注册的线程函数。普通 workqueue 由工作线程执行回调，softirq 则按其专门的上下文规则处理待办工作。

共享状态、关中断与锁

假设进程上下文正在修改驱动队列，同一 CPU 的中断处理函数也要取得该队列的锁。如果前者持锁时被中断，后者一直等锁，就会阻止前者继续释放它。在本文的非实时内核条件下，spin_lock_irqsave() 组合本地中断控制与自旋锁：本地控制避免这种重入，锁协调其他 CPU 上遵守同一规则的访问。

单独关闭本地中断只影响当前 CPU，其他 CPU 和设备 DMA 仍可继续。CPU 间共享状态的锁、设备描述符的发布顺序和 DMA 同步需要分别满足各自约定；持有自旋锁的区段也应保持短小并遵守原子上下文限制。参见 自旋锁与本地中断控制。

通知、完成与唤醒

{{ diagram('linux-interrupt-completion', '完成、通知与继续运行', '一次中断可以促成多项完成的处理；线程是否需要唤醒、何时实际运行，是后续的独立条件。') }}

四个边界应分开看：设备记录完成；通知 CPU 检查；驱动处理完成并唤醒等待者；等待者获得 CPU。屏蔽通知不会把已经完成的 DMA 撤销，解除屏蔽也不代表应用立即运行。驱动必须按设备协议处理状态读取、重新开中断和竞争窗口，不能只依赖“数中断”。

一次中断可覆盖多个队列完成项；轮询发现完成则可能不需要新的中断。网络 TX completion 表示某层可以回收发送资源，不是远端收到确认。磁盘请求的完成状态可以携带错误；普通写入完成也未必代表已持久化。这些语义由设备和上层协议决定，不由“用了中断”决定。

一个批次可以只有一次硬件通知

假设 RX 队列积累了 3 个完成项，设备触发一次 MSI-X，驱动调度 NAPI poll 并读走这 3 项。IRQ 计数增加 1，收包工作量为 3。应用是否被唤醒，还取决于协议检查、socket 匹配结果，以及是否存在等待者。

定位停顿时，完成项未出现可查设备与 DMA；完成项已有而 poll 未运行，可查通知与调度；socket 已有数据而应用未运行，可查等待唤醒和 CPU 调度。

完成状态的记录与等待

需要等待某项内核工作的代码可以使用 struct completion。等待方先初始化对象，再发布工作；完成方调用 complete() 更新完成状态并唤醒等待者。即使 complete 先发生，稍后的 wait_for_completion() 仍能消费已记录的完成，无需再睡眠。等待必须处于允许睡眠的上下文，完成通知则可在中断上下文发出。

等待超时仅表示调用方停止等待，后台工作和设备访问可能仍在继续。释放缓冲区或包含 completion 的对象前，需要通过相应取消、排空或同步机制确认后续使用已经结束，防止迟到的完成回调访问已释放内存。规则见 completion 的顺序与生命期。

屏蔽、重开与通知竞态

考虑接收队列的一次处理：驱动暂时屏蔽该队列通知，轮询取走所有已完成项，准备退出。若它刚判断“队列空”时又到一个包，处理不当就可能既没有继续轮询，也没有等到下一次通知。因此“队列空了再开中断”不是足够完整的算法，必须结合设备的状态保留、重新使能和复查规则封闭这个竞争窗口。

NAPI 在仍有工作时保持调度状态；满足完成条件后，驱动通过完成接口结束这一轮，再按硬件约定恢复通知。预算耗尽与确认队列已空是两种情况。早期 NAPI 设计文档的附录 2就专门讨论了漏掉队列尾部报文的竞态，现代接口规则见 NAPI 文档。

还要区分三种操作：确认或清除设备事件，向中断控制器报告 EOI，以及消费队列里的完成项。它们不能互相替代。CPU 对共享队列的访问顺序、DMA 数据可见性也必须满足协议；一致性 DMA 内存仍不意味着可以省略所有内存屏障，非一致性映射还可能需要 DMA 同步操作，参见 DMA API。

中断合并与轮询可以减少通知次数。完成记录持续积压时，需要结合队列所有权、通知使能状态和消费者获得 CPU 的情况排查。

只读观察与客户机中断

在实验机读取 /proc/interrupts 可看 IRQ 在各 CPU 的累计计数，读取 /proc/softirqs 可看 softirq 类别计数；两者都不能直接当作包数或 I/O 请求数。应比较同一负载窗口前后的变化，并结合驱动队列统计。读取权限和可见字段依赖系统配置。

虚拟化增加了路由与交付环节：后端发布 Guest 队列完成，通过 QEMU 设备通知或 eventfd/irqfd 进入 KVM；KVM 建立待处理中断状态，再由软件注入或硬件辅助路径交付 Guest。Guest 驱动随后按自己的 IRQ/NAPI 路径处理。同一完成事件由各层接力递送。

直通设备的 MSI-X 消息可经宿主转发，也可在具备相应条件时使用 VT-d posted interrupt 递送，见 中断传递演示。
