事件与处理上下文

设备把数据写入内存，与 CPU 开始处理这些数据，是两件事。以普通网卡为例，DMA 完成后，设备可发中断提示驱动检查队列；驱动也可以轮询发现完成。不论采用哪种方式，真正的工作记录在设备状态和队列中，中断只是通知。

下面以常见 x86 Linux 的非实时内核路径说明概念。同步异常（例如执行当前访存指令触发缺页）与外设异步中断不是同一种事件；系统调用进入内核也不能一概称为设备中断。

从共享中断线到多队列与线程化处理

中断机制的演变有两条线：设备如何把事件送到 CPU，以及 CPU 在什么上下文里处理工作。前者解决中断线共享、路由与多核扩展，后者解决高负载开销、并发和响应延迟。MSI-X、softirq 与 IRQ 线程并不处在同一层，不能排列成一串互相替代的版本。

发展脉络要解决的问题机制与取舍
早期 PC 到 SMP：PIC、APIC 与共享 INTx有限的硬件中断线，多设备共享与多 CPU 路由控制器提供屏蔽、优先级和路由；共享 IRQ 的驱动仍须辨认是否是本设备的事件
PCI MSI / MSI-X：从电平线到消息共享线带来的处理与扩展限制设备以消息事务通知，MSI-X 便于为不同队列配置向量；实际可分配数量受设备与平台约束
多核与高包速率：softirq、NAPI 与工作队列在硬中断入口处理太多工作，抢占应用 CPU，或频繁进出中断把可延后的工作放到相应上下文，批量推进；仍须控制预算、锁与 CPU 间共享
低延迟与实时需求：线程化 IRQ、PREEMPT_RT长时间不可抢占区段使高优先级任务迟迟不能运行让更多工作成为可调度线程，并调整锁语义；最底层入口与部分关键路径仍不能随意睡眠

这些机制今天仍然并存：一块 MSI-X 网卡可以由 hardirq 调度 NAPI；某个慢速设备则可能用线程化 IRQ。依据见 PCI MSI 驱动指南与 PREEMPT_RT 的设计说明。后者改变的是内核的可抢占与锁模型，不是把所有中断都变成普通用户线程。

硬件标识与内核 IRQ

层次含义不能直接等同
MSI / MSI-XPCI 设备通过消息写事务报告事件；MSI-X 可配置多个表项MSI-X 表项编号不是 Linux IRQ 编号
CPU 中断向量经过路由后，CPU 按向量进入相应入口某个向量不永久对应某个应用或数据包
Linux IRQ内核用 irq_desc、irq_chip 与 irqaction 组织控制器操作和驱动处理函数IRQ 号、硬件中断号与 CPU 向量属于不同命名空间

驱动注册处理函数，内核与中断控制器协作配置路由和目标 CPU。IRQ affinity 影响中断在哪里被处理，不等于把后续应用也绑在那个 CPU；网络处理还可能通过队列和跨 CPU 工作分派继续推进。

以 PCI 驱动为例，pci_alloc_irq_vectors() 请求设备可用的向量，pci_irq_vector() 把设备内的向量索引转换为 Linux IRQ，随后 request_irq() 或 request_threaded_irq() 关联处理函数。驱动提供队列等上下文，通用 IRQ 层维护分派关系；设备的向量编号并不直接充当 CPU 的 IDT 下标。

例如，驱动可以让 RX 队列 2 使用 MSI-X 表项 3，内核给它分配 Linux IRQ 137，并把消息路由到某个目标 CPU 的向量 0x51。这里的编号仅作示例：表项 3 不是由队列号固定计算出的，137 也不等于 0x51。CPU 根据向量进入入口，内核再找到对应 irq_desc 和已注册的驱动处理函数；驱动根据初始化时保存的队列上下文检查 RX 队列 2。

这张图解释的是一次通知的路由，不是报文数据走过的路径。数据已通过 DMA 放在接收缓冲区中；CPU 收到向量后进入驱动，再根据队列里的完成记录找到数据。改变中断亲和性可以改变接收通知的 CPU，并不会把 socket 的应用线程自动迁过去。

中断入口与延后处理

  1. 设备发布完成状态并发出允许的中断，处理器保存必要现场，进入内核架构相关入口。
  2. 通用 IRQ 层调用驱动注册的处理函数，完成必要的状态确认与通知控制。不是每个处理函数都要在这里把整个请求处理完。
  3. 驱动可调度延后工作。例如网卡调度 NAPI，在轮询函数中批量处理 RX 和 TX completion；线程化 IRQ 则可唤醒对应的内核线程。
  4. 延后路径更新上层队列、释放资源，必要时唤醒等待任务。应用要等自己被调度后，才继续执行。
上下文典型用途约束
hardirq快速响应与调度后续工作不能任意睡眠，应避免长时间占用 CPU
softirq / 常规 NAPI有预算的批量网络处理等通常也不能睡眠；即使由 ksoftirqd 承接，仍须遵守该回调的上下文约束
IRQ 线程 / 普通 workqueue在可调度线程中完成延后工作可按进程上下文规则阻塞，但持锁与原子区段仍有限制

PREEMPT_RT、threaded NAPI 和 busy polling 会改变部分执行位置；不能把某条普通路径说成所有内核配置的唯一行为。代码入口可对照 handle_irq_event() 与 request_threaded_irq()。

中断上下文与接收线程

网卡中断到达时，这个 CPU 可能正在执行完全无关的线程 B。hardirq 进入内核中断上下文，执行驱动注册的函数；它不是先找到接收应用 A，再把 CPU 调度给 A。中断退出后，内核可能处理待办 softirq，再决定是否需要调度。应用 A 的接收条件满足后，只是重新变成可运行任务。

线程化 IRQ 才具有独立的、可被调度的 IRQ 线程。主处理函数返回 IRQ_WAKE_THREAD 时，通用 IRQ 层唤醒已注册的线程函数；它与“唤醒接收应用”仍是两个对象。普通 workqueue 也由工作线程执行回调，而 softirq 是内核登记的延后处理类别，不是用户线程发起的一次软件系统调用。

通知、完成与唤醒

{{ diagram('linux-interrupt-completion', '完成、通知与继续运行', '一次中断可以促成多项完成的处理；线程是否需要唤醒、何时实际运行，是后续的独立条件。') }}

四个边界应分开看：设备记录完成；通知 CPU 检查；驱动处理完成并唤醒等待者；等待者获得 CPU。屏蔽通知不会把已经完成的 DMA 撤销，解除屏蔽也不代表应用立即运行。驱动必须按设备协议处理状态读取、重新开中断和竞争窗口，不能只依赖“数中断”。

一次中断可覆盖多个队列完成项；轮询发现完成则可能不需要新的中断。网络 TX completion 表示某层可以回收发送资源，不是远端收到确认。磁盘请求的完成状态可以携带错误；普通写入完成也未必代表已持久化。这些语义由设备和上层协议决定，不由“用了中断”决定。

一个批次可以只有一次硬件通知

假设 RX 队列积累了 3 个完成项，设备触发一次 MSI-X，驱动调度一次 NAPI poll 并读走这 3 项。IRQ 计数增加 1，收包工作量却是 3；是否唤醒应用还取决于报文是否通过协议检查、是否匹配 socket，以及有没有等待者。这里没有丢掉 2 次中断，也不需要给每个包补发一次中断。队列保存可消费的记录，通知负责让消费者有机会检查。

沿这一过程可以分别定位停顿：完成项未出现，查设备与 DMA；完成项已有但 poll 不运行，查通知与调度；socket 已有数据但应用没运行，查等待唤醒和 CPU 调度。这比把全部延迟都称为“中断慢”更有区分度。

屏蔽、重开与通知竞态

考虑接收队列的一次处理：驱动暂时屏蔽该队列通知，轮询取走所有已完成项，准备退出。若它刚判断“队列空”时又到一个包，处理不当就可能既没有继续轮询，也没有等到下一次通知。因此“队列空了再开中断”不是足够完整的算法，必须结合设备的状态保留、重新使能和复查规则封闭这个竞争窗口。

NAPI 在仍有工作时保持调度状态；满足完成条件后，驱动通过完成接口结束这一轮，再按硬件约定恢复通知。预算耗尽与确认队列已空是两种情况。早期 NAPI 设计文档的附录 2就专门讨论了漏掉队列尾部报文的竞态，现代接口规则见 NAPI 文档。

还要区分三种操作：确认或清除设备事件，向中断控制器报告 EOI，以及消费队列里的完成项。它们不能互相替代。CPU 对共享队列的访问顺序、DMA 数据可见性也必须满足协议；一致性 DMA 内存仍不意味着可以省略所有内存屏障，非一致性映射还可能需要 DMA 同步操作，参见 DMA API。

这解释了为什么“中断次数减少”未必是故障：中断合并与轮询可以用一次通知处理许多项；但如果完成记录不断积压且消费者没有推进，就应检查队列所有权、通知重新使能和消费者是否真正获得 CPU，而不是只检查 IRQ 计数。

这里第二次通知对应新到达的工作，不是给前一批报文重复确认。若驱动清掉 pending 又没有复查队列，就可能让新包留在队列里而无人继续处理。问题在于生产者与消费者的交接规则，而不是单纯“中断开得早还是晚”。

只读观察与客户机中断

在实验机读取 /proc/interrupts 可看 IRQ 在各 CPU 的累计计数，读取 /proc/softirqs 可看 softirq 类别计数；两者都不能直接当作包数或 I/O 请求数。应比较同一负载窗口前后的变化，并结合驱动队列统计。读取权限和可见字段依赖系统配置。

虚拟化再增加了路由与交付边界：后端发布 Guest 队列完成，通过 QEMU 设备通知或 eventfd/irqfd 进入 KVM，KVM 建立待处理中断状态，再由软件注入或相应硬件辅助路径交付 Guest。Guest 驱动随后按自己的 IRQ/NAPI 路径处理。这通常是同一完成事件的递送过程，不是每经过一层都产生一个新的业务完成通知。

直通设备也可产生 MSI-X；宿主转发与 VT-d posted interrupt 是这些消息的不同递送路径，不是“MSI-X 或硬件”的二选一。见 中断传递演示。
