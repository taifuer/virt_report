前言

预拷贝迁移在虚拟机运行期间复制内存，最后暂停虚拟机，传输剩余脏页及处理器、设备状态。难点在于，复制和写入同时发生：已经传过的页可能再次变化，持续迭代也未必能把剩余量降下来。QEMU 如何保证这些修改不被遗漏，又如何决定暂停时机，是本文讨论的两个问题。

以下分析以 x86 / KVM、普通 RAM 的预拷贝路径为例，假定两端机器配置兼容、存储已就绪，不涉及磁盘复制、VFIO 或机密虚拟机。

基本原理

先暂停、再复制全部内存，最容易得到一致状态，但停机窗口需要容纳整个内存传输过程。预拷贝把这项工作拆开：先建立目的端内存副本，再重复修补运行期间的修改，最后用一次短暂停顿完成交接。它以额外的重传流量，换取较少的暂停期间工作量。

{{ diagram('migration-precopy-sequence', '预拷贝迁移与最终状态交接', '运行期间传送内存；暂停后同步余页与处理器、设备状态，目的端完成恢复后继续执行。') }}

Libvirt 协调目的端准备和迁移任务；QEMU 保存、传送和恢复状态；KVM 提供客户机执行及脏页记录能力。目的端 QEMU 边接收边填充内存，但客户机尚未运行。运行阶段得到的副本不要求任意时刻都一致，最终一致性依靠停止修改、最后一次脏页同步和状态交接建立。

暂停后不仅要补齐 RAM，还要保存寄存器、中断控制器、设备队列处理位置等状态。普通预拷贝路径先完成 RAM 等可迭代状态，再同步 vCPU 并保存非迭代状态；目的端恢复完成且允许启动后才执行。字节流的组织方式另见《QEMU 迁移流格式与状态恢复》。

脏页跟踪与内存迭代

待传位图与脏页记录不是同一件事

QEMU 为各个 RAMBlock维护迁移位图 bmap，表示哪些页还需要发送。初始化时将相应位设为 1，使首次扫描覆盖需要迁移的内存；与此同时开启脏页跟踪，记录运行期间的新修改。初始化代码还处理了可排除的丢弃页，因此“全量”不等于无条件传送每个已配置地址。

KVM 的 dirty bitmap 或 dirty ring 记录客户机写脏的页；QEMU 内存子系统汇总相关记录，再由 migration_bitmap_sync()合入迁移位图。原来为 0、此次变为 1 的页增加待传数量，已经为 1 的页不会重复计数。同一页写入一千次，通常也只产生一项待传工作，而不是一千份写操作日志。位图合并、同步入口

为什么传过的页再被修改不会漏掉

假设页 P 已传到目的端，随后客户机又修改了 P。迁移位图中的发送任务虽然完成，底层脏页跟踪仍在工作；下次同步把 P 重新标入待传集合，目的端旧内容便会被覆盖。清除发送标记并不是关闭跟踪。

更关键的是读取页面与重新建立跟踪的顺序。migration_bitmap_clear_dirty()在发送前处理底层脏标记的清除，再清除迁移位图中的该页。源码特别要求：相关页的跟踪必须在读取、发送之前就重新有效，否则发送之后才清标记，可能把两者之间的新写入一并抹掉。手动 dirty-log 模式可以按块推迟清除，但不能推迟到发送之后。清除顺序、页面发送

运行阶段复制到的页甚至可能不是某个瞬间的原子快照；只要期间发生修改，它就需要再次同步。最后暂停客户机并静止相关 I/O 后，ram_save_complete()再次汇总脏页并发送剩余内容，才形成恢复所需的最终内存。用户态设备或 DMA 的写入也必须经过对应的脏页记录路径，不能假定 KVM 自动覆盖所有写入来源。

一次回调不等于一轮内存扫描

ram_save_iterate()从上次扫描位置继续寻找待传页；达到限速或时间预算时就返回，下次再接着发送。外层为一次调用写出的 SECTION_PART，因此不等于“复制完一整轮内存”。扫描位置、位图同步次数和流中的 PART 数是三个不同概念，不能互相替代。扫描游标、迭代回调

收敛与切换条件

用一个简化的轮次模型可以说明重传的代价。设内存量为 M，第 n 轮待传量为 Rn，有效内存传输速率为 B，按脏页粒度去重后的新增数据速率为 D。在速率稳定、没有压缩和其他开销的近似下：

本轮耗时      Tₙ ≈ Rₙ / B
下一轮待传量  Rₙ₊₁ ≈ min(M, D × Tₙ)
                    = min(M, Rₙ × D / B)

例如 M 为 8 GiB、B 为 1000 MiB/s、D 为 256 MiB/s，待传量大致按 8192 → 2097.152 → 536.871 → 137.439 → 35.184 MiB 下降；下方演示以这组参数开始，可切换 4、8、16 GiB 内存或修改带宽。D/B 越接近 1，每轮减少得越少；达到或超过 1 时，这个模型就不能靠继续迭代收敛。实际负载的热页集合、突发写入、扫描顺序和带宽变化，会使曲线偏离几何级数。

这里的 D 不是应用写入字节率：修改一页中的少量字节，也可能需要重传整页；反复修改同一页又会被合并。B 也不是网卡标称带宽，而是当前路径处理内存的有效速率。压缩或零页编码启用后，逻辑内存字节数与链路字节数还要区分。

继续迭代并不是越久越好。每多传一轮，都会延长迁移、消耗网络与主机资源；而剩余量足够小时，暂停后直接补齐通常更合适。判断依据因此应是预计暂停期间的工作量，而不是固定轮数或等待脏页归零。

停机时间与观测指标

从时间目标换算剩余量阈值

migration_update_counters()使用近期观测带宽，或配置的 avail-switchover-bandwidth，计算切换阈值。固定版本中的关键表达式为：

s->threshold_size = expected_bw_per_ms * migrate_downtime_limit();

随后 migration_iteration_run()先读取各状态处理器报告的剩余量估计；当它低于阈值时，再请求更精确的剩余量。对 RAM 来说，后一步会重新同步脏页，避免只看已经过时的位图。最终剩余量不超过阈值，并且切换条件满足，才进入完成阶段。启用 switchover-ack时，还需目的端确认。阈值、判断逻辑、精确剩余量

为什么 downtime-limit 不是停机承诺

剩余内存除以带宽，只解释暂停阶段的一部分。实际还要停止 vCPU 和相关 I/O、汇总最终脏页、提取与序列化 CPU 和设备状态、完成传输，并在目的端完成装载、存储激活和恢复执行。其中部分发送与接收可以重叠，不能简单把所有函数耗时相加。设备状态、带宽突变、线程调度及同步等待都可能让实际停顿超过目标。

参数或指标含义
downtime-limit用于切换决策的时间目标，单位为毫秒；不是业务 SLA。
expected-downtime迁移活动期间报告的估计值，随脏页同步和带宽估计更新，不是已经发生的停机。
downtime成功完成后报告的停机统计；需结合源端计时点与启用的协议理解。
total-time整个迁移过程的耗时，包含运行期间的迭代，不能与停机时间混用。

在本文的预拷贝实现中，源端在 migration_stop_vm()调用停止操作前开始计时，在源端完成处理时结束；是否等待返回通道也影响这个区间。因此 QMP 的 downtime不是一次直接测量“源端最后一条客户机指令到目的端第一条指令”的跨主机计时。业务侧还会受到网络切换、连接重试和应用调度影响，应另行测量请求中断与尾延迟。计时开始、完成流程、计时结束

关键源码

迁移线程负责判断是否继续，RAM 处理器负责维护待传集合，两者通过状态保存回调连接。沿下面的调用链，可以把“复制、重传、暂停”对应到实际代码：

migration_thread
  qemu_savevm_state_setup
    ram_save_setup → ram_init_bitmaps
  migration_iteration_run
    pending_estimate / pending_exact → 必要时同步脏页
    qemu_savevm_state_iterate
      ram_save_iterate → ram_find_and_save_block
        ram_save_host_page → ram_save_target_page
  migration_completion_precopy
    migration_stop_vm
    qemu_savevm_state_complete_precopy
      ram_save_complete → 最终脏页同步、发送余页
      complete_precopy_non_iterable → 同步 vCPU、保存设备

savevm_ram_handlers注册了初始化、迭代、完成和装载回调。暂停阶段的最终保存流程先完成可迭代处理器，再通过 cpu_synchronize_all_states()读取所需的 CPU 状态，并保存各非迭代处理器。CPU 与具体设备的先后依赖注册顺序，不能概括成所有机器都严格“先全部 CPU、再全部设备”。

观察一次实际迁移时，可同时记录 query-migrate中的 ram.remaining、dirty-pages-rate、dirty-sync-count、pages-per-second与时间指标；页速率须结合 page-size换算。再用 migration_bitmap_sync_end、migrate_pending_exact和 vmstate_downtime_checkpoint等 trace 事件区分“剩余量降不下来”和“暂停后的处理太慢”。单看链路吞吐或完成时间，无法分辨这两类问题。

优化机制与代价

预拷贝面对的限制可以归为传得慢、写得快、重传多和暂停收尾重。后续机制分别改变这些条件，并不是在同一个开关上不断升级。

传输能力不足：并行化

当单一路径的页面处理或传输成为瓶颈时，MultiFD 使用多个工作线程和通道处理内存；QAPI 的 multifd能力自 QEMU 4.0 提供。它有机会提高有效 B，但会增加线程、缓冲区和同步开销；若已受网络总带宽或内存带宽限制，增加通道不会按比例提速。MultiFD 实现、能力版本

写脏速度过高：从统一限速到按 vCPU 限制

QEMU 1.6 的 auto-converge通过限制客户机 CPU 执行降低写脏速度。代价是迁移期间的业务性能，也会影响不负责大量写内存的 vCPU。QEMU 8.1 的 dirty-limit利用 KVM dirty ring 观察各 vCPU 的写脏活动，更有针对性地施加等待；它需要相应 KVM 能力，仍然不是免费收敛，也不能替代所有设备写入路径的处理。自动收敛、Dirty limit 设计

跟踪本身有开销：缩短清除与读页的间隔

传统整槽位同步、清除与重新写保护，在大内存客户机上可能持锁较久；而过早重新保护，还会记录一些随后本就会随当前页一起传走的修改。KVM 的手动 dirty-log 保护把“获取记录”和“清除并重新保护”分开，允许按较小范围、更接近发送时刻处理。它减少无效工作，却增加了顺序要求：必须在读页前恢复跟踪。dirty ring 则以队列收集脏页，带来回收、满环处理及内存顺序方面的新约束。手动保护的设计动机、Dirty ring 约束

减少流量与控制收尾成本

零页识别避免发送整页零值；XBZRLE 在适合的重传场景中编码与已缓存页面的差异；压缩以 CPU 工作换取链路字节减少。效果取决于页面内容、缓存命中和处理能力，不能只看压缩率。若内存剩余量已经很小而停机仍长，应检查设备保存、目的端装载和 I/O 交接，而不是继续增加迭代。放宽停机目标可以更早切换，但会把更多工作留在暂停阶段。

后拷贝进一步改变问题：先交接执行，再按需取回缺失内存，减少预拷贝式反复重传，却引入运行时远程缺页和两端状态依赖。它不是预拷贝的一项无代价加速。选择机制前，先用剩余量、脏页速率和停机阶段的测量确定瓶颈，才能判断节省了什么、又把代价转移到了哪里。后拷贝设计
