一次状态查询如何跨越进程

应用程序调用 Libvirt API 时，连接 URI 决定请求交给哪个驱动。对于常见的 qemu:///system 连接，客户端通过 RPC 访问管理守护进程，再由服务端 QEMU 驱动处理虚拟机对象。应用拿到的 virDomainPtr 是本进程中的句柄，跨进程传输的是对象标识与参数。

本文跟踪一次 virDomainGetInfo()：查询已有虚拟机的状态、内存、vCPU 数和 CPU 时间。连接建立与认证已完成；传输采用本机 UNIX socket，服务端可以是 libvirtd 或模块化的 virtqemud。

以虚拟机 demo 为例，客户端把 UUID 等标识编码进 CALL；服务端按过程号选择查询函数，用 UUID 找到对象，再把结果放入 REPLY。客户端靠调用序号找到原等待者。编码解决跨进程表示，分发决定执行哪项操作，序号解决多个调用并发时的响应归属，下面依次展开这三段。

驱动表如何把 API 变成 RPC

virDomainGetInfo() 校验参数后调用 conn->driver->domainGetInfo。客户端连接绑定 remote 驱动时，这个函数指针指向 remoteDomainGetInfo()；服务端的本地 QEMU 连接则指向 qemuDomainGetInfo()。相同的公开 API 可以在两端出现，实际执行者由连接对象上的驱动表决定。

过程号、参数结构和返回结构在 remote_protocol.x 中定义，构建时生成 XDR 编解码与两端样板代码。查询操作的过程号是 REMOTE_PROC_DOMAIN_GET_INFO = 16；通用 remote program 为 0x20008086，协议版本为 1。这里的 version 是 RPC 协议版本，不是 Libvirt 软件版本。程序与版本号、过程定义

对象所在位置保存的内容
virDomainPtr调用者进程所属连接、名称、UUID 和运行时 ID；不包含 QEMU 进程的完整状态
remote_nonnull_domainRPC 参数name、16 字节 uuid、32 位 id，不传指针
virNetMessage两端 RPC 层解码后的头、字节缓冲区、长度与当前位置，负责消息读写
virDomainObj服务端 QEMU 驱动定义、运行状态、进程 PID、作业与驱动私有数据；由驱动按 UUID 查找

示例：56 字节请求与 60 字节响应

UNIX stream socket 和 TCP 都提供字节流，单次读取可能只得到半条消息，也可能带来多条消息的数据。Libvirt 先读取 4 字节长度，再按长度接收其余部分。长度包含自身，后接固定 24 字节头与过程专用载荷；接收端检查长度边界后才扩展缓冲区。线格式、长度解码

字节偏移字段本次 CALL 的值含义
0–3length56完整消息长度，含前面的 4 字节
4–7prog0x20008086选择 RPC 程序
8–11vers1程序的协议版本
12–15proc16查询虚拟机信息
16–19type0，CALL区分调用、响应、事件和流数据
20–23serial42本次调用的序号，响应必须保留
24–27status0，OKCALL 固定为 OK；响应可携带错误状态

XDR 按大端序编码整数，并以 4 字节为基本对齐单位。C 结构中的 char 和 short 在 XDR 中也占 4 字节，hyper 占 8 字节；字符串由长度和内容构成，必要时补齐到 4 字节边界，不传结尾 NUL。因此报文不能用 C 结构的 sizeof 或本机内存布局解释。

公共长度回答“还要接收多少字节”，载荷里的字符串或数组长度回答“如何解释这些字节”，两者分别检查。协议对消息、字符串和各类数组设置上限，解码器按具体过程的结构处理。这样可避免对端声明一个巨大长度后，接收进程直接按该值无限分配内存；结构解码成功也不等于业务参数有效，驱动仍要验证实际操作。

以名称 demo 为例，请求载荷为 name 长度 4 B + 名称 4 B + UUID 16 B + id 4 B = 28 B，加公共部分共 56 B。若名称是 vm1，3 字节内容后补 1 字节，长度仍是 56 B。UUID 是固定长度 opaque，不额外增加长度字段。对象标识

请求：length=56，CALL / OK，serial=42
      payload = name("demo") | UUID[16] | id

响应：length=60，REPLY / OK，serial=42
      payload = state[4] | maxMem[8] | memory[8]
              | nrVirtCpu[4] | cpuTime[8]

示例：state=RUNNING，maxMem=8388608 KiB，memory=8388608 KiB
      nrVirtCpu=4，cpuTime=2500000000 ns

返回载荷共 32 字节，完整响应是 60 字节。maxMem 与 memory 的单位是 KiB，cpuTime 的单位是纳秒。实际值由驱动查询得出，上例只展示编码关系。返回结构

服务端分发与对象查询

客户端 callFull() 递增连接上的计数器，取得本次 serial，再由 virNetClientProgramCall() 填充头、编码参数并等待响应。等待期间释放 remote 驱动锁，使事件与流数据的处理不被这把锁阻塞。调用入口

{{ diagram('libvirt-rpc-dispatch', '一次 virDomainGetInfo 调用的往返', '客户端和服务端分别绑定 remote 与 QEMU 驱动。UUID 用于定位服务端对象，响应通过同一连接上的 program、version、serial 匹配等待者。') }}

服务端按 program/version 找程序，按 proc 找 virNetServerProgramProc。该表项包含处理函数、参数与返回结构大小、XDR 过滤函数和认证要求。通用分发器检查认证，解码参数，设置当前客户端身份，再调用过程处理函数；QEMU 驱动随后执行对象级 ACL 检查。认证通过只说明客户端身份可被接受，仍需判断它能否读取目标虚拟机。通用分发

生成的 remoteDispatchDomainGetInfo() 从客户端上下文取得服务端连接，把 name/uuid/id 转成本地句柄，再调用公开 API。QEMU 驱动通过 UUID 查找并锁住 virDomainObj，从对象读取状态、内存和 vCPU 信息；对运行中的虚拟机，还读取 QEMU 进程的 CPU 时间。该查询没有“一条 RPC 必须对应一条 QMP 命令”的关系。对象查找、GetInfo 实现

名称便于展示，运行时 ID 随实例启动而分配，UUID 则用于这里的对象定位。客户端持有旧句柄时，服务端对象可能已经删除或状态改变，因此发送一个曾经有效的 ID 不能跳过查找与权限检查。获得句柄和执行查询属于不同时间点，对象锁只保护本次访问的一致性。

返回值填入 remote_domain_get_info_ret，RPC 层复用请求头，只把 type 改为 REPLY、status 改为 OK，再编码载荷并加入发送队列。两端样板代码由协议生成器维护，修改接口时仍需同步考虑协议兼容、长度限制和整数转换。

响应如何返回原调用，错误如何区分

多个线程可以使用同一连接发出调用。客户端收到响应后，以 prog + vers + serial 查找等待记录，将报文交给相应调用；上层还检查 proc、type 和 serial，再使用该过程的返回过滤函数解码。不能用“第一个收到的响应对应第一个发出的请求”来匹配。等待队列匹配、响应检查

生命周期等异步事件使用 MESSAGE 类型，经事件分发路径处理，不会当作普通 API 返回值。协议还定义了 STREAM、带文件描述符的调用和响应等类型；流控制与 FD 传递有各自规则，不能直接套用本例的固定载荷布局。

目标 UUID 不存在、ACL 拒绝或驱动查询失败时，服务端返回 REPLY / ERROR，载荷改为 virNetMessageError，包含错误域、错误码、级别及文本等信息。客户端恢复本地错误对象，API 返回 -1。连接断开和解码失败则可能直接终止等待，连一条完整的错误响应都收不到。错误结构

serial 负责本连接内的响应关联，不是服务端的持久化去重键。尤其对于启动、修改配置等写操作，断线时请求可能已经执行，只是响应尚未抵达；应用应先查询实际状态，再决定是否重试。启动过程见Libvirt 虚拟机启动的进程与状态管理。

守护进程拆分与接口兼容

传统部署由单个 libvirtd 加载 QEMU、网络、存储等驱动。模块化架构把有状态驱动分到 virtqemud、virtnetworkd、virtstoraged 等进程，降低不同驱动共享一个进程的耦合；代价是服务、socket、配置与跨服务连接的管理更复杂。

virtproxyd 可以提供兼容入口与远程访问，再把请求转发到对应驱动守护进程。应用仍使用原有 API 和连接 URI，底层到达的进程与中转层可能改变。socket activation 允许连接到来时再启动服务，也使“socket 已监听”和“驱动已初始化完成”成为不同阶段。Libvirt 守护进程架构

这个演进保留了 API 与 RPC 的边界：上层应用不需要把每一种进程拆分映射为新的调用接口。协议过程号、消息头和错误语义仍需兼容既有客户端；新功能通过新增过程或扩展参数表达。分析一次调用变慢时，可分别观察连接建立、RPC 等待、服务端作业等待与驱动执行，单看网络往返时间不足以解释整个延迟。
