接收事件与发送请求

外部可随时发来报文。网卡接收后，内核按协议、地址和端口分派，匹配的数据进入 socket 队列。应用调用 recvmsg() 从队列读取数据，队列为空时可以等待后续报文。

以普通 UDP、复制式缓冲区交接和网卡 NAPI 路径为例，下面跟踪接收、发送与资源回收。UDP 提供数据报传输，本身不提供逐包的远端收到确认。

从逐包中断到批处理与多核收发

网络压力通常同时体现在带宽和包速率上：同样的字节速率，小包需要更多次收包、协议处理与队列操作。早期逐包触发并处理的方式，在高负载下可能让 CPU 忙于中断而没有足够时间让应用消费数据。2002 年的 NAPI 设计说明已经把中断抑制、有预算的轮询和减少过载成本列为核心动机。

发展方向解决什么代价与边界
中断驱动接收 → NAPI低负载靠通知启动，高负载按预算批量轮询需要正确重新使能通知；预算和批量大小会影响延迟与其他任务获得 CPU 的机会
单队列 → RSS、多队列与软件分流让多个 CPU 分担不同流的处理队列数、IRQ 亲和性与应用位置需要协调；跨核转交也有缓存和 IPI 开销
逐包重复工作 → GSO / GRO 等批处理在合适的协议和设备条件下减少协议栈重复处理内核观察的 skb 数量与链路帧数可能不同，抓包和计数需识别所在层次
专用高速路径：XDP / AF_XDP把部分处理提前，或让应用直接管理报文缓冲区的交接需要额外程序、队列与内存管理；不自动获得普通 socket 协议栈的全部语义

NAPI、多队列和分段卸载可以组合使用，分别影响通知开销、CPU 分工和协议处理批次。具体组合取决于硬件能力、驱动与应用需求。

缓冲区、队列与 socket

对象保存什么生命期边界
应用 buffer用户提供的发送载荷或接收空间普通复制式发送返回后可复用；零拷贝接口另有约定
skb协议元数据及对线性区、分页数据等的引用可能复制、克隆或共享引用；不是固定等于一块连续内存
驱动 RX/TX ring设备描述符及 DMA 缓冲区的引用提交前与设备完成后分别由驱动按协议管理
socket 接收队列已通过协议处理、等待应用读取的数据有数据可读与应用实际取走是两个阶段

硬件 ring 管理设备描述符，socket 队列管理应用待收数据，virtqueue 管理 Guest 与虚拟后端的请求。描述符引用数据缓冲区；共享数据的最后一个引用结束后，内存才能回收。

外部数据到应用

{{ diagram('linux-network-handoffs', '外部到包与应用读取', '图示普通 UDP 成功接收的一次通知；NAPI 可批量轮询，不要求每个包触发一次中断，也不要求应用先调用 recvmsg。') }}
  1. 驱动事先向网卡准备可写接收缓冲区；外部帧到达后，网卡 DMA 写入数据并发布接收状态。
  2. 中断通常触发 NAPI 调度，poll 按预算批量取包；持续轮询期间可暂时抑制重复设备通知。
  3. 内核处理以太网、IP 和 UDP，验证并分派到匹配 socket；数据可排队，等待中的接收线程可以被唤醒。
  4. 应用被调度并读取 socket，内核将载荷复制到用户空间。数据先到时可直接取，应用先等待时则要等报文到达。

UDP 分派与接收就绪

应用创建 socket 并绑定本地地址和端口后，内核即可分派报文。UDP 经过协议检查，再按目的地址、端口及 socket 的绑定／连接条件查找。匹配成功且接收内存额度允许时，skb 进入 socket 接收队列，数据就绪回调随后通知等待者；可对照 __udp_enqueue_schedule_skb() 中入队与 sk_data_ready 的顺序。

若应用已经阻塞在 recv，通知使它有机会重新运行；若应用尚未调用 recv，数据可以先排队，之后直接读取；若用 epoll，得到的是“此刻值得尝试读取”的就绪提示，真正取数据仍是 recv 一类调用。其他线程也可能抢先取走数据，因此就绪不保证下一次非阻塞读取一定成功。

无匹配 socket、接收额度不足和网卡缺少 RX buffer，分别发生在不同阶段。用户缓冲区过小则可能在读取时截断已经入队的 UDP 数据报。net_rx_action() 展示设备轮询预算，udp_recvmsg() 展示向应用交付的路径。

epoll 与应用的读取循环

默认水平触发模式下，只要描述符仍就绪，后续 epoll 等待可以继续返回它。使用边沿触发 EPOLLET 时，常见做法是配合非阻塞 socket，在得到读事件后持续接收，直到返回 EAGAIN。若为公平性提前停止，事件循环需要自行记住尚未处理完的描述符，避免留着数据却一直等待下一条边沿通知。见 epoll 的两种触发模式。

UDP 保留数据报边界，一次接收最多取一条普通数据报，缓冲区不足时可能截断。长度为 0 的 UDP 数据报也合法，recv 返回 0 可以表示收到了空报文；TCP 流在非零接收长度下返回 0 则通常表示对端有序关闭。应用必须按 socket 类型解释返回结果，接口约定见 recv(2)。

从 sendto 到缓冲区回收

应用提交载荷，协议栈形成报文，经过路由、排队和驱动提交给设备。普通复制式 sendto() 成功返回表示本地接受了返回长度对应的数据，不保证物理发送已经结束。网卡完成 DMA/发送工作后，驱动再回收该次提交占用的描述符与缓冲区；这个完成不等于远端收到，更不等于远端应用处理成功。

发送缓冲区的所有权交接

{{ diagram('linux-network-tx-ownership', '先返回发送调用，再回收设备资源', '示意路由已就绪、驱动直接接受且设备稍后完成的一次 UDP 复制发送。图中的先后是一条允许的执行轨迹，不代表 sendto 必须等待物理发送。') }}

继续看普通 UDP 复制发送，并假设路由与邻居解析已就绪。应用提交载荷后，内核构造或填充 skb、建立 UDP/IP 等协议头，选择出口设备与发送队列。qdisc 管理设备前的软件排队和调度；可以直接发送时也可能走快速路径，并非每个包都会在软件队列里停留。

  1. 用户到内核：载荷复制进内核维护的报文存储。成功返回后，这条普通复制路径不再引用原用户 buffer，应用可以重用它。
  2. 协议栈到驱动：通过 ndo_start_xmit() 提交 skb。驱动接受后负责后续释放，并将相关内存映射成设备可用的 DMA 地址，填写 TX 描述符、通知设备。
  3. 设备到驱动：驱动观察到 TX completion，确认设备已结束相关访问，再解除或同步 DMA 映射、释放 skb 引用和描述符槽位。
  4. 恢复提交：如果此前因 TX ring 空间不足停止了队列，回收出空间后可唤醒队列，让上游继续发送。

驱动必须在资源用尽前适当停止队列，并协调检查与唤醒，避免“已经回收出空间，队列却永远停着”。如果返回 NETDEV_TX_BUSY，skb 所有权仍属于调用方，驱动不能保留或释放它。驱动约定见 Softnet 驱动指南。这条所有权链解释了：sendto 已返回，内核仍会在之后处理 TX completion。

观察到的事件确认的边界不能推出
sendto 返回本地发送调用的接受结果；普通复制路径不再依赖原用户 buffer物理 NIC 已发完
virtio-net TX Used虚拟后端结束了对此 Guest 描述符链的访问宿主物理 NIC 已完成，或远端已收到
物理 NIC TX completion按驱动／设备协议可回收本地 TX 资源远端协议栈或应用已经处理
协议／应用层应答取决于该协议：例如 TCP ACK 确认接收序列空间TCP ACK 也不证明远端应用已读；UDP 本身没有这类确认

以 QEMU + TAP 普通复制发送为例，TAP 接受帧后，后端结束对 Guest 发送缓冲区的访问并可发布 Used。宿主继续转发自己的报文副本。Guest Used 与物理 NIC completion 分别归还两层的资源，后续转发可与 Guest 回收并行。

发布 Used、通过 irqfd 或 QEMU 设备通知 KVM、交付 Guest 中断，是同一完成事件的不同环节。通知是否发出还受抑制、合并和驱动轮询影响。

批处理、多核与缓冲区生命期

{{ diagram('linux-napi-budget', '一次通知可以启动多轮轮询', '示例固定 100 个 RX 包、每轮预算 64、期间无新包。第二轮靠已保留的 NAPI 调度状态继续，不需要设备为剩下的 36 个包再发一次中断。') }}

NAPI 一轮 poll 受到 RX 预算约束；仍有工作时可继续被调度，处理完成才恢复相应通知。这样可以摊薄每次中断和调度的成本，但一次取很多包也可能让先到的小请求多等一会儿。TX completion 也可在 poll 中回收，不能把 poll 返回的 RX 工作量直接当作所有完成操作的数量。

例如 RX 预算为 64、队列已有 100 个包，期间无新到包：第一轮处理 64 个并返回预算值，保留后续轮询；下一轮处理剩余 36 个，调用 napi_complete_done() 成功结束本轮后，再按设备规则恢复通知。若处理数量恰好等于预算且队列已空，可继续保留轮询，也可完成后返回 budget - 1。预算为 0 的调用用于 TX 等处理，此时禁止调用 napi_complete_done()。

RSS 由网卡选择接收队列，RPS 在内核中选择后续协议处理 CPU，RFS 进一步考虑应用位置，XPS 影响发送队列选择。这些机制按流分工，兼顾并行与局部性。跨核转交会增加 IPI 和缓存迁移成本，已有合适硬件分流时，应测量软件分流的额外收益。见 Linux 网络扩展机制。

GSO 在发送方向保留较大的逻辑报文，稍后由软件或支持卸载的设备分段；GRO 在接收方向合并符合条件的报文，减少后续重复处理。可否合并、如何分段取决于协议与特性协商，不能把任意 UDP 数据报都当作一个连续字节流。相关约束见 分段卸载文档。

AF_XDP 用 UMEM 和 FILL、RX、TX、COMPLETION rings 管理缓冲区；发送帧返回 completion 后，应用才能复用该帧。它支持 copy 模式，以及依赖驱动能力的 zero-copy 模式。两种模式都要求按环上的所有权约定交接内存，见 AF_XDP 的 rings 与模式。

只读观察与 virtio-net

可读取 ip -s link、ss -u -a -m 和 /proc/net/softnet_stat；驱动支持时，ethtool -S 接口名 可补充队列计数。各层 drops 的统计位置不同，定位丢包需要对照同一负载窗口中的设备、协议栈和 socket 计数。

接收路径上，RX ring、协议栈处理能力和 socket 接收额度是不同的容量约束。应用消费不及时，可能使 socket 排队和丢包，即使网卡 ring 仍有空间；扩大 socket 缓冲区能吸收部分突发，但也可能延长排队，无法弥补持续的处理速率差。普通 UDP 没有接收窗口反馈，接收方本地缓冲区耗尽时不能依靠 UDP 自动让发送方减速。

虚机接收时，Guest 驱动也先发布可写 RX buffer；后端将外部到达的数据写入这些缓冲区并发布 Used，Guest 协议栈再交给 socket。应用无需先为每个包发 virtio 请求。结合 网络 I/O 演示 和 Virtio RX 路径，可以把 Guest 与宿主的两套队列分开观察。
