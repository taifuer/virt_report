前言

QEMU 可以向客户机提供 e1000 或 virtio-net 网卡。前者实现已有网卡的寄存器和描述符接口，客户机可以使用对应的硬件驱动；后者采用 virtio 协议，由客户机驱动和设备端通过 virtqueue 交换请求。沿一次发包过程，可以看到两种接口如何提交报文、通知设备，以及回收缓冲区。

本文分析 x86 / KVM 下的 QEMU 用户态网卡路径：e1000 与 modern virtio-net PCI 设备使用相同的 TAP 后端，关闭 vhost；virtio-net 采用 split virtqueue。示例只发送一个普通以太网帧，省略校验和与分段卸载，不配置客户机 IOMMU。涉及 DMA 地址的实际系统，还需按平台配置完成地址转换。

设备接口与队列

网络发送包含三类交互：客户机在内存中准备报文和队列元数据，通过设备接口提交工作，再从完成记录中判断哪些缓冲区可以回收。报文内容、提交通知和完成通知承担不同职责，追踪时应分别观察。

e1000：实现硬件定义的接口

e1000 驱动在客户机内存中分配 TX 描述符环。描述符记录缓冲区地址、长度以及命令和状态位；EOP标记一个报文的结束，RS请求状态回写。设备寄存器 TDBAL/TDBAH保存环地址，TDLEN保存长度，TDH和 TDT表示消费位置与驱动提交的尾位置。

驱动填好描述符后写 TDT，QEMU 的 e1000 模型就按硬件接口约定读取客户机内存。这里已经存在描述符环和 DMA 语义：软件模型通过 pci_dma_read()、pci_dma_write()完成设备视角的内存访问。描述符环本身无需复制到某个“宿主设备专属内存”才能使用。e1000 发送实现

virtio-net：通用队列与网络设备格式

split virtqueue 把队列划分为描述符表、available ring 和 used ring。驱动填写描述符链，将链首编号放入 available ring；设备读取链上的缓冲区，完成后把链首编号写入 used ring。avail.idx与 used.idx分别记录已发布和已完成的队列项数量，按协议规定的整数宽度回绕。

virtio-net 在帧前携带 virtio_net_hdr，用于描述网络卸载等信息。该头属于客户机与设备间的协议元数据；它不会作为以太网帧的一部分发送到远端。TAP 支持的 vnet_hdr还允许 QEMU 与宿主内核传递这些元数据，具体长度和能力需要协商。发送头与缓冲区整理

两种接口的差异主要在驱动与设备的约定。virtio 把队列机制从具体硬件寄存器模型中独立出来，便于不同设备类型复用；客户机仍需要相应驱动，QEMU 仍需检查描述符、访问内存和完成后端 I/O。

virtqueue 的数据结构与操作

split virtqueue 使用三个共享区域：描述符表保存缓冲区位置，available ring 发布可用的描述符链，used ring 归还已处理的链。两个环中的项可以循环复用，报文则保存在描述符指向的内存中。描述符表、环槽和报文缓冲区各有自己的地址与生命周期。

{{ diagram('virtqueue-tx-layout', '一条 TX 请求在 split virtqueue 中的关联', '本例队列长度为 4，图示请求已完成、驱动尚未回收。环槽 3 保存链首 0，描述符链为 0 → 2，实际数据位于各自的客户机缓冲区；used.len 为 0 表示设备没有向这条发送链写入数据。') }}
描述符表 · desc[N]
addr: u64 · len: u32 · flags: u16 · next: u16

每项 16 B。驱动填写设备可访问的地址和长度；NEXT 表示沿 next 继续读取链，WRITE 表示设备可写，INDIRECT 表示 addr 指向另一张描述符表。本例为设备只读的直接 TX 链。

可用环 · avail
flags: u16 · idx: u16 · ring[N]: u16

驱动写、设备读。ring 中每项保存链首描述符编号；一个请求即使使用两个描述符，也只发布一个链首。驱动先准备数据和描述符，再写 ring 项，通过内存屏障发布新的 idx。

已用环 · used
flags: u16 · idx: u16 · ring[N]: { id: u32, len: u32 }

设备写、驱动读。id 是原链首编号，len 是设备向该链的缓冲区写入的字节数。本例 TX 的 len 为 0，驱动仍可据此回收整条链。

实际数据缓冲区
desc[0].addr → 网络头；desc[2].addr → 报文 P1

链中的描述符编号可以不连续。驱动提交后保持描述符与数据有效，设备发布 used 后由驱动回收；设备私有的 last_avail_idx 和驱动私有的 last_used_idx 分别记录消费与回收进度。

上述字段展示共享格式的主体。启用 VIRTIO_F_RING_EVENT_IDX 时，可用区末尾还有 used_event，已用区末尾还有 avail_event，用于控制完成通知和 kick 的触发位置。未使用该特性时，通过对应 flags 抑制通知。modern virtio 的多字节共享字段使用小端序。Linux 的 vring 结构

索引、环槽与描述符编号

idx 是 16 位递增计数器，访问数组时再计算 idx % N。对于长度为 4 的环，提交位置 3 对应 ring[3]，下一次位置 4 对应 ring[0]；计数器达到 65535 后回到 0。ring[3] 中可以保存链首编号 0，链首 0 又可以通过 next 指向描述符 2，三种数字不能互换。

操作共享状态私有进度与缓冲区
准备链 0 → 2填写两个 desc，网络头和 P1 就绪驱动保留这两个描述符，暂不允许复用
发布一个请求avail.ring[旧 idx % N] = 0，屏障后推进 avail.idx设备通过 avail.idx 与自己的消费位置判断新增项
设备取出请求按链首与 NEXT 读取描述符，used.idx 暂未变化设备推进 last_avail_idx；缓冲区继续由本次请求占用
设备发布完成used.ring[旧 idx % N] = {id: 0, len: 0}，再推进 used.idx设备已用完缓冲区，驱动尚未回收
驱动回收不要求清零旧环项推进 last_used_idx，把链 0 → 2 归还空闲集合

新旧项由生产与消费索引区分，不能用“字段是不是 0”判断环为空。回绕时按 16 位计算索引差，驱动还要跟踪尚未回收的描述符，避免覆盖设备仍在使用的请求。下面的演示可选择起始索引 0、3 或 65535，观察环槽与计数器的不同变化。

从共享描述符到 QEMU 本地对象

virtqueue_split_pop() 取到链首后检查描述符编号、链长度和可访问范围，将设备可读的段整理到 VirtQueueElement.out_sg，设备可写的段整理到 in_sg。元素的 index 保留链首，用于完成时写回 used.id。这些 iovec 是 QEMU 的宿主内存视图；它们与客户机共享的 desc[] 是不同对象。split 队列消费、VirtQueueElement 定义

本例把 modern virtio-net 的 12 B 网络头放在 desc[0]，把 60 B 以太网帧放在 desc[2]；两项均为设备可读。实际驱动也可把网络头与报文合并在一个缓冲区，或用更多描述符组织分散的数据。描述符链长度、报文数量和通知次数应分别计数。

e1000 的发送路径

  1. 驱动准备 P1，填写发送描述符并设置 EOP、RS。完成必要的内存顺序操作后，写入新的 TDT。
  2. e1000_mmio_write()分派寄存器写操作；TDT 对应的 set_tctl()调用 start_xmit()。
  3. start_xmit()从 TDH 开始读取描述符。process_tx_desc()读取报文内容，并在遇到 EOP 时调用 xmit_seg()。
  4. 报文经 e1000_send_packet()和 QEMU 网络接口到达 TAP。正常可写路径最终执行 writev()。
  5. 模型按状态回写条件设置 DD、推进 TDH，并更新中断原因。客户机驱动检查完成记录后回收缓冲区。

这里的“DMA 读取”由 QEMU 软件执行。固定版本的 e1000 模型将报文读入自己的发送缓冲区，并在那里完成分段、校验和等模拟工作；这些工作量会受到客户机选择的功能影响。报文处理与状态回写、TDT 回调表

virtio-net 的发送路径

  1. 驱动准备网络设备头与 P1 的缓冲区，建立设备可读的描述符链，发布 available 项。
  2. 驱动检查通知条件，必要时通知对应的发送队列。QEMU 的队列处理函数安排发送任务。
  3. virtio_net_flush_tx()调用 virtqueue_pop()取出请求。通用 virtio 层验证描述符并建立 VirtQueueElement，其中 out_sg描述设备需要读取的客户机缓冲区。
  4. QEMU 整理网络头与 iovec，经 qemu_sendv_packet_async()交给 TAP 后端。可写时，TAP 直接接收；暂不可写时，后端排队等待继续发送。
  5. 同步完成路径或异步完成回调调用 virtqueue_push()发布 used 项，再检查是否需要通知客户机。驱动据此回收链和报文缓冲区。

使用 iovec 可以避免为每个请求都先拼成一块连续的用户态报文。实际复制次数还取决于客户机内存映射、网络头转换、TAP 和宿主协议栈等实现，不能仅凭 virtio 或 scatter-gather 接口推算端到端零拷贝。virtio-net 发送与异步完成

通知与完成

发布队列与发送 kick

驱动先发布可用缓冲区，后端才能安全地消费。通知只提示设备检查队列；多个请求可以共享一次 kick，设备正在处理队列时也可以抑制新的 kick。队列发布需要正确的内存屏障，通知抑制还需要防止“设备准备休眠时恰好新增请求”的竞态。仅删除通知操作，会让后端失去唤醒机会。

在普通 MMIO 路径中，客户机写 virtio PCI 通知地址，QEMU 的 virtio_pci_notify_write()找到队列后调用通知函数。启用 ioeventfd 时，QEMU 预先注册通知地址与 eventfd 的对应关系；KVM 处理匹配的写入并触发 eventfd，QEMU 的事件处理再调度该队列。这减少了通过 KVM_RUN返回用户态模拟此次 MMIO 的往返。CPU 从客户机执行切换到 KVM 的硬件退出仍可能发生，二者应分开计数。ioeventfd 注册、QEMU 事件处理、KVM_IOEVENTFD

完成记录与完成中断

used 项先成为可见状态，再根据驱动配置决定是否发出中断。virtio_notify()内部会检查通知条件，调用它并不保证每个报文都对应一次中断。发送路径可以主动回收先前完成的请求，也可以在需要时使用中断；这为批处理提供了空间。完成通知检查。MSI-X 消息、虚拟 LAPIC 和驱动响应见virtio 完成通知与 KVM 中断注入。

完成记录界定的是缓冲区生命周期。virtio-net 发送链的 used.len可以为 0，因为设备没有向发送缓冲区写入数据；它仍然是一条有效的完成记录。驱动据此回收本地内存，远端报文接收和应用处理则由相应网络协议确认。

后端拥塞会暴露两种实现的细节差异。virtio-net 在异步排队后保留当前元素，等待发送回调再发布完成；e1000 模型已将客户机内容读入内部缓冲区，描述符处理与后端队列排空不必同步完成。此外，发送错误或丢弃路径也可能回收请求。因此观察 DD 或 used 时，还要结合设备统计和宿主网络状态判断发送结果。异步回调、TAP 暂不可写处理

接口演进与后端分工

兼容硬件驱动与统一虚拟设备接口

模拟已有网卡可以利用操作系统现成的驱动，代价是设备模型需要遵循硬件的寄存器、副作用、描述符格式和中断行为。virtio 选择统一的特性协商、队列和通知机制，再按网络、块设备等用途扩展设备格式。这样可以减少不同虚拟设备之间重复设计的接口，也要求客户机安装匹配的驱动，并正确处理功能协商与版本兼容。

virtio 的队列格式本身也在演进。1.0 及更早规范使用 split virtqueue，1.1 加入 packed virtqueue，将请求发布与完成状态合并到同一描述符环，减少处理队列时涉及的分散内存区域。packed 描述符使用 addr / len / id / flags，以 AVAIL、USED 位和 wrap counter 判断所有权；直接链按环中连续位置组织，不再使用 split 的 next 字段。驱动和设备仍分别保留事件抑制结构。两种格式需通过特性协商选定。VIRTIO 1.1 规范

后端迁移到内核或独立进程

统一客户机接口之后，可以继续调整宿主处理位置。vhost-net 将 virtqueue 的主要网络数据处理移到宿主内核，减少经 QEMU 用户态处理报文的环节；vhost-user 则通过控制协议，让独立用户态进程取得共享内存、队列和通知所需的信息。客户机侧仍可使用 virtio-net 驱动。vhost-user 的控制面与队列共享

处理位置的变化带来新的资源和状态管理任务：线程如何调度、内存如何共享、后端退出时如何处理队列，以及迁移时如何保存尚未完成的请求。vhost-user 的 Unix socket 负责建立与管理这些关系，普通报文通过共享队列和内存交换。网络后端可以使用 DPDK，块设备后端可以使用 SPDK；两者的具体请求路径需要分别分析。

三种后端的初始化与发包过程见《virtio-net 的后端处理：vhost-net 与 vhost-user》。比较方案时，应固定客户机负载、后端出口和卸载配置，再观察队列处理、通知、复制与调度开销。设备接口和后端位置是两个独立维度，同一 virtio 接口可以连接不同后端，硬件直通和 vDPA 则还会改变设备访问与数据面实现。
