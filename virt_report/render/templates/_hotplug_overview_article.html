热插拔的资源范围与协作过程

热插拔允许虚拟机运行期间增加或移除设备、CPU 与内存。管理程序表达变更目标，QEMU 修改虚拟硬件，客户机驱动完成发现、上线或停用。资源是否已经可用或可以回收，取决于这些阶段是否全部完成。

客户机操作系统维护着自己的设备清单、驱动绑定与资源分配。在线变更需要通过它能识别的硬件协议通知变化：增加时发现并配置新资源，移除时先停止使用并交还资源。由此，热插拔同时改变虚拟硬件和客户机的软件状态，需要双方完成交接。

下面依次说明设备、CPU 和内存三类资源。热添加先准备资源，再交给客户机使用；热移除先让客户机停止使用，再回收资源。通知协议与完成条件随资源类型而变。

配置变更、硬件通知与客户机资源状态

冷启动时，客户机可以从头枚举所有硬件。运行中增加网卡，操作系统却不会因管理程序改了一个配置字段就自动发现它。QEMU 要模拟插槽状态变化并发出通知，客户机的总线驱动重新枚举设备，分配地址与中断，再把设备交给具体驱动。

移除更困难：网卡可能仍持有发送缓冲区，内存可能还装着进程页或内核对象。先删掉宿主资源，会让后续访问落到无效对象上。因此热移除要先发出请求，等客户机停止使用资源，再解除后端引用。这是增加与移除不能简单互为反向操作的原因。

热增：准备空间，再通知客户机

本例先为网卡预留可热插拔的 PCIe 端口、总线号与 BAR 窗口。运行中，管理程序创建宿主网络后端，再由 QEMU 创建并连接网卡 net1；端口报告插槽变化，客户机重新枚举设备、分配资源并绑定驱动。至此虚拟硬件与驱动已经建立，客户机还需配置接口和业务通路，才能真正使用新增网卡。

热移除：先停止使用，再归还资源

移除同一块 net1 时，管理程序发起请求，QEMU 通过插槽通知客户机。客户机停止网卡队列和驱动访问，交还设备后，QEMU 才完成虚拟网卡的拆除。独立创建的网络后端还要等网卡不再引用它时清理。客户机可能延迟响应或无法完成，因此从请求受理到资源回收之间需要保留待处理状态。

设备、CPU 与内存的热插拔流程

设备：停止驱动，再拆除网卡

向 QMP 发送 {"execute":"device_del","arguments":{"id":"net1"}} 后，成功响应只表示删除请求已受理。对于需要客户机配合的设备，管理程序继续等待对应 DEVICE_DELETED，再清理已无引用的网络后端。未收到完成事件时，要查看客户机驱动、插槽状态与错误事件，不能直接复用设备 ID。

DEVICE_DELETED 标识 QEMU 设备已移除；它并不证明应用已把流量切换到另一块网卡。若 net1 承载管理连接，应先让业务转用另一条通路，再发起移除，否则热插拔协议即使正确完成，业务仍会断连。

PCIe 端口预留、插槽事件与具体命令见 PCIe 热插拔专篇。

CPU：预留拓扑、通知上线与异步拔出

CPU 热添加同样需要启动时的规划。例如为 x86 虚拟机配置 2 个启动 vCPU、最大 4 个槽位，拓扑须能容纳最大数量。管理程序通过 query-hotpluggable-cpus 查询可用位置，再用 device_add 创建相应 CPU；支持的型号、属性和拔出粒度由机器与体系结构决定。

QEMU 建立 CPU 对象、宿主 vCPU 线程和 KVM vCPU，通过 ACPI CPU 热插拔事件通知 Guest。Guest 发现处理器后建立每 CPU 数据、调度与中断状态，执行启动流程并将其置为 online，才会把普通任务调度给它。QEMU 中多了一个 vCPU 对象，不等于客户机已经在使用它。

热移除先请求客户机停用目标 CPU。Guest 迁走可迁移的任务、定时器与中断处理，将 CPU offline，再按 ACPI _EJ0 交还资源。QEMU 完成虚拟 CPU 拔出后发出 DEVICE_DELETED；线程和内核资源的释放由实现管理。本文的 x86 PC 路径不支持拔出启动处理器 BSP，客户机和拓扑也可能限制可移除对象。

只在 Guest 中把 CPU offline，是调度与处理器在线状态的变更，QEMU 仍可能保留该 CPU 对象。检查时分别比较 QMP query-cpus-fast、Guest 的 /sys/devices/system/cpu/online 以及持久配置。命令、ACPI 寄存器和完成条件见 x86 vCPU 热插拔专篇。

内存热添加：建立 DIMM，再由客户机上线

以支持 ACPI 内存热插拔的 x86 虚拟机为例，启动时预留内存插槽和可扩展的地址空间。运行中增加一条 2 GiB 虚拟 DIMM，管理程序先准备宿主内存后备，再添加 QEMU 的 pc-dimm 设备；QEMU 通过 ACPI 通知客户机出现新的内存区域。

Guest Linux 分两步接纳这段内存：先添加内存块及其管理元数据，再将内存块置为 online，交给页分配器使用。上线可由配置的策略自动完成，也可由客户机用户空间触发。QEMU 中设备已存在和客户机已能分配这些页面，是两个需要分别观察的状态。

内存热移除：下线页面，再完成设备拔出

移除同一条 DIMM 时，管理程序发起 device_del，QEMU 通过 ACPI 请求客户机 eject。Guest Linux 先将对应内存块置为 offline：迁移仍被使用的页面，并从页分配器撤下该范围。不可迁移页或长期固定的页面可能使下线失败，此时内存设备应继续保留。

客户机成功停用该区域后，通过 ACPI _EJ0 完成拔出交接，QEMU 随后移除 DIMM 并发布 DEVICE_DELETED。独立的内存后备对象要等引用解除后再清理。检查时，用 QMP query-memory-devices 观察设备，用 Guest 中的 lsmem 观察内存块及其在线状态，再核对客户机可用内存与宿主 RSS；这些指标描述的是不同层次。

下表把网卡、vCPU 与内存放回相同的交接顺序。各类资源都先通知客户机，但客户机的停用工作和管理层应核对的结果不同；内存还应分别观察设备提供容量、客户机在线容量和宿主 RSS。

从整设备增删到细粒度资源调整

设备与内存沿着各自的协议发展。前者侧重插槽发现、地址空间与驱动生命周期，后者侧重可调整容量、页面迁移与回收粒度。

传统 PCI 热插拔可以借助 ACPI 事件通知操作系统；PCIe 原生热插拔使用 Root Port 等端口的插槽寄存器与事件机制，客户机在获得相应控制权后由 PCIe 热插拔驱动处理。两者对应不同的机器配置与控制方式，不能假定所有虚拟机都走相同通知路径。资源预留帮助新增设备获得地址空间，但端口、总线号和 BAR 窗口仍有边界。

DIMM 方式按内存设备增删；virtio-mem 是另一种在线调整方式，在设备区域内按较小的块提供或收回容量。两者都需要与客户机内存管理协作，调整粒度和通知协议各有不同。评价热插拔要记录操作完成时间、客户机停顿与失败原因，并检查页面能否迁移。

内存调整方式宿主资源回收方式主要限制

用完成状态和业务影响判断操作结果

超时后先查询 QEMU 对象和客户机资源状态，再决定是否重试。操作可能仍在等待客户机；重复提交无法替代尚未到达的完成事件。

内存缩容还应观察页面迁移耗时、不可迁移页和客户机延迟。更细的回收粒度能避开部分忙页，代价是维护更多块状态；更大的地址空间预留方便后续扩容，也会占用有限的桥窗口或拓扑资源。方案选择应结合实际扩容上限和可接受的回收等待。
