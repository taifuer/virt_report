前言

启动一台 QEMU 虚拟机，需要先确定机器布局和 CPU 能力，建立内存与设备，再把初始处理器状态交给执行后端。QEMU 进程、vCPU 线程、客户机固件和操作系统分别有自己的启动时刻；进程已经存在，不代表客户机已经执行了指令。

本文以 x86 的 pc-q35-10.2、KVM 加速、普通 RAM 和 BIOS 冷启动为例，从命令行跟踪到启动处理器执行固件。重点是初始化顺序和对象之间的依赖，后续执行循环见KVM vCPU 执行与 I/O 退出。

一个暂停启动的配置

下面的命令创建 2 个 vCPU、4 GiB 内存的 Q35 虚拟机，并通过 -S 停在客户机执行之前。示例不配置启动盘，便于单独观察机器创建和固件入口；它不会引导一个已安装的操作系统。

qemu-system-x86_64 \
  -machine pc-q35-10.2,accel=kvm \
  -cpu host -smp 2 -m 4G \
  -nodefaults -display none -S \
  -qmp unix:/tmp/virt-startup-qmp.sock,server=on,wait=off

-machine 选择芯片组、总线和兼容属性；-cpu 决定客户机可见的处理器能力；-smp 描述启动 CPU 数量与拓扑。-m 配置的是客户机 RAM 容量，既不表示所有宿主物理页已分配，也不表示 EPT 已全部建好。-nodefaults 省去默认外设，不会取消 Q35 的核心芯片组和 CPU。

连接 QMP 后，先完成能力协商，再查询或继续执行：

{"execute":"qmp_capabilities"}
{"execute":"query-status"}
{"execute":"query-cpus-fast"}
{"execute":"cont"}

正常冷启动的 -S 配置在 cont 前处于 prelaunch，running 为 false。此时 query-cpus-fast 已能返回 vCPU 的宿主线程信息。QMP 的 RESUME 事件表示开始恢复执行，不代表固件初始化、磁盘引导或客户机服务已经完成。

这些对象的生命周期互相关联，但创建动作不同。object_new() 分配并初始化 QOM 对象；qdev_realize() 检查属性、连接总线并完成设备可用化；KVM_CREATE_VM 和 KVM_CREATE_VCPU 则建立内核对象。一个 CPU 对象经过 realize 才会创建执行线程。对象与设备的关系见QEMU 对象模型与设备初始化。

源码中的 created 表示 vCPU 线程初始化握手完成，stopped 表示 QEMU 主动停止它执行客户机。两者可以同时为 true。客户机执行 HLT 后的 halted 又是另一种处理器状态，不能拿来代替管理侧暂停。

从参数解析到板级初始化

main() 进入 qemu_init()。后者解析参数、初始化主循环基础设施，选定机器类型并创建 MachineState；机器属性设置完成后，才配置 accelerator。KVM 的初始化需要读取 irqchip 等机器属性，所以这两步有明确的先后关系。

kvm_init() 打开 /dev/kvm，检查 API 版本与能力，调用 KVM_CREATE_VM 获取 vmfd，初始化架构相关功能与中断控制器，并注册内存监听器。此时已经有 KVM 虚拟机容器，客户机 RAM 和板级设备尚未全部挂入地址空间。

随后 QEMU 建立后端、解析 CPU 型号与 NUMA 配置。machine_run_board_init() 准备 RAM 后端，调用机器类的 init。对于本例，pc_q35_init() 先计算低端和高端 RAM 容量，再调用 x86_cpus_init() 创建 CPU，然后通过 pc_memory_init() 布置内存、加载固件，继续创建 PCIe 根总线、ICH9 等板级设备。命令行 -device 指定的附加设备在板级初始化之后创建。

因此，不能将启动过程概括成“全部设备创建完，再统一创建 vCPU”。本路径在 CPU 初始化期间已经有 vCPU 线程，但它们保持 stopped，仍可响应寄存器同步等内部工作。QEMU 用运行状态、线程条件变量和 BQL 协调初始化，防止客户机提前访问尚未完成的机器布局。

在示例的默认 Q35 布局中，4 GiB RAM 的后端被切成两个别名：前 2 GiB 映射在 4 GiB 以下，后 2 GiB 从 4 GiB 以上开始映射，为 PCI 等区域留出地址空间。低端地址中还会叠加固件和传统设备窗口，所以客户机物理地址空间不能简单理解为从 0 连续铺满 4 GiB。

内存区域加入 AddressSpace 后，KVM 的监听回调把合适的 RAM 区域转成内存槽，登记 GPA 范围与 QEMU 用户态地址。这个步骤提供地址转换的基础，EPT 的实际叶子映射通常在客户机访问时逐步建立；详见KVM 内存映射与 EPT 缺页处理。

vCPU 线程与内核接口的建立

x86_cpus_init() 按拓扑计算 APIC ID，为每个启动 CPU 创建 X86CPU 并 realize。x86_cpu_realizefn() 验证 CPU 特性，准备 APIC，进入 qemu_init_vcpu()。该函数先设 cpu->stopped = true，再通过 accelerator 的 create_vcpu_thread 回调创建线程。

{{ diagram('qemu-startup-vcpu', 'vCPU 创建握手与首次执行', 'KVM vCPU 和共享区由新线程建立；主线程等待 created 通知，再继续机器初始化。cont 之后，BSP 从复位向量开始，其他处理器等待启动事件。') }}

KVM 线程进入 kvm_vcpu_thread_fn()，获取 BQL，在自己的线程上下文中调用 kvm_init_vcpu()：创建内核 vCPU，查询共享区长度，mmap 得到 kvm_run，再完成架构相关初始化。之后 cpu_thread_signal_created() 设置 created 并唤醒等待中的主线程。

/dev/kvm 的 fd
  ├─ KVM_CREATE_VM → KVMState.vmfd
  └─ KVM_GET_VCPU_MMAP_SIZE → 共享区长度

vmfd
  ├─ KVM_CREATE_VCPU(APIC ID 0) → CPU 0 的 kvm_fd
  └─ KVM_CREATE_VCPU(APIC ID 1) → CPU 1 的 kvm_fd

每个 kvm_fd
  ├─ mmap → 各自的 kvm_run
  └─ KVM_RUN → 运行或处理该 vCPU 的执行请求

默认的两核拓扑下，APIC ID 为 0 和 1；其他拓扑可以产生不连续的 APIC ID，不能总把它当成 cpu_index。两个 vCPU 共享一个 KVM 虚拟机的内存槽与机器资源，各自拥有独立 kvm_run 和寄存器状态。

线程的创建握手不包含客户机第一条指令。主线程等待 created 时会释放 BQL，使新线程可以完成初始化；它收到通知后继续设备创建。vCPU 线程通过 cpu_can_run() 检查 stopped 和整机运行状态，只在允许执行时进入 kvm_cpu_exec()。

复位、继续执行与固件入口

设备创建完成后，qdev_machine_creation_done() 同步 CPU 初始化状态，推进到 MACHINE_READY，发送机器初始化完成通知，登记 ROM 复位处理，再执行整机复位。x86 CPU 的复位回调建立起始寄存器和启动状态，后续通过 KVM 的寄存器同步接口写入内核 vCPU。

普通 BIOS 冷启动时，启动处理器 BSP 的 CS selector 为 0xf000，CS 隐藏基址为 0xffff0000，EIP 为 0xfff0，得到复位取指地址 0xfffffff0。这里要使用 CS 的隐藏基址计算，不能用实模式常见的 selector × 16 公式把它算成 0xffff0。固件随后跳转并完成平台初始化。

客户机开始执行从复位向量取指等待客户机的 INIT / SIPI 启动序列，随后从指定入口执行

qmp_cont() 完成状态检查后调用 vm_start，后者更新运行状态、通知后端、恢复虚拟时钟并唤醒 vCPU。KVM_RUN 最终让 BSP 进入客户机。AP 的宿主线程也可以进入内核等待启动事件，因此看到两个线程或两次 ioctl 入口，不等于两个客户机 CPU 都在执行固件指令。

不指定 -S 时，普通冷启动会在初始化结束路径中自动调用 cont。-incoming 则先恢复迁移状态，-loadvm 先恢复快照；这些路径的第一条客户机指令可能是恢复点，而非复位向量。直接加载内核也会改变引导准备过程，需要另外跟踪所选机器的内核装载代码。

启动阶段拆分与配置边界

自动启动适合直接运行虚拟机，管理程序则需要在客户机运行前检查拓扑、设置资源策略或等待迁移。-S 提供了“机器已经完成初始化、客户机尚未执行”的控制点。此时内存和 CPU 拓扑已经落地，不能再把启动参数当成任意可改的配置表。

2018 年引入的 preconfig 模式 把控制点前移到板级初始化之前，让管理程序可以先查询允许的配置，再通过 QMP 设置 NUMA 等信息。在本文版本中，它仍是实验接口，只有标记允许的命令可用；x-exit-preconfig 才会继续创建板级设备。它也已经完成一部分前置初始化，不能理解为 QEMU 尚未创建任何对象。

控制点解决的问题约束
preconfig在板级创建前补充允许的机器配置QMP 命令集合受限，退出后不能回到此前的配置阶段
-S / prelaunch机器创建完成后检查状态，再决定何时执行已确定的启动拓扑不再通过普通配置命令重建
运行时暂停检查或保存已有执行状态设备异步工作、I/O 收尾和线程同步仍需协调

另一条演进线是机器类型版本化。q35 别名指向当前默认版本；pc-q35-10.2 固定相应机器兼容设置，使软件升级时能够继续选择既有虚拟硬件接口。CPU 能力、设备属性和固件也会影响客户机可见行为，所以单独固定机器名不能保证任意两台宿主都能迁移。-cpu host 暴露宿主能力，跨宿主兼容需求通常还需要单独约束 CPU 模型。

分析启动耗时时，也应沿这些边界分别计量：QEMU 参数与对象初始化、内存后端准备、设备 realize、固件执行、内核引导和服务就绪。预分配内存可能把首次访问成本移到启动阶段；减少外设能缩短设备枚举，但不直接消除客户机服务的启动时间。仅比较进程创建到 QMP 可连接的间隔，会漏掉后面的主要工作。
