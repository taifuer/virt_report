在线增删设备为什么需要客户机配合

运行中的虚拟机增加一块网卡，需要 QEMU 创建设备、插槽报告变化、客户机枚举资源并绑定驱动。移除时则需要先停止客户机对设备的使用，再撤销模型和后端关联。这些动作分属管理程序、设备模型和客户机操作系统，完成时间也不同。

本文以 q35 上预先创建的 PCIe Root Port 和一块现代 virtio-net-pci 网卡为例，分析 PCIe 原生热插拔。客户机通过 PCIe 插槽寄存器与中断配合操作；ACPI 热插拔使用另一套通知和应答路径。

例子中的端口是 rp1，网卡是 net1，宿主网络后端是 n1。添加时按“预留插槽 → 创建后端和网卡 → 通知客户机 → 枚举并绑定驱动”推进；删除时先请求客户机停用，再拆除网卡，最后清理独立后端。QMP 命令受理只覆盖其中一个阶段，后文用完成事件把这条异步流程接起来。

插槽拓扑与资源预留

PCIe 原生热插拔控制器位于 Root Port 或 Downstream Port。网卡接在端口的下游总线上，端口自己的配置空间保存插槽状态。启动时直接放在 pcie.0 上的集成端点没有这套下游插槽交接；不能只给任意设备调用 device_del，就认为所有拓扑都有相同能力。PCIe 拓扑与热插拔规划

本例启动配置中的相关部分为：

-machine pc-q35-10.2,accel=kvm
-global ICH9-LPC.acpi-pci-hotplug-with-bridge-support=off
-device pcie-root-port,id=rp1,chassis=1,slot=1

第一行选择机器型号；第二行关闭本例的 ACPI PCI 热插拔控制，让客户机协商使用原生路径；第三行预留一个端口。当前 q35 也支持 ACPI 控制 PCI 热插拔，是否走本文路径需要同时看机器兼容属性、固件的 _OSC 协商和客户机驱动。ACPI 控制属性、原生控制权协商

空端口只解决拓扑位置。客户机还需要总线号、BAR 对应的 MMIO 窗口和中断资源。固件通常在启动时安排桥窗口，后续客户机能否重分配资源也受系统能力限制。QEMU 的 Root Port 提供 bus-reserve、mem-reserve、pref64-reserve 等资源预留属性；它们向固件描述需求，不代表插入后必然能得到资源。资源预留属性

添加 net1：创建、通知与客户机枚举

管理程序先创建网络后端，再把设备连接到它。以下是完成 QMP 握手后的请求示例，id 位于命令外层时用于匹配响应，位于 arguments 内时表示设备或后端标识。

{"execute":"netdev_add","arguments":{"type":"user","id":"n1"},"id":"backend-add"}
{"return":{},"id":"backend-add"}

{"execute":"device_add","arguments":{"driver":"virtio-net-pci","id":"net1",
 "bus":"rp1","netdev":"n1","disable-legacy":true},"id":"nic-add"}
{"return":{},"id":"nic-add"}

user 后端需要相应构建支持，示例选它以集中观察设备生命周期。实际发包的队列与后端处理见网卡模拟与 virtio-net 发包路径。

  1. 查类型和总线qdev_device_add_from_qdict() 查找设备类和 rp1 总线，检查类型、可用位置与迁移状态。
  2. 创建并设置属性qdev_new() 建立对象，设置 net1 标识及 netdev 等属性，再调用 qdev_realize()。
  3. 检查与初始化热插拔处理器执行 pre_plug；设备实现注册 BAR、队列和后端关联；框架完成后续初始化。
  4. 发布插槽变化端口 plug 回调置 PDS，并记录 PDC / ABP 等事件。满足使能条件后向客户机通知。
  5. 客户机配置设备客户机扫描下游总线、分配资源、绑定驱动并初始化 virtio 队列。

单功能端点的插入会让插槽报告存在；多功能设备还有 function 0 的可见性和添加顺序要求，不能直接把本例推广成每添加一个 function 都发同样通知。插入回调

device_add 成功表示 QEMU 已完成本次设备创建路径，客户机驱动仍可能尚未绑定，甚至因 BAR 资源不足而失败。反过来，设备创建报错时，前一步单独创建的 n1 后端也不会作为这条命令的事务自动回滚，需要管理程序按实际关联情况处理。QOM 的创建与 realize 关系见对象模型与设备初始化。

删除 net1：客户机停用与完成事件

对正在使用的网卡，管理程序首先发送移除请求。QEMU 找到 net1 后调用 qdev_unplug()，若处理器实现了 unplug_request，就交给它发起与客户机的交接。此时模型和后端关联可能仍然存在。

{"execute":"device_del","arguments":{"id":"net1"},"id":"nic-del"}
{"return":{},"id":"nic-del"}

稍后收到事件（这里省略 timestamp）：
{"event":"DEVICE_DELETED","data":{"device":"net1","path":"/machine/peripheral/net1"}}

确认设备已删除后，清理独立后端：
{"execute":"netdev_del","arguments":{"id":"n1"},"id":"backend-del"}

上面展示常见的先响应、后事件顺序。管理程序需要持续接收事件并按设备 ID 或 QOM 路径关联，不能假定它与命令响应的相对位置。删除请求的响应 ID 也不会变成 DEVICE_DELETED 的匹配字段。异步删除接口约定

{{ diagram('pcie-hotplug-removal', 'PCIe 原生热拔出的交接', '图示已上电、正在使用的单功能端点。QMP 返回只表示请求已受理；客户机停用设备并关闭插槽后，QEMU 才执行拆除，完成后再报告 DEVICE_DELETED。') }}

原生插槽回调先检查热插拔能力和锁定状态，再设置删除标记，并模拟注意按钮事件。客户机热插拔驱动处理请求，协调设备驱动停用、释放资源，并改变插槽控制寄存器。QEMU 在检测到有设备的插槽从未关闭状态切换到 PCC = off 且 PIC = off 时，调用 pcie_cap_slot_do_unplug()。已经关闭的插槽和部分尚未向客户机暴露的设备存在直接拆除分支。请求回调、关闭插槽后的拆除

实际拆除依次调用处理器的 unplug、qdev_unrealize() 和 object_unparent()。unrealize 停止设备实现并撤销其资源；unparent 解除对象树及总线关系；对象引用释放到零后才进入 finalize。device_finalize() 检查删除标记并发送 DEVICE_DELETED，不能把“realized 已变 false”当作对象内存已经释放。拆除端点、最终事件与父子关系清理

端口模型按插槽处理下游设备，多功能设备可能一起被移除。本文使用单功能网卡；生产管理层需要按实际插槽与功能关系决定操作范围，不能只看一个 QMP ID。

控制方式与管理接口的演进

PCI / PCIe 热插拔的控制方式与所用机器和桥类型有关。ACPI 通过固件描述、通知及 eject 方法组织交接；PCIe 原生路径把插槽能力、事件和电源控制放在端口标准寄存器中，由客户机的 PCIe 热插拔驱动处理。两种路径长期并存，不能简单按“新旧 QEMU”划分。

2017 年 QEMU 引入通用 PCIe Root Port，将端口能力与特定芯片模型解耦；随后增加资源预留能力，帮助固件为后续设备分配空间。统一端口模型简化了拓扑组织，但总线号、桥窗口和客户机支持仍需规划。

管理接口也逐步把“发起”和“完成”分开：QMP 的 device_del 从 0.14 提供，DEVICE_DELETED 从 1.5 提供，DEVICE_UNPLUG_GUEST_ERROR 从 6.2 提供。完成事件让管理程序能够安排 ID 复用及后端清理；代价是需要维护异步状态、处理连接中断，并区分可检测错误和无响应。版本标注见 QAPI 定义。
