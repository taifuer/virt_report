设备如何复用行为并独立保存状态

QEMU 用 C 语言实现大量设备模型。每种设备既有独立的寄存器、队列和配置，又需要复用总线、复位、迁移与热插拔框架。QEMU Object Model（QOM）提供类型、继承、属性和对象生命周期；qdev 在其上增加设备与总线的组织规则。

本文以 virtio-net-pci 为例，跟踪类型注册、对象创建、属性配置和设备实现（realize）。外层 PCI 设备与内部 virtio 网络设备共同完成一次创建过程，可以据此分清类继承、对象组合以及总线连接的关系。

例如创建两块 virtio-net-pci 网卡：两者复用同一套 PCI 和 virtio 类方法，却各有队列、MAC 地址及后端。创建其中一块的主线是“查找类型 → 初始化实例 → 设置属性 → 接入总线并 realize”；失败清理再沿资源归属返回。后面的类型表、对象树和回调链都围绕这条创建路径展开。

TypeInfo、类方法与实例内存

TypeInfo 是注册时的类型描述。QOM 把它转成内部 TypeImpl，以类型名为键保存。类对象按需初始化，每个类型共享一份；设备实例各自分配状态，通过 Object.class 指向所属类。创建两块同型号网卡时，队列与寄存器各有一份，实现这些操作的类方法则可以共用。

结构关键字段用途
TypeInfoname、parent、instance_size、class_size、初始化与析构回调描述类型名、父类型、内存布局及生命周期入口
TypeImplparent_type、class、实例大小与回调缓存解析后的父类型与类对象，供类型查找和实例创建使用
ObjectClasstype、interfaces、properties、unparent类级类型信息、接口和属性描述；设备派生类继续增加方法
Objectclass、ref、parent、properties、free单个对象的类指针、引用计数、组合树父节点及释放方式
DeviceClass / DeviceState类：realize、unrealize、vmsd；实例：realized、parent_bus、child_bus设备行为与迁移描述由类提供，设备当前状态和总线连接由实例保存

定义见 Object 与 ObjectClass、TypeInfo、TypeImpl 和 设备类与实例。QOM 支持单继承和多个无实例状态的接口；接口用于声明一组能力，实际状态仍保存在实现它的对象中。

派生实例把父结构放在首成员，例如 DeviceState.parent_obj 是 Object。因此从派生实例向基类转换时，内存起点一致。DEVICE(obj) 等转换同时表达预期类型；它们不会新建另一个设备对象。

注册类型并继承初始化方法

type_register_static() 把描述加入类型表，此时不必分配每种类型的类对象。首次需要类时，type_initialize() 分配本类型的类结构，确保父类已经初始化，再把父类结构复制到子类前部，最后执行本类型的 class_init。函数指针由此继承；子类可以覆盖其中一部分。类型注册、类初始化

复制父类方法不代表调用时会自动执行整条继承链。覆盖一个方法后，若还需要父类操作，子类必须保存并显式调用父方法。virtio_pci_class_init() 就用 device_class_set_parent_realize() 保存原来的设备 realize，再安装自己的包装函数；包装函数设置 PCIe 能力后继续调用保存的方法。virtio PCI 的父方法调用

实例初始化的规则不同：object_init_with_type() 自动按父类到子类的顺序调用各级 instance_init，之后再执行同方向的 instance_post_init。新实例的状态内存先清零，属性默认值在初始化过程中建立；qdev 的 post-init 阶段还会应用机器兼容属性和全局属性。实例回调顺序、对象初始化、兼容属性

virtio-net-pci 的继承、组合与总线

virtio-net-pci 的类型链经过 virtio-net-pci-base、virtio-pci、pci-device、device，最终到 object。具体类型由 virtio_pci_types_register() 根据描述生成，包含通用、transitional 和 non-transitional 变体。网卡类型描述、类型生成

struct VirtIONetPCI {
    VirtIOPCIProxy parent_obj;  /* PCI 传输层：继承 */
    VirtIONet vdev;             /* 网络设备实例：组合 */
};

这里有两个独立的 QOM 对象。外层对象继承 PCI 传输层，嵌入的 vdev 另有自己的 Object、类指针和引用计数。virtio_instance_init_common() 把它初始化成 virtio-net-device，以 virtio-backend 为名称加入外层对象的组合树。嵌入结构的内存由外层一起分配，内部对象的初始化和生命周期仍由 QOM 管理。实例布局、内部对象初始化

QOM 的 Object.parent 和 qdev 的 DeviceState.parent_bus 可以不同。外层网卡可以放在机器的 peripheral 容器下，却接到某条 PCI 总线上；内部网络对象归外层所有，却接到外层创建的 virtio 总线上。前者组织对象的路径与所有权，后者决定总线操作、复位和设备连接关系。调试时，info qom-tree 与 info qtree 回答的是不同问题。

设置属性：从 vectors=5 到实例字段

属性包含名称、类型、读写回调和相关数据。qdev 的字段属性进一步记录结构偏移与类型处理函数，设置属性时先检查是否允许修改，再解析输入，最后写入对应实例字段。因此命令行字符串、QMP 输入和 C 调用可以进入同一套属性处理逻辑。

例如 virtio-net-pci,vectors=5 中，vectors 是一个 32 位无符号字段属性，目标字段为 VirtIOPCIProxy.nvectors。属性赋值保存数值；后续 realize 才据此建立传输层资源。其默认值是“未指定”，网卡 realize 会按队列对数量计算默认向量数，显式设置的 5 则保留下来。属性与默认值处理

外层对象还把内部网络设备的属性建立为别名，使用户能在同一个设备配置中设置网络功能。别名最终访问原对象的属性，不会创建第二份网络状态。bootindex 也显式指向内部设备的同名属性。别名建立

多数配置字段要求在 realize 前设置，避免运行中的资源规模与字段值脱节。qdev 的字段 setter 检查 realized_set_allowed，只有允许动态修改的类型才能越过该限制；自定义 QOM 属性则由各自的 setter 决定。realized 本身也是属性，它的写回调会执行生命周期操作，不能将所有属性都视作普通内存赋值。字段写入限制

realize 如何连接两层设备实现

qdev_new() 仅调用 QOM 创建对象，初始 realized=false。这一阶段建立局部状态、子对象与属性，不依赖用户已经填完全部配置。能够失败的资源连接、参数校验和设备启用集中在 realize 阶段，通过 Error ** 返回错误。对象已分配与设备已经接入虚拟机是两个时点。

qdev_realize(dev, bus, errp) 先关联父总线，再写 realized=true。device_set_realized() 执行可迁移性检查、必要的对象树挂接、热插拔 pre-plug、设备类 realize，随后处理监听器、VMState 注册、子总线与热插拔 plug，最后发布成功状态。中途失败不会把 dev->realized 留为 true。入口、框架顺序

失败回滚与对象释放

在 device_set_realized() 中，dc->realize() 自身返回错误时直接进入 fail 分支，不会自动调用 dc->unrealize()。这个回调可能只完成一半初始化，其内部及它调用的各层必须清理各自已取得的资源。若设备回调已经成功，随后 VMState 注册、子总线或 plug 阶段失败，框架才走对应的回滚路径，调用 unrealize 并撤销已完成的注册。失败位置、回滚分支

unrealize 撤销设备的工作状态，unparent 拆除组合树关系，finalize 处理引用归零后的最终清理。正常设备 unparent 会先按需 unrealize、移除子总线并脱离父总线；随后组合树释放它持有的引用。其他持有者仍在时，对象内存继续存在。设备 unparent

操作引用与生命周期变化
object_new()返回一个调用者持有的初始引用
object_property_add_child()父对象新增一个对子对象的强引用；子对象只能有一个组合树父节点
object_initialize_child()初始化嵌入对象、添加 child，再释放临时初始引用；成功后由父节点持有
link 属性建立对象之间的关系；是否持有强引用取决于 OBJ_PROP_LINK_STRONG 等语义，不能仅按指针存在判断所有权
最后一次 object_unref()清理实例属性，按子类到父类执行 instance_finalize；独立分配的对象再调用 free 释放存储

引用计数负责生命周期，不会自动回收任意强引用环，也不会同步设备的普通状态访问。嵌入对象的存储跟随外层结构，不能保留一个指向其内部的引用却任由外层存储先释放。设备框架在拆除总线、清理 child 与 link 时必须共同维持这些约束。子对象引用交接、最终清理、child 释放

成功运行过的设备在 unrealize 时标记 pending_deleted_event，device_finalize() 再发出 DEVICE_DELETED。管理端发出删除命令、客户机接受拔除、设备停用和对象最终消失可能相隔一段时间；PCIe 的客户机协作过程见PCIe 设备热插拔。停用、删除事件

从 qdev 到统一对象模型

qdev 已经为设备配置提供了公共框架，但类型、属性和所有权问题同样存在于机器、内存后端等非设备对象。2012 年初合入的 Object 基类 引入通用对象基础；同年 属性从 qdev 下沉到 Object，让非设备对象也能使用属性与对象路径。设备管理继续由 qdev 负责，QOM 承担更底层的公共机制。

2013 年的 realized 属性改造 为设备实现引入明确的状态转换，最初通过兼容回调包装旧的 init 方法，再逐步迁移设备。把对象构造、用户配置与可失败的设备实现分开，便于查询属性、按配置组合设备，也让热插拔与错误处理有共同入口。

统一框架减少了重复的注册和管理代码，也增加了间接层：一个方法名可能对应多层类回调，一个对象路径未必就是它的总线拓扑，属性也可能是别名或带副作用的 setter。分析设备创建时，先确认具体类型和父类型，再区分实例初始化、属性写入与 realize，最后检查失败分支的资源归属，通常比单纯沿函数名跳转更容易找到完整路径。
