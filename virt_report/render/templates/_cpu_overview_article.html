客户机内核需要权限，宿主需要控制权

一段程序做整数加法，只需 CPU 按指令修改寄存器。操作系统内核还会切换页表、管理中断、访问设备。如果让虚拟机里的内核直接控制宿主的这些资源，它就可能覆盖宿主地址空间，或影响其他虚拟机；若把它简单当作普通用户程序运行，原本合法的内核操作又会因权限不足而失败。

CPU 虚拟化需要建立一套客户机可见的 CPU 状态：寄存器、指令位置、特权状态和异常行为都应符合客户机架构，同时真实资源仍由宿主控制。一个 vCPU 表示这套执行上下文，物理 CPU 则在调度时实际执行它。两者并不要求一对一独占。

本文以 x86 系统虚拟化为主，比较软件执行与硬件辅助的解决办法，再跟踪一段小程序，看普通计算、能力查询、设备访问和空闲分别在哪里完成。

解释执行：逐条读懂并实现指令

最直接的方案是取出客户机指令，解码，再用宿主程序更新模拟寄存器和内存。例如客户机加法由解释器完成运算并更新客户机标志位；客户机修改页表基址，也只修改模拟状态。访问都经过软件控制，便于隔离和跨架构实现，但热点循环每次都要重新取指、解码和分派，管理成本很高。

TCG：把重复解码变为可复用代码

QEMU 的 Tiny Code Generator（TCG）将一段客户机指令翻译为中间表示，再生成宿主机器码，缓存为 Translation Block（TB，翻译块）。普通运算成为宿主代码，复杂操作调用实现相应语义的 helper。下一次进入相同代码和匹配的 CPU 状态时，可以复用 TB；满足条件的块还能直接连接，减少返回主循环查找的次数。

翻译要付出首次生成和缓存管理成本。客户机修改代码后，旧 TB 必须失效；中途发生异常时，还需恢复准确的客户机指令位置。TCG 因而适合不同指令集之间的执行、开发调试及缺少硬件辅助的环境，它与 KVM 在当前 QEMU 中并存。TB 状态匹配与直接连接

硬件辅助：保留客户机权限，分开宿主控制

Intel VT-x、AMD-V 提供受宿主配置控制的客户机执行环境。客户机内核仍可处于自己的高权限级；处理器按虚拟化控制决定哪些行为直接完成，哪些触发 VM exit（客户机退出），把控制权交回宿主。客户机从应用进入自身内核，与离开客户机环境进入宿主，是两类不同切换。

以 Intel VT-x 为例，VMX root / non-root 区分宿主与客户机执行环境，ring 0 / ring 3 区分各自环境内的权限级。这是两个维度：

权限级VMX root：宿主环境VMX non-root：客户机环境
ring 3QEMU 等宿主用户程序客户机应用
ring 0Linux 内核与 KVM客户机操作系统内核

客户机应用执行系统调用，可以在 non-root 内进入自己的 ring 0；是否同时触发退出取决于配置和具体执行事件。VM exit 则把控制权交给宿主内核。客户机 ring 0 的权限只适用于它的执行环境，不允许它自行改写宿主配置的虚拟化控制。

VMCS（虚拟机控制结构）使这条边界可以配置：客户机状态区域保存 RIP、RSP、控制寄存器和段状态等；宿主状态区域指定退出后的 RIP、RSP、CR3 等；执行控制指定中断窗口、指令拦截及其他条件。进入时恢复所需客户机状态，退出时保存相应状态并装入宿主执行环境。它并不自动保存所有通用寄存器，KVM 的进入/退出汇编仍参与现场交接。AMD 的 VMCB 提供相应的状态与控制机制，字段和执行细节另有定义。KVM VMX 进入与退出汇编、Intel SDM：VMCS 与 VMX transitions

KVM 在 Linux 内核中建立并维护这个执行环境，QEMU 的 vCPU 线程通过 KVM_RUN 进入它。硬件退出后，KVM 能处理的事件在内核中完成，再次进入客户机；只有需要用户态设备模型或管理参与的情况才返回 QEMU。因此 VM exit 次数与 KVM_RUN 返回次数通常不同。

四个操作怎样保持连续执行

假设客户机先计算 3 + 4，查询 CPUID，再读取一个由 QEMU 模拟的设备寄存器，最后执行 HLT 等待工作。设备应返回 0x12345678。这四步对应四种成本：

  1. 计算。TCG 运行已翻译的宿主加法及标志更新；KVM 路径通常直接执行客户机指令，结果都是 7。
  2. CPUID。TCG 按虚拟 CPU 配置模拟结果。在 Intel VMX 路径中，CPUID 触发退出，由 KVM 填入客户机应看到的能力并推进执行，通常无需返回 QEMU。
  3. 设备读取。KVM 以 KVM_EXIT_MMIO 返回地址、长度和方向。QEMU 调用设备模型，将结果写入 kvm_run.mmio；下一次 KVM_RUN 才完成该次读取的交接。TCG 的访存辅助路径直接分派到相应设备模型。
  4. 等待。在常见内核管理的 KVM 路径中，HLT 可进入短暂轮询或阻塞。事件到来后唤醒 vCPU 线程，宿主调度器决定它何时重新取得 CPU。

这条路径说明，接近原生的指令执行速度仍可能被高频设备往返或调度等待拖慢。QEMU 的 KVM 执行循环把用户态需要处理的原因分开，但无法只凭退出总数判断具体瓶颈。

演进围绕重复工作、退出和并行展开

动态翻译把逐条解释中的重复工作移到首次翻译，后续通过缓存与块连接降低分派成本。硬件辅助让兼容架构的指令直接执行，并把权限隔离交给明确的硬件边界。两条路线解决的条件不同：跨架构执行仍需要翻译，硬件辅助也仍需要设备模型和异常处理。

继续优化时，TCG 用多线程执行不同 vCPU，需要同时维护客户机内存顺序、共享设备锁和翻译失效。KVM 则可用共享队列与事件通知减少设备往返，或由硬件加速部分中断处理。这些改进把工作移动到不同层次，无法消除后端处理与状态同步。

虚拟 CPU 型号还有兼容性取舍。向客户机暴露更多宿主特性，可能改善本机计算性能，却减少能接收该虚拟机的迁移目标。固定兼容的 CPU 能力集合有利于跨宿主调度，代价是不能使用其中较新机器的全部能力。

按执行成本评价方案

主要成本改进着力点需要一起检查的代价
取指、解码与翻译复用 TB、连接热块，条件允许时采用 KVM代码失效、首次执行成本与架构兼容性
设备访问和频繁退出批处理、virtio 队列、内核或独立后端后端 CPU、通知延迟与设备状态协调
空闲与唤醒等待平衡短暂轮询和阻塞，调整调度与 CPU 放置尾延迟、物理 CPU 占用与其他虚拟机的公平性

更多 vCPU 不保证更快：程序需要可并行，宿主也要提供足够运行时间。实际评价应同时记录业务吞吐、尾延迟和宿主 CPU 消耗，再把等待拆为客户机内部锁、硬件退出处理、用户态 I/O 和宿主调度。这样才能把优化对应到具体的一段执行过程。

进一步阅读

  • QEMU TCG 的翻译块与执行循环：首次翻译、热块连接与代码失效。
  • KVM vCPU 执行与退出处理：CPUID、MMIO 及 ioeventfd/irqfd 两个方向。
  • KVM vCPU 的阻塞、轮询与唤醒：短等待延迟与 CPU 成本。
  • 虚拟 CPU 模型与迁移兼容性：能力暴露、运行状态与目标主机检查。
  • vCPU 与 NUMA 内存放置：线程、物理页及后端的局部性。
  • KVM 虚拟时钟与定时器：TSC、共享时钟页、到期通知与迁移后的时间衔接。
  • 中断虚拟化：设备事件如何进入客户机。
