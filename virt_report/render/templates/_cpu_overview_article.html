CPU 虚拟化的执行环境与权限边界

CPU 虚拟化为客户机提供独立的处理器状态和指令执行环境，同时保留宿主对真实资源的控制。一段程序做整数加法，只需 CPU 按指令修改寄存器；操作系统内核还会切换页表、管理中断、访问设备。如果让客户机内核直接控制宿主的这些资源，它就可能覆盖宿主地址空间，或影响其他虚拟机；若把它简单当作普通用户程序运行，原本合法的内核操作又会因权限不足而失败。

一个 vCPU 表示客户机可见的一套寄存器、指令位置、特权状态和异常行为；物理 CPU 则在调度时实际执行它。客户机可以看见 4 个 vCPU，宿主仍能把这 4 个执行线程与其他任务共享调度。指令语义、资源隔离和执行机会因此是三个要分别解决的问题。

本文以 x86 系统虚拟化为主，比较软件执行与硬件辅助的实现，再跟踪一段程序中的普通计算、能力查询、设备访问和空闲操作，说明它们的处理位置与开销。

解释执行：逐条读懂并实现指令

最直接的方案是取出客户机指令，解码，再用宿主程序更新模拟寄存器和内存。例如客户机加法由解释器完成运算并更新客户机标志位；客户机修改页表基址，也只修改模拟状态。访问都经过软件控制，便于隔离和跨架构实现，但热点循环每次都要重新取指、解码和分派，管理成本很高。

TCG：把重复解码变为可复用代码

QEMU 的 Tiny Code Generator（TCG）将一段客户机指令翻译为中间表示，再生成宿主机器码，缓存为 Translation Block（TB，翻译块）。普通运算成为宿主代码，复杂操作调用实现相应语义的 helper。下一次进入相同代码和匹配的 CPU 状态时，可以复用 TB；满足条件的块还能直接连接，减少返回主循环查找的次数。

翻译要付出首次生成和缓存管理成本。客户机修改代码后，旧 TB 必须失效；中途发生异常时，还需恢复准确的客户机指令位置。TCG 因而适合不同指令集之间的执行、开发调试及缺少硬件辅助的环境，它与 KVM 在当前 QEMU 中并存。TB 状态匹配与直接连接

硬件辅助：保留客户机权限，分开宿主控制

Intel VT-x、AMD-V 提供受宿主配置控制的客户机执行环境。客户机内核仍可处于自己的高权限级；处理器按虚拟化控制决定哪些行为直接完成，哪些触发 VM exit（客户机退出），把控制权交回宿主。客户机从应用进入自身内核，与离开客户机环境进入宿主，是两类不同切换。

以 Intel VT-x 为例，VMX root / non-root 区分宿主与客户机执行环境，ring 0 / ring 3 区分各自环境内的权限级。这是两个维度：

权限级VMX root：宿主环境VMX non-root：客户机环境
ring 3QEMU 等宿主用户程序客户机应用
ring 0Linux 内核与 KVM客户机操作系统内核

客户机应用执行系统调用，可以在 non-root 内进入自己的 ring 0；是否同时触发退出取决于配置和具体执行事件。VM exit 则把控制权交给宿主内核。客户机 ring 0 的权限只适用于它的执行环境，不允许它自行改写宿主配置的虚拟化控制。

{{ diagram('cpu-vmx-state-controls', 'VMCS 的状态区域与执行控制', 'VMCS 的客户机状态区域保存客户机执行现场，宿主状态区域提供退出后的执行环境，控制字段决定进入、退出以及需要拦截的操作。通用寄存器等未由硬件完整交接的状态仍需软件保存。') }}

VMCS（虚拟机控制结构）把这条边界具体化：客户机区域记录进入时的执行现场，宿主区域指定退出后的执行环境，控制字段决定哪些事件需要接管。硬件负责规定的状态交接，其余通用寄存器等仍由 KVM 保存。AMD 的 VMCB 承担相应职责。理解总流程时，可以先把它们看作“执行现场＋拦截规则”；具体交接见KVM 执行循环及进入与退出汇编。

KVM 在 Linux 内核中建立并维护这个执行环境，QEMU 的 vCPU 线程通过 KVM_RUN 进入它。硬件退出后，KVM 能处理的事件在内核中完成，再次进入客户机；只有需要用户态设备模型或管理参与的情况才返回 QEMU。因此 VM exit 次数与 KVM_RUN 返回次数通常不同。

执行路径的差异

每个例子都可以沿三条边界判断：是否从客户机退出到 KVM，是否结束本次 KVM_RUN 返回 QEMU，以及宿主调度器是否切换了正在运行的线程。它们对应不同的状态和开销。

CPUID有，进入内核 CPUID 处理常规路径不需要KVM 写回虚拟 CPU 信息并推进 RIP

CPUID 的结果由虚拟 CPU 配置决定，KVM 在内核中完成查询。MMIO 示例需要设备模型提供读结果：第一次 KVM_RUN 返回请求，QEMU 填入数据，第二次进入内核才消费数据并完成指令。CPUID 处理与用户态 I/O 继续处理分别体现了这两种分工。

在 HLT 截获场景中，客户机已进入空闲，KVM 可以短暂轮询，也可以阻塞宿主线程；本例固定轮询预算为 0。后端事件到达后，线程先变为可运行，随后才有机会被调度。TASK_RUNNING 同时覆盖运行队列中的等待者和当前执行者，分析延迟时还要观察调度事件。

Idle Passthrough 与硬件等待

Idle Passthrough 通过关闭相关指令拦截，让 Guest 直接使用硬件等待。以 Intel VMX 为例，KVM 根据预先启用的 KVM_X86_DISABLE_EXITS_HLT 清除 HLT exiting，Guest HLT 进入 non-root 下的硬件等待，跳过 kvm_emulate_halt()、halt polling 和宿主 schedule()。处理器保持 Guest 执行环境，KVM 软件的 vCPU 状态仍可为 RUNNABLE。执行控制配置

直通选项固定采用另一宿主 CPU 发布的 posted interrupt：发送方运行 KVM 代码，目标 CPU 同步 PIR 并唤醒 Guest，不能把发送方的执行误认为目标 vCPU 退出。这里同时选用了两项独立条件：HLT 不截获，以及 APICv posted 交付。前者不保证所有唤醒都无退出；普通宿主 IRQ、定时器、抢占或配置变化仍可能要求退出。本例不插入这些额外事件，故目标 vCPU 的退出次数保持 0。

QEMU 的 -overcommit cpu-pm=on 可请求关闭受支持的相关退出，默认关闭，启用还受平台与安全策略限制。它主要适合绑定独占逻辑 CPU 的低延迟场景：Guest 空闲不会经常规阻塞路径主动归还 CPU，超卖共享时可能拖延其他线程，宿主 CPU 使用率统计也可能不计入 Guest 的硬件空闲。QEMU 的配置与取舍、KVM 能力限制

任务休眠与两层调度

定时休眠示例中，任务 A 请求等待 1 ms。Guest 内核创建 hrtimer_sleeper，登记到期回调，再把 A 交给调度器等待。如果任务 B 可以运行，Guest 就选择 B，vCPU 继续执行指令；没有其他可运行的普通任务时，Guest 进入 idle，本例通过 HLT 把等待机会交给 KVM。这样，同一个应用请求会对应两条不同的 vCPU 路径。

宿主抢占正在执行 B 的 vCPU仍在阻塞宿主线程仍为 TASK_RUNNING，等待物理 CPU；B 的执行暂时停下
A 休眠后只有 Guest idle仍在阻塞HLT 使 vCPU 进入 HALTED；KVM 发布等待者后，宿主线程才睡眠
宿主定时器到期并唤醒线程Guest 尚未处理到期回调宿主线程进入运行队列，仍需获得 CPU 才能继续处理虚拟中断

Guest 调度器选择客户机任务，宿主调度器选择包括 vCPU 线程在内的宿主任务。这两个选择可以独立发生。正在运行 B 的 vCPU 被宿主抢占时，Guest 不需要执行一次 A、B 之间的切换；反过来，Guest 从 A 切到 B，也不要求宿主更换 vCPU 线程。演示分别显示任务状态、当前执行者与宿主执行上下文，保留这两层关系。

从定时到期到应用继续执行

两个示例使用 Guest TSC-deadline clockevent 和 KVM 的宿主软件 hrtimer 分支。Guest 选定下一次时钟事件 D，KVM 将虚拟 LAPIC 的 deadline 转为宿主定时器。宿主回调到期后，先增加 lapic_timer.pending 并请求唤醒；vCPU 执行循环随后把事件提交给虚拟 LAPIC。客户机接受定时中断、运行自己的 hrtimer 队列后，hrtimer_wakeup() 才清除 sleeper 中的任务指针并唤醒 A。宿主定时器与 pending 标记、Guest 到期回调对应这两端的处理。

在 HLT 场景中，宿主线程被唤醒后，mp_state 仍可暂时为 HALTED。线程先恢复 KVM 执行，把待处理定时事件转为 LAPIC 中断，再由运行循环检查可接受事件、恢复 RUNNABLE。接着才是 Guest 中断处理、A 进入 Guest 运行队列以及 A 获得 CPU 开始执行。演示把这些阶段分开，便于区分“到期”“可运行”和“正在执行”。

1 ms 是应用提交的休眠时长。实际 clockevent D 还受 Guest 当前时间、timer slack 和定时器安排影响；D 之后，宿主运行队列等待、虚拟中断递送和 Guest 调度还可能继续增加返回延迟。本例不加入信号打断，最终返回值为 0。播放速度只控制讲解节奏，不模拟这些延迟的实际长度。

代码复用、退出处理与并行执行的演进

动态翻译把逐条解释中的重复工作移到首次翻译，后续通过缓存与块连接降低分派成本。硬件辅助让兼容架构的指令直接执行，并把权限隔离交给明确的硬件边界。两条路线解决的条件不同：跨架构执行仍需要翻译，硬件辅助也仍需要设备模型和异常处理。

继续优化时，TCG 用多线程执行不同 vCPU，需要同时维护客户机内存顺序、共享设备锁和翻译失效。KVM 则可用共享队列与事件通知减少设备往返，或由硬件加速部分中断处理。这些改进把工作移动到不同层次，无法消除后端处理与状态同步。

虚拟 CPU 型号还有兼容性取舍。向客户机暴露更多宿主特性，可能改善本机计算性能，却减少能接收该虚拟机的迁移目标。固定兼容的 CPU 能力集合有利于跨宿主调度，代价是不能使用其中较新机器的全部能力。

扩展 vCPU 数量的效果取决于业务并行度与宿主可提供的运行时间。客户机内观察任务和锁等待，宿主侧观察 vCPU 线程调度、KVM 退出及设备后端；两侧数据对应同一段业务负载后，再比较吞吐、尾延迟和 CPU 消耗。客户机中的 CPU 利用率反映其自身调度视图，宿主线程消耗还可能包含设备处理和轮询。

多 vCPU 协同：从固件启动到应用并行进一步串起 CPU 拓扑发现、辅助处理器启动、跨核同步以及 Guest 与宿主两层调度。
