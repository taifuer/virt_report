一次写入何时可以归还缓冲区

virtio-blk 用一条描述符链表达一次块设备请求。客户机驱动提交命令和数据缓冲区，QEMU 将请求交给块层，在操作完成后写回状态、归还描述符。读写接口虽然简单，队列完成、宿主缓存和持久化却分别发生在不同位置。

本文使用 QEMU 10.2.0 的现代 virtio PCI 接口和 split virtqueue，跟踪向 raw 文件写入 4 KiB 的过程。设备采用 writeback 模式，客户机已协商 FLUSH；先看普通写完成，再看刷新如何建立持久化边界。队列的基本结构可结合描述符表、available ring 与 used ring阅读。

这次写入有两次需要分清的完成：OUT 成功后，设备已不再使用本次数据缓冲区，驱动可以回收；随后 FLUSH 成功，才满足这组写入要求的持久化边界。全文沿同一条 5 → 9 → 12 描述符链，从命令解析跟踪到 used 回写，再检查刷新和错误策略如何改变完成条件。

一次 4 KiB 写入的描述符链

假设队列大小为 16，本次使用描述符 5 → 9 → 12。请求写入磁盘字节偏移 1 MiB，故头部的 sector = 2048；4096 字节覆盖 2048 至 2055 共 8 个扇区。协议中的 sector 始终按 512 字节计数，设备报告的逻辑块大小不会改变这个单位；逻辑块大小仍决定请求的对齐要求。

描述符指向的客户机缓冲区长度与标志QEMU 的访问方向
5：请求头type = OUT、保留字段、sector = 204816 B；NEXT，next = 9读取命令与磁盘偏移
9：写入数据需要写入磁盘的 4096 字节4096 B；NEXT，next = 12读取客户机数据
12：状态驱动预留的 status 字节1 B；WRITE，无 NEXT写回 OK、IOERR 或 UNSUPP

WRITE表示设备可以写这个缓冲区。因此磁盘写请求的数据描述符不设 WRITE；磁盘读请求的数据描述符才设 WRITE。请求头始终由设备读取，末尾状态始终由设备写入。数据可以分布在多个描述符中，三个描述符只是本例的布局。

QEMU 的 virtio_blk_outhdr保留了 type / ioprio / sector三个字段名；现代协议将中间 32 位称为 reserved，本例置零。头部共 16 字节，多字节字段按小端编码。sector是磁盘位置，描述符的 addr则定位客户机内存，二者属于不同地址空间。请求头定义、范围与对齐检查

若提交前 avail.idx = 12，驱动把链头 5 写入 avail.ring[12]，按发布顺序更新 idx 为 13，再按通知条件 kick。available 项只保存链头编号，4096 字节数据仍在原缓冲区；该请求被归还前，驱动必须保留这些内存及其内容。

描述符如何转换为 VirtIOBlockReq

virtqueue_pop()解析并映射描述符，构造带有 VirtQueueElement的 VirtIOBlockReq。设备可读区域进入 out_sg，设备可写区域进入 in_sg。这里的 in / out 以客户机数据流向命名，阅读实现时需要同时检查操作类型和描述符权限。

结构或字段本例内容作用
elem链头编号，out_sg 和 in_sg保存队列元素及已映射的分散缓冲区
out / sector_num复制的 16 字节头；扇区 2048解析命令并计算磁盘偏移
qiov4096 字节数据的 iovec提交块层的数据视图，不含请求头和状态
in / in_len状态指针；本例为 1 B写回结果并确定 used 长度
vq / mr_next原队列；合并请求链把一次后端操作的结果分别归还给各个请求
MultiReqBuffer最多 32 个请求及读写方向暂存本轮队列处理中可合并的请求

virtio_blk_handle_request()先复制头部，从 out iovec 前端剥离这 16 字节；再定位最后一个 in iovec 的末尾状态字节，并将它从数据视图中剥离。OUT 使用剩余 out iovec，IN 使用剩余 in iovec。剥离操作有 undo 记录，完成时恢复原始视图，供通用 virtqueue 代码解除映射。请求结构、命令解析

构造 iovec 不要求先复制全部写入数据。不过下层的缓冲方式、对齐处理、镜像格式和宿主 I/O 接口仍可能产生复制，不能据此把整条路径称为零拷贝。

合并相邻请求并异步提交块后端

virtio_blk_handle_vq()连续提取可用请求，经过类型、长度、对齐和磁盘边界检查后，将读写请求暂存到 MultiReqBuffer。同方向的相邻磁盘区域可以合并，合并后的 iovec 数和传输长度必须满足后端限制；改变读写方向、达到批次上限或完成本轮消费时，暂存批次会被提交。

合并前，QEMU 按 sector 排序。例如本例的 2048—2055 和另一个请求的 2056—2063 可以组成 8 KiB 后端写入；两个客户机请求仍各自保有状态字节和完成记录。mr_next把它们串起来，后端回调再逐一处理。提交顺序和完成顺序因此不应当作客户机写入依赖的保证。合并与提交

virtio_blk_handle_vq()
  virtio_blk_get_request() → virtqueue_pop()
  virtio_blk_handle_request()
    读取 OUT 头，提取数据 iovec，校验范围
  virtio_blk_submit_multireq() → submit_requests()
    blk_aio_pwritev(blk, 2048 << 9, qiov, flags, callback, req)
      BlockBackend → 块节点 → 文件后端
        异步完成 → virtio_blk_rw_complete(req, ret)

BlockBackend提供设备访问入口；raw 文件示例继续经过格式节点和文件协议节点。qcow2 的地址映射与写时复制还会处理簇分配、映射与元数据，不能把客户机磁盘偏移直接当作镜像文件偏移。blk_aio_pwritev()接受完成回调，内部进入协程执行块操作；即使操作立即完成，也通过延后回调避免在提交尚未返回时归还请求。异步接口与回调安排

请求处理可以运行在配置的 IOThread 中。QEMU 10.2 使用逐队列的 vq_aio_context映射，多个队列可以分配给不同线程；队列数量、处理线程和后端的实际并发能力需分别观察。协程和线程的执行关系见《QEMU AioContext、协程与 IOThread》。

状态、used 项与完成通知

后端成功返回后，virtio_blk_rw_complete()遍历合并请求链，调用 virtio_blk_req_complete()。后者依次写状态、恢复 iovec、发布 used，再调用通知检查。客户机通过 used 找到原请求，读取 status，回收描述符和缓冲区。

本例的完成记录
  status = VIRTIO_BLK_S_OK = 0
  used.ring[7] = { id: 5, len: 1 }
  used.idx: 7 → 8

id = 原始描述符链头
len = 设备写入的缓冲区长度，本次只有 status 的 1 字节

4096 字节写入数据由设备读取，所以不会计入本例的 used 长度。相同大小的普通读请求，设备会写入 4096 字节数据和 1 字节状态，长度则为 4097。virtio_notify()还会检查通知条件，中断可以合并或抑制；驱动应按 used 消费完成，不能把一次中断等同于一个请求。完成发布、读写和刷新回调

写入完成与持久化

writeback 模式允许写请求在易失缓存中完成。对本例文件后端，数据可能已经复制到宿主页缓存，客户机即可复用缓冲区，但此时宿主断电仍可能丢失数据。绕过宿主页缓存也无法自动消除设备内部的易失写缓存。

客户机等待相关写请求成功后，提交 VIRTIO_BLK_T_FLUSH：type 为 4，sector 为 0，无数据载荷，只保留命令头和状态。QEMU 先提交当前批次尚未下发的写操作，再调用 blk_aio_flush()；块层沿存储图刷新，完成后才回报该 FLUSH。等待写完成再发 FLUSH 也使该边界不依赖队列间的处理先后。FLUSH 入口、VIRTIO 1.2 §5.2.6.2 写入稳定性约定

设置或操作影响需要注意
writeback允许普通写在易失缓存中完成需要客户机正确发出刷新，形成持久化边界
writethroughBlockBackend 给写请求加 BDRV_REQ_FUA块层按后端能力处理，必要时用刷新实现要求
cache.direct控制宿主页缓存的使用与是否忽略刷新、是否启用客户机写缓存是不同开关
cache.no-flush允许跳过对持久存储的强制刷新对应 unsafe 行为，破坏客户机依赖的掉电持久性

这些保证依赖存储链各层正确执行刷新；镜像格式元数据、文件系统、控制器及远端存储都可能参与。应用的 write()还可能只到客户机页缓存，文件系统的 fsync()也可能生成多次写入和刷新。因此本文的单个 virtio 请求只对应其中一个设备操作。写缓存与 FUA、块层刷新、缓存模式组合

错误处理与请求保留

磁盘越界或不满足对齐要求的请求可直接完成为 IOERR，后端执行错误则按照块设备错误策略处理。report 把失败返回客户机；stop 将请求放入设备的待重试链并触发相应暂停处理，恢复后再按队列重新提交；ignore 则可能把后端错误当作成功继续完成。

stop 路径没有提前发布 used，客户机仍不能回收该请求。QEMU 10.2 用 rq_lock保护设备级重试链，恢复时按 virtqueue 分组并调度到对应的 AioContext。排查“请求一直未完成”时，应同时查看客户机 used 进度、QEMU 的块错误事件与虚拟机状态，而不能只看是否收到过 kick。错误策略、恢复与重新提交

多队列与 IOThread 的收益和代价

virtio-blk 将命令、数据和完成组织为共享队列，减少了逐个模拟传统磁盘寄存器的工作。批量消费和相邻请求合并继续降低每次提交的开销，但共享队列和单线程处理也会成为高 IOPS 设备的瓶颈。多队列让客户机分散提交；IOThread 将处理工作从主事件循环中分离。

单个设备的多条队列若仍归同一 IOThread，宿主侧处理仍集中于一条线程。QEMU 引入 iothread-vq-mapping后，可按队列分配多个 IOThread；QEMU 10.2 的设备直接维护 vq_aio_context[]，块请求和重试路径也相应处理多线程访问。引入逐队列线程映射的提交、当前映射初始化

更多队列增加并发机会，也会带来线程调度、缓存竞争和 NUMA 访问成本；零散的小请求还可能降低合并机会。应结合客户机负载、请求深度、后端延迟和处理线程占用选择配置。性能比较尤其要保持缓存与刷新语义一致，否则降低持久化要求得到的延迟改善，无法说明队列路径本身变快了。
