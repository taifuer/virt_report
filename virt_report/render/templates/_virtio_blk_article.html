一次虚拟磁盘读写的处理层次

从虚机内的应用开始：程序对虚拟磁盘的块设备执行 pread(fd, buf, 4096, 1048576) 或 pwrite()，读取或写入偏移 1 MiB 处的 4 KiB 数据。设备已用 O_DIRECT 打开。在演示顶部选择设备接口、后端与读写操作，观察对应的系统调用、Guest 内核、共享队列、后端处理与 KVM 中断注入，直到结果返回应用。

为看清设备路径，本例不经过 Guest 文件系统与页缓存：缓冲区已按 4 KiB 对齐，固定为一个页面、一个 bio 和一个块请求 R1，不发生拆分、合并或错误。Guest 内核固定用户页并建立 I/O 映射；读取时后端填充这份内存，写入时后端读取其内容，各层通过映射访问同一份缓冲区。普通文件读写的差异见后文。

共同前提是 x86 / KVM、modern virtio PCI 与 split ring；队列大小为 8，本次使用 3 个直接描述符，未启用 Guest vIOMMU。不同后端采用各自的执行上下文、通知与完成路径；具体配置随选择一起更新。本地文件可能命中宿主页缓存，SPDK 场景固定为轮询与 NVMe 后端，Ceph 展示到 QEMU / librbd 的异步接口边界，不展开集群内部协议。

演示从设备已就绪开始。队列建立过程见设备初始化与特性协商，队列布局与索引更新见 Virtqueue：Split 与 Packed。

选择本地写入时可以进一步观察完成保证：写后 FLUSH 沿用应用起点，后续显式提交刷新 F1；FUA 则从已携带该要求的块请求 R1 开始，止于上层块请求完成，不推断应用的系统调用方式。

正文以 virtio-blk 的写请求解释结构和回调；演示同时提供 virtio-scsi、本地文件、RBD 与 SPDK 对照，各后端的配置与完成保证分别标注。

一次 4 KiB 写入的描述符链

假设队列大小为 16，本次使用描述符 5 → 9 → 12。请求写入磁盘字节偏移 1 MiB，故头部的 sector = 2048；4096 字节覆盖 2048 至 2055 共 8 个扇区。协议中的 sector 始终按 512 字节计数，设备报告的逻辑块大小不会改变这个单位；逻辑块大小仍决定请求的对齐要求。

描述符指向的客户机缓冲区长度与标志QEMU 的访问方向
5：请求头type = OUT、保留字段、sector = 204816 B；NEXT，next = 9读取命令与磁盘偏移
9：写入数据需要写入磁盘的 4096 字节4096 B；NEXT，next = 12读取客户机数据
12：状态驱动预留的 status 字节1 B；WRITE，无 NEXT写回 OK、IOERR 或 UNSUPP

WRITE表示设备可写客户机缓冲区：OUT 把客户机数据写到磁盘，设备读取数据；IN 把磁盘数据读到客户机，设备写入数据。请求头由设备读取，末尾 status 由设备写入。数据可以分布在多个描述符中，本例用一个数据描述符装下 4 KiB。

QEMU 的 virtio_blk_outhdr保留了 type / ioprio / sector三个字段名；现代协议将中间 32 位称为 reserved，本例置零。头部共 16 字节，多字节字段按小端编码。sector是磁盘位置，描述符的 addr则定位客户机内存，二者属于不同地址空间。请求头定义、范围与对齐检查

若提交前 avail.idx = 12，驱动把链头 5 写入 avail.ring[12]，按发布顺序更新 idx 为 13，再按通知条件 kick。available 项只保存链头编号，4096 字节数据仍在原缓冲区；该请求被归还前，驱动必须保留这些内存及其内容。

Linux 的单请求入口是 virtio_queue_rq()。它取得原始 struct request 及其私有的 virtblk_req，准备命令和数据散列表，再由 virtblk_add_req() 把请求头、数据、状态三个部分交给 virtqueue_add_sgs()。驱动把 virtblk_req 作为本地关联保存，完成时据此找回原 request。本例的直接链用 5、9、12 三个描述符表示这些部分；实际 Linux 驱动也可能使用间接描述符或多个数据片段。请求组装、单请求提交与条件通知

这些关联建立后，多个请求可以同时等待后端；每次返回仍能找到自己的链头、数据和状态字节。Linux 队列回调登记、blk-mq 操作表、QEMU 队列入口登记、异步回调与请求关联

virtio_blk_handle_vq()连续提取可用请求，经过类型、长度、对齐和磁盘边界检查后，将读写请求暂存到 MultiReqBuffer。同方向的相邻磁盘区域可以合并，合并后的 iovec 数和传输长度必须满足后端限制；改变读写方向、达到批次上限或完成本轮消费时，暂存批次会被提交。

合并前，QEMU 按 sector 排序。例如本例的 2048—2055 和另一个请求的 2056—2063 可以组成 8 KiB 后端写入；两个客户机请求仍各自保有状态字节和完成记录。mr_next把它们串起来，后端回调再逐一处理。提交顺序和完成顺序因此不应当作客户机写入依赖的保证。合并与提交

此时链头 5 已从队列取出，块后端接受了偏移 1 MiB 的写入，原链尚未发布 used。异步请求等待完成期间，缓冲区仍由这次请求占用；后端回调通过保存的请求对象找回它。

    状态、used 项与完成通知

    后端成功返回后，virtio_blk_rw_complete()遍历合并请求链，调用 virtio_blk_req_complete()。后者依次写状态、恢复 iovec、发布 used，再调用通知检查。客户机通过 used 找到原请求，读取 status，回收描述符和缓冲区。

    本例的完成记录
  status = VIRTIO_BLK_S_OK = 0
  used.ring[7] = { id: 5, len: 1 }
  used.idx: 7 → 8

id = 原始描述符链头
len = 设备写入的缓冲区长度，本次只有 status 的 1 字节

    本例 OUT 的设备写入量为 status 的 1 字节；相同大小的普通 IN 请求会写入 4096 字节数据和 1 字节状态，used.len = 4097。完成记录发布后，virtio_notify()检查通知条件。一次中断可以承接多个完成，驱动根据 used 逐项取回请求，再读取各自的状态。完成发布、读写和刷新回调

    客户机从完成链头找回原始块请求

    完成通知触发之前登记的 virtblk_done()。它循环调用 virtqueue_get_buf() 消费 used，取得提交时保存的 virtblk_req，再通过 blk_mq_rq_from_pdu() 找回 request，提交给 blk-mq 完成路径。最后的 virtblk_request_done() 读取 status、解除数据映射、清理命令，并调用 blk_mq_end_request()。至此，链头 5 对应的设备请求在客户机块层结束；上层文件系统和应用继续处理各自的完成。

    缓存与持久化

    写请求和读请求一样，需要向 Guest 交付完成状态。后端写入状态并发布 used，驱动通过中断提示或轮询发现完成记录，检查成功或失败，解除数据映射、回收描述符并结束块请求，再唤醒等待者或交付异步完成。中断本身不是成功标志，也不保证每个请求对应一次中断；普通写完成仍不等于掉电后数据可恢复。

    演示覆盖块设备直接读写，不代表所有应用 I/O。普通文件、缓存与持久化还涉及以下区别：

    场景Guest 内部设备与完成语义
    块设备直接读（本例）固定用户页，经 bio / blk-mq 提交。一次应用调用形成一个 R1 是本例的前提。数据描述符带 WRITE，设备把 4096 B 结果写入 Guest 缓冲区；完成结构与 used.len 随设备接口和实现变化，见关键结构视图。
    普通文件缓冲读先经过 VFS、文件系统和 Guest 页缓存。命中可能不发起设备 I/O；缺页读取、预读及请求拆分可能产生多个请求。设备通常先填充 Guest 缓存页，随后由内核向用户缓冲区交付所需数据，不能等同于本例的直接映射。
    块设备直接写应用先准备数据，内核固定缓冲区并提交写请求；完成前不能任意复用。数据描述符不带 WRITE，设备从 Guest 读取数据；virtio-blk 使用 OUT 与状态字节，virtio-scsi 使用 SCSI CDB 与响应结构。
    普通文件缓冲写写入可能先完成于 Guest 页缓存，设备 I/O 由后续回写触发。write() 返回、设备请求完成与掉电后仍可恢复是不同边界，持久化还需看同步操作、flush/FUA 及后端约定。

    写入完成与持久化

    在上方同一演示中选择“写入”，再选择“写入完成要求”：本地 virtio-blk 提供普通写与写后 FLUSH，本地 virtio-scsi 提供普通写与 FUA。R1、队列、源码和当前完成保证在同一个工作区连续展示，不需要另开播放器。RBD/SPDK 目前只展示其已核验的普通读写，不套用本地文件的刷新语义。

    本地场景使用 raw 文件、aio=threads、writeback=on 与 no-flush=off。写后 FLUSH 在普通 O_DIRECT 写返回后发起 fsync()，形成独立请求 F1；FUA 从已经携带 REQ_FUA 的块请求开始，到上层请求完成，不冒充完整应用同步写路径（后者还可能包含额外刷新）。缓存状态表达接口契约，不推断物理设备内部时序或真实耗时。

    区分缓存路径与同步要求

    配置或操作控制范围完成保证
    Guest O_DIRECT本次 I/O 绕过 Guest 页缓存单独使用不保证掉电持久化，也不控制宿主页缓存
    QEMU cache.direct=on尽量绕过宿主页缓存设备仍可能有易失写缓存；direct 不等于同步持久化
    writeback=on 的普通 WRITE允许下层在缓存接受数据后报告完成应用可回收本次缓冲区，稳定存储状态尚未由该操作确认
    WRITE 完成后执行 FLUSH确认此前已完成、属于刷新范围的写入刷新成功后，这些数据达到下层承诺的稳定存储边界
    WRITE FUA约束本次写的完成条件本次数据持久化后才完成，不自动保证所有前序写入
    QEMU cache.no-flush=on允许跳过向存储落实的刷新；也会清除下传的 FUA 要求不能沿用本演示的持久化保证

    cache=none 对应 writeback=on、direct=on、no-flush=off，仍需要 Guest 正确发起同步。cache=unsafe 则允许忽略刷新。这些参数和 Guest 打开文件时的标志属于不同层，不能只凭“direct”或“无缓存”的名称判断数据安全。QEMU 缓存模式定义。

    FUA 在两种设备接口中的实现

    Linux 6.18 的块设备同步直接写可产生 REQ_FUA。virtio-scsi 在目标支持时把它编码到 SCSI WRITE 的 FUA 位；QEMU scsi-hd 再转换成 BDRV_REQ_FUA。本例的 raw threads 后端先完成文件写入，再执行刷新，最后才向 Guest 完成这条 SCSI 命令。其他后端可以直接支持 FUA，具体实现需分别检查。文件后端实现。完整系统调用还可能安排其他同步：例如同步块设备写在 write_iter 末尾还会经过 generic_write_sync()，不能把这里的一条命令直接当作完整调用的全部设备请求。Linux 调用边界。

    virtio-blk 的普通 OUT 命令没有这里的原生 FUA 位。固定版本的 Linux 驱动声明写缓存能力而不声明 BLK_FEAT_FUA，块层会为需要 FUA 的写入安排写后 FLUSH。它与应用先完成普通写、再显式调用 fsync() 的外部调用顺序不同；共同要求是同步操作不能在所需刷新完成前成功返回。驱动能力、块层 POSTFLUSH。

    需要同时约束前序数据和当前写时，上层可以组合 PREFLUSH 与 FUA。FUA 的契约只覆盖该写；某个后端用较大范围刷新来实现它，也不应让应用依赖额外的前序顺序保证。持久化还不同于原子性：本例不保证一组写入整体生效，也不涵盖文件创建、目录项或跨设备事务。Linux 写缓存控制契约。

    用 VirtIOBlockReq 保留请求与回调关联

    前面的异步流程需要记住链头 5、数据缓冲区和状态字节，才能在后端返回时完成正确的请求。virtqueue_pop()解析并映射描述符，构造带有 VirtQueueElement的 VirtIOBlockReq。设备可读区域进入 out_sg，设备可写区域进入 in_sg。这里的 in / out 以客户机数据流向命名，阅读实现时需要同时检查操作类型和描述符权限。

    结构或字段本例内容作用
    elem链头编号，out_sg 和 in_sg保存队列元素及已映射的分散缓冲区
    out / sector_num复制的 16 字节头；扇区 2048解析命令并计算磁盘偏移
    qiov4096 字节数据的 iovec提交块层的数据视图，不含请求头和状态
    in / in_len状态指针；本例为 1 B写回结果并确定 used 长度
    vq / mr_next原队列；合并请求链把一次后端操作的结果分别归还给各个请求
    MultiReqBuffer最多 32 个请求及读写方向暂存本轮队列处理中可合并的请求

    virtio_blk_handle_request()先复制头部，从 out iovec 前端剥离这 16 字节；再定位最后一个 in iovec 的末尾状态字节，并将它从数据视图中剥离。OUT 使用剩余 out iovec，IN 使用剩余 in iovec。剥离操作有 undo 记录，完成时恢复原始视图，供通用 virtqueue 代码解除映射。请求结构、命令解析

    构造 iovec 不要求先复制全部写入数据。不过下层的缓冲方式、对齐处理、镜像格式和宿主 I/O 接口仍可能产生复制，不能据此把整条路径称为零拷贝。

    错误处理与请求保留

    磁盘越界或不满足对齐要求的请求可直接完成为 IOERR，后端执行错误则按照块设备错误策略处理。report 把失败返回客户机；stop 将请求放入设备的待重试链并触发相应暂停处理，恢复后再按队列重新提交；ignore 则可能把后端错误当作成功继续完成。

    stop 路径把原请求保留到重试结束，used 也随之等待。QEMU 10.2 用 rq_lock保护设备级重试链，恢复时按 virtqueue 分组并调度到对应的 AioContext。若链头 5 已取出却迟迟未完成，可以把客户机 used 进度与 QEMU 块错误事件、虚拟机暂停状态关联起来，区分后端仍在执行和请求已进入待重试链。错误策略、恢复与重新提交

    多队列与 IOThread 的收益和代价

    virtio-blk 将命令、数据和完成组织为共享队列，减少了逐个模拟传统磁盘寄存器的工作。批量消费和相邻请求合并继续降低每次提交的开销，但共享队列和单线程处理也会成为高 IOPS 设备的瓶颈。多队列让客户机分散提交；IOThread 将处理工作从主事件循环中分离。

    单个设备的多条队列若仍归同一 IOThread，宿主侧处理仍集中于一条线程。QEMU 引入 iothread-vq-mapping后，可按队列分配多个 IOThread；QEMU 10.2 的设备直接维护 vq_aio_context[]，块请求和重试路径也相应处理多线程访问。引入逐队列线程映射的提交、当前映射初始化

    以链头 5 的请求为例，处理入口改由配置的 IOThread 调度，仍经同一个请求对象关联后端回调，最后发布 status 和 used。线程调整不会改变前面的完成与刷新语义。队列数量描述客户机的提交通道，IOThread 数描述宿主的处理线程，后端能力决定实际可推进的 I/O 并发。协程和线程的执行关系见《QEMU AioContext、协程与 IOThread》。

    更多队列增加并发机会，也会带来线程调度、缓存竞争和 NUMA 访问成本；零散的小请求还可能降低合并机会。应结合客户机负载、请求深度、后端延迟和处理线程占用选择配置。性能比较尤其要保持缓存与刷新语义一致，否则降低持久化要求得到的延迟改善，无法说明队列路径本身变快了。
