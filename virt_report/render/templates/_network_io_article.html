从应用收发到虚拟网卡

发送由客户机应用调用 sendto()，UDP/IP 协议栈封装网络帧，再由 virtio-net 驱动交给后端。接收由驱动预置可写 RX 缓冲区；外部报文到达后，经设备、驱动和协议栈进入已绑定的 socket，应用用 recvfrom() 取走数据或等待后续报文。

QEMU、内核 vhost-net、DPDK vhost-user 与硬件 vDPA 使用相同的客户机设备接口，但数据处理位置和缓冲区交接方式不同。本页分别观察应用调用、Guest 队列、完成中断与宿主处理；它们的“完成”不代表同一件事。

示例发送 ASCII 字符串 virt-report-demo01，共 18 B。加上 8 B UDP 头、20 B IPv4 头和 14 B Ethernet 头，得到 60 B 帧 P1；virtio-net 另外使用 12 B 网络头，设备 RX 的实际写入量为 72 B。接收应用提供 128 B 缓冲区，成功时 recvfrom() 返回 18。

队列按 8 个槽位展示，使用直接描述符。发送选取头部不能直接压入 skb 的分支，desc[0] → desc[2] 分别指向 12 B 网络头和 60 B 帧；接收采用 add_recvbuf_small()，desc[2] 提供 12 + GOOD_PACKET_LEN = 1530 B 可写空间。本次实际写入仍为 72 B。页片段还会分配 headroom 和 skb 元数据，分配大小不等于描述符向设备暴露的长度。

演示采用 x86 + KVM、QEMU 10.2.0、Linux 6.18；DPDK 路径采用 24.11。设备为 modern virtio-net，使用 split ring 和一个队列对：队列 0 接收，队列 1 发送。路由、邻居、设备协商与内存映射已经就绪；使用普通 UDP 复制路径，关闭分段、校验和卸载、合并 RX 缓冲区、UDP cork 和零拷贝发送。报文不带 IP 选项或 VLAN，也无需分片。

接口选择：e1000 寄存器与 virtio 队列

网络发送包含三类交互：客户机在内存中准备报文和队列元数据，通过设备接口提交工作，再从完成记录中判断哪些缓冲区可以回收。报文内容、提交通知和完成通知承担不同职责，追踪时应分别观察。

e1000：实现硬件定义的接口

e1000 驱动在客户机内存中分配 TX 描述符环。描述符记录缓冲区地址、长度以及命令和状态位；EOP标记一个报文的结束，RS请求状态回写。设备寄存器 TDBAL/TDBAH保存环地址，TDLEN保存长度，TDH和 TDT表示消费位置与驱动提交的尾位置。

驱动填好描述符后写 TDT，QEMU 的 e1000 模型就按硬件接口约定读取客户机内存。这里已经存在描述符环和 DMA 语义：软件模型通过 pci_dma_read()、pci_dma_write()完成设备视角的内存访问。描述符环本身无需复制到某个“宿主设备专属内存”才能使用。e1000 发送实现

virtio-net：通用队列与网络设备格式

split virtqueue 把队列划分为描述符表、available ring 和 used ring。驱动填写描述符链，将链首编号放入 available ring；设备读取链上的缓冲区，完成后把链首编号写入 used ring。avail.idx与 used.idx分别记录已发布和已完成的队列项数量，按协议规定的整数宽度回绕。

virtio-net 在帧前携带 virtio_net_hdr，用于描述网络卸载等信息。该头属于客户机与设备间的协议元数据；它不会作为以太网帧的一部分发送到远端。TAP 支持的 vnet_hdr还允许 QEMU 与宿主内核传递这些元数据，具体长度和能力需要协商。发送头与缓冲区整理

两种接口的差异主要在驱动与设备的约定。virtio 把队列机制从具体硬件寄存器模型中独立出来，便于不同设备类型复用；客户机仍需要相应驱动，QEMU 仍需检查描述符、访问内存和完成后端 I/O。

发送与接收共用的队列约定

split virtqueue 用描述符保存缓冲区地址与访问方向，available 发布链头，used 归还已处理的链。TX 提交已填好的设备可读数据；RX 预先提交设备可写空间。驱动和设备分别维护自己的消费进度，通过共享索引发布状态。

共享队列与两侧私有对象

Guest 的 struct vring_virtqueue 与 QEMU 的 VirtQueue 位于各自的软件地址空间。驱动通过 split.avail_idx_shadow 累积提交位置，通过 last_used_idx 跟踪回收位置；QEMU 通过 last_avail_idx 跟踪消费位置。共享的 avail.idx 和 used.idx 发布进度，两侧私有索引分别记录自己已经处理到的位置。

从描述符到后端访问

QEMU 解析链后用 VirtQueueElement 保存链首与本地 iovec：out_sg 对应设备可读区域，in_sg 对应设备可写区域。完成项的 id 关联原链头，len 表示设备写入长度，TX 可以为 0。完整的字段、回绕和两种队列布局见Virtqueue：Split 与 Packed。

从驱动提交到后端发送

先沿 QEMU + TAP 路径对照 e1000 和 virtio-net。两种网卡连接相同后端，驱动提交与设备消费使用各自的寄存器或队列约定。

e1000 的发送路径

  1. 驱动准备 P1，填写发送描述符并设置 EOP、RS。完成必要的内存顺序操作后，写入新的 TDT。
  2. e1000_mmio_write()分派寄存器写操作；TDT 对应的 set_tctl()调用 start_xmit()。
  3. start_xmit()从 TDH 开始读取描述符。process_tx_desc()读取报文内容，并在遇到 EOP 时调用 xmit_seg()。
  4. 报文经 e1000_send_packet()和 QEMU 网络接口到达 TAP。正常可写路径最终执行 writev()。
  5. 模型按状态回写条件设置 DD、推进 TDH，并更新中断原因。客户机驱动检查完成记录后回收缓冲区。

这里的“DMA 读取”由 QEMU 软件执行。固定版本的 e1000 模型将报文读入自己的发送缓冲区，并在那里完成分段、校验和等模拟工作；这些工作量会受到客户机选择的功能影响。报文处理与状态回写、TDT 回调表

virtio-net 的发送路径

  1. 驱动准备网络设备头与 P1 的缓冲区，建立设备可读的描述符链，发布 available 项。
  2. 驱动检查通知条件，必要时通知对应的发送队列。QEMU 的队列处理函数安排发送任务。
  3. virtio_net_flush_tx()调用 virtqueue_pop()取出请求。通用 virtio 层验证描述符并建立 VirtQueueElement，其中 out_sg描述设备需要读取的客户机缓冲区。
  4. QEMU 整理网络头与 iovec，经 qemu_sendv_packet_async()交给 TAP 后端。可写时，TAP 直接接收；暂不可写时，后端排队等待继续发送。
  5. 同步完成路径或异步完成回调调用 virtqueue_push()发布 used 项，再检查是否需要通知客户机。驱动据此回收链和报文缓冲区。

使用 iovec 可以避免为每个请求都先拼成一块连续的用户态报文。实际复制次数还取决于客户机内存映射、网络头转换、TAP 和宿主协议栈等实现，不能仅凭 virtio 或 scatter-gather 接口推算端到端零拷贝。virtio-net 发送与异步完成

缓冲区与完成语义

普通发送会把用户数据复制到客户机内核的 skb。应用缓冲区 U0、内核 skb S1、设备描述符，以及 DPDK 路径中的宿主 mbuf 是不同对象。sendto() 返回后，应用可以复用 U0，已经复制出的数据仍可沿后续路径转发。UDP 发送内存预算用于约束本地资源使用；普通无 cork UDP 不会像 TCP 那样保留可靠重传队列。

TX 发布的是已准备好的帧，后端获得设备可读的缓冲区；RX 提前发布空闲空间，后端获得设备可写的缓冲区。两种方向都先写内容或描述符，再发布索引。通知只提示另一端检查队列，完成记录由 used 保存，多个报文可以共用一次通知。

本例先发布 used，再发起完成提示；KVM 记录 vLAPIC 待处理中断，目标 vCPU 随后接受它，Guest 回调安排 NAPI。这是一次完成通知从提交到处理的完整路径。驱动依据 used 消费完成记录，单次通知可以覆盖多个完成项；通知也可以被抑制或由轮询替代。

avail.ring[n] 保存链头编号，描述符的 addr 指向缓冲区；used.ring[n] 保存链头与本次设备写入长度。另一端须观察到发布的新索引后才能消费对应槽位。TX 的 used.len = 0 表示设备向可写描述符写入了 0 字节，帧长记录在发送描述符中。RX 的 used.len = 72 是本次写入长度，缓冲区容量为 1530 B。

发送在队列发布后分成并行的两条路径：Guest 沿系统调用返回，宿主后端消费已发布的链。本页展示先返回、后处理的一种调度顺序，后端也可能更早运行。图中返回边直接连接客户机协议栈和应用，设备完成不会作为 sendto() 返回的前置条件。真实系统若先把 skb 排入客户机 qdisc，返回还可能早于 virtqueue 发布。

QEMU + TAP 的普通 TX 路径在 writev() 成功返回后发布 used，再判断完成通知条件。此时宿主已经接受了帧，网络转发可以独立推进；Guest 侧依次处理虚拟中断和队列回收。宿主转发可能在写 TAP 的调用内部就已开始，两条路径之间没有“Guest 回收后才发送”的依赖。TAP 暂不可写时则保留请求，等待重试成功后发布 used。QEMU 发送与完成、TAP 写入

RX 演示选取单帧接收路径：NAPI poll 从 used 取回链，构造 skb 并交给 GRO；GRO_NORMAL 普通列表尚未达到提前刷新条件，驱动先补充新 RX 空间。本轮处理量小于 budget，随后在 NAPI 完成阶段由 gro_flush_normal() 把普通列表交给协议栈。IPv4 / UDP 校验与分发完成后，数据才进入 socket。批量阈值或处理预算不同，协议交付与 refill 可以交错；补充新空间始终不以应用读完旧数据为前提。

本例数据先进入 socket，应用随后调用 recvfrom，直接读取已有数据。若应用先调用、socket 尚无数据，阻塞调用会等待；入队时再唤醒等待者，线程获得 CPU 后才能复制载荷。非阻塞调用在无数据时返回 EAGAIN。这是同一接收机制下调用时机的区别，不需要另选一种收包模式。设备完成也不保证数据能进入 socket：协议校验、接收预算等可能导致后续丢弃。

DPDK 的普通同步路径有两份独立存储。TX 将 Guest 帧复制为 mbuf，在发布 used 并检查通知条件后返回；应用取得 mbuf，即可交给 PMD，无需等待 Guest 执行中断或回收描述符。RX 则从 mbuf 复制到 Guest 空间；rte_vhost_enqueue_burst() 成功返回后，应用可释放已复制报文对应的宿主 mbuf，Guest 的 NAPI 与协议栈继续处理自己的副本。rte_vhost_dequeue_burst() 从 Guest 取包，rte_vhost_enqueue_burst() 向 Guest 送包，两个名字以 vhost 接口为视角。

硬件 vDPA 直接访问 Guest 缓冲区。设备必须结束对本次发送链及其数据的使用，才可发布 TX used；DMA 刚开始或报文刚进入硬件处理流程都不足以满足这一条件。内部缓存、流水线和发送完成策略由具体设备实现，通用 virtio 接口只保证 used 之后可以归还缓冲区。演示保留这条保证，不把设备完成解释为远端收包确认。

队列空间和网络交付能力也应分别观察。TX 的 TAP 暂不可写时，QEMU 会保留异步请求；RX 没有可写缓冲区时，也可能暂停上游交付。持续超载受有限队列约束，仍可能丢包。演示固定空间充足的成功路径，下面继续说明 NAPI、缓冲区补充与通知竞态。

NAPI 的中断与批量轮询切换

如果每个报文都引发一次中断，流量增大后，CPU 会频繁进入通知处理路径，却没有足够时间真正处理报文。NAPI 用一次调度承接一批完成：回调安排 poll 并抑制重复通知，poll 逐步取走 used 中已经完成的接收缓冲区。常规处理发生在客户机网络软中断上下文，也存在 threaded NAPI 和 busy polling 等模式。

设一轮 poll 的预算为 4，这是便于观察的教学值。如果 used 中已有 7 帧，第一轮取 4 帧并返回预算值，NAPI 继续保持待处理状态；下一轮取剩余 3 帧，观察到队列已空后才尝试完成本轮调度。预算限制一次轮询的接收工作量，防止一个繁忙队列长期占用执行机会；它不等于硬件队列大小，也不保证每帧各占一个描述符。

恰好取走 4 帧时，即使队列此刻为空，也不能同时用“返回 4”向 NAPI 表示已经完成。Linux virtio-net 在 received < budget 时调用完成辅助函数，等于预算则交给后续轮询确认。budget = 0 是只处理特定 TX 完成等场景的特殊输入，不能据此执行普通 RX 消费或完成 NAPI。virtnet_poll、Linux 6.18 NAPI API

GRO 在客户机网络栈中把适合合并的报文组织为更大的处理单元，降低上层逐包开销。设备仍逐项发布 RX 完成，NAPI 消费这些完成后再向上层交付。接收帧、used 项、NAPI poll、通知与应用读取分别记录这条路径上不同阶段的工作量。

通知边界：kick、完成记录与中断

发布队列与发送 kick

驱动先发布可用缓冲区，后端才能安全地消费。通知只提示设备检查队列；多个请求可以共享一次 kick，设备正在处理队列时也可以抑制新的 kick。队列发布需要正确的内存屏障，通知抑制还需要防止“设备准备休眠时恰好新增请求”的竞态。仅删除通知操作，会让后端失去唤醒机会。

设 avail.idx = last_avail_idx = 7，设备暂时关闭 kick，准备结束本轮处理。如果它检查空队列之后直接恢复通知并等待，驱动可能已在这两步之间发布第 8 项，却因为当时通知关闭而省略 kick。队列中有请求，事件循环却没有新通知可等。

安全路径先恢复通知，以必要的内存屏障约束顺序，再复查队列。第 8 项早到，复查会发现它；晚到，驱动按新的通知条件发出 kick，事件通知保持就绪，等待端继续处理。两端都需要遵守发布与检查规则，单独给某个计数器加一次屏障并不能替代完整协议。这里用 split 队列的通知开关演示；协商 EVENT_IDX 后，通知条件改用事件索引，重新启用与复查的要求仍然存在。QEMU 通知设置与顺序约束、发送处理的通知重启与复查

在普通 MMIO 路径中，客户机写 virtio PCI 通知地址，QEMU 的 virtio_pci_notify_write()找到队列后调用通知函数。启用 ioeventfd 时，QEMU 预先注册通知地址与 eventfd 的对应关系；KVM 处理匹配的写入并触发 eventfd，QEMU 的事件处理再调度该队列。这减少了通过 KVM_RUN返回用户态模拟此次 MMIO 的往返。CPU 从客户机执行切换到 KVM 的硬件退出仍可能发生，二者应分开计数。ioeventfd 注册、QEMU 事件处理、KVM_IOEVENTFD

通知恢复与接收缓冲区补充

队列刚空时，可能又来了新报文

驱动最后一次检查 used 时没有数据；紧接着设备写入新完成，却看到驱动仍在抑制通知。如果驱动随后直接退出 poll 等下一次中断，这个完成可能无人处理。正确交接需要协调 NAPI 状态、重新启用队列回调，并再次检查完成进度；发现窗口内到达的新工作，就重新安排处理。Linux 将这些步骤封装在 virtqueue_napi_complete() 等辅助函数中。

这里通过 virtqueue 协议请求设备暂缓完成通知。通知可能已经在路上，多个队列也可能共享中断，因此驱动恢复回调后继续检查 used 进度。通知决定何时检查，used 记录决定本轮有哪些缓冲区可取回。

接收空间耗尽后的背压与补充

客户机长时间得不到 CPU、分配内存失败或补充速度不足，都会让 RX available 耗尽。QEMU 的 virtio_net_has_buffers() 会启用缓冲区到达通知并复查队列，确认仍无空间后让上游暂缓交付。后端可能排队、暂停读取或丢包，取决于具体路径和排队上限；这不构成无限缓存或不丢包保证。

Linux 补充空间遇到内存不足时可安排延迟 refill 工作；如果描述符已满却应用仍慢，瓶颈也可能在后续协议栈、socket 或应用消费。排查顺序应是可写缓冲区数量、used 消费速度、NAPI 调度与预算、CPU 时间，再到上层协议和应用。单纯增大 ring 可以吸收短时突发，但持续超载时还会增加排队延迟。QEMU 空间检查、Linux 回收与 refill

TAP 文件描述符连接宿主网卡接收路径

继续沿 P1 向下看：QEMU 的 tap_fd 是打开的字符设备文件句柄，宿主网络栈中的 TAP 网卡由另一个 net_device 对象表示。这里取 QEMU 通过 /dev/net/tun 创建普通 TAP、未启用 XDP 的路径。打开文件时，内核分配 tun_file 并放入 file->private_data；随后 TUNSETIFF 找到或创建接口，将这个文件与 tun_struct 关联，后者的 dev 指向 TAP 的 net_device。QEMU 打开与配置 TAP、文件与网卡对象、字符设备打开

P1 经过的位置此处完成的交接
QEMU：writev(tap_fd, iov, iovcnt)通过已打开的文件，把帧及已协商的 vnet 头交给宿主内核
字符设备：tun_chr_write_iter()从 file 找到 tun_file，再取得关联的 tun_struct，调用 tun_get_user()
TAP 接收：tun_get_user()解析元数据、形成 skb；以 tun->dev 作为接收网卡处理以太网头
宿主网络栈：netif_receive_skb()普通非 NAPI 路径经 tun_rx_batched() 到达这里，开始宿主侧的报文接收处理
QEMU 用户态发送 P1
  writev(tap_fd) → tun_chr_write_iter → tun_get_user
    tun_file → tun_struct → TAP net_device
    skb → tun_rx_batched → netif_receive_skb
      按宿主配置：桥接到其他端口 / 交给本机协议栈及路由

因此，客户机的 TX 在宿主 TAP 接口上表现为 RX。TAP 若加入 Linux bridge，报文可继续被桥转发；后续是否经过物理网卡取决于拓扑、目的地址和转发规则。固定版本中，QEMU 的普通 TAP 创建代码不设置 IFF_NAPI，上述 x86 路径经 tun_rx_batched() 调用 netif_receive_skb()。预先配置 NAPI 的 TAP 可以进入另一条排队与 NAPI/GRO 路径；外部传入 FD 或 /dev/tap<ifindex> 接口也需单独确认。writev 对应的写入口、接收分支、普通 TAP 的宿主接收入口

追踪本例时，先确认客户机设备型号、QEMU 网络后端和 vhost 开关。vhost 关闭时，可以关联 QEMU 的 virtio_queue_notify、virtqueue_pop和 virtio_notify等 trace 事件，观察通知、取请求与完成通知的顺序。启用 vhost 后，消费进度要到对应后端观察。报文数量可与这些事件分别计数，用来判断一次通知承接了多少工作。

后端演进与取舍

这些路径保留相同的客户机设备接口，把不同部分放到更合适的执行位置。优化应同时观察吞吐、尾延迟、CPU 消耗，以及迁移和维护能力，单看少经过一个进程无法判断最终效果。

后端数据面变化代价与适用条件
QEMU + TAPQEMU 解析队列，并通过 TAP 连接宿主网络路径集中、易于观察；逐包处理和跨用户态边界会消耗 CPU
内核 vhost-net队列处理接入宿主内核，减少 QEMU 的逐包往返仍受内核调度、网络栈、内存访问与 CPU 亲和性影响
DPDK vhost-user独立用户态进程通过轮询、批处理和 PMD 组织数据面需要配置数据线程、内存及 NUMA；持续轮询消耗 CPU，普通路径仍有复制
硬件 vhost-vDPA设备通过 DMA 处理 Guest 队列，减少宿主软件逐包参与依赖硬件能力、映射和设备状态管理；迁移与可观测性需要额外支持

vhost-user 的 Unix socket 负责共享内存、队列和通知配置，逐包数据通过共享内存访问。vDPA 也包括软件实现；本页固定为硬件 direct 模式，关闭 Shadow Virtqueue（SVQ）。启用 SVQ 后，QEMU 会参与队列转接，不能沿用本页的直接访问路径。对应实现分别见vhost-net 与 vhost-user、DPDK 网络转发和vhost-vDPA 与 SVQ。
