场景与边界

发送由客户机应用调用 sendto()，UDP/IP 协议栈封装网络帧，再由 virtio-net 驱动交给后端。接收由驱动预置可写 RX 缓冲区；外部报文到达后，经设备、驱动和协议栈进入已绑定的 socket，应用用 recvfrom() 取走数据或等待后续报文。

QEMU、内核 vhost-net、DPDK vhost-user 与硬件 vDPA 使用相同的客户机设备接口，但数据处理位置和缓冲区交接方式不同。本页分别观察应用调用、Guest 队列、完成中断与宿主处理；它们的“完成”不代表同一件事。

示例发送 ASCII 字符串 virt-report-demo01，共 18 B。加上 8 B UDP 头、20 B IPv4 头和 14 B Ethernet 头，得到 60 B 帧 P1；virtio-net 另外使用 12 B 网络头，设备 RX 的实际写入量为 72 B。接收应用提供 128 B 缓冲区，成功时 recvfrom() 返回 18。

队列按 8 个槽位展示，使用直接描述符。发送选取头部不能直接压入 skb 的分支，desc[0] → desc[2] 分别指向 12 B 网络头和 60 B 帧；接收采用 add_recvbuf_small()，desc[2] 提供 12 + GOOD_PACKET_LEN = 1530 B 可写空间。本次实际写入仍为 72 B。页片段还会分配 headroom 和 skb 元数据，分配大小不等于描述符向设备暴露的长度。

演示采用 x86 + KVM、QEMU 10.2.0、Linux 6.18；DPDK 路径采用 24.11。设备为 modern virtio-net，使用 split ring 和一个队列对：队列 0 接收，队列 1 发送。路由、邻居、设备协商与内存映射已经就绪；使用普通 UDP 复制路径，关闭分段、校验和卸载、合并 RX 缓冲区、UDP cork 和零拷贝发送。报文不带 IP 选项或 VLAN，也无需分片。

缓冲区与完成语义

普通发送会把用户数据复制到客户机内核的 skb。应用缓冲区 U0、内核 skb S1、设备描述符，以及 DPDK 路径中的宿主 mbuf 是不同对象。sendto() 返回后，应用可以复用 U0，已经复制出的数据仍可沿后续路径转发。UDP 发送内存预算用于约束本地资源使用；普通无 cork UDP 不会像 TCP 那样保留可靠重传队列。

TX 发布的是已准备好的帧，后端获得设备可读的缓冲区；RX 提前发布空闲空间，后端获得设备可写的缓冲区。两种方向都先写内容或描述符，再发布索引。通知只提示另一端检查队列，完成记录由 used 保存，多个报文可以共用一次通知。

本例先发布 used，再发起完成提示；KVM 记录 vLAPIC 待处理中断，目标 vCPU 随后接受它，Guest 回调安排 NAPI。这是一次完成通知从提交到处理的完整路径。驱动依据 used 消费完成记录，单次通知可以覆盖多个完成项；通知也可以被抑制或由轮询替代。

avail.ring[n] 保存链头编号，描述符的 addr 指向缓冲区；used.ring[n] 保存链头与本次设备写入长度。另一端须观察到发布的新索引后才能消费对应槽位。TX 的 used.len = 0 表示设备向可写描述符写入了 0 字节，帧长记录在发送描述符中。RX 的 used.len = 72 是本次写入长度，缓冲区容量为 1530 B。

观察点已经完成后续工作
sendto 返回 18本例的本机发送路径接受了 18 B UDP 载荷，应用可复用用户缓冲区不保证交付，不等待 TX used、物理发送或远端响应
TX used设备结束对该 Guest 链的使用，驱动可回收缓冲区本地网络排队、链路发送与远端接收可能尚未结束
本地网卡 TX 完成网卡结束对相应发送缓冲区的使用远端协议栈与应用接收仍需独立确认；UDP 自身不提供可靠送达确认
RX used帧已写入 Guest 可写空间，实际写入量可见客户机还要消费队列、处理协议，再交给应用
DPDK TX 提交返回数量对应的 mbuf 交给 PMD网卡完成使用后，PMD 才能清理这些 mbuf
Guest RX 回收描述符槽可重新关联可用空间旧数据页可能仍被 skb 引用，补充空间要遵守引用生命周期
recvfrom 返回 1818 B UDP 载荷已复制到应用的 128 B 缓冲区应用继续处理数据；新的 RX 缓冲区可以早已发布

发送在队列发布后分成并行的两条路径：Guest 沿系统调用返回，宿主后端消费已发布的链。本页展示先返回、后处理的一种调度顺序，后端也可能更早运行。图中返回边直接连接客户机协议栈和应用，设备完成不会作为 sendto() 返回的前置条件。真实系统若先把 skb 排入客户机 qdisc，返回还可能早于 virtqueue 发布。

QEMU + TAP 的普通 TX 路径在 writev() 成功返回后发布 used，再判断完成通知条件。此时宿主已经接受了帧，网络转发可以独立推进；Guest 侧依次处理虚拟中断和队列回收。宿主转发可能在写 TAP 的调用内部就已开始，两条路径之间没有“Guest 回收后才发送”的依赖。TAP 暂不可写时则保留请求，等待重试成功后发布 used。QEMU 发送与完成、TAP 写入

RX 演示选取单帧接收路径：NAPI poll 从 used 取回链，构造 skb 并交给 GRO；GRO_NORMAL 普通列表尚未达到提前刷新条件，驱动先补充新 RX 空间。本轮处理量小于 budget，随后在 NAPI 完成阶段由 gro_flush_normal() 把普通列表交给协议栈。IPv4 / UDP 校验与分发完成后，数据才进入 socket。批量阈值或处理预算不同，协议交付与 refill 可以交错；补充新空间始终不以应用读完旧数据为前提。

本例数据先进入 socket，应用随后调用 recvfrom，直接读取已有数据。若应用先调用、socket 尚无数据，阻塞调用会等待；入队时再唤醒等待者，线程获得 CPU 后才能复制载荷。非阻塞调用在无数据时返回 EAGAIN。这是同一接收机制下调用时机的区别，不需要另选一种收包模式。设备完成也不保证数据能进入 socket：协议校验、接收预算等可能导致后续丢弃。

DPDK 的普通同步路径有两份独立存储。TX 将 Guest 帧复制为 mbuf，在发布 used 并检查通知条件后返回；应用取得 mbuf，即可交给 PMD，无需等待 Guest 执行中断或回收描述符。RX 则从 mbuf 复制到 Guest 空间；rte_vhost_enqueue_burst() 成功返回后，应用可释放已复制报文对应的宿主 mbuf，Guest 的 NAPI 与协议栈继续处理自己的副本。rte_vhost_dequeue_burst() 从 Guest 取包，rte_vhost_enqueue_burst() 向 Guest 送包，两个名字以 vhost 接口为视角。

硬件 vDPA 直接访问 Guest 缓冲区。设备必须结束对本次发送链及其数据的使用，才可发布 TX used；DMA 刚开始或报文刚进入硬件处理流程都不足以满足这一条件。内部缓存、流水线和发送完成策略由具体设备实现，通用 virtio 接口只保证 used 之后可以归还缓冲区。演示保留这条保证，不把设备完成解释为远端收包确认。

队列空间和网络交付能力也应分别观察。TX 的 TAP 暂不可写时，QEMU 会保留异步请求；RX 没有可写缓冲区时，也可能暂停上游交付。持续超载受有限队列约束，仍可能丢包。默认演示固定空间充足的成功路径，不额外设置“正常/缓冲区不足”选择。有关 NAPI、缓冲区补充与竞态的细节见virtio-net 接收路径。

后端演进与取舍

这些路径保留相同的客户机设备接口，把不同部分放到更合适的执行位置。优化应同时观察吞吐、尾延迟、CPU 消耗，以及迁移和维护能力，单看少经过一个进程无法判断最终效果。

后端数据面变化代价与适用条件
QEMU + TAPQEMU 解析队列，并通过 TAP 连接宿主网络路径集中、易于观察；逐包处理和跨用户态边界会消耗 CPU
内核 vhost-net队列处理接入宿主内核，减少 QEMU 的逐包往返仍受内核调度、网络栈、内存访问与 CPU 亲和性影响
DPDK vhost-user独立用户态进程通过轮询、批处理和 PMD 组织数据面需要配置数据线程、内存及 NUMA；持续轮询消耗 CPU，普通路径仍有复制
硬件 vhost-vDPA设备通过 DMA 处理 Guest 队列，减少宿主软件逐包参与依赖硬件能力、映射和设备状态管理；迁移与可观测性需要额外支持

vhost-user 的 Unix socket 负责共享内存、队列和通知配置，逐包数据通过共享内存访问。vDPA 也包括软件实现；本页固定为硬件 direct 模式，关闭 Shadow Virtqueue（SVQ）。启用 SVQ 后，QEMU 会参与队列转接，不能沿用本页的直接访问路径。对应实现分别见vhost-net 与 vhost-user、DPDK 网络转发和vhost-vDPA 与 SVQ。

源码与相关内容

演示每一步均附相应源码或规范。客户机发送从 __sys_sendto() → udp_sendmsg() → ip_make_skb() 进入网络输出，再由 start_xmit() 提交给 virtio 队列。接收由驱动进入 UDP socket 排队，__sys_recvfrom() → udp_recvmsg() 在读取时复制载荷。QEMU 路径跟踪 virtio_net_flush_tx()、virtio_net_receive_rcu() 和 TAP 回调；vhost-net 跟踪 handle_tx_copy()、handle_rx()；DPDK 跟踪 split 队列消费、复制与 used 发布。

  • Linux 6.18 sendto、recvfrom与UDP 载荷复制：客户机应用入口和返回。
  • 用户数据复制与UDP socket 排队和唤醒：用户缓冲区与内核 skb 的交接。
  • virtio-net 接收与 refill、GRO_NORMAL 普通接收列表与NAPI 完成：驱动回收和协议交付的分界。
  • VIRTIO 网络设备规范：收发队列、网络头与缓冲区方向。
  • QEMU 10.2.0 TX、RX与TAP：交付、背压及完成。
  • Linux 6.18 vhost-net TX与RX：宿主内核中的队列处理。
  • DPDK 24.11 dequeue与enqueue：同步复制及完成发布。
  • virtio 完成通知：从队列通知到 KVM 中断交付。
