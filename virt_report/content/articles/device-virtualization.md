## 序言 {#preface}

设备虚拟化给客户机提供网卡、磁盘等设备接口，并把驱动提交的请求交给宿主软件或物理设备执行。以发送报文为例，应用仍调用 `sendmsg()`；到了驱动，同一帧可以交给 QEMU 模拟的网卡、使用共享队列的 virtio 网卡，也可以交给分配给虚机的物理网卡功能。跟踪这帧报文，可以看到三条路径在队列处理、内存访问权限和完成通知上的差别。

### 设备 I/O 虚拟化的演进 {#evolution}

早期系统模拟的目标是让现成的操作系统和驱动启动起来。随着虚机承载网络和存储服务，开销逐渐集中在寄存器访问、逐包处理和跨进程唤醒上。由此发展出两条并行路线：一条保留虚拟设备接口，把队列交给更合适的后端；另一条把真实设备的功能直接分给虚机。

| 时间与实现 | 解决的问题与分工变化 |
| --- | --- |
| 2005 · QEMU 系统模拟 | QEMU 模拟网卡、磁盘控制器和中断控制器，既有驱动按硬件手册操作。兼容旧系统的代价，是软件需要重现设备寄存器和队列的行为。 |
| 2008 · Linux 2.6.24，virtio-net | 客户机和虚拟设备直接约定缓冲区格式，用描述符链批量交接。VMM 可以实现这个协议，省去模拟某款网卡的寄存器操作。 |
| 2010 · Linux 2.6.34，vhost-net | 保留 virtio-net 接口，让宿主内核直接消费网络队列。QEMU 负责建队列、配内存和通知，常规收发留在内核。 |
| 2012 · Linux 3.6，VFIO | 对有 IOMMU 隔离能力的设备，用户态 VMM 有了标准的设备访问、DMA 映射与中断接口。直通整块 PCI 功能或 SR-IOV VF 时，读取原生队列的是硬件。 |
| 2014 · QEMU 2.1，vhost-user | 独立后端进程可以通过 Unix socket 接收内存、队列与通知配置，在共享内存中处理请求。网络交换和存储服务由此可以有各自的线程、驱动和发布周期。 |
| 2020 · Linux 5.7，vDPA | virtio 前端还可以连接实现 virtqueue 的卸载设备。客户机沿用 virtio 驱动，宿主 vDPA 驱动负责设备配置和队列接入。 |

模拟设备至今仍用于启动旧系统；virtio、vhost 和 VFIO 也常出现在同一台虚机里，比如系统盘用 virtio-blk、业务网卡用直通 VF。

## 设备接口与后端 {#architecture}

客户机驱动面对的是**设备接口**：从哪里读配置，按什么格式描述一个请求，向哪里通知有新工作。**后端**负责执行请求。QEMU 可以向客户机呈现不同的网卡，连接同一个宿主 TAP 接口；也可以保持同一个 virtio-net 接口，把队列处理从 QEMU 移到宿主内核或独立进程。

| 方式 | 客户机驱动提交到哪里 | 谁处理队列 | 报文如何离开虚机 |
| --- | --- | --- | --- |
| 设备模拟（e1000） | Intel 网卡格式的发送描述符环和寄存器 | QEMU 的 e1000 设备模型 | QEMU 从客户机内存读取报文，交给网络后端，如 TAP |
| 半虚拟化（virtio-net） | virtio 发送队列 | QEMU、vhost 后端或支持 vDPA 的设备 | 后端按描述符访问缓冲区，将报文送入宿主网络或硬件 |
| PCI 直通（以 SR-IOV VF 为例） | VF 原生驱动管理的硬件发送队列 | 物理网卡 | 网卡通过 DMA 读取授权内存，经硬件交换或物理端口发送 |

virtio 约定客户机和设备之间的接口，vhost 是处理该接口的一种分工。vhost-net 在宿主内核中处理 virtqueue；vhost-user 通过 Unix socket 协商内存区域、队列位置和通知用的文件描述符，独立后端进程从共享内存读取描述符和报文。vDPA 则把 virtio 数据队列交给相应后端，例如支持卸载的网卡。更换这些后端时，客户机仍使用 virtio-net 驱动。

设备启动时，驱动通过 PCI 配置空间找到设备及 BAR，在配置寄存器中启用功能、选择队列、写入队列地址，并配置中断。这是控制路径。进入稳定收发后，驱动主要在内存里填写描述符，按需写一次门铃唤醒后端。门铃写入的是“这里有新请求”，报文和磁盘数据位于描述符指向的缓冲区。把处理门铃的代码移进内核，与把数据搬运交给硬件，是两种不同的优化。

## 一个报文的三条发送路径 {#example}

**模拟网卡。** 客户机 e1000 驱动把报文缓冲区的 DMA 地址、长度等信息写入描述符，更新发送环的尾寄存器 `TDT`。QEMU 的设备模型处理寄存器写入，`start_xmit()` 从头指针走到尾指针，读取描述符和报文，把组装好的帧交给网络后端，再按描述符的要求写回状态。兼容性来自对硬件寄存器和描述符语义的实现，解析这些结构也会占用宿主 CPU。

**virtio 网卡。** 以 split virtqueue 为例，客户机驱动把 virtio-net 头和报文放进一个描述符链，在 available ring 发布链头。需要通知时，驱动发出 kick。使用 vhost-net 和 TAP 时，宿主内核从队列取走请求，将报文交给 TAP 所连的网络，再把完成的链头写入 used ring。这条路径把逐包处理移出 QEMU 的设备模型；QEMU 仍负责协商特性、配置队列和连接后端。

**直通网卡。** 宿主把物理网卡提供的一个虚拟功能（VF）分给虚机，QEMU 通过 VFIO 配置设备访问、中断和 DMA 映射。客户机的 VF 驱动写入硬件描述符并敲响门铃；网卡按描述符里的 I/O 虚拟地址（IOVA）发起 DMA，宿主 IOMMU 将地址翻译到获准访问的内存页。网卡更新完成状态后，可通过 MSI-X 通知客户机。逐包工作交给硬件后，设备复位、地址映射的撤销和中断路由仍由宿主参与管理。

## 缓冲区与完成通知 {#queue}

发布发送请求后，驱动要保留缓冲区，直到设备交还它。对 split virtqueue，驱动写好描述符和 available ring 条目，再按规范要求的内存顺序推进索引；设备写好完成项后才推进 used 索引。驱动看到完成项即可回收相应缓冲区。对端应用收到报文则是网络协议层面的另一个事件。

队列索引记录进度，通知负责唤醒处理方。后端正在轮询时，驱动可以按双方协商的规则省略 kick；客户机也可以在一轮处理中回收多个完成项。批量处理减少通知次数，轮询消耗 CPU，等待批次凑齐还会增加单个请求的延迟。排查发送停顿时，available 索引、used 索引和驱动回收位置可以分别定位到提交、后端处理和完成回收三个环节。

以队列长度 8 为例，设备消费位置是 7，驱动将链头 3 写入 `avail.ring[7]` 并发布 `avail.idx = 8`。后端发现一个新请求，按描述符长度取走数据，在 used 区归还链头 3。下个请求的 avail 槽回到 0，索引继续推进。队列槽位、链头和累计索引各有用途。同一个 kick 可以覆盖多次发布，同一次完成中断也可以让驱动回收多条链。在 vhost 配置中，kickfd 对应“驱动通知后端”，callfd 对应“后端通知驱动”。

## DMA 地址与内存隔离 {#dma}

设一个发送缓冲区位于客户机物理地址（GPA）`0x42000`。客户机 CPU 通过自己的页表访问它；在没有客户机 IOMMU 的常见 virtio 配置里，驱动把这段 GPA 交给设备。QEMU 软件后端通过虚机内存映射找到宿主进程中的地址（HVA），检查范围和访问方向，再读取报文。vhost-user 后端把同一块共享内存映射到自己的地址空间；两个进程中的虚拟地址可以不同。

直通时，网卡把描述符中的地址当作 IOVA。宿主为设备的 IOMMU 地址空间建立映射，限制它可读写的宿主物理页。简单配置可以让 IOVA 的数值与 GPA 相同；若客户机也启用了 IOMMU，驱动可以另选 IOVA，宿主还需要将客户机的映射变化同步到硬件可用的翻译路径。网卡在这个地址空间内发起 DMA，宿主 CPU 无需逐包替它查页表。

映射有生命周期。增加内存时，映射要在设备拿到描述符前生效；撤销映射或复位设备时，要停下相关队列，等未完成的 DMA 结束，再解除映射和释放页面。否则同一宿主页分配给下一个使用者时，旧设备还可能向它写数据。这也是把整个设备交给虚机之后，宿主仍须管理内存隔离的原因。

## 一次 4 KiB 磁盘读取 {#storage}

同一套交接方式也适用于磁盘。假设客户机向 virtio-blk 提交一个从扇区 2048 开始的 4 KiB 读请求。virtio-blk 以 512 B 为单位记录起始扇区，本次覆盖 2048 至 2055。客户机准备三部分缓冲区：

| 部分 | 设备的访问方向 | 内容 |
| --- | --- | --- |
| 请求头 | 读 | 操作码 `VIRTIO_BLK_T_IN`、起始扇区 2048 |
| 数据区 | 写 | 总长 4096 B，可以分布在多个描述符里 |
| 状态字节 | 写 | 后端写入成功或错误状态 |

```diagram device-io-read-handoff
4 KiB 读请求的提交与完成
成功路径中，数据写入缓冲区在前，状态字节和 used 项在后。驱动既可轮询完成队列，也可等待通知再读取它。
```

以 QEMU 自身作为后端时，`virtio_blk_handle_request()` 解析请求，把读操作提交给块层。虚拟盘若由宿主文件提供，数据可能来自宿主页缓存，也可能需要底层存储完成读取，具体取决于缓存配置和命中情况。读操作返回后，QEMU 写状态字节，将请求放入完成队列，按通知配置唤醒客户机。客户机块驱动据此结束请求，成功时上层即可使用这 4096 B 数据。

换成写请求，数据区变为设备读取，状态字节仍由设备填写。启用了写回缓存时，一次写完成可以表示数据已进入缓存；有持久化要求的客户机会在相应的写入之后提交已协商的 `VIRTIO_BLK_T_FLUSH`，等待此前的写到达后端承诺的持久化边界。比较两套存储配置的写延迟，需要同时说明缓存策略和测量的是普通写还是 flush。

## 性能定位与设备迁移 {#evaluation}

以发送延迟升高为例，驱动已发布而后端消费位置长时间落后，应查看消费队列的线程是否得到 CPU、多个队列是否集中在同一线程。后端已取走请求而 used 迟迟不动，重点是后端处理和下游设备。used 已推进而应用仍在等待，则看通知合并、vCPU 调度和驱动回收。比较 vhost、轮询或多队列时，固定报文长度、队列深度与 CPU 绑定，同时记录吞吐、尾延迟和每核占用，才能看出工作移到了哪里。

热迁移还要保存设备已经走到哪一步。假设块后端已接收一笔写入，客户机尚未看到 used：目的端重复提交会把同一请求再执行一次，直接丢掉则会让驱动一直等待。软件设备可以暂停接收新请求，排空在途工作，或按迁移协议保存并恢复它们；切换时还要交接队列位置、设备配置和未发出的通知。直通设备的内部队列由硬件和厂商驱动掌握，迁移需要设备提供状态保存、恢复及 DMA 写入追踪或相应的停机处理。能在源端直通，和能在另一台主机接着运行，是两项独立的设备能力。

## 总结 {#summary}

设备模拟保存的是旧驱动熟悉的硬件接口；virtio 把设备与驱动之间的交接定义成共享队列；VFIO 直通让硬件处理原生队列，用 IOMMU 划定访问范围。网络发送完成意味着缓冲区可复用，磁盘 flush 完成意味着此前的写达到约定的持久化边界。选后端、排查延迟或评估迁移能力时，沿着同一笔请求核对队列执行者、内存权限和完成语义，比只看设备型号更有用。
