## 本届观察 {#preface}

2019 年，一端是数百 vCPU、TB 级内存的云虚机，另一端是面向函数与容器的轻量 VMM。两类场景都促使开发者重新检查原有抽象：大锁能否拆开，宿主文件能否直接共享，公共组件能否脱离完整 VMM，硬件共享又会带来怎样的安全影响。本届精选保留设计与验证之间的距离，也保留生产中的实际失败经验。

## TDP MMU：让大虚机并行处理缺页 {#tdp-mmu}

```component talk-source-tdp-mmu
```

### 问题与工程价值

大虚机的多个 vCPU 可能同时等待二级地址映射建立。若所有缺页处理都竞争一把 MMU 锁，增加物理核也无法相应提高处理能力，在线应用还会出现长尾延迟与软锁死警告。Ben Gardon 针对非嵌套 TDP 场景提出独立、可并行的页表处理方式，目标是让内存管理随虚机规模扩展。

### 实现挑战

并发处理不仅需要原子修改 PTE，还要安全遍历和释放页表。Linux 可能通过 MMU notifier 撤销宿主映射，此时 KVM 必须阻止客户机继续访问旧物理页。CPU 的 TLB 和页表遍历缓存又可能保留已经从软件页表断开的路径，软件读者结束并不意味着硬件也停止引用相关页面。

### 解决方案

设计直接遍历 TDP 页表，用统一迭代器管理范围、修改和收尾，减少对通用影子页表元数据及反向映射的依赖。页表项用 cmpxchg 更新，冲突时重试；软件遍历在 RCU 保护下进行，移除的页表等待读者离开后回收。MMU 锁改为读写锁，普通缺页可并发，需独占的失效操作使用写侧保护。

页表回收还需要完成必要的 TLB 失效，防止硬件继续通过缓存访问已释放页表。能够延后的失效集中在真正要求同步的位置执行，减少每次缺页的额外开销。RCU 与 TLB 分别保护软件和硬件访问，两者不能互相替代。

### 验证结果

压力测试配置 416 个 vCPU、每个 4 GiB 地址范围，以 userfaultfd 模拟高并发按需供页。原始剖析中，MMU 自旋锁慢路径占比约 98.11%。并行化后，热点更多转向 GUP 和普通内存管理锁，说明 KVM 的主要串行点得到缓解，但系统仍有其他竞争。讲稿还估算移除部分元数据可节省约 0.2% 客户机内存，12 TB 规模约为 24 GiB。

### 局限与后续工作

这是针对非嵌套 TDP 的 RFC，如何与原影子 MMU 共存或整合当时仍在讨论。单项压力测试没有包含完整业务和网络传输，锁占比也不能直接转成应用加速倍数。后续需要验证大页拆合、宿主页迁移、并发失效及页表释放顺序，并继续处理移到普通 Linux 内存路径上的热点。收益来自减少共享状态和明确生命周期，不能只归结为换一种锁。

## Core scheduling：SMT 隔离与调度成本 {#core-scheduling}

```component talk-source-core-scheduling
```

### 问题与工程价值

同一物理核的 SMT 线程共享部分微架构资源。不同租户同时运行时，既可能影响彼此吞吐，也会暴露某些侧信道攻击面。关闭 SMT 简单直接，却可能损失整体容量。Core scheduling 尝试只让相互信任的任务同时占用同一物理核，保留可用的 SMT 收益，并改善共享资源的可解释性。

### 实现挑战

逻辑 CPU 的运行队列原本可以独立选任务，成组调度却需要协调同核兄弟线程。若没有合适的同组任务，一条线程必须强制空闲，即使系统仍有其他可运行任务。跨队列优先级、虚拟运行时间和负载均衡也需要统一，否则可能出现不公平或饥饿。按虚机分组与按虚拟核分组的效果也不同。

### 解决方案

讲稿比较 Xen 的固定调度单元与 Linux 的标签方案。前者把固定的一组 vCPU 映射到物理核资源；后者为任务打上兼容标签，调度一个任务时，为兄弟线程寻找同标签任务，找不到则空闲。Linux 方案更灵活，也增加了匹配、优先级比较和动态迁移的复杂度。

虚拟拓扑是否与物理执行位置一致需要额外策略，单纯给整台虚机同一个标签并不自动保证每对虚拟 SMT 线程始终同核。安全上，这类策略主要限制不同信任组并发共享同核资源；宿主与客户机之间的其他泄漏路径仍需要独立缓解。

### 验证结果

作者在 4 核 8 线程 Xeon 上比较关闭 HT、仅应用补丁、启用 core scheduling，覆盖一台和两台虚机及多种负载。内核编译等场景中，成组调度保留了更多 SMT 收益；sysbench 数据库场景却存在明显退化，部分结果还差于关闭 HT。测试使用开发中的补丁，作者也指出若干异常尚待解释，适合分析取舍，不能概括为普遍低开销。

### 局限与后续工作

2019 年 Linux 实现仍处于 RFC，匹配效率、公平性和超分开销需要继续改进。强制空闲比例、同组任务数量以及业务对缓存和内存带宽的敏感性都会改变结果。实际评估应比较相同安全目标下的方案，并分别测容量、尾延迟和隔离覆盖范围。把 core scheduling 当作消除全部侧信道风险的开关，会超出它的设计边界。

## virtio-fs：共享宿主文件与缓存的设计取舍 {#virtio-fs}

```component talk-source-virtio-fs
```

### 问题与工程价值

轻量虚机和容器虚机希望直接使用宿主目录，减少启动时复制文件和重复缓存。传统网络文件系统没有充分利用客户机与宿主共处一台机器的条件，既有目录共享方案的语义和性能也存在限制。virtio-fs 以本地文件系统语义为目标，提供可与独立后端配合的文件访问路径。

### 实现挑战

文件数据、路径查找和元数据缓存的共享方式并不相同。多个客户机或宿主同时修改文件时，需要失效与一致性协议。传统 FUSE 假设内核可信、守护进程受限，virtio-fs 却面对不可信客户机内核，必须检查其请求。客户机重启、卸载文件系统后，后端还可能继续存活，需要正确清理旧状态。

### 解决方案

客户机通过 Virtio 传输 FUSE 类请求，独立 virtiofsd 后端访问宿主文件，采用沙箱缩小权限。DAX 方案把部分文件页映射到客户机可见窗口，减少重复数据缓存和来回复制；窗口只是文件系统的一部分，需要按请求建立、撤销映射，不能当作整个共享目录永久直映。

缓存一致性可以在通信成本与可见性之间选择。讲稿还提出共享版本表，让多个客户机快速检查缓存是否过期，但当时尚未完整覆盖宿主文件变更。共享数据页并不会自动共享路径查找和元数据缓存，因此 DAX 不能独立解决全部一致性问题。

### 验证结果

测试使用 32 GB、24 逻辑 CPU 宿主和 ramfs 后端，客户机 8 GB、16 vCPU，DAX 窗口 8 GB；比较 cache=none 的 9p、virtio-fs 及带 DAX 的路径。同步 fio 中 DAX 明显提高多个负载吞吐；异步并发随机读写中，普通 virtio-fs 的结果却高于 DAX。图表说明减少复制并非唯一瓶颈，不能给 DAX 一个固定加速比例。

### 局限与后续工作

讲稿报告 Linux 5.4 的核心驱动和 QEMU 4.2 前端支持，DAX 与守护进程集成仍在推进。实现当时让共享文件系统的客户机彼此信任，并允许客户机控制文件身份与权限，这与安全隔离预期必须一致。后续需要完善缓存失效、后端复位和权限模型；部署应使用真实存储与应用验证，ramfs 基准主要突出协议和 CPU 路径。

## Firecracker 生产复盘：安全边界与测试遗漏 {#firecracker}

```component talk-source-firecracker
```

### 问题与工程价值

Firecracker 通过精简设备模型、Rust、jailer 和 seccomp 服务多租户轻量虚机，材料报告约 125 ms 启动和约 3 MiB 内存开销，并注明依赖负载与配置。演讲更有价值的部分是生产故障复盘：安全机制和严格语言仍可能在运行时变化、异常输入和测试遗漏面前失效，维护流程必须覆盖这些边界。

### 实现挑战

VMM 并不只执行项目自己直接写出的系统调用。Rust 运行时升级可能改变内存分配行为，只有特定负载才触发的新调用会逃过短测试。设备输入中的地址和长度也可能使整数运算溢出；调试构建触发 panic，发布构建却可能表现为无声回绕，导致同一缺陷在不同环境中呈现不同症状。

### 解决方案

一次更新中，Rust 版本变化引入未被 seccomp 白名单允许的 madvise，造成 VMM 异常退出。修复不仅补充白名单，也增加长时间、接近生产的测试，并利用日志与指标识别触发点。完全自动收集调用集合会扩大白名单，仍需对权限范围作人工判断。

另一个问题出现在客户机内存模型的偏移与长度相加。项目改用受检整数运算，把隐藏的 panic 或回绕转成可传播错误；CI 加入 Clippy 检查，进一步审查 unwrap、expect 等可能终止进程的路径。设备输入模糊测试也被列入后续计划，以弥补正常客户机驱动覆盖不到的情况。

### 验证结果

材料明确列出受影响版本、错误表现与修复方向：系统调用白名单问题影响 0.15.0、0.15.1，整数运算问题影响 0.12.0 之前版本。故障经过生产链路发现，原有约 20 分钟 CI 未覆盖特定运行条件。这里的证据是可定位的缺陷与修复，而非证明某种语言或沙箱已经排除所有错误。

### 局限与后续工作

延长测试会增加反馈时间，生产负载也无法穷举。较合理的组合是快速静态检查与边界测试，配合独立长测、运行时兼容测试和上线观测。Rust 能限制某些内存错误，仍需检查整数语义、外部接口和逻辑一致性。这个复盘适合所有 VMM：安全边界的变化应进入发布验收，故障处理路径本身也应保留可诊断信息。

## rust-vmm：把 VMM 拆成可复用组件 {#rust-vmm}

```component talk-source-rust-vmm
```

### 问题与工程价值

Firecracker、crosvm 等项目面向不同负载，却都需要客户机内存模型、KVM ioctl 封装、内核加载和设备基础设施。重复实现这些代码会分散审查与测试资源。rust-vmm 希望将共性提取为独立 crate，让项目按需求组合组件，同时保留自身设备范围和管理方式。

### 实现挑战

直接复制一个项目的结构，容易把它的内存布局和生命周期假设一并带入。不同 VMM 可能使用匿名或文件后备内存、不同总线与线程模型。接口过于具体会限制复用，过度通用又增加复杂度。Rust 的所有权规则帮助表达生命周期，但外部内核对象、共享内存和设备输入仍需要明确的安全契约。

### 解决方案

讲稿以 vm-memory 为例，把原来的具体内存结构抽象成地址、区域和客户机内存访问接口，使匿名内存与文件映射实现可以共享调用方。linux-loader 等组件依赖这些接口加载内容，无需了解所有底层布局。KVM bindings、ioctl 封装和系统工具组件则分别承担底层交互职责。

项目使用独立讨论、设计、测试和发布阶段管理 crate 成熟度。VMM 选择已经稳定的组件，暂时维护未完成组件的分支，再实现自身连接代码。这种方式把复用边界放在可审查的接口上，而非要求所有项目接受同一套完整虚机管理器。

### 验证结果

材料展示 Firecracker 内存模型的抽象过程，以及 Cloud Hypervisor 对 bindings、KVM、内存、加载器等组件的实际使用。与此同时，Cloud Hypervisor 仍有约四万行代码，设备和 Virtio 等组件还存在开发中分支，部分功能需要项目自行实现。这个数字说明公共组件已经有用，也说明“搭积木”并不等于只写少量配置即可获得成熟 VMM。

### 局限与后续工作

组件版本、错误语义和并发规则需要长期协调，公共库发布也不能替代组合后的系统测试。不同项目对迁移、设备模型和兼容性的要求可能差异很大，应避免把单一需求强塞进通用接口。后续价值取决于更多独立消费者验证抽象，并共同维护模糊测试与边界条件。复用可以集中审查力量，但也会让公共组件缺陷影响更多项目。

## SEV 运维配套：迁移加密内存与减少启动开销 {#sev-evolution}

```component talk-source-sev-evolution
```

### 问题与工程价值

SEV 为不同虚机使用独立内存密钥，宿主无法按普通明文页处理私有内容。迁移、页面移动和虚机频繁创建因此需要额外配套。演讲讨论安全保护如何进入日常运维路径：既要保持密钥和页面语义，也要避免安全处理器、全量内存固定和缓存刷新成为规模化部署的瓶颈。

### 实现挑战

源端与目标端的内存密钥不同，加密结果还与物理位置有关，复制密文不能直接完成迁移。安全处理器参与每批数据转换时可能限制带宽。普通页面整理或换出也不能随意移动加密页。虚机启动和销毁还涉及 ASID 回收及昂贵缓存刷新，频繁执行会放大管理成本。

### 解决方案

安全迁移让两端固件协商传输保护，并通过 SEND、RECEIVE 等接口转换页面；客户机通知共享与私有属性变化，宿主据此选择处理路径。迁移助手原型把认证与大量数据处理拆开：可信助手位于受保护执行上下文，完成授权后用 CPU 加密指令处理主体数据，减轻安全处理器的带宽负担。

ASID 管理将已停用标识暂存为可回收集合，等可用集合耗尽时统一刷新和回收，减少每次创建、销毁都触发重操作。页面移动则探索专用固件复制接口与内核回调；缺乏支持时仍需禁止移动，不能沿用普通 memcpy。

### 验证结果

讲稿报告迁移助手概念验证可达到数 Gbit/s，但未给出完整硬件、内存容量和负载参数，适合说明卸载数据处理的可行性，不能用于直接容量规划。SEV-ES 的 GHCB、固件和内核配套当时仍在完善，SNP 作为增加完整性保护的后续方向提出。材料中的不同阶段应分别理解，不能把它们合并成已经完成的统一产品能力。

### 局限与后续工作

当时没有通用私有页换出接口，消除启动前全量固定内存仍需更多内核整合。迁移助手扩大了受信代码范围，身份验证、密钥交付和失败恢复必须一起设计。SEV/SEV-ES 的机密性目标也不能替代后续 SNP 所处理的完整性问题。工程评估应同时关注保护边界、启动密度、维护耗时及页面状态变化的正确性。
