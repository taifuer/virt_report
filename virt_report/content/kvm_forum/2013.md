## 本届观察 {#preface}

这一年的五项精选都通过重新划分处理边界减少开销：嵌套地址转换选择更稳定的一层进行合成，共享内存视图把读取与回收分开，短时等待尝试保留执行上下文。图形转发与 COLO 则引入新的跨进程、跨机器协议。判断这些设计的价值，需要同时查看数据路径与一致性条件。

## Nested EPT：合成两层物理地址转换 {#nested-ept}

```component talk-source-nested-ept
```

### 问题与工程价值

L2 客户机的进程地址需要经过 L2 页表、L1 提供的二级映射和 L0 的宿主映射，最终才能访问物理内存。普通硬件二级地址转换不能直接承载这三层关系。早期影子方式会让 L2 页表修改与地址空间切换频繁退出，嵌套环境中的编译等负载因此付出很高代价。

### 实现挑战

L0 必须同时执行 L1 想呈现的映射规则和自身的隔离规则，并把不同来源的故障交给正确层处理。合成缓存还需要跟随映射更新失效。EPT 的位定义又与普通 x86 页表不同，读取、执行、内存类型和访问/脏位不能复用相同常量直接解释。

### 解决方案

Nested EPT 合成 L2 客户机物理地址到宿主物理地址的映射，让硬件继续遍历 L2 自己的进程页表。进程创建和 CR3 切换因此不必反复重建同一类影子进程地址空间；相较于进程页表，虚拟机物理映射通常变化更少。L1 与 L0 的权限和地址关系被组合到硬件实际使用的二级表中。

实现把 KVM 影子页表处理中的格式差异参数化，补充 EPT 语义。指令模拟仍需要从 L2 虚拟地址开始的软件翻译，因此使用额外的 nested MMU 上下文，依次得到 L2 物理地址和 L1 物理地址，不能直接拿只接受 L2 物理地址的 EPT 上下文代替。

### 验证结果

讲稿给出内核编译示例：Shadow-on-EPT 为 33 分 22 秒，Nested EPT 为 9 分 46 秒，运行时间约缩短 71%。它有力说明了频繁进程页表变化的场景会受益于不同的合成位置。

### 局限与后续工作

嵌套二级映射仍是软件维护的合成结果，页表更新、失效和故障归属都不能省略。大页、权限组合和指令模拟需要分别测试。后续评价应包括 L1 频繁改映射、L2 多 vCPU 并发和迁移，观察稳态收益之外的缓存重建成本与正确性。

## QEMU 多线程：内存视图、对象寿命与无锁访问 {#memory-concurrency}

```component talk-source-memory-concurrency
```

### 问题与工程价值

virtio-blk dataplane 证明专用线程可以改善高 IOPS 负载，但早期路径绕过部分通用内存和块层逻辑，功能维护成本随之增加。要让更多设备安全地并行运行，需要把共享地址空间读取、设备寿命和管理更新整理成可复用机制。讲稿展示渐进移除高频锁依赖的路线。

### 实现挑战

设备 DMA 在映射与解除映射之间可能跨越热拔除，内存区域若已经释放就会产生悬空引用。地址翻译本身与设备回调也不是不可分割的操作：一个 vCPU 翻译 BAR 后，另一个 vCPU 可以改变映射，前者随后访问的对象可能已经不符合新的设备状态。局部回调加锁无法自动解决这个整体顺序问题。

### 解决方案

FlatView 按不可变快照更新，读取者持有引用，更新者发布新视图；MemoryRegion 通过所有者关系维持设备寿命。设备从客户机视图移除与实际内存回收分开，已有访问结束后才释放资源。讲稿进一步以 RCU 降低读取侧同步成本，写侧仍可保留 BQL 简化更新。

无锁 MMIO/PIO 采用选择性开放，优先面向静态映射或语义清楚的半虚拟设备。对动态映射，需要额外检查或锁来保证翻译与访问的关系。该设计承认通用管理路径与高频数据路径的需求不同，并不追求一次删除全部全局锁。

### 验证结果

四 CPU Ivy Bridge 平台上的 ACPI PM timer 微基准中，单 vCPU 去除 BQL 后约改善 3%，四 vCPU 访问成本约减少 30%；八 vCPU 时仍有明显额外成本。并发访问越多，锁竞争对访问成本的影响越明显。材料还明确脏页位图处理等工作尚未完成。

### 局限与后续工作

地址空间快照解决读取稳定性，却不自动保证设备内部状态的原子性。脏页记录、迁移、热拔除和跨设备 DMA 仍需共同审查。后续验证应检查对象回收时机及映射变化期间的访问，避免只验证无竞争的吞吐，把低频但危险的生命周期错误留在系统中。

## Virgil3D：通过 Virtio 提交图形命令 {#virgil}

```component talk-source-virgil
```

### 问题与工程价值

客户机需要硬件加速图形，但整卡分配限制共享，完整图形 API 转发又涉及大量接口语义。Virgil3D 从 Mesa Gallium 的状态与命令表示出发，通过虚拟设备把绘制任务交给宿主 GPU。它让图形虚拟化可以建立在通用设备接口上，并复用宿主已有的 OpenGL 实现。

### 实现挑战

客户机上下文、纹理和着色器需要在宿主维护对应对象，异步执行还要求明确完成通知。客户机能力不能超过宿主接口能够表达的范围，着色器语言转换也可能遇到语义差异。命令与资源都来自不可信客户机，宿主渲染器及图形驱动成为新的输入处理边界。

### 解决方案

客户机 Mesa 驱动把 Gallium 状态、绘制和资源操作编码后送入 Virtio 队列，宿主渲染器将其转换为 OpenGL 调用，并把 TGSI 着色器转换为 GLSL。客户机上下文对应宿主 GL 上下文，以维持条件渲染等语义。资源传输、能力查询和 fence 共同构成设备协议。

讲稿同时区分基础 virtio-gpu 显示设备与可附着的 3D 渲染器。多显示头、光标和窗口系统属于显示集成工作，绘制加速属于渲染路径；显示集成和 3D 渲染各自有独立的能力要求。

### 验证结果

2013 年材料把项目明确标为研究原型，展示 Linux 图形渲染和多显示头演示。客户机接口当时主要达到 OpenGL 2.1 一类能力，更高版本仍涉及多重采样、上下文和迁移问题。演示验证了图形功能；与原生 GPU 的帧率、延迟及资源占用对比仍待测量。

### 局限与后续工作

完成事件的返回方式、64 位状态传递、安全隔离及 libvirt 集成仍在讨论。DRM render nodes、EGL 和 dma-buf 被列为后续方向。工程评价需要同时测试图形正确性、恶意命令、资源耗尽和上下文销毁；一个成功演示只覆盖了功能路径的一小部分。

## COLO：以对外响应校验虚拟机副本 {#colo}

```component talk-source-colo
```

### 问题与工程价值

虚拟机级容错希望在主机故障后继续服务，避免每个应用单独实现复制协议。逐指令锁步需要控制多核非确定性，连续检查点又会带来同步和输出等待成本。COLO 将观察点放到对外响应：主备分别运行，只要产生的输出保持匹配，就可以减少频繁完整同步的需要。

### 实现挑战

副本内部状态可能不同，网络输出必须在适当边界比较并受控放行。检测到差异后，需要让内存、设备和磁盘回到一致检查点。磁盘写入若过早持久化，会留下无法回退的外部状态；故障发生在比较、缓存或同步的不同阶段，也会改变接管条件。

### 解决方案

输入报文复制给主备虚拟机，备用输出回传比较模块。输出相同时对外发送，不同时触发检查点同步。讲稿使用流量镜像与重定向接入既有虚拟网卡路径，避免要求客户机应用或驱动专门配合。

存储路径增加磁盘管理层，分别维护主副本写缓存，按检查点或故障切换状态选择提交内容。QEMU 迁移流程被改造成可重复同步内存与设备的检查点机制，主备之间还需要心跳和切换协调。网络、存储和虚拟机状态构成一个整体协议。

### 验证结果

Web Bench 和 Pgbench 图给出的是基于 SoCC 2013 数据的性能预测。图中结果随并发数和 vCPU 数量变化明显，高并发 Web 场景仍有较大损失。讲稿的后续计划包括重新设计、开发并提交评审，说明当时方案距离完整上游实现还有工程工作。

### 局限与后续工作

COLO 覆盖哪些外部副作用，取决于系统接管了哪些 I/O，以及如何处理故障。比较延迟、频繁检查点和副本落后也会影响服务质量。从工程角度，还需要独立验证故障检测、隔离旧主机和重复输出防护。

## 短时空闲：消息负载中的 vCPU 切换成本 {#idle-latency}

```component talk-source-idle-latency
```

### 问题与工程价值

短消息服务每次处理很少工作，随后等待下一条消息或响应。客户机进入空闲会触发宿主处理、保存扩展状态并可能调度其他任务；若等待本身很短，这些工作可能超过有效处理时间。讲稿通过消息队列实验定位切换成本，解释为何低 CPU 利用率也可能伴随较差吞吐。

### 实现挑战

宿主并不知道客户机上次运行期间是否切换过任务、是否使用了 FPU，通常必须按安全规则保存状态。让客户机持续占用 CPU 可以避免部分切换，却可能阻止真正负责产生响应的宿主线程运行。延迟保存状态还涉及抢占、跨 CPU 迁移和调试读取，不能只改一条空闲路径。

### 解决方案

作者逐步拆分调度、vCPU 加载卸载与 FPU 保存，再比较三条方向：客户机感知的短时空闲策略、延迟 FPU 保存，以及让当前任务短暂进入可唤醒等待而不立即完整切换上下文。最后一种提案允许有其他任务需要 CPU 时执行正常保存和调度，试图同时兼顾短等待与宿主公平性。

讲稿讨论的 idle_poll 等接口属于实验设计。在这个版本的实现中，保存上下文的成本和下一次事件到达的时间共同决定了轮询是否划算。

### 验证结果

Java 读写线程队列实验中，默认路径约为每秒 13.55 万次，绕过部分保存与调度后可达到约 21 万次。部分测量通过跳过必要工作来定位成本，并不是可以直接部署的安全实现。这些测量将开销分解到各执行步骤。

### 局限与后续工作

空闲预测错误会浪费 CPU，过量分配时也可能放大等待依赖。跨 CPU 保存状态的 IPI 成本可能使长尾更差。后续验证应加入竞争线程、不同消息间隔和功耗测量，比较吞吐改善与宿主可调度性，并确保所有状态在抢占和迁移边界得到正确保存。
