## 本届观察 {#preface}

2021 年的精选讨论了资源效率与可靠运行之间的关系。内存超分需要客户机、宿主换页和控制策略协作；大虚机迁移使原本不起眼的位图操作变成显著开销。VDUSE 与外部设备迁移尝试建立更通用的后端接口，SEV-SNP 则让内存管理承担新的安全职责。理解这些工作，需要同时看机制、失败路径和当时的实现状态。

## 生产内存超分：组合 balloon、换页与工作集估计 {#memory-overcommit}

```component talk-source-memory-overcommit
```

### 问题与工程价值

虚机配置的内存通常大于持续使用的工作集，回收闲置容量可以提高宿主利用率。生产平台却不能假设所有客户机都及时响应 balloon，也不能任由宿主换页造成业务抖动。演讲将 Linux 内存管理、cgroup、virtio-balloon 和监控信息组合成自适应控制系统，重点在于如何应对不完整信息和不可控的客户机行为。

### 实现挑战

宿主和客户机可能同时选择同一批冷页换出。客户机准备写交换区时，又要把宿主已经换出的页读回来，形成重复 I/O。需求突增时，其他虚机回收内存也需要时间。监控数据还有不同来源和可信程度：客户机可报告可回收内存与交换活动，宿主只能从缺页、驻留页和访问采样推断需求。

### 解决方案

控制器优先用 balloon 回收，再降低 cgroup 限额；扩容时提高宿主限额后再释放 balloon 占用，避免两侧动作互相施压。客户机迟迟不响应时，系统回退到宿主换页。宿主保留一小部分未分配内存，满足紧急增长后再逐步补回储备，以容量利用率换取响应速度。

需求评估结合客户机交换统计和 QEMU 的主要缺页，并用 Idle Page Tracking 对物理页抽样估计工作集。采样结果做滑动平均，减少短期噪声。分配按需求排序，回收按可释放容量分摊；这套策略承认无法精确预测每台虚机下一刻需要多少内存，通过连续反馈修正决定。

### 验证结果

生产部署暴露了一个容量问题：迁移全量扫描会把已换出的冷页读回内存，甚至为原本不驻留的零页分配空间。扫描产生的访问也会干扰工作集判断。作者用 MADV_COLD、MADV_PAGEOUT 等机制缓解影响，同时指出共享页的 pagemap 信息与普通私有映射不同。

### 局限与后续工作

工作集抽样有误差，备用池也不可能吸收所有同时到来的需求。控制系统应限制单轮调整幅度，并监测业务尾延迟及持续换页，防止反馈来回震荡。共享交换空间、迁移时只传冷页位置等方案属于后续方向。这里最有价值的经验是把回收方式、观测口径与失效回退一起设计，而非仅选择一个看似精确的内存使用指标。

## 大内存迁移：脏页位图也会成为瓶颈 {#dirty-tracking}

```component talk-source-dirty-tracking
```

### 问题与工程价值

迁移需要持续知道客户机改写了哪些页面。小虚机上，收集这些标记的成本容易被数据传输掩盖；内存增长到 TB 级后，位图本身就达到数十到数百 MB。Peter Xu 展示一个不算繁忙的 3 TB 客户机，QEMU 同步脏页位图仍约需 200 ms。优化迁移因此也要检查管理数据的处理路径。

### 实现挑战

写入捕获和结果上报是两个环节：写保护或硬件记录负责发现修改，位图或每 vCPU ring 负责汇报。进入 QEMU 后，KVM memslot、通用 RAM 脏标记和迁移逻辑还可能维护多层位图，vhost、VFIO 等来源也需要合并。并发置位与清除必须可靠，否则会漏掉迁移期间的写入；但逐字原子操作的成本不低。

### 解决方案

讲稿梳理 dirty ring、并行 MMU 缺页处理和延迟写保护等已有进展，并把位图归并作为独立优化目标。候选方法包括减少重复层次，以及用更明确的同步区间替代整张位图上的大量原子交换。作者提出写入侧在读锁下原子置位、收集侧持写锁批量复制的思路，以交换并发度和复制效率。

这套替换需要证明所有置位来源都受同一协议保护。原子操作虽有成本，却承担了正确性职责，不能直接改成普通 memcpy。KVM 的 CLEAR_DIRTY_LOG 与 QEMU 的位图归并走不同路径，两处开销应分开测量。

### 验证结果

256 MB 位图对应约 8 TB、4 KiB 粒度内存。微基准中，i7-8665U 上逐字 xchg 约 240 ms，普通复制约 80 ms；Xeon E5-2630 v4 上约为 525 ms 与 148 ms。结果说明批量处理有优化空间，并非迁移总时间可以缩短三倍。微基准运行环境与前述 3 TB 虚机观察不同，读写并发和缓存状态也会改变比例。

### 局限与后续工作

读写锁方案当时仍需验证，收集期间长时间阻塞置位可能把成本转移到客户机执行。dirty ring 可以减少稀疏修改时的扫描，也需要及时消费和处理环满。完整评估应同时看收集耗时、vCPU 停顿、不同设备的脏页覆盖和最终一致性。更快的网络会让这些 CPU 端管理开销更加突出，值得独立纳入迁移性能测试。

## VDUSE：让用户态设备服务虚机和容器 {#vduse}

```component talk-source-vduse
```

### 问题与工程价值

用户态存储后端便于开发、更新和隔离，但虚机与普通宿主应用通常需要不同接入方式。VDUSE 在 vDPA 框架下实现用户态设备，让同一后端既能连接 vhost-vDPA 服务虚机，也能连接 virtio-vDPA，作为宿主可用设备。这样可以复用协议与实现，减少为容器另建一套存储路径的工作。

### 实现挑战

后端必须访问请求缓冲区，却不能随意映射宿主内存。虚机已有可共享的客户机内存，宿主 Virtio 驱动提交的 DMA 缓冲区则需要不同保护。设备初始化、状态变化和 IOTLB 更新还可能与数据处理并发，若映射撤销后继续使用旧地址，就会产生错误访问。控制与数据路径需要共同约束后端行为。

### 解决方案

VDUSE 通过字符设备和 ioctl 创建设备、声明特征与队列参数，内核承担大部分 vDPA 控制逻辑。需要用户态处理的状态变更和队列查询通过消息传递。达到 DRIVER_OK 后，守护进程获取队列信息、建立被允许的 IOVA 映射，再消费描述符。

虚机场景共享对应内存，宿主 virtio-vDPA 场景使用回弹缓冲区和软件 IOTLB，限制用户态后端可访问范围。kick 可以通过 eventfd 接收，完成后更新 used ring 并请求注入队列中断。队列和数据缓冲区都必须通过映射接口取得访问权，不能只映射描述符后就信任其中的任意地址。

### 验证结果

演讲给出了内核第 11 版补丁系列、用户态示例及完整初始化步骤，已经可以沿接口搭建后端。这里比较的是各条路径的接口和职责；吞吐与延迟尚无对照数据。结果主要证明统一接入方式的可实现性，也展示了虚机共享内存与宿主回弹缓冲区之间的实际区别。

### 局限与后续工作

当时用户态公共库、更多设备类型和性能改进仍在计划中。后端崩溃、消息超时、IOTLB 撤销与设备复位的交互需要充分测试，尤其不能让等待用户态的控制请求永久卡住设备管理。回弹复制还可能成为宿主路径的成本。对使用者而言，统一接口降低维护负担，但仍应按虚机和容器分别测量实际数据路径。

## SEV-SNP：把页面所有权纳入硬件检查 {#sev-snp}

```component talk-source-sev-snp
```

### 问题与工程价值

SEV 的内存加密与 SEV-ES 的寄存器保护提高了机密性，但客户机还需要防止恶意宿主修改映射关系、重放或破坏私有数据。SEV-SNP 引入页面所有权和验证规则，让私有内存的访问受到额外硬件约束。演讲把安全目标与 Linux、QEMU、固件的具体改造联系起来，适合理解机密虚机为何需要完整软件栈支持。

### 实现挑战

宿主仍要分配物理页和建立嵌套页表，客户机又必须决定何时接受页面。私有页转换为共享页时，大页粒度可能与 RMP 记录不一致，产生新的缺页处理。设备 I/O、额外 vCPU 创建和证明请求也需要通过受控协议与宿主或安全处理器通信，不能沿用会泄露私有寄存器和数据的普通路径。

### 解决方案

RMP 按系统物理页记录归属及相关属性，硬件检查页面是否可被当前主体使用或写入。客户机通过 GHCB 页面状态变更请求协调宿主更新记录，再用 PVALIDATE 接受私有页面。页面归属与客户机主动验证共同限制恶意重映射；私有页的交付还需要完成所有权和访问权限的转换。

启动流程由安全处理器建立客户机上下文、加入初始页并形成测量，完成后使客户机可运行。不同页面类型区分普通内容、寄存器状态、密钥信息和受过滤的 CPUID 信息。客户机驱动可请求证明报告与派生密钥，让远端验证与应用密钥使用有明确接口。

### 验证结果

2021 年的材料列出内核、OVMF 和 QEMU 的开发分支及补丁版本，已有多 vCPU、证明报告、过滤 CPUID 和 THP 后备内存等支持。固件当时在启动阶段验证全部客户机 RAM。当年的材料记录了已实现的接口流程；内核和管理工具的进一步集成属于后续工作。

### 局限与后续工作

延迟验证、客户机 kexec、热迁移、HugeTLB 和受限中断注入都列在后续工作中。硬件具备相关能力与软件栈完整使用该能力之间存在距离。SNP 也不保证宿主持续调度客户机，部分侧信道和高级物理攻击在范围之外。部署时需要核对固件、内核、VMM 和证明策略的组合，明确哪些数据和状态受保护。

## 外部设备迁移：状态格式与兼容性如何约定 {#device-migration}

```component talk-source-device-migration
```

### 问题与工程价值

VFIO、vhost-user 和 vfio-user 把设备处理放在 QEMU 之外，迁移时仍要保持客户机观察到的状态连续。管理平台还需要在开始传输前判断目标是否兼容，否则可能在投入大量时间和带宽后才失败。演讲关注设备状态表示和兼容性协商，直接关系到后端更新、跨宿主维护与异构设备部署。

### 实现挑战

设备状态包含寄存器和恢复处理所需的内部进度，例如队列消费位置；宿主文件描述符等本地资源需要在目标端重新建立。不同实现即使提供相同设备类型，也未必使用相同状态格式。状态格式升级还可能修复历史错误，兼容版本与软件发布版本之间不能简单画等号。

### 解决方案

传统 vhost-user 迁移可在停止后端后由 QEMU 接管 virtqueue，并复用 Virtio 状态保存。具有额外内部状态的设备则需要扩展协议或辅助状态通道。VFIO 和 vfio-user 通过设备提供的数据流保存恢复，使 QEMU 无需理解每种设备内部结构，但格式演进责任也随之落到设备实现者。

作者提出设备模型标识和迁移兼容版本，由目标查询是否接受源端组合；兼容时再实例化目标设备并传输状态。相容的软件和硬件实现可以约定同一状态表示。版本标识用于查询，实际兼容性由目标设备根据客户机可见接口和状态格式判断。

### 验证结果

讲稿比较了已有迁移机制，并给出面向管理工具的协议提案。它没有展示完整实现之间的跨设备性能测试，模型和版本协商也仍待讨论与落地。当时已有设备状态数据流；演讲提出的跨实现兼容检查仍处于设计阶段。

### 局限与后续工作

将创建参数固定进版本可以简化检查，却可能使版本组合膨胀；复杂设备还需要更细致的能力描述。共享格式必须覆盖完整客户机状态，并定义拒绝、回滚及部分恢复失败的行为。后续需要 libvirt 等管理工具接入，以及多个独立实现共同验证。兼容性检查可以在传输前排除不匹配的组合；目标端恢复后还需要验证设备能继续处理请求。
