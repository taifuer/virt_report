## 本届观察 {#preface}

KVM Forum 2026 于 11 月 12—13 日在加拿大温哥华举行。本页选择六场与资源利用、存储性能和热迁移直接相关的分享。它们涉及云平台运行中的具体问题：空闲虚机仍占着 CPU 和内存，固定的 I/O 线程配置跟不上负载变化，迁移扫描干扰业务，机密虚机与 GPU 又带来了新的状态传输要求。

这些方案的工程价值各有侧重。CPU 超分与 EPT 写时复制着眼于单机可承载的实例数量；内存分层关注资源节省对业务延迟的影响；IOThread 控制器尝试降低人工调参成本；TDX 与 vGPU 迁移分别处理状态保护和大体量设备数据传输。

实验数据引自原始讲稿，实现状态以大会时点为准。

## CPU 超分：空闲识别与 vCPU 调度 {#cpu-overcommit}

```component talk-source-cpu-overcommit
```

### 问题与工程价值

CPU 超分利用不同虚机的负载错峰，让一组物理 CPU 承载更多 vCPU。能否提高密度，取决于空闲时间是否真正交还宿主，以及调度这些 vCPU 本身消耗多少 CPU。大量短任务和等待外部服务的会话，会同时放大这两方面的成本。

字节跳动的分享区分了三个场景：专用、绑核虚机的空闲时间被隐藏；共享虚机中的大量 vCPU 线程产生唤醒和切换开销；已分配完 CPU 的宿主上，后台工作抢占 vCPU，造成延迟抖动。三种场景分别采用动态截获 MONITOR/MWAIT、轻量 vCPU 执行上下文和基于 sched_ext 的调度策略。

### 实现挑战

MONITOR/MWAIT 允许客户机监控一段内存，并等待相关写入。在允许这组指令直接执行的绑核配置中，客户机已经进入等待，宿主仍可能把 vCPU 线程记为运行。使用这个线程的 CPU 占用率判断客户机忙闲，会漏掉可回收的空闲时间。

把 vCPU 线程阻塞后，还需要可靠的唤醒来源。中断可以沿 KVM 已有路径唤醒它，另一个 vCPU 对监控地址的普通写入却通常不会退出到 KVM。定时检查能够发现变化，但周期长会增加等待，周期短会频繁触发调度和重新进入客户机。

共享虚机还有另一层成本：每次唤醒一个 vCPU 都可能涉及宿主线程调度，vCPU 之间的交接也会带来线程上下文切换。替换这个执行模型需要维护每个 vCPU 的寄存器、地址空间、可运行状态与阻塞状态。

### 解决方案

动态 MWAIT 方案利用绑核物理 CPU 的 C0 驻留情况判断客户机是否持续空闲。C0 表示处理器正在执行的状态，这个信号能补充宿主线程统计看不到的空闲情况。负载较高时保留指令直执行，持续空闲时切换到截获路径。

截获 MONITOR 时，KVM 保存目标页号与 64 字节缓存行的位置。MWAIT 的短暂轮询没有等到变化、vCPU 即将阻塞时，方案登记等待者，并清除对应 4 KiB 二级页表项的写权限。其他 vCPU 的写入由此触发写保护异常：命中监控缓存行就恢复写权限、重试写入并唤醒等待者；同页的无关写入由模拟路径处理。页是截获粒度，缓存行是匹配粒度。

实现使用叶子页表项的原子更新减少锁竞争，并保留较长周期的兜底定时器。涉及大页时，会拆成 4 KiB 映射并限制反复合并，避免重复拆分成本。这也意味着回收空闲 CPU 会改变该区域的映射方式。

轻量 vCPU 方案则为每个物理 CPU 设置承载内核线程，在本地队列中选择可运行的 vCPU 上下文。执行过程包括切换上下文和地址空间、进入客户机、处理退出或阻塞、选择下一个上下文。讲稿中的当前实现采用函数调用式分派。sched_ext 部分面向绑核宿主，结合客户机忙闲与待处理事件调整调度，兼顾 vCPU 响应和宿主任务的执行机会。

### 验证结果

动态 MWAIT 的实验使用 Intel Granite Rapids 2.8 GHz、32-vCPU 虚机。唤醒测试中，vCPU 0 每 10 ms 唤醒 vCPU 1，测量后者的响应延迟。

| 观察项 | HLT 基线 | 1 ms 定时检查 | 写保护唤醒 |
| --- | --- | --- | --- |
| 唤醒延迟 | 10 µs | 508 µs | 11 µs |
| UnixBench 单并发得分 | 1997 | 933 | 2019 |
| UnixBench 32 并发得分 | 12724 | 8012 | 13130 |

HLT 基线关闭 CPU-PM，后两组开启 CPU-PM。结果表明，在这组配置中，写保护唤醒把响应时间恢复到接近 HLT 的水平，并避免了定时检查组的明显性能损失。

轻量 vCPU 的独立微基准以每 vCPU 内核线程为基线，报告唤醒到客户机入口减少约 1.7 µs，vCPU 交接减少约 1.6 µs。sched_ext 部分展示了宿主竞争下观察到的最长约 13 ms 调度延迟，并介绍处理思路；这部分尚缺少完整的优化前后对照数据。

### 局限与后续工作

动态 MWAIT 更适合有持续空闲窗口、监控写入频率适中的绑核虚机。作者报告，高并发、低负载场景仍可能因为频繁退出而退化。轻量上下文虽然缩短了部分调度路径，跨 CPU 移动仍会破坏缓存局部性。

工程上最值得继续验证的是整机收益：回收多少可用 CPU、付出多少退出和切换成本，以及混合负载的尾延迟是否稳定。轻量执行模型还应覆盖公平性、资源计费和阻塞唤醒竞态；sched_ext 策略需要验证宿主后台任务能够持续推进。三部分应针对各自场景评测，分别确认收益。

## QEMU 内存分层：迁移时保留冷热分布 {#memory-tiering}

```component talk-source-memory-tiering
```

### 问题与工程价值

内存分层将经常访问的页面保留在 DRAM，把仍有业务内容、访问较少的页面放到成本较低的存储层。宿主可以通过内存控制组、swap 和页面回收策略管理 QEMU，客户机继续使用原有地址空间。这对内存长期驻留、活跃工作集较小的虚机有直接价值。

热迁移会破坏这种分布。迁移线程遍历客户机内存时，已经换出的冷页被重新读入 DRAM；内存压力又可能把业务热页挤出去。目的端接收页面后，也要重新建立冷热分布。虚机虽然一直运行，业务却可能经历明显的缺页等待与尾延迟上升。

### 实现挑战

迁移需要读取每个有效页面，但这些读取来自维护操作，不能准确代表业务对页面的需求。源端需要保存迁移前的分层信息，目的端需要按这个信息恢复页面驻留状态，同时继续满足内存数据一致性和脏页迭代的要求。

现有接口也有精度与时序限制。`mincore()` 提供某一时刻的驻留快照，访问频率还需要其他信息判断；`MADV_PAGEOUT` 尽力请求回收，返回时页面可能仍在内存或 swap cache 中。`memory.high` 是触发回收与节流的阈值，实际驻留量会随负载变化。多个进程映射同一页时，PAGEOUT 还存在限制，vhost-user 需要特别关注这一点。

### 解决方案

Peter Xu 比较了三条路径：

| 路径 | 主要做法 | 工程代价 |
| --- | --- | --- |
| 新增分层访问接口 | 读取页面时保留热度信息，冷页数据直接从换出位置读取 | 需要新的内核 ABI，目的端直接写入慢层仍待实现 |
| QEMU 自己管理慢层 | 跟踪访问、移出冷页，用 userfaultfd 处理按需读入 | 需要维护用户态换页系统，并解决热度跟踪与内核回收的协调 |
| 复用现有内核接口 | 记录驻留状态，读取冷页后请求回收，并向目的端传递冷页标记 | QEMU 改动较小，受 PAGEOUT 的回收语义和共享映射限制影响 |

讲稿重点验证第三条路径，把驻留状态作为冷热的近似信号。源端在读取页面前用 `mincore()` 记录状态，对原本不驻留的页面在读取后执行 PAGEOUT；迁移流携带冷页标记，目的端收到这些页面后也请求回收。这个设计让迁移操作能够保留原有分层策略的信息。

为了减少异步回收造成的短时驻留量增长，作者又尝试了 `MADV_PAGEOUT_FULL`：等待换出与 swap cache 回收完成，并扩展多重映射页面的处理。更充分的等待可以减小对业务工作集的冲击，同时延长迁移线程完成首轮扫描的时间。

### 验证结果

实验使用 Linux 7.1、QEMU 11.1.50，客户机内存 6 GB，memcg 阈值 3 GB，迁移带宽限制 1 GB/s。业务在 2 GB 热内存上以约 300 MB/s 的速度写脏，另有 3.5 GB 冷内存。慢存储由单机 `scsi_debug` 模拟约 100 µs 延迟。

| 内存后端与观察项 | 普通迁移 | 传递冷页标记并 PAGEOUT |
| --- | --- | --- |
| shmem：迁移总时间 | 约 32 s | 约 13 s |
| shmem：业务 p99 峰值 | 约 100 ms | 约 30 µs |
| 匿名内存：迁移总时间 | 约 25 s | 约 12 s |
| 匿名内存：业务 p99 峰值 | 约 40 ms | 约 400 µs |

匿名内存继续采用 FULL 版本时，p99 峰值从约 400 µs 降到约 20 µs，迁移总时间由约 12 s 增加到约 20 s。这个结果说明了取舍：迁移线程多等待一部分回收工作，业务承受的内存压力随之减小。

### 局限与后续工作

这些结果来自模拟慢存储。作者计划补充真实 NVMe 测试、整理并发布 QEMU／内核补丁，以及根据每台虚机的负载动态调整分层比例。`ram-tiering` 与 `MADV_PAGEOUT_FULL` 在这次分享中属于实验方案。

这项工作的价值在于把迁移性能与业务性能放在一起评价。落地时应分别测量业务吞吐和尾延迟、换入换出量、迁移耗时及内存峰值，并覆盖共享内存后端。最短的迁移耗时和最小的业务扰动可能对应不同配置，需要按服务目标选择。

## EPT 写时复制：共享快照与独立写入 {#ept-cow}

```component talk-source-ept-cow
```

### 问题与工程价值

Agent 沙箱等待模型回复时，CPU 可以处理其他工作，浏览器、服务进程和会话状态却仍占着内存。大量沙箱使用相近的软件环境，重复保存这些初始化内容会限制单机实例密度。检查点恢复和训练环境复用还会产生快照存储与读取成本。

共享一份初始化快照、只为各实例保存修改，能够减少重复内存与数据传输。这场分享的重点是把共享扩展到整个虚机：vCPU、VMM 和独立的 vhost-user 后端要访问同一份实例数据，同时保持不同实例之间的隔离。

### 实现挑战

普通的进程私有写时复制按进程产生独立页面。虚机的 VMM 和 vhost-user 后端却需要共享客户机内存；若它们各自复制，双方看到的数据就会分离。这里需要的复制单位是“一台 VM 及其后端进程”。

页面切换还涉及并发。一个 vCPU 已经把页面复制到私有后备，另一个尚未结束的读缺页可能仍持有旧地址。设备模拟与 vhost-user 又可以从宿主访问内存，单独处理客户机的写异常不足以覆盖这些入口。

快照存储同样需要可回收的可写层。讲稿使用 virtio-pmem DAX，将相关存储缓存交给宿主管理，并把远端按需读取、文件支持的私有修改与 RAM 快照复用放在同一套设计中。

### 解决方案

实验实现为同一段客户机物理地址设置配对的 C/W memslot。C 指向共享只读内容，W 指向该 VM 的可写后备。读取未修改页面时使用 C，首次写入复制 4 KiB 到 W，并将二级页表映射切到 W。`KVM_ENABLE_COW` 等接口属于这个实验实现。

| 访问入口 | 保持同一份实例数据的做法 |
| --- | --- |
| vCPU 写异常 | 原子认领复制操作，复制页面、标脏、失效旧映射并同步 TLB；并发缺页在安装映射前重新检查当前后备 |
| VMM 设备模拟 | 通过共享位图判断页面归属，需要私有页面时调用范围 CoW 操作 |
| vhost-user 后端 | 只映射 W；客户机 virtio 驱动在发布队列前准备相应的缓冲区页面 |

客户机缓冲区准备的做法很具体：从 I/O 缓冲区的每页读出一个字节并原值写回，让仍处于 C 的页面完成 CoW。输入、输出缓冲区以及 Split、Packed 队列都在发布请求前完成这一步，后端因而能从 W 读写正确的数据。这是该路径需要客户机驱动配合的原因。

快照以 2 MiB 块保存和获取数据，未变块沿用原有引用，变化块生成新内容。恢复时由 userfaultfd 触发远端块读取并映射到 C；实例的首次写入仍按 4 KiB 复制到 W。存储读取粒度与私有页面粒度分别控制远程访问成本和内存增长。

### 验证结果

一台宿主上的 1,000 个空闲沙箱，平均占用从冷启动的 322 MB 降到快照恢复后的 13.11 MB，降幅约 95.9%。另一个工作负载观察记录了两个实例：工具执行前平均共享比例约 85.0%，实例 A 完成后约 82.1%。后者是两个实例、两个时点的采样结果。

恢复后的访问测试使用 2 vCPU、4 GB RAM、Xeon Platinum 8336C 2.30 GHz，快照文件位于本地磁盘。首轮访问耗时如下：

| 访问模式 | 进程私有映射 CoW | KVM CoW |
| --- | --- | --- |
| 顺序读 | 165.772 ms | 154.177 ms |
| 顺序写 | 213.762 ms | 216.362 ms |
| 随机读 | 133.657 ms | 134.309 ms |
| 随机写 | 210.724 ms | 218.335 ms |

顺序测试遍历 256 MiB；随机测试在相同数量的页面中每页访问 8 字节，实际触碰 512 KiB。因此应在同一行内比较两种实现。结果支持这组本地磁盘条件下的首轮访问成本接近，远程恢复延迟仍需单独测量。

### 局限与后续工作

当前 vhost-user 路径依赖客户机缓冲区准备，Windows 和用户自带内核需要其他方案。作者提出两个方向：由共享内存对象的宿主缺页路径处理 CoW，或截获 I/O，在交给后端前完成 CoW。前者需要重新考虑内存回收与共享范围，后者增加队列截获和转发工作。

这项设计值得关注的地方，是给多进程虚机建立统一的可写视图。工程验证应继续覆盖活跃实例的共享率衰减、远程缺页尾延迟、后端写入与脏日志的一致性，以及快照恢复中的故障处理。空闲密度收益、活跃负载成本和客户机兼容性需要一起衡量。

## IOThread 动态伸缩：按负载调节 I/O 线程 {#io-thread-controller}

```component talk-source-io-thread-controller
```

### 问题与工程价值

虚机磁盘负载会随业务阶段、备份任务和部署位置变化，启动时选定的 I/O 线程数量很难一直合适。线程不足时，某个宿主 CPU 可能限制 I/O 吞吐；配置过多时，又会增加调度成本和每次 I/O 的 CPU 消耗。

io-thread-controller 尝试把这项配置变成运行时控制：观察负载，调整线程数量与队列分配，并检查调整是否有效。工程价值在于减少逐台虚机调参的工作，同时把单 VM 的性能需求与整机 CPU 预算放在一起考虑。

### 实现挑战

线程数量与设备队列归属需要同步改变。在途请求、完成回调和事件循环仍可能引用原来的执行上下文；调整期间必须保证这些工作被正确处理。讲稿中的 QEMU 原型通过暂时停止相关 I/O 完成重绑定，带来毫秒级成本和延迟尖峰。

调节策略也容易误判。高 CPU 利用率可能意味着线程已成瓶颈，也可能表示当前吞吐正好满足业务；磁盘本身饱和时，加线程收益有限。多台 VM 同时扩容还会争抢宿主 CPU，反复扩缩容则会制造额外抖动。

### 解决方案

控制器作为独立宿主服务运行，决策模块读取线程利用率和 IOPS，后端模块通过 QMP 执行操作。演讲时的 QEMU PoC 支持 virtio-scsi，实验性 QMP 命令 `x-virtio-scsi-set-iothread-vq-mapping` 用于改变队列到线程的分配。

讲稿给出了可配置的阈值策略，包含操作后的效果检查：

| 情况 | 控制动作 |
| --- | --- |
| 平均线程利用率超过 95% | 增加一个 I/O 线程 |
| 增加线程后 IOPS 收益不足 3% | 撤销调整；重复失败时延长下次尝试的等待 |
| 宿主 CPU 利用率超过 90% | 阻止继续扩容 |
| 考虑缩容 | 按剩余线程数估算新利用率，满足条件后尝试，性能下降过多则撤销 |

缩容估算使用“当前平均利用率 × 当前线程数 ÷ 剩余线程数”。例如四个线程平均占用 73%，减少到三个后的估算约为 97%，超过扩容阈值；四个线程平均 45%，减少到两个的估算为 90%。这些数字是策略参数与估算示例。

控制器还设置持续负载观察、冷却时间、失败后的暂停期，以及每轮可调节的 VM 数量上限。QEMU 执行时暂停相关 I/O，完成线程增减与队列重绑定后恢复处理；控制器根据随后的性能决定保留或撤销调整。

### 验证结果

原稿展示了运行中的控制器界面，可以观察线程数、线程利用率与 IOPS；同时说明重绑定会造成毫秒级暂停。公开材料以监测与调节的原型展示为主，尚缺少跨负载、跨硬件的完整性能对照。

评测这类控制器，应让负载经历低谷、突增和稳定阶段，分别记录吞吐、每 I/O CPU 成本、扩缩容次数及调节窗口内的 p99/p999 延迟。这样才能判断减少了多少资源开销，以及业务为调节动作付出了什么代价。讲稿中的 3% 是保留一次扩容的策略门槛，不能作为整个方案的性能收益。

### 局限与后续工作

作者列出的后续方向包括：按队列热点分配线程、一次移动一个队列以减小暂停、引入延迟与队列深度等指标、进行规模分析，并允许为不同 VM 设置独立规则。当前按轮转方式分配队列，可能把多个热点放到同一线程，平均利用率也会掩盖局部瓶颈。

这项工作的实际价值在于可回退的自动调参机制。延迟敏感 VM 需要明确的调节许可和暂停预算，整机策略需要遵守 CPU 限额并控制并发调整数量。稳定的工作负载识别和低成本队列重绑定，将决定它能否从演示走向日常运维。

## TDX 热迁移：受保护状态的导出与接管 {#tdx-migration}

```component talk-source-tdx-migration
```

### 问题与工程价值

热迁移让云平台在维护宿主、调整资源和处理负载变化时保留客户机的运行状态。普通虚机可以由 QEMU 读取内存、获取 vCPU 状态并传到目的端；TDX 机密虚机的私有内存和 vCPU 状态受平台保护，宿主没有同样的明文访问权限。

机密虚机也需要不停机维护。解决这一问题，需要在维持状态保护的前提下完成传输，并让目的端取得继续运行的资格。Intel 这场分享以 TDX 为原型，提出供机密虚机使用的 KVM 迁移接口。

### 实现挑战

状态导出、脏页识别和运行权交接都要经过平台机制。普通迁移中的内存读取与寄存器获取路径无法直接承担这些操作，QEMU 仍需负责连接、传输、迭代、停机与失败处理。两部分职责要能配合，避免平台细节散落到通用迁移代码中。

接口还要表达阶段关系。建立会话、传输多批页面、停止源端、导出最终状态、让目的端运行，涉及不同的平台操作。迁移取消或中途失败时，源端是否可继续运行、目的端已接收的状态怎样处理，都关系到服务可用性与状态安全。

### 解决方案

提案保留 QEMU 的迁移阶段，由 KVM 把受保护状态的导入导出请求交给 TDX module。QEMU 组织和传输平台导出的加密状态数据，私有状态的访问由平台完成。

| 操作类别 | 在迁移中的作用 |
| --- | --- |
| 能力查询 | 确定 VM 使用的迁移路径，以及接口可传输的数据块上限 |
| 阶段命令 | 建立会话、结束一轮迭代、进入停机阶段，以及结束或取消迁移 |
| 内存导入导出 | 按客户机页号数组传输页面批次，并用流编号区分并行通道 |
| vCPU 导入导出 | 在停机阶段通过各 vCPU 的文件描述符交接其受保护状态 |

内存接口中，TDX 示例每批处理 512 个页面。多通道传输沿用 multifd，每个通道对应平台的一条流。QEMU 通过 confidential-guest 对象上的保存／加载钩子连接平台实现，通用迁移框架继续控制阶段推进。

脏页查询复用 `KVM_GET_DIRTY_LOG` 入口，但 TDX 的脏页状态位于 Secure EPT，需要 KVM 请求平台扫描，并把结果合入 memslot 的脏页位图。这个步骤增加了平台工作，其成本需要独立测量。

### 验证结果

大会时点已经跑通 TDX 预拷贝热迁移 PoC，包含 multifd。已有 KVM uAPI RFC v2，QEMU RFC 尚待提交。原稿公布的是接口设计与端到端可行性验证，停机时间、迁移吞吐和宿主 CPU 开销的对照结果仍待补充。

当前 PoC 的 Secure EPT 脏页扫描仅在迁移会话中运行，而且使用单线程。即使状态传输能够并行，扫描仍可能限制整体进度。性能验证需要区分扫描、平台导出、网络传输和目的端导入，才能确定增加通道的实际收益。

### 局限与后续工作

作者计划继续推进 KVM RFC v3 和 QEMU RFC，并邀请其他机密计算平台参与接口评审。讲稿中的 `KVM_EXPORT_*`、`KVM_IMPORT_*` 仍是讨论中的 uAPI 提案。

这项工作的工程意义是补齐机密虚机的生命周期管理能力。实现验收除了成功迁移，还需覆盖取消、断连、部分导入及目的端接管失败，确认运行资格的交接与错误恢复。通用接口是否能容纳不同平台的会话要求，也需要更多实现验证。

## vGPU 热迁移：缓冲区交接与复制开销 {#vgpu-migration}

```component talk-source-vgpu-migration
```

### 问题与工程价值

GPU 虚机迁移需要交接设备状态和显存内容。数据量达到数十 GB 时，停机窗口会明显受到 GPU DMA、CPU 复制和数据传输速度影响。GPU 服务的维护与资源调整因此依赖高效的设备迁移路径。

NVIDIA 这场分享沿 vGPU Manager、内核 VFIO 驱动和 QEMU 的缓冲区交接定位成本，给出了驱动内部优化及实验结果，并提出进一步减少 QEMU 路径复制的方案。

### 实现挑战

旧路径中，GPU 将数据 DMA 到 vGPU Manager 的暂存区，Manager 把它复制到内核 VFIO 缓冲区，驱动又将数据复制到 QEMU。Manager 与 VFIO 之间的复制用于跨地址空间交接，额外消耗 CPU 与内存带宽。

单个 VFIO 缓冲区还使工作串行化：QEMU 需要等待当前块填充或消费，GPU DMA 与 QEMU I/O 难以重叠。扩大一次传输量只能改变部分调用开销，缓冲区复用和在途 DMA 的所有权仍需明确。

### 解决方案

驱动在迁移准备阶段分配共享缓冲池，同时映射给 vGPU Manager 和 GPU DMA。Manager 通过非阻塞 GET/PUT 操作取得空闲缓冲区、提交已准备好的缓冲区，QEMU 继续使用原有的 VFIO 保存／恢复数据 FD。

```text
原路径：GPU DMA → Manager 暂存区 → 复制到 VFIO 缓冲区 → 复制到 QEMU
新路径：GPU DMA → Manager 与 VFIO 共享缓冲池             → 复制到 QEMU
```

源端 GPU 填充下一块数据时，QEMU 可以读取上一块；目的端 GPU 消费上一块时，QEMU 可以写入下一块。共享缓冲池省去驱动内部的一次复制，多个缓冲区又允许 DMA 与 QEMU I/O 并行推进。QEMU 和网络路径中的其他复制仍然保留。

### 验证结果

实验使用同宿主迁移、RHEL 9.4、QEMU 10.1。VM 配置为 12 vCPU、64 GB RAM，挂载四个 H20-96C vGPU。两组实验的设备状态量与传输配置如下：

| 实验配置 | 原接口停机时间 | 共享缓冲池接口停机时间 |
| --- | --- | --- |
| 无 multifd，约 24 GB 设备状态 | 36.075 s | 10.728 s |
| 八个 multifd 通道，约 22 GB 设备状态 | 4.460 s | 4.172 s |

两组停机时间分别下降约 70% 和 6.5%。总迁移时间也分别由 642.106 s 降到 210.596 s、由 593.136 s 降到 207.203 s。已有并行传输时，总时间仍有较大改善，停机窗口的剩余收益则明显缩小。

这些数字应在各组内比较。两组设备状态量不同，而且都是同宿主实验，跨宿主网络条件还需另外验证。讲稿中的 VFIO 读写带宽按驱动处理函数内花费的时间计算，与端到端网络吞吐的测量范围不同。

### 局限与后续工作

作者观察到驱动内部优化后，QEMU 侧的数据读取、复制和发送成为更明显的限制。后续提案由 QEMU 分配每设备缓冲池，通过 memfd、udmabuf 和 dma-buf 交给 VFIO 与设备 DMA 使用，让 QEMU 与驱动交接缓冲区所有权。

提案分两阶段：第一阶段去除 VFIO 到 QEMU 的复制及 QEMU 中间复制，保留网络栈复制；第二阶段研究继续减少 socket 路径复制。原稿展示的这部分路径以未启用 TLS 为例，属于后续方案。

这项优化的实际价值，是把可以并行的工作重叠起来，并消除只为地址空间交接产生的复制。继续推进时，需要核算固定页面的成本，处理 DMA 完成、缓冲区回收、取消迁移和网络背压，并覆盖加密传输。停机时间与总迁移时间都应保留为独立指标。
