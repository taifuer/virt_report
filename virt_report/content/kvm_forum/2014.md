## 本届观察 {#preface}

这一年的精选围绕几个长期存在的工程问题展开：跨 NUMA 节点访问怎样减少，设备模拟怎样利用多核，复杂客户机输入应该在哪个权限层处理，以及共享设备和远端内存怎样建立清楚的接口。方案中既有已经可测量的性能变化，也有仍在讨论的内核接口；下面分别说明。

## KVM 安全加固：缩小内核中的客户机输入处理面 {#hardening}

```component talk-source-hardening
```

### 问题与工程价值

公有云允许不可信客户机运行任意代码，设备寄存器、MSR 和异常指令都可能成为攻击输入。KVM 位于宿主内核，相关漏洞可能影响其他虚拟机或宿主。讲稿用实际发现的漏洞说明输入验证的薄弱点，并讨论将部分模拟逻辑移到较低权限位置，以缩小单个错误的影响范围。

### 实现挑战

客户机可以构造普通操作系统不会产生的访问组合。只检查请求起始地址会遗漏跨页写入，仅依赖调试断言会使发布版失去边界检查，指令模拟器还需要处理访问跨越 MMIO 与普通 RAM 的情况。减少内核功能又可能增加用户态退出，性能关键操作不能无差别移动。

### 解决方案

讲稿分析时钟 MSR 越界写、IOAPIC 数组索引和 pusha 模拟的具体错误。共同要求是对完整访问范围和所有执行分支进行运行时验证，而非假定客户机遵守正常软件习惯。代码审查与模糊测试用于发现错误，攻击面缩减用于限制仍未发现错误的后果。

架构上，作者探索将 PIC、IOAPIC、部分指令模拟和 MSR 处理放到用户态，同时在内核保留 APIC 硬件加速及高频操作。材料提出若干实验接口，用于选择退出范围或保留轻量中断能力。

### 验证结果

漏洞示例提供了明确的失败机制，其中部分已经确认可导致逃逸。作者把攻击面减少超过一半、宏观性能影响低于 0.1% 列为重构目标，当时的原型还在验证架构。

### 局限与后续工作

用户态设备进程仍可能拥有大量客户机内存和文件权限，移出内核后的影响取决于实际沙箱配置。代码行数衡量的是代码规模；风险还取决于接口能做什么、谁能访问。后续验证需要覆盖权限收缩、接口新增复杂度、异常客户机行为和高频中断负载，同时检查性能优化是否重新把不必要的解析逻辑带回内核。

## 自动 NUMA 平衡：页面迁移与任务放置如何配合 {#numa}

```component talk-source-numa
```

### 问题与工程价值

NUMA 机器上，远端内存访问会增加延迟并占用节点互连带宽。虚拟机和多线程应用的访问模式会变化，手动绑定难以长期适应。自动 NUMA 平衡通过观察实际访问，让任务靠近常用内存，或把页面移到任务所在节点，目标是改善默认配置的性能并减少人工调优。

### 实现挑战

观察访问本身有开销，页面搬运也比一次提示缺页昂贵。共享内存可能被多个节点持续访问，盲目跟随最新访问者会造成反复迁移。调度器还需要保持 CPU 负载均衡；若 NUMA 策略与负载均衡相互抵消，任务和页面都会在节点间来回移动。

### 解决方案

讲稿中的实现周期性改变部分页面的访问权限，以 NUMA 提示缺页采样访问位置。统计按任务和节点累计，页面迁移使用重复访问过滤，降低一次偶然访问导致搬运的概率。任务放置则结合本地性收益与负载约束，必要时交换两个节点上的任务。

对共享内存，相关任务形成 NUMA 分组，用组统计帮助把协作任务放近；当工作负载必须跨多个节点运行时，伪交错策略让共享页面分布更均衡，抑制无收益的来回移动。私有页面仍可更积极地跟随其使用任务，兼顾局部性和内存带宽。

### 验证结果

四路 Ivy Bridge EX 上的 SPECjbb2005 客户机实验，自动平衡与手动绑定结果相差约 ±3%。但混合运行 OLTP 与 Java 负载时，部分较小客户机比手动绑定低约 10%—25%，较大客户机甚至比未调优基线低约 5%—15%。实验关闭超线程、启用 THP，并使用特定虚拟 NUMA 配置；这些条件不能省略。

### 局限与后续工作

当时策略主要考虑 CPU 与内存，设备中断位置、IPC 关系和复杂节点距离仍需改进。固定页面、设备 DMA 及某些大页配置也限制页面移动。工程判断应结合缺页、页迁移、远端访问和业务延迟，而非只观察是否开启自动平衡；短任务还可能在策略收敛前就已结束。

## KVMGT：共享 GPU 的选择性直通 {#kvmgt}

```component talk-source-kvmgt
```

### 问题与工程价值

桌面图形、媒体和计算希望在客户机内使用原生 GPU 驱动，同时由多个虚拟机共享一块设备。API 转发受接口覆盖限制，整卡分配又难以共享。KVMGT 的早期方案尝试保留性能敏感操作的直接访问，对特权状态进行软件中介，以兼顾功能覆盖与多租户使用。

### 实现挑战

GPU 包含命令、地址空间和全局状态，多个客户机不能随意修改彼此资源。宿主自身的 i915 使用也需要与虚拟机协调。地址解释必须保持一致，客户机驱动看到的图形地址空间不能误指向其他实例；进一步支持进程级页表又需要额外的影子映射。

### 解决方案

vGT 设备模型为每台客户机维护实例并进行分时调度，QEMU 提供 PCI 设备视图与实例生命周期。宿主 i915 访问也经过中介层，统一管理物理 GPU。性能关键区域可以通过映射直接访问，需要管理的操作则被捕获并交给内核设备模型。

讲稿使用图形地址空间划分与 ballooning，使客户机和宿主对可用图形区域保持一致。这里的 ballooning 针对 GPU 地址空间，不是普通客户机内存气球。2014 年原型通过 KVM 内核接口提供捕获服务，后来的实现才采用 mdev。

### 验证结果

讲稿报告第四代 Core 集成图形上的 Linux 客户机可运行，但关闭了 PPGTT。在演示的四个 3D 示例中，单客户机的性能约为原生的八成或更高。共享 GPU 还需要考察多个客户机竞争时的公平性、持续负载下的表现和隔离效果。

### 局限与后续工作

影子 PPGTT 被列为支持 Windows 客户机的重要前提，代码清理、稳定性和上游架构讨论仍在进行。后续工作需要审查命令与地址隔离、切换成本和设备错误恢复。它值得保留的原因是清楚展示了选择性直通的分工，以及高性能路径为何仍需要受控的资源管理。

## IOThread 与 AioContext：设备处理移出全局锁 {#iothreads}

```component talk-source-iothreads
```

### 问题与工程价值

多个 KVM vCPU 可以并行执行，但设备请求若集中到 QEMU 主循环和全局锁，存储吞吐仍可能受单线程限制。virtio-blk dataplane 把高频请求交给专用线程，减少与显示、管理等事件的争用。讲稿进一步解释怎样让块层和设备状态真正支持这种并行，而不只是把函数搬到另一条线程。

### 实现挑战

块设备会同时被数据路径和管理操作访问，线程归属改变后，文件描述符、定时器和延迟回调都需要转移。设备 DMA 还可能落到另一个设备的 MMIO 区域，导致跨设备上下文递归访问；若两个线程反向获取对方锁，就会死锁。迁移脏页位图也不能遗漏并发设备写入。

### 解决方案

IOThread 运行独立 AioContext 事件循环，块设备状态绑定到相应上下文，访问方遵守获取与释放规则。ioeventfd 和 irqfd 连接请求与完成通知，让常见数据路径避开主循环。设备可以按需要分配给多个 IOThread，无需机械地为每块磁盘创建一条独占线程。

当对象转移上下文时，需要同步移除与重新登记事件源，并处理尚未执行的回调。讲稿还提出脏页位图原子化和多队列状态拆分等工作，强调每设备共享状态与每队列状态应有不同的并发边界。

### 验证结果

材料说明 QEMU 2.1 的各组件多线程状态、可查询的 IOThread 标识及 libvirt 集成，并给出实际调用路径。脏页位图的原子更新当时尚未完成，跨设备递归访问也仍依赖同步。

### 局限与后续工作

把同一 raw 文件以多个块状态重复打开可以做实验，却会破坏快照、扩容等管理语义，讲稿明确指出这一限制。后续需要在正式块层中处理共享状态、队列并行和管理操作排空。工程验证应覆盖热拔除、迁移和错误回调，检查高吞吐之外的生命周期正确性。

## userfaultfd 的设计起点：远端内存与原子补页 {#userfaultfd-design}

```component talk-source-userfaultfd-design
```

### 问题与工程价值

应用的一部分内存位于远端时，本地缺页需要通知了解数据位置的用户态服务。早期虚拟机专用方案会限制交换、THP、KSM 或 NUMA 管理，难以成为通用基础设施。讲稿尝试把问题放回 Linux 内存管理层，使普通进程和 QEMU 都能使用相同的缺页协作机制。

### 实现挑战

SIGBUS 可以通知用户态直接访问，却不能透明处理内核通过 get_user_pages 或系统调用访问同一地址的情况。缺页线程还可能持有 mmap_sem，若无限等待用户态取页，会阻塞其他地址空间操作。补页必须原子可见，避免并发线程读取未完整准备的内容。

### 解决方案

设计使用文件描述符通知专门处理线程，让访问线程释放必要的内核锁后等待。用户态取回数据，再通过原子重映射或原子复制把页面放入目标位置，并唤醒相关缺页。讲稿比较两种补页方式的 TLB、对齐和内存类型代价；MADV_USERFAULT、remap_anon_pages 等名称属于当时提案。

QEMU 侧还需要请求返回通道、已发送与已接收页面记录，以及独立处理线程。设备状态恢复也可能访问尚未到达的内存，因此页面请求服务必须在恢复期间就能工作，避免同一线程既等待页面又负责接收页面。

### 验证结果

作者报告原型经过数千次迁移压力测试。10GbE 实验中，较小发送缓冲区下按需页面延迟约为毫秒量级，默认缓冲配置可能升至十毫秒以上。这组数据测的是源端和目标端 QEMU 用户态之间处理一次补页请求的时间。结果揭示后台顺序传输会排挤紧急按需请求。

### 局限与后续工作

接口当时仍在征求意见，后续发布形式可能与原型不同。背景传输限速、气球释放页面的区分，以及远端故障后的等待处理都需要完善。多个线程同时缺页、设备尚在恢复或资源紧张时，补页还能否继续，直接关系到应用能否恢复执行。
