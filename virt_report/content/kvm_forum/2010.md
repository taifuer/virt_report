## 本届观察 {#preface}

2010 年的五篇精选涉及后来长期使用的基础设计。qdev、VMState 和 QMP 分别整理设备创建、状态传输和管理接口，让功能扩展有了共同结构。透明大页与异步缺页则利用宿主和客户机之间的协作，降低地址转换及换页等待成本。阅读这些早期讲稿，可以看到接口最初解决的具体问题，以及当时仍处于提案或原型阶段的部分。

## qdev：统一 QEMU 设备的创建与管理 {#qdev}

```component talk-source-qdev
```

### 问题与工程价值

早期 QEMU 设备各有参数与创建路径：磁盘、网卡、串口和 USB 设备使用不同的命令行形式，初始化代码与管理逻辑也散布在各处。增加一种设备往往需要修改多个入口。qdev 将这些共同行为集中起来，让机器初始化、命令行和热插拔能够使用同一套设备描述与创建接口。

### 实现挑战

不同设备连接到不同总线，配置属性、可迁移状态与运行时资源也并不相同。设备删除尤其涉及客户机配合：管理端发出请求后，客户机还可能使用该设备。统一接口需要保留这些差异，并分别报告设备标识、归属、请求受理和资源释放。

### 解决方案

qdev 以设备与总线组成树，将名称、属性和生命周期回调放入设备描述。创建过程分为分配设备、设置属性和初始化；具体设备通过回调建立自身资源。命令行 `-device`、monitor 的 `device_add` 与配置文件可以复用这套结构，减少各入口重复解析和分派设备类型的代码。

讲稿用 ISA 串口展示 DeviceState、ISADevice 与具体设备状态的关系，并把属性表、初始化函数和 VMState 描述放到同一设备定义中。属性表达配置，VMState 表达需要保存的状态，两者用途不同。PCI 热拔除则通过 ACPI 与客户机协调，删除命令本身只启动这一过程。

### 验证结果

原稿提供串口实现、设备树与管理命令示例。作者同时指出设备路径、标识歧义和热拔除完成通知仍需改进。qdev 把设备接入和管理的共用步骤集中起来，减少了每个设备重复实现的代码。

### 局限与后续工作

当时仍有设备保留旧式入口，属性自描述和设备分类也有待完善。后续验证需要覆盖创建失败、部分初始化后的清理，以及客户机拒绝或延迟热拔除等情况。这里讨论的是早期 qdev 的设备模型，后来的 QOM 又扩展了对象体系；阅读当前代码时，应按对应版本检查具体生命周期。

## 透明大页：降低虚拟机地址转换成本 {#transparent-hugepages}

```component talk-source-transparent-hugepages
```

### 问题与工程价值

虚拟机的一次地址转换可能同时遍历客户机页表与宿主二级页表。小页让 TLB 覆盖范围有限，也增加页表数据的访问量。预留大页可以改善这些成本，却要求管理者提前安排内存。透明大页希望在常规匿名内存中自动获得大页收益，同时保留按需分配与内存回收能力。

### 实现挑战

2 MiB 映射需要连续且满足对齐条件的物理内存，长期运行后的碎片会降低分配成功率。内存不足时，系统还必须能够拆分和回收。客户机与宿主各有自己的页表，宿主使用大页并不会自动让客户机也使用大页，两层映射需要分别观察。

### 解决方案

满足条件的匿名缺页尝试建立大页映射，无法满足时回退到小页；后台 khugepaged 把合适的 512 个 4 KiB 页面合并成 2 MiB 页面。内存压力下又可拆分大页，恢复细粒度回收和换页。扫描、分配与合并需要控制频率，避免后台工作抵消访问路径上的收益。

讲稿用四级页表的模型说明缩短遍历路径的价值：在其简化条件下，嵌套遍历需要的访问次数可由 24 降到 19 或 15。这个理论模型计算的是页表遍历次数，未计入目标数据访问和缓存命中。

### 验证结果

编译实验使用双路、12 个物理核和 24 个硬件线程，宿主 16 GB 内存，客户机 24 vCPU、15 GB 内存；GCC 还做了 2 MiB 对齐分配改造。相对启用透明大页的裸机，EPT 虚拟机在两层均关闭透明大页时慢 24.81%，仅宿主启用时慢 12.71%，两层都启用时慢 5.67%。这些数值来自同一特定基线与定制负载。

### 局限与后续工作

当时透明大页仍处于上游推进阶段。吞吐提高的同时，大块清零、复制和内存整理也可能增加延迟或内存占用。后续评估应同时检查大页命中率、内存压力、NUMA 放置与长尾延迟，并使用未修改的实际应用验证，而非只复用这组编译结果。

## VMState：描述可迁移的设备状态 {#vmstate}

```component talk-source-vmstate
```

### 问题与工程价值

迁移设备状态需要源端保存、目的端加载同一组字段。手工编写两套函数容易出现字段遗漏、顺序不一致和版本判断分散等问题，设备越复杂越难审核。VMState 将这些信息集中到结构化描述，让状态格式更容易与设备实现对照，也减少重复的序列化代码。

### 实现挑战

设备状态既包含寄存器和队列，也包含由其他字段推导出的中间结果。部分状态只在特定工作模式或在途操作中存在。新版本增加字段后，还要明确哪些旧版本可以接收，以及缺少某段状态会不会改变设备行为。单纯复制内存结构无法解决这些问题。

### 解决方案

VMStateDescription 描述状态名称、版本、最低兼容版本与字段表，字段可以是标量、数组或嵌套结构。公共代码据此处理传输格式，设备通过版本条件和测试函数表达布局变化。加载后的回调负责恢复派生状态；讲稿中的触摸屏设备就需要重新计算相关状态并更新中断。

可选子节用于组织仅在特定条件下出现的扩展状态，例如 IDE 尚未结束的 PIO 操作。发送方根据条件决定是否包含子节；这可以减少新功能对旧接收端的影响，但需要该状态确实可以省略。接收端必须能解释运行所需的全部状态，才能恢复执行。

### 验证结果

原稿通过设备字段与回调示例说明转换方法，并列出尚未完成改造的 Virtio、网络和 CPU 等状态路径，没有迁移吞吐或停机时间基准。声明式结构提高了格式的可检查性，正确性仍需要保存与恢复后的行为比较，特别是中断、定时器和在途 I/O，而非只确认加载函数返回成功。

### 局限与后续工作

设备描述保存设备状态，RAM 修改由脏页跟踪处理，外部共享存储在两端单独配置。新旧版本之间的兼容还受机器配置和设备行为影响。讲稿把格式清理、校验与更强的自描述能力列为改进方向；工程验证应覆盖多版本组合、缺失子节、损坏数据和恢复后的持续运行。

## QMP：建立面向管理程序的控制接口 {#qmp}

```component talk-source-qmp
```

### 问题与工程价值

传统 monitor 面向人阅读和操作，管理程序解析文本时容易受格式变化影响，也难以可靠区分返回值和异步消息。虚拟机规模扩大后，启动、迁移和故障处理需要可编程接口。QMP 用结构化消息表达命令与状态，为 libvirt 等管理层提供明确的交互基础。

### 实现挑战

设备热拔除、迁移和 balloon 调整可能等待客户机或外部资源，命令接受与操作完成之间存在时间差。管理端还要在等待返回时处理磁盘错误等事件。旧 monitor 的错误处理和命令语义也不能简单包一层 JSON 就获得稳定接口，异步任务需要可识别的状态与关联方式。

### 解决方案

QMP 通过 JSON 对象承载请求、成功返回、错误和事件，并在连接建立时协商能力。原稿用弹出介质说明成功与 DeviceNotFound 等结构化错误的区别，再用 BLOCK_IO_ERROR 展示设备、操作类型、处理动作与时间戳等事件字段，管理程序可以按字段处理而不必匹配一整句提示。

作者进一步讨论长操作的响应语义，以及原有全局错误状态如何妨碍多个异步操作并存。延迟回复、显式异步标记和独立异步执行形式在讲稿中属于设计讨论，应与当时已提供的命令和事件区分开。

### 验证结果

讲稿记录 QMP 已合入 QEMU 0.13，包含 40 个命令和 11 个事件，libvirt 与 kvm-autotest 已开始使用，同时明确接口仍不稳定。原始消息示例展示了管理程序如何解析命令结果和异步事件。

### 局限与后续工作

结构化编码只解决消息表达的一部分问题，操作完成条件、错误分类与事件顺序仍需逐项定义。后续测试应覆盖事件与回复交错、连接中断、客户机不响应和重复请求，让管理端能够判断任务是否真正完成。长期接口演进还需要兼容策略，避免将内部实现细节直接固定为外部契约。

## 异步缺页：让宿主换页不再阻塞整个 vCPU {#async-page-faults}

```component talk-source-async-page-faults
```

### 问题与工程价值

宿主把客户机的一页内存换出后，vCPU 再次访问它可能阻塞在宿主缺页处理。客户机调度器对此缺乏直接认识，同一 vCPU 上其他不需要该页的任务也失去执行机会。异步缺页把这一等待传递给客户机，让客户机可以挂起当前任务，继续运行仍有可用内存的任务。

### 实现挑战

宿主必须区分可以立即处理的映射与需要等待 I/O 的缺页，并把等待、完成两类事件准确送到客户机。普通取页接口可能直接睡眠，无法完成这种拆分。客户机收到通知时也不一定处于可调度状态，页面完成与任务进入等待之间还可能出现竞争，需要双方共同处理。

### 解决方案

讲稿的原型使用 PageNotPresent 和 PageReady 两类通知，通过缺页异常向量及每 CPU 的原因字段传递。宿主将慢速取页交给独立执行路径；客户机收到等待通知后阻塞相关任务，调度其他任务。页面就绪后再通知客户机唤醒等待者，从而把一个 vCPU 的整体停顿缩小到真正依赖该页的任务。

为识别慢速路径，原稿分析已有快速取页接口的限制，并提出不触发 I/O 等待的取页方式。这要求 KVM、内存管理与客户机异常处理共同配合，仅修改宿主调度策略无法让客户机知道究竟哪个任务需要等待。

### 验证结果

测试在 512 MB 内存 cgroup 中运行配置 2 GB 内存、4 vCPU 的客户机，包含四个随机访问内存的任务和四个计数工作线程，持续 60 秒。在这种重度超分条件下，计数总量由约 1297.5 亿增加到 2588.5 亿，按原始计数计算约为两倍。讲稿图中的百分比标注与这些计数不一致，此处以计数比值呈现。

### 局限与后续工作

计数程序在等待期间继续推进，演示了把这段 CPU 时间用于其他工作的可能性。方案需要客户机配合，也要求存在不依赖缺失页面的可运行任务；它不能消除换页 I/O 或过度超分本身。后续应检查通知竞争、不可调度上下文、连续缺页和真实应用的响应时间，确认额外协作成本可接受。
